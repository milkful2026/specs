## 2. Problem Statement

From My Orders (MA-145) a customer needs to open an order and see exactly what was in it,
what it cost, when it will be (or was due to be) delivered, and — when something went wrong —
why, in plain language. The mock `order_details_inr` shows a much richer screen: bill
breakdown, delivery address and time, delivery partner, invoice, re-order, support and
feedback. Most of that data does not exist yet, so this spec builds the part that can be
filled truthfully today. MA-35 extends the same screen later.

## 3. Scope

### In scope

- Route `/orders/:orderId`: the detail of a real order, from `GET /orders/{id}`.
- Route `/orders/scheduled/:subscriptionId`: a read-only view of a scheduled subscription
  delivery (MA-145 FR-4), with its estimate explained.
- Sections from the mock that have real data: **order header** (order ID, placed-on date,
  status), **Items in this Order**, **Bill Details** (grand total only), **Delivery Info**
  (delivery date), **Payment Method**.
- A plain-language explanation for every failure reason.
- Loading, error and not-found states.

### Out of scope (MA-35 or later)

- Download Invoice (MA-38), Reorder Items, Support, Leave Feedback (MA-28).
- Bill breakdown (item total, delivery fee, taxes) and per-item unit prices: Order Service
  stores only the order total.
- Delivery address, "Delivered At", slot and delivery partner (need MA-102 and address or
  slot data on orders).
- Editing, skipping or cancelling anything from this screen.

## 4. Functional Requirements

### Screen structure (real order)

```
AppBar: [←]  Order Details
┌ Header card ─────────────────────────┐
│ ORDER ID            Placed On        │
│ #3F9A2C1B           24 Oct 2026      │
│ [status banner]                      │
│ (reason text, when failed/cancelled/ │
│  under review)                       │
└──────────────────────────────────────┘
┌ Items in this Order ─────────────────┐
│ [img] Product name     2 × 500ml     │  (one row per item)
└──────────────────────────────────────┘
┌ Bill Details ────────────────────────┐
│ Grand Total                 ₹155.00  │
└──────────────────────────────────────┘
┌ Delivery Info ───────────────────────┐
│ (clock) Delivery date                │
│         Sat, 26 Oct 2026             │
└──────────────────────────────────────┘
┌ Payment Method ──────────────────────┐
│ (wallet) Milkful Wallet              │
└──────────────────────────────────────┘
```

### FR-1: Routes

- `GoRoute('/orders/:orderId')` → `OrderDetailScreen(orderId)`.
- `GoRoute('/orders/scheduled/:subscriptionId')` → `ScheduledDeliveryScreen(subscriptionId,
  entry: state.extra as ScheduledEntry?)`.
- **Declaration order matters:** `/orders/scheduled/:subscriptionId` is declared **before**
  `/orders/:orderId`, so "scheduled" is never read as an order ID.
- Both screens are pushed and have a back arrow and the title **"Order Details"**.

### FR-2: Loading a real order

- On open: `OrderRepository.getById(orderId)` (added by MA-145), then product details for its
  items through the cached `CatalogRepository.getProduct`, in parallel.
- While loading: a skeleton of the header and items cards.
- **404 `ORDER_NOT_FOUND`**: a full-screen message **"Order not found"**, with sub-text
  "This order doesn't exist or isn't on your account." and a **"Back to My Orders"** button
  that pops.
- **Any other error**: **"Couldn't load this order."** + **"Retry"**.

### FR-3: Header card

- **ORDER ID**: a display ID — the first 8 characters, uppercased, of the order ID after its
  `ord_` prefix, shown as `#3F9A2C1B`. Long-press copies the **full** order ID and shows the
  SnackBar "Order ID copied" (support can find the order with it).
- **Placed On**: `createdAt` converted to IST, formatted `24 Oct 2026`.
- **Status banner**: same labels as MA-145 FR-6, as a wider banner:

| Status | Banner text | Style |
|--------|-------------|-------|
| `CONFIRMED` | Order Placed | neutral/success-tint, check icon |
| `CREATED` | Processing | neutral |
| `PAYMENT_FAILED` | Payment Failed | error |
| `CANCELLED` | Cancelled | error |
| `NEEDS_ATTENTION` | Under Review | warning |
| `FAILED` | Failed | error |
| unknown | raw value, title-cased | neutral |

No "Delivered Successfully" banner (MA-26 decision; needs MA-102).

- **Reason text** under the banner, from `failureReason`. It's shown for PAYMENT_FAILED,
  CANCELLED, NEEDS_ATTENTION and FAILED:

| `failureReason` | Text |
|-----------------|------|
| `INSUFFICIENT_BALANCE` | "Your wallet didn't have enough balance for this order." |
| `WALLET_NOT_ACTIVE` | "Your wallet wasn't active when this order was placed." |
| `DELIVERY_ADDRESS_UNKNOWN` | "We couldn't find a delivery address on your account." |
| `PRODUCT_UNAVAILABLE` | "This product is no longer available." |
| `CUTOFF_PASSED` | "This order couldn't be completed before the delivery cut-off. You weren't charged." |
| `SWEEP_EXHAUSTED` | "We couldn't finish this order automatically. Our team has been alerted, and you won't be charged twice." |
| null / other | "Something went wrong with this order." |

**Copy rule:** "You weren't charged" appears **only** for `CUTOFF_PASSED`, where the backend
has proven it with a Wallet void (MA-142/143/144). For `SWEEP_EXHAUSTED` the charge may be
unknown, so the copy promises no double charge instead, matching MA-144's
`CHECKOUT_NEEDS_ATTENTION` message.

### FR-4: Items in this Order

- One row per item, in API order:
  - product image (placeholder on failure);
  - product name ("Item" on failure);
  - `"{quantity} × {unit}"` (e.g. `2 × 500ml`), or `"Quantity: {q}"` when the unit is
    unknown.
- **No per-item price**: Order Service stores only the total. Rows stay aligned without an
  amount column.
- A SUBSCRIPTION order has one row, with the line **"From your subscription"** under the
  name.
- Tapping a row does nothing in this spec (no product navigation).

### FR-5: Bill Details

- One row: **"Grand Total"** and `amountPaise` formatted `₹155.00` (always two decimals on
  this screen).
- For `CANCELLED` and `PAYMENT_FAILED`, the amount is struck through with the caption
  **"Not charged"** under it. Both states mean no debit was taken.
- For `FAILED` (a legacy status nothing currently sets), the amount is struck through with
  **no** caption, since the charge isn't known.
- A `NEEDS_ATTENTION` amount is shown normally, with the caption **"Charge under review"**.
- An amount of 0 (a pre-pricing failure, MA-132) shows **"—"** instead of `₹0.00`.

### FR-6: Delivery Info

- A clock icon, the label **"Delivery date"**, and `deliveryDate` formatted `Sat, 26 Oct
  2026`. It's a date only, never time-zone-converted.
- No address, time, slot or partner rows (out of scope).

### FR-7: Payment Method

- A wallet icon and **"Milkful Wallet"**. Both order paths (MA-132 subscriptions, MA-136
  checkout) debit the Milkful wallet; no other method exists yet.

### FR-8: Scheduled delivery view (`/orders/scheduled/:subscriptionId`)

- **Data:**
  - Use the `ScheduledEntry` passed as `extra` when present.
  - Otherwise (a deep link, or after an app restart) fetch `GET /subscriptions/{id}` through
    the existing subscription repository and build the entry from `nextDeliveryDate`.
  - If the subscription is not ACTIVE, or has no future next delivery, show **"This delivery
    is no longer scheduled."** + **"Back to My Orders"**.
- **Header card:**
  - no order ID; the label **"SCHEDULED DELIVERY"**;
  - a "Scheduled" banner (primary-tint, calendar icon);
  - the text **"This is your subscription's next delivery. It becomes an order the evening
    before, when your wallet is charged."**
- **Items:** one row: the product, `"{quantity} × {unit}"`, and "From your subscription".
- **Bill Details:** **"Estimated Total"**, `≈ ₹130.00`, with the caption **"Final price
  (including any tax and delivery fee) is confirmed the evening before."** When the product
  lookup failed: "Price confirmed the evening before" and no amount.
- **Delivery Info:** "Delivery date" = `nextDeliveryDate`.
- **Payment Method:** "Milkful Wallet".
- A text button **"Manage subscription"** goes to `/subscriptions` (existing screen).

### FR-9: Pull-to-refresh

Both screens support pull-to-refresh: they reload the order (or the subscription) and the
product details.

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Performance | Skeleton < 100 ms; content as soon as `GET /orders/{id}` returns (products fill in after) |
| Correctness | Dates: `createdAt` in IST, `deliveryDate` as a plain date; never claim delivery or "not charged" beyond FR-3's copy rule |
| Security | Only the owner's order is returned (backend returns 404 otherwise); the full order ID is only copied on explicit long-press |
| Accessibility | Status banner semantics `"Status: {label}. {reason}"`; 48dp targets; AA contrast; text scale 1.3 |
| Maintainability | Reason/status copy lives in one map shared with MA-145's chip mapping (`order_status_copy.dart`) |

## 6. Technical Design

**New files (`lib/features/orders/`):**

| File | Responsibility |
|------|----------------|
| `bloc/order_detail_cubit.dart` | `OrderDetailCubit(orderRepo, catalogRepo)`: `load()`, `refresh()`; states `loading / loaded(order, products) / notFound / error` |
| `bloc/scheduled_delivery_cubit.dart` | `ScheduledDeliveryCubit(subscriptionRepo, catalogRepo, initial: ScheduledEntry?)`; states `loading / loaded(entry, product?) / gone / error` |
| `presentation/order_detail_screen.dart` | Real-order screen (FR-2..FR-7) |
| `presentation/scheduled_delivery_screen.dart` | Scheduled view (FR-8) |
| `presentation/widgets/detail_cards.dart` | Shared card widgets: header, items, bill, delivery info, payment |
| `domain/order_status_copy.dart` | Status labels/styles and failure-reason copy (shared with MA-145) |

**Reuse:** `OrderRepository.getById` and the `OrderSummary` model from MA-145. The existing
`SubscriptionRepository` is used for `GET /subscriptions/{id}`; if it has no `get(id)` today,
add one (`GET {subscriptionBaseUrl}/subscriptions/{id}` → `SubscriptionView`).

**Router:** both routes are added in `app_router.dart` (scheduled first; see FR-1), and each
provides its cubit through `BlocProvider`.

## 7. Data Considerations

- No persistence; nothing is written.
- `createdAt` is ISO-8601 with an offset → converted to IST for display. `deliveryDate` is
  `YYYY-MM-DD` → formatted directly.
- `failureReason` is free text on the wire; the mapping in FR-3 has a default.
- Money is integer paise; formatting is in presentation only.

## 8. Integration Considerations

| Dependency | Contract | Failure behaviour |
|------------|----------|-------------------|
| Order Service `GET /orders/{id}` | Order (MA-132 FR-3 / MA-136 FR-10); `404 ORDER_NOT_FOUND` for missing or foreign | Not-found screen; other errors → Retry |
| Subscription Service `GET /subscriptions/{id}` | `SubscriptionView` with `status`, `nextDeliveryDate` | Error → Retry; not active / no date → "no longer scheduled" |
| Catalog `GET /products/{id}` | name, unit, price, imageUrl | Placeholders; estimate unknown |

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Deep link to another user's order | Backend 404 → "Order not found" (no existence leak) |
| Order changes status while open (e.g. CREATED → CONFIRMED) | Shown on pull-to-refresh; no polling |
| `NEEDS_ATTENTION` order | "Under Review" + the SWEEP_EXHAUSTED copy; amount shown with "Charge under review" |
| `CANCELLED` with `CUTOFF_PASSED` | "Cancelled" + "…You weren't charged." + struck amount, "Not charged" |
| Pre-pricing `PAYMENT_FAILED` (amount 0) | Grand Total "—" |
| Scheduled entry opened after the Daily Run made it an order | `GET /subscriptions/{id}` now returns a later `nextDeliveryDate`: the screen shows the new date. The entry is no longer the same delivery, so the screen also shows a SnackBar "This delivery is now an order. Check My Orders." and the new next delivery |
| Scheduled route opened with a malformed `extra` | Ignored; fetched by ID |
| Order ID with no `ord_` prefix | Display ID = first 8 characters, uppercased |

## 10. Testing Strategy

**Cubit tests (fakes):**
- A loaded order with its products; a 404 → notFound; a 500 → error, then retry → loaded.
- A product lookup failure → loaded with placeholders (not an error).
- Scheduled:
  - uses `extra` without a network call;
  - no `extra` → fetches by ID;
  - PAUSED, or a null date → gone;
  - a changed date → loaded with the new date and the "now an order" flag.

**Widget tests (`find.text`):**
- **Scenario: confirmed checkout order.**
  - Given a CONFIRMED order with 2 items, ₹155.00, delivery Sat 26 Oct 2026.
  - Expect: "Order Details", "#…" display ID, "Order Placed", both product names,
    "2 × 500ml", "Grand Total", "₹155.00", "Delivery date", "Sat, 26 Oct 2026",
    "Milkful Wallet".
  - Expect **no** "Delivered", "Download Invoice", "Reorder Items" or "Leave Feedback".
- **Scenario: cancelled at the cut-off.**
  - `CANCELLED` / `CUTOFF_PASSED` → "Cancelled", "…You weren't charged.", "Not charged".
- **Scenario: under review.**
  - `NEEDS_ATTENTION` / `SWEEP_EXHAUSTED` → "Under Review", "…won't be charged twice.",
    "Charge under review", and **no** "You weren't charged".
- **Scenario: payment failed before pricing.**
  - `PAYMENT_FAILED` / `DELIVERY_ADDRESS_UNKNOWN`, amount 0 → "Payment Failed", the address
    copy, Grand Total "—".
- **Scenario: not found.** A 404 → "Order not found"; tapping "Back to My Orders" pops.
- **Scenario: scheduled delivery.**
  - Expect "SCHEDULED DELIVERY", "Scheduled", "Estimated Total", "≈ ₹130.00", the final-price
    caption and "Manage subscription".
  - Tapping "Manage subscription" goes to `/subscriptions`.
- **Scenario: copy order ID.** Long-pressing the ID puts the full ID on the clipboard and
  shows "Order ID copied".
- **Router test:** `/orders/scheduled/sub_1` resolves to the scheduled screen, not
  `OrderDetailScreen('scheduled')`.
- **Keys:** `Key('orderDetail.orderId')`, `Key('orderDetail.statusBanner')`,
  `Key('orderDetail.item.{index}')`, `Key('orderDetail.grandTotal')`.

**Integration (local-dev):** open a real confirmed order from My Orders and check that the
total matches the wallet debit in Wallet transactions (MA-24). Open a scheduled entry; after
the Daily Run, refresh and see the "now an order" notice.

## 11. Risks and Trade-offs

- **Sparse screen vs the rich mock.** Only truthful sections are shown, and the layout
  leaves room for MA-35 to add address, bill breakdown and actions without redesign.
- **Display ID vs full ID.** A short ID is friendlier; long-press copy keeps support
  workable. Order Service has no human-friendly order number yet.
- **Reason copy is maintained in the app.** New backend reasons fall back to a generic
  message until the app adds them. It's acceptable at this volume.
- **The scheduled view can go stale** once the Daily Run runs. Handled by fetching by ID and
  telling the customer it's now an order.
