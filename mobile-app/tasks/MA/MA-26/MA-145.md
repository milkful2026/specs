## 2. Problem Statement

Customers can place orders (MA-137 checkout) and run subscriptions (MA-133), but the app has
no screen that lists their orders. They cannot see what arrives today, what is coming, or
what happened to an order. That includes orders the platform could not complete: payment
failed, cancelled at the cut-off, or held for review by the MA-138 reconciliation sweep.
Customers find out only when a delivery does not arrive.

Expected outcome: a **My Orders** screen that shows today's delivery, upcoming deliveries
(including each subscription's next delivery before it becomes an order) and past orders,
with statuses that only state what the platform actually knows.

## 3. Scope

### In scope

- New `lib/features/orders/` feature: order read repository, models, the `MyOrdersBloc`, and
  the `/orders` screen.
- Today's Delivery section, and the **Upcoming** and **Past Orders** tabs.
- Merging real orders with scheduled next subscription deliveries in Upcoming.
- Product name, pack size and image lookup through the existing `CatalogRepository`.
- The status-chip mapping and the amount rules (per order; marked estimates).
- Loading, empty, error, partial-failure, pagination and pull-to-refresh behaviour.
- Navigation from any order to its detail (the detail screen itself is MA-146).

### Out of scope

- Filters (date range, status, type) and search. The mock's search icon is **not shown**.
- Re-order, invoice download, feedback/complaint, support.
- A "Delivered" status, delivery time or delivery partner (needs MA-102 Delivery Service).
- The entry point on the Profile screen (MA-147) and the detail screen (MA-146).
- Any backend change.

## 4. Functional Requirements

### Terms

- **Today**: the current date in IST (UTC+05:30), computed from `DateTime.now().toUtc()`
  plus 5:30. It never depends on the device time zone.
- **Order entry**: an order returned by `GET /orders/me`.
- **Scheduled entry**: a subscription's next delivery that is not yet an order (FR-4).
- **Entry**: either of the two.

### Screen structure

```
AppBar: [←]  My Orders
Body (pull-to-refresh):
  Today's Delivery                      [N Items]
    ┌ item card ┐  (one per item of every order entry dated today)
  [ Upcoming | Past Orders ]            (TabBar)
    day group cards
```

### FR-1: Route and app bar

- Route `/orders`, pushed (not a bottom-bar tab). Title **"My Orders"**.
- A back arrow returns to the previous screen (Profile, per MA-147).
- No search icon and no bottom navigation bar on this screen (it is a pushed screen).

### FR-2: Data loading

On open, and on every pull-to-refresh, the bloc loads in parallel:

1. **Orders:** the first page of `GET {orderBaseUrl}/orders/me?limit=50`.
2. **Subscriptions:** `GET {subscriptionBaseUrl}/subscriptions`, through the existing
   `SubscriptionRepository.list()`.

Then it resolves product details (FR-7). The two sources succeed or fail independently
(FR-10).

### FR-3: Buckets

Each order entry is placed by comparing its `deliveryDate` (an IST date on the wire) with
**Today**:

| deliveryDate | Bucket |
|--------------|--------|
| = Today | Today's Delivery |
| > Today | Upcoming |
| < Today | Past Orders |

Every status is bucketed, including `CANCELLED`, `PAYMENT_FAILED`, `NEEDS_ATTENTION` and
`FAILED`, so the customer sees orders that did not go through.

### FR-4: Scheduled entries (Upcoming only)

For each subscription with `status != STOPPED` and a non-null `nextDeliveryDate` later than
Today:

- Add a scheduled entry: subscription ID, product ID, quantity, `nextDeliveryDate`.
- Skip it if an order entry already exists with the same `subscriptionId` and
  `deliveryDate`. The backend already excludes materialized dates; this is a second guard.
- **`nextDeliveryDate` decides, not `status`.** A pause with a future start date sets
  `status = PAUSED` immediately, but deliveries before the pause start still happen and
  `nextDeliveryDate` still carries the next one (Subscription Service computes it from the
  pause window). So a PAUSED subscription with a non-null `nextDeliveryDate` **is**
  scheduled; one whose pause is in effect has a null or post-pause date and is handled by
  the rules above.
- STOPPED subscriptions produce no scheduled entry.
- At most one scheduled entry per subscription (its next delivery only).
- A `nextDeliveryDate` equal to Today is ignored. Today's subscription delivery is a real
  order by then; if it is not, nothing is scheduled for today.

### FR-5: Today's Delivery section

- Header **"Today's Delivery"** with a truck icon. A pill on the right reads **"N Items"**,
  where N is the total number of item cards (`1 Item` when N is 1).
- **One item card per item** of each order entry dated Today, in the order the API returned
  them, with each order's items in their API order. Each card shows:
  - product image (FR-7), product name, and `"{unit} • Quantity: {q}"` (e.g. `500ml •
    Quantity: 1`);
  - the order's status chip (FR-6);
  - the amount (FR-8).
- Tapping any card opens that order's detail: `context.push('/orders/{orderId}')` (MA-146).
- **Empty:** a card reading **"No deliveries today"**, with no pill. Only when the orders
  call loaded; if it failed, see FR-11.

### FR-6: Status chip

| Order status | Chip label | Style (theme token) | Icon |
|--------------|------------|---------------------|------|
| `CONFIRMED` | Order Placed | neutral (grey surface) | check circle outline |
| `CREATED` | Processing | neutral | schedule |
| `PAYMENT_FAILED` | Payment Failed | error (red surface) | error outline |
| `CANCELLED` | Cancelled | error | cancel outline |
| `NEEDS_ATTENTION` | Under Review | warning (amber surface) | info outline |
| `FAILED` | Failed | error | error outline |
| (scheduled entry) | Scheduled | primary-tint (green surface) | calendar |
| any other value | the raw value, title-cased | neutral | none |

There is **no "Delivered" chip** (MA-26 decision, 2026-09-30). The chip's semantics label is
`"Status: {label}"`.

### FR-7: Product details

- Collect the distinct product IDs from every entry. For an order, those are `items[].productId`;
  a SUBSCRIPTION order has one item.
- Resolve each ID once through `CatalogRepository.getProduct(id)`, with the calls in
  parallel and the results cached in the bloc for the screen's lifetime. This is the same
  cached pattern `SubscriptionBloc` uses.
- The list renders **before** the lookups finish: names show a text placeholder and images a
  neutral placeholder, then fill in.
- A failed lookup falls back to the name **"Item"**, no unit, and a placeholder image. It
  never fails the screen.

### FR-8: Amounts

Amounts are integer paise on the wire, displayed as `₹` with no decimals when the paise
part is 0 and two decimals otherwise (`₹65`, `₹65.50`). Order Service stores only an order's
total, so:

- **Single-item order entry** (every SUBSCRIPTION order, and a one-line checkout order): the
  item card or row shows the order's `amountPaise`.
- **Multi-item order entry** (a checkout order with 2+ items):
  - in Today's Delivery, a small header row above that order's item cards reads
    **"Order total ₹X"**, and the item cards show **no amount**;
  - in a day group, the order's row shows its total.
- **Scheduled entry**: the estimate from the Catalog product, prefixed **"≈"** and suffixed
  **"est."** (e.g. `≈ ₹130 est.`). Catalog's `Product.price` is **decimal rupees** (a
  `double`), not paise, so the estimate is converted before it is used anywhere:
  `estimatePaise = (product.price * 100).round() * quantity` (round the unit price first,
  then multiply, so the result is whole paise). From there it is handled like any other
  paise amount; no rupee value reaches `dayTotal` or the formatter. If the product lookup
  failed, it shows **"Price confirmed the evening before"** and contributes nothing to the
  day total.
- **Day group total** (FR-9): the sum over the group's entries, labelled **"₹X Total"**. If
  any scheduled entry contributes, the label reads **"≈ ₹X Total"**. Entries whose amount is
  unknown are left out.
- `CANCELLED`, `PAYMENT_FAILED` and `FAILED` orders show their amount struck through and are
  **excluded** from the day total, because they were not charged or not delivered.
- `NEEDS_ATTENTION` depends on `failureReason`, because the app is not sent the order's
  charge state:
  - `CUTOFF_PASSED`: the sweep closed the order **after** Wallet voided the debit, so it
    was not charged. Amount struck through and **excluded**, like `CANCELLED`.
  - `SWEEP_EXHAUSTED`, null or any other reason: the charge may be unknown. Amount shown
    normally and **included** in the day total.
  This rule lives in one pure helper, `isKnownNotCharged(order)`, in
  `order_status_copy.dart`, shared with MA-146 FR-5.

### FR-9: Upcoming and Past Orders tabs

- A `TabBar` with **"Upcoming"** (selected by default) and **"Past Orders"**.
- Both tabs list **day group cards**, one per delivery date:
  - Header: a calendar icon, then the date label. Upcoming uses **"Tomorrow, 24 Oct"** for
    Today+1 and **"Sat, 26 Oct"** otherwise; Past uses **"Yesterday, 22 Oct"** or
    **"Wed, 22 Oct"**, and appends the year when it is not the current IST year
    (`"Wed, 22 Oct 2025"`). The day total (FR-8) sits on the right.
  - **One row per entry** on that date. Each row shows:
    - thumbnails of up to two product images, then a **"+N"** bubble for the rest;
    - a summary: the first product's name, with `", {second}"` when there are two and
      `" & more"` beyond two (e.g. "Fresh Vegetables, Bread & more"); scheduled entries
      append **"(Subscription)"** (e.g. "Pure Cow Milk (Subscription)");
    - the status chip, **only when** the status is not `CONFIRMED` (normal orders stay as
      clean as the mock) — scheduled entries always show **Scheduled**;
    - a chevron button.
- **Order of groups:** Upcoming soonest first; Past most recent first. Within a group, order
  entries come first (API order), then scheduled entries.
- **Tap a row:**
  - order entry → `context.push('/orders/{orderId}')`;
  - scheduled entry → `context.push('/orders/scheduled/{subscriptionId}', extra: entry)`.
  Both are MA-146.
- **Empty Upcoming:** **"No upcoming deliveries"**, plus a **"Browse products"** button that
  goes to `/catalog`.
- **Empty Past Orders:** **"No past orders yet"**.

### FR-10: Past Orders pagination

- The first page (FR-2) fills all three buckets. When the Past Orders tab is visible and the
  customer scrolls within 300 px of its end while `nextCursor` is non-null, the bloc fetches
  `GET /orders/me?limit=50&cursor={nextCursor}` and appends.
- A bottom spinner shows while a page loads. A failed page shows a **"Couldn't load more.
  Retry"** row that retries only that page.
- Orders from later pages are bucketed by FR-3 like any other. They are almost always Past,
  because creation order tracks delivery order within ±2 days.
- Only one page request is in flight at a time (`droppable` transformer).

### FR-11: Loading, error and partial failure

| Situation | UI |
|-----------|----|
| First load in progress | Skeleton: 2 item-card placeholders and 2 group placeholders |
| Orders **and** subscriptions failed | Full-screen error: **"Couldn't load your orders."** + **"Retry"** button |
| Orders failed, subscriptions loaded | Banner at the top: **"Some orders couldn't be loaded."** + **"Retry"**. The orders-backed empty states are **not** shown, because the app doesn't know there are none: Today shows **"Couldn't load today's deliveries."** (no "N Items" pill); Past shows **"Couldn't load past orders."**; Upcoming shows the scheduled entries, and if there are none, **"Couldn't load upcoming orders."** instead of "No upcoming deliveries" / "Browse products" |
| Subscriptions failed, orders loaded | Banner: **"Upcoming subscription deliveries couldn't be loaded."** + **"Retry"**; everything else renders normally |
| Pull-to-refresh fails | Keep the data already shown; SnackBar **"Couldn't refresh. Try again."** |
| `401` from any call | Treated like any failure of that source (rows above). The app has no global session-expiry handling today; adding one is out of scope and applies app-wide, not just to this screen |

"Retry" reloads only the source(s) that failed.

**Empty-state rule:** an empty state ("No deliveries today", "No upcoming deliveries", "No
past orders yet") is shown only when every source that feeds that section **loaded** and
returned nothing. A section fed by a failed source shows its "Couldn't load …" text instead.

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Performance | First meaningful paint (skeleton) < 100 ms after navigation; lists render as soon as orders and subscriptions return, without waiting for Catalog; scrolling at 60 fps with 200 entries (lazy `ListView.builder` / slivers) |
| Network | ≤ 2 list calls per open/refresh + 1 Catalog call per distinct product (cached for the screen's lifetime); Past pages only on demand |
| Correctness | Buckets and labels use IST regardless of device time zone; no entry appears twice; no "Delivered" state |
| Accessibility | Touch targets ≥ 48dp; status chips announce `"Status: …"`; chevrons have semantics label `"Open order"`; text contrast WCAG AA; supports text scale up to 1.3 without clipping |
| Observability | No new analytics events are required; errors are logged through the app's existing debug logging only |
| Maintainability | Bucketing, merging and amount rules live in pure functions (no Flutter imports), so they're unit-testable |

## 6. Technical Design

**Files (new, under `lib/features/orders/`):**

| File | Responsibility |
|------|----------------|
| `models/order_summary.dart` | `OrderSummary` (`fromJson` of an `/orders/me` item), `OrderItem`, `OrderStatus` enum with `fromWire` (unknown → `OrderStatus.unknown` keeping the raw string), `OrderSource` |
| `models/order_entry.dart` | Sealed `OrderEntry` = `OrderedEntry(OrderSummary)` \| `ScheduledEntry(subscriptionId, productId, quantity, date)` |
| `models/orders_page.dart` | `OrdersPage(items, nextCursor)` |
| `data/order_repository.dart` | `abstract class OrderRepository { Future<OrdersPage> listMine({String? cursor, int limit}); Future<OrderSummary> getById(String id); }` + `DioOrderRepository(ApiClient)` using `AppConfig.orderBaseUrl`. `getById` is used by MA-146 |
| `domain/order_buckets.dart` | Pure functions: `istToday(DateTime utcNow)`, `bucket(entries, today)`, `mergeScheduled(orders, subscriptions, today)`, `dayTotal(entries, prices)` |
| `domain/order_status_copy.dart` | Status labels, styles and icons (FR-6), shared with MA-146 (which adds the failure-reason copy) |
| `bloc/my_orders_bloc.dart` (+ `_event`, `_state`) | Events: `MyOrdersOpened`, `MyOrdersRefreshed`, `PastPageRequested`, `RetryFailedSources`. State: orders, nextCursor, subscriptions, product cache, per-source status (`loading/loaded/failed`), `pagingStatus` |
| `presentation/my_orders_screen.dart` | Screen, sections and cards; widgets split into `widgets/` as needed |

**Wiring:** `main.dart` registers `RepositoryProvider<OrderRepository>` (a
`DioOrderRepository(apiClient)`). `app_router.dart` adds `GoRoute('/orders')`, which builds
`BlocProvider(create: MyOrdersBloc(orderRepo, subscriptionRepo, catalogRepo, clock)..add(MyOrdersOpened()))`.
The bloc takes a clock function (`DateTime Function() now`) so tests can pin Today.

**Flow:**

```
MyOrdersOpened
 ├─ orderRepo.listMine(limit 50) ─┐
 ├─ subscriptionRepo.list() ──────┤ (Future.wait, each wrapped → Result)
 └─ emit(loaded/partial)  ◄───────┘
     └─ for each unseen productId: catalogRepo.getProduct → cache → emit
PastPageRequested (droppable) → listMine(cursor) → append → emit
```

## 7. Data Considerations

- No local persistence. The data is refetched on open; the product cache is in memory per
  screen instance.
- Parsing is defensive:
  - an unknown `status` maps to `OrderStatus.unknown(raw)`;
  - an unknown `source` is treated as CHECKOUT for display;
  - missing `items` are treated as `[]` (the row shows "Order");
  - `deliveryDate` is parsed as a date only (`YYYY-MM-DD`), never through time-zone
    conversion.
- Money is kept as integer paise, and formatted only in the presentation layer. The one
  rupee-denominated input, Catalog's `price`, is converted to paise at the point it is read
  (FR-8).

## 8. Integration Considerations

| Dependency | Contract | Failure behaviour |
|------------|----------|-------------------|
| Order Service `GET /orders/me` | `{items: [order], nextCursor}`; order fields per MA-132 FR-3 / MA-136 FR-10 | FR-11 rows; page errors per FR-10 |
| Subscription Service `GET /subscriptions` | list with `status`, `nextDeliveryDate` (null when none) | FR-11 subscriptions-failed banner |
| Catalog `GET /products/{id}` | `Product` (MA-115 §7): `name`, `unit`, `price` (decimal rupees; converted to paise per FR-8), `imageUrl` | FR-7 fallback; estimate shows "Price confirmed the evening before" |
| Existing `ApiClient` | Bearer token, `{status, data}` unwrap, `ApiException` | Unchanged |

Timeouts and retries: the `ApiClient` defaults. No automatic retry beyond the user's
"Retry" and pull-to-refresh.

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Customer has no orders and no subscriptions | Today "No deliveries today", Upcoming "No upcoming deliveries" + Browse products, Past "No past orders yet" |
| Subscription's next delivery already has an order | Only the order entry shows (FR-4 guard) |
| Subscription stopped, or `nextDeliveryDate` null | No scheduled entry |
| Subscription PAUSED from a future date, with a delivery due before the pause starts | Scheduled entry for that `nextDeliveryDate` (FR-4) |
| Order `NEEDS_ATTENTION` / `SWEEP_EXHAUSTED` for tomorrow | Upcoming row with the "Under Review" chip; counted in the day total |
| Order `NEEDS_ATTENTION` / `CUTOFF_PASSED` | "Under Review" chip; amount struck through; **not** counted in the day total (debit was voided) |
| Catalog price `32.5` (rupees), quantity 2 | Estimate `≈ ₹65 est.` (3250 paise × 2 = 6500 paise), never `₹0.65` or `₹6500` |
| Order `CANCELLED` today (MA-144 PD-1) | Today's Delivery card with the "Cancelled" chip; amount struck through |
| Multi-item checkout order today | Order-total header + one card per item, no per-item amounts |
| Product removed from Catalog (404) | Name "Item", placeholder image; scheduled estimate unknown |
| Device time zone ≠ IST, or device date near midnight | Buckets follow IST (e.g. 23:30 UTC = 05:00 IST next day) |
| An order on page 2 dated in the future (unusual) | Bucketed into Upcoming when its page loads |
| Same product in two orders on one day | One Catalog call (cache); two rows |
| Pull-to-refresh while a Past page is loading | Refresh wins: the page result is discarded if it returns after the refresh started |
| Customer returns from the detail screen | No automatic reload; pull-to-refresh is available |
| Very long product names | Ellipsised to 1 line on cards and 2 lines in summaries |

## 10. Testing Strategy

**Unit (pure functions, `test/features/orders/domain/`):**
- `istToday`: 18:29 UTC → same IST date; 18:30 UTC → next IST date.
- Bucketing: today, past and future dates across every status.
- `mergeScheduled`:
  - an ACTIVE subscription with a future date → an entry;
  - an existing order for the same (subscriptionId, date) → no entry;
  - PAUSED with a future `nextDeliveryDate` (future-dated pause) → an entry;
  - STOPPED, or a null date (including PAUSED with the pause in effect) → none;
  - a date equal to Today → none.
- `dayTotal`: excludes cancelled/failed; includes NEEDS_ATTENTION/SWEEP_EXHAUSTED;
  excludes NEEDS_ATTENTION/CUTOFF_PASSED; an estimate sets the "≈" flag; an unknown price
  is left out.
- Estimate conversion: price `32.5` × quantity 2 → 6500 paise; price `24.99` × quantity 3
  → 7497 paise; a mixed day (one 6500-paise order + that estimate) totals in paise only.
- `order_status_copy`: every row of FR-6, including unknown values.

**Bloc (`bloc_test`, with fakes for Order, Subscription and Catalog repositories):**
- open → loading → loaded with the correct buckets;
- orders fail but subscriptions load → partial state; retry reloads orders only;
- both fail → error; retry → loaded;
- the product cache means one `getProduct` per distinct ID across refreshes;
- `PastPageRequested` appends and updates the cursor; a second request while in flight is
  dropped; a page failure keeps the existing items and sets the paging error;
- refresh during paging discards the stale page.

**Widget (`test/features/orders/presentation/my_orders_screen_test.dart`, `find.text` / `find.byKey`):**
- **Scenario: today's delivery renders item cards.**
  - Given one CONFIRMED order today with 2 items and one CANCELLED single-item order today.
  - Expect: "Today's Delivery", "3 Items", "Order total ₹…" once, and chips "Order Placed" and
    "Cancelled".
- **Scenario: upcoming merges a scheduled subscription.**
  - Given tomorrow's checkout order and a subscription whose next delivery is Today+2.
  - Expect: "Tomorrow, …" group with "₹X Total", and a "… (Subscription)" row with a
    "Scheduled" chip and an "≈ ₹… Total" group label.
- **Scenario: no Delivered label.** A CONFIRMED order yesterday → the Past tab shows no
  "Delivered" text anywhere.
- **Scenario: tap navigates.** Tapping an order row pushes `/orders/{id}`; tapping a
  scheduled row pushes `/orders/scheduled/{subscriptionId}`. Verified with a `GoRouter`
  test harness.
- **Scenario: empty states.** Each empty text from FR-5 and FR-9, and "Browse products" goes
  to `/catalog`.
- **Scenario: partial failure banner.** An orders failure with subscriptions loaded shows
  "Some orders couldn't be loaded.", "Retry", "Couldn't load today's deliveries." and (on
  the Past tab) "Couldn't load past orders.", and **no** "No deliveries today" or "No past
  orders yet".
- **Scenario: pagination.** Scrolling Past to the end requests page 2, then shows the
  appended groups.
- **Keys** (for integration tests where there's no unique text):
  - `Key('orders.today.card.{orderId}.{index}')`
  - `Key('orders.group.{yyyy-mm-dd}')`
  - `Key('orders.row.{orderId}')`
  - `Key('orders.row.scheduled.{subscriptionId}')`
  - `Key('orders.past.loadMoreRetry')`

**Integration / acceptance** (local-dev stack):
- Place a checkout order for tomorrow, and have a subscription with a next delivery.
- Open My Orders: tomorrow's group shows the order; the subscription shows as Scheduled with
  an estimate; after the Daily Run and a refresh, the scheduled entry is replaced by the real
  order with its exact amount.

**Negative:**
- A malformed `/orders/me` item (e.g. missing `items`) renders "Order" without crashing.
- An unknown status renders a neutral chip with the raw text.

## 11. Risks and Trade-offs

- **Buckets computed in the app from newest-created pages** instead of a server-side date
  filter. This is safe because orders are created ≤ 2 days before delivery. A future
  backend change to that rule would need a `from/to` filter on `/orders/me` (noted for MA-35
  / later).
- **Only the next delivery per subscription**: a customer with daily milk sees one scheduled
  entry, not a week. This is accepted (MA-26 decision). A projection API would be new
  backend work.
- **Estimates can differ from the final charge** (tax, delivery fee, offers, price changes).
  They are always marked "≈ … est."; MA-146 explains it on the detail screen.
- **No per-item price** on multi-item orders: the mock's per-card prices can't be shown
  truthfully. We show the order total once instead (MA-26 decision).
- **N Catalog calls** for N distinct products on first open. They are cached and parallel;
  a batch product endpoint can come later if needed.
