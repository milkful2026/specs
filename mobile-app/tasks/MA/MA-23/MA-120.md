## 2. Problem Statement

MA-22/115 shipped a catalog screen whose product cards have no working tap handler — there is
currently no path from "browsing products" to "something is in my cart." This spec covers the
single configuration screen (matching the attached mockup) that a customer reaches by tapping a
product: choose a delivery frequency (for subscription-eligible products), a start date, and a
quantity, see a live price estimate, and confirm — persisting the result as a cart line item.
Without this screen, MA-24 (Payment) and MA-25 (Subscription) have nothing to act on.

## 3. Scope

**In scope:**
- Wiring the tap handler on MA-22's `_ProductCard` (currently declared but never connected) to
  navigate here with the tapped product.
- The configuration screen itself: frequency selector (Daily / Alternate Days / One Time, shown
  only when `product.subscriptionEligible`), start-date calendar (subscription frequencies only),
  quantity stepper bound to real available stock, live price estimate, wallet-balance-≥-₹500 gate
  before a subscription confirm, and the confirm action itself.
- A new `CartRepository` (interface + Dio-backed impl + hand-written fake) and `PricingRepository`
  (same pattern), following this codebase's established `RegistrationRepository`/
  `CatalogRepository` convention.
- A small, additive contract change to the already-shipped Catalog Service (MA-94/115/116) — see
  §7 — needed so this screen's quantity stepper has a real ceiling to validate against.

**Out of scope:**
- A cart list/review screen (view all items, edit/remove, multi-item subtotal/tax/delivery
  breakdown, offers/coupons display, empty-cart state, re-order-from-history). Named in MA-23's
  ticket text but no mockup exists for it — explicitly deferred to a follow-up story per product
  direction (2026-08-19 conversation).
- The subscription lifecycle engine (recurring order generation, auto-debit, pause/resume/skip) —
  NSMB spec row 6.0, tracked as MA-25. This screen only captures frequency + start date as
  attributes on the cart line item; it does not create or manage a subscription.
- Payment/checkout (MA-24).
- Cart Service (MA-96) and Pricing & Offer Service (MA-101) backend implementations — this spec
  defines the mobile app's consumption of their APIs (spec'd in parallel, see MA-121/MA-122), not
  the services' own behavior.

## 4. Functional Requirements

### Screen structure (matches attached mockup)

```
AppBar-equivalent: back arrow (left) · share icon · favourite icon (right, both present but
  not wired — no share/favourite backend exists yet; matches this codebase's established
  "present per mockup, not yet wired" treatment used elsewhere, e.g. home_screen.dart's Profile/
  Wallet icons)
Banner: product category image + tagline (reuses MA-22's existing product image asset for this
  product; no new banner-image concept introduced)
Product title + "Premium Selection"-style tag (reuses `product.tag` if present, else omitted)
"Subscription Plan" section (only if product.subscriptionEligible):
  three selectable cards — Daily / Alternate Days / One Time
"Select Start Date" calendar (only visible when a subscription frequency, not One Time, is
  selected)
"Quantity per delivery" stepper with a recommendation caption
Sticky bottom bar: "Estimated Total ₹{amount} / {unit}" (left) · primary CTA (right) —
  "Subscribe Now" for a subscription frequency, "Add to Cart" for One Time
```

### FR-1: Navigation from catalog

- `catalog_screen.dart`'s `_ProductCard` gains a working `onTap` (a new constructor parameter — see
  §7's built-state note for the current, un-wired state) that pushes this screen via `go_router`,
  route `/product/:productId`, passing the tapped `Product`.
- Products with `stockState == StockState.outOfStock` remain tappable (per MA-22's existing
  dimmed-but-not-disabled card treatment) — this screen shows an out-of-stock state (FR-6) rather
  than being unreachable.

### FR-2: Frequency selector

- Rendered only when `product.subscriptionEligible == true`. Non-eligible products skip straight
  to a One-Time-only layout (no frequency cards, no calendar) — resolves Step 1 open question #1.
- Three options: **Daily**, **Alternate Days**, **One Time** — exactly the mockup's set; no other
  frequency values in this pass (custom/weekly frequencies belong to MA-25's Subscription module,
  per NSMB row 6.0).
- Exactly one selected at a time; **One Time** is the default selection on screen open.
- `Key('frequency-daily')`, `Key('frequency-alternate')`, `Key('frequency-one-time')` on each
  selectable card.
- Selecting Daily or Alternate Days reveals the start-date calendar (FR-3) and changes the primary
  CTA label to **Subscribe Now**; selecting One Time hides the calendar and sets the CTA to
  **Add to Cart**.

### FR-3: Start-date calendar

- Visible only when a subscription frequency is selected.
- Month-grid calendar (per mockup), defaulting to the current month with today's date
  pre-selected where selectable.
- Dates before today are not selectable (greyed out, matching the mockup's past-date treatment).
- `Key('start-date-calendar')`; selected date exposed via `Key('start-date-selected')` for test
  assertions.

### FR-4: Quantity stepper

- `-`/`+` buttons around a numeric display, default value `1`.
- Minimum `1` (the `-` button is disabled at `1`).
- Maximum bound to the product's real available stock — see §7 for the Catalog Service contract
  addition this depends on. The `+` button is disabled once the maximum is reached, with a caption
  "Only {n} left" shown once within 5 units of the maximum (mirrors typical scarcity-messaging
  patterns; exact copy confirmed in Step 5 review, not re-litigated here).
- `Key('quantity-stepper-decrease')`, `Key('quantity-stepper-increase')`,
  `Key('quantity-stepper-value')`.
- `Semantics(label: 'Decrease quantity')` / `Semantics(label: 'Increase quantity')` on the two
  buttons (icon-only, no visible text label — accessibility requirement, not optional).

### FR-5: Price estimate

- On screen load, and again on quantity/frequency change **debounced 300ms** (matching
  `catalog_page.dart`'s existing search-field debounce pattern, since rapid `+`/`-` taps would
  otherwise fire one request per tap), calls `PricingRepository.quote(...)` with the product ID,
  quantity, frequency, and the customer's delivery-address state (required by MA-101 FR-1/FR-2 for
  CGST/SGST vs. IGST determination — sourced from the address captured during onboarding,
  `address_screen.dart`'s `state-field`).
- Each quote request carries a monotonically increasing sequence number; a response is only
  applied to the displayed price if it's the most recent request issued — out-of-order responses
  (an older, lower-quantity quote landing after a newer one under variable network latency) are
  discarded rather than overwriting the current price.
- Displays the result as "₹{amount}" for One Time, "₹{amount} / month" for a subscription
  frequency (matching the mockup's "/ month" framing) — the exact amount is Pricing & Offer
  Service's computed total (base price × quantity, plus tax/delivery per MA-101 §Data
  Considerations), never computed client-side from `product.price` alone.
- Shows a loading skeleton in place of the amount while a quote is in flight; a quote failure
  shows "Price unavailable — pull to retry" (non-blocking — the rest of the screen stays usable,
  but the primary CTA is disabled without a successful quote, since confirming without a known
  price is not acceptable).

### FR-6: Stock / availability states

- `stockState == outOfStock`: quantity stepper and primary CTA both disabled; a banner "Currently
  out of stock" replaces the quantity section.
- `stockState == availableFrom`: same disabled treatment, banner reads "Available from
  {availableFrom, formatted as 'MMM d'}".
- `stockState == inStock`: normal interactive state (FR-4/FR-5 apply).

### FR-7: Wallet-balance gate (subscription only)

- Before enabling **Subscribe Now** (Daily/Alternate Days only — never checked for One Time), the
  screen reads the customer's current wallet balance. **Gap found, not yet resolved:** the app
  today has no code path that exposes a numeric wallet balance — the only existing wallet-related
  state is a `walletStatus` string (`PENDING`/`FAILED`/ready) surfaced once after registration in
  `home_screen.dart`; no `AuthBloc` field, bloc state, or repository call returns a balance. This
  is a new read path this screen needs, not a reuse of something that already exists — see §12
  Open Questions for the unresolved call site (existing MA-100 contract vs. a new endpoint).
- If balance `< ₹500`, **Subscribe Now** is disabled and an inline message is shown: "A minimum
  wallet balance of ₹500 is required for subscriptions — your balance is ₹{balance}." No blocking
  dialog / forced top-up flow in this pass (Step 1 open question #3 resolved in favor of the
  simpler inline-message treatment; a "Recharge Wallet" shortcut can be added later since
  `home_screen.dart`'s Wallet icon is already present, if not yet wired).
- One Time confirms are never gated by wallet balance — payment happens later, at checkout
  (MA-24), same as today's un-built cash/online flow.

### FR-8: Confirm action

- **Add to Cart** / **Subscribe Now** calls `CartRepository.addItem(...)` with product ID,
  quantity, frequency (`ONE_TIME` / `DAILY` / `ALTERNATE_DAYS`), and — for subscription
  frequencies — the selected start date.
- The call sends an `Idempotency-Key` header: a UUID generated once when the confirm CTA is first
  tapped and reused on any retry of that same attempt (per MA-96/MA-121 FR-2's documented
  idempotent-writes convention) — this is the actual dedup mechanism for a timed-out request or an
  app kill/relaunch mid-request; the in-flight button-disable below only prevents a double-tap
  within a single live screen session, it is not a substitute for the header.
- While in flight: button shows a spinner (matching `welcome_screen.dart`'s `FilledButton`
  loading-state pattern), disabled to prevent a double-submit.
- On success: a `SnackBar` confirmation ("Added to cart") and the screen pops back to the catalog
  — there is no cart-review screen to navigate to yet (§3 Out of Scope), so returning to where the
  customer came from is the only sensible destination (resolves Step 1 open question #2).
- On failure: the button re-enables and an inline error message shows `ApiException.message`
  verbatim (matching the existing pattern in `welcome_screen.dart`/`address_screen.dart`), not a
  generic "something went wrong" unless the exception truly is unclassified.

### FR-9: Re-visiting a configured product

- Every visit starts fresh (One Time selected, quantity 1, no pre-fill from an existing cart line
  item) — resolves Step 1 open question #4. Reconciling with an already-in-cart line item for the
  same product is Cart Service's/the future cart-review screen's concern, not this screen's; this
  screen only ever adds, it does not read existing cart state.

## 5. Non-Functional Requirements

- **Performance:** price quote round-trip should not visibly block interaction — the screen must
  render (frequency/quantity controls interactive) before the first quote resolves; the quote
  result fills in progressively (FR-5's skeleton state).
- **Reliability:** a Pricing or Cart Service outage must degrade to a clear, retryable error state
  (FR-5, FR-8) — never a silent failure or an uncaught exception crashing the screen.
- **Accessibility:** touch targets ≥ 48dp for stepper buttons and frequency-selector cards;
  `Semantics` labels on every icon-only control (FR-4); calendar dates reachable via screen reader
  with the date announced.
- **Testability:** every interactive element carries a `Key` (enumerated per-FR above) or a
  `Semantics` label, following this codebase's established selector convention — no test should
  need to rely on a `find.text` match against copy that product may still be iterating on.

## 6. Technical Design

- **State management:** a new `ProductConfigBloc` (events: `ProductConfigStarted`,
  `FrequencyChanged`, `StartDateChanged`, `QuantityChanged`, `AddToCartRequested`; states carry the
  product, current selection, quote-in-flight/quote-result, wallet-balance-check result, and
  add-in-flight/add-result) — mirrors `RegistrationBloc`'s shape (a single bloc owning a
  multi-step, single-screen flow) more closely than `CatalogBloc`'s (list/filter) shape.
- **Repositories:**
  - `CartRepository` (`lib/features/cart/data/cart_repository.dart`): abstract interface +
    `DioCartRepository` impl, calling Cart Service (MA-96/MA-121) per its approved contract, once
    available — until then, implementation proceeds against `FakeCartRepository`
    (`test/fakes/fake_cart_repository.dart`), matching this codebase's fake-first pattern used
    throughout onboarding/catalog.
  - `PricingRepository` (`lib/features/cart/data/pricing_repository.dart`): same shape, calling
    Pricing & Offer Service (MA-101/MA-122) / `FakePricingRepository`.
  - `CatalogRepository` (existing, `lib/features/catalog/data/catalog_repository.dart`) gains a new
    `Future<Product> getProduct(String productId)` method (`GET /products/{id}`) — the interface
    today only exposes `getProducts({categoryId})`, a list fetch; a single-product fetch is a small,
    additive addition needed for the stale-stock re-fetch (§9 Edge Cases), alongside a
    `FakeCatalogRepository` update.
- **Routing:** new `GoRoute(path: '/product/:productId', ...)` in `app_router.dart`, consistent
  with the existing flat-path convention (`/otp`, `/address`, `/home`). The `Product` itself is
  passed via `extra:` rather than re-fetched by ID, since the catalog screen already holds the full
  `Product` object at tap time — avoids a redundant fetch. `welcome_screen.dart` already calls
  `context.go('/otp', extra: state.mobile)`, but no existing route builder actually reads
  `state.extra` (the `/otp` builder ignores it; `OtpScreen` sources its data from `AuthBloc`
  instead) — this route would be the first to consume `state.extra`, not a continuation of an
  established pattern. The builder must therefore null-check `state.extra` and redirect back to
  `/home` if it's missing (e.g. a deep link or a restored route with no `Product` attached).
- **Screen:** `lib/features/cart/presentation/product_config_screen.dart`, `ProductConfigScreen`
  (`StatefulWidget` wrapping a `BlocProvider<ProductConfigBloc>` + `BlocBuilder`), following the
  `Card`-based layout conventions already established in `welcome_screen.dart`/`address_screen.dart`
  (rounded cards, `FilledButton` with `StadiumBorder`, existing `AppTheme` tokens — no new design
  tokens introduced).

## 7. Data Considerations

**Built-state note (corrected):** `catalog_screen.dart`'s `_ProductCard` constructor is
`const _ProductCard({required this.product});` — it has no `onTap` parameter today, and the
`Container` it builds has no tap handler at all (only the inner "Add" `FilledButton` has an empty
`onPressed: () {}`) — confirmed by reading the file directly. FR-1 is therefore not just "pass a
real callback": it requires adding a `required VoidCallback onTap` field to `_ProductCard`,
wrapping the card body in a tap handler (e.g. `InkWell`/`GestureDetector`), passing it from the
one call site (`itemBuilder: (context, index) => _ProductCard(product: products[index])`), and
deciding how the card's tap zone interacts with the inner Add button's own tap target (the Add
button should keep its own quick-add behavior and not also trigger navigation — e.g. via
`GestureDetector` hit-test ordering or wrapping only the non-button area).

**Gap found and resolved — stock quantity:** the mobile `Product` model
(`lib/features/catalog/models/product.dart`) and Catalog Service's own domain model
(`services/catalog/src/domain/models.py`) both carry only the tri-state `stock_state` enum, with
no numeric quantity field — yet Catalog Service's own `StockChanged` consumer
(`services/catalog/src/adapters/stock_changed_consumer.py`) **already receives** an
`availableQuantity` field on every event (payload contract jointly agreed during MA-116/MA-118
SDD review) and **silently discards it** — `apply_stock_change(...)` is called without it, and
`Product` has nowhere to store it even if it were passed. This is resolved, not left open, as
follows:

- Catalog Service (MA-94, already shipped): `Product` domain model gains `available_quantity: int`
  (default `0` for any product whose most recent event predates this field, i.e. no destructive
  migration needed — a backfill from Inventory's own current state is Catalog Service's own
  concern at implementation time, out of this spec's control). `apply_stock_change(...)` gains an
  `available_quantity` parameter and persists it. `GET /products`, `GET /products/{id}`, and
  `GET /search` responses gain an `availableQuantity` field alongside the existing `stockState`.
  This is additive/backward-compatible — no existing consumer breaks.
- Mobile `Product` model gains `final int? availableQuantity;` (nullable — defensive against a
  transitional period where the backend hasn't deployed the change yet, or an older cached
  response), parsed via `json['availableQuantity'] as int?`.
- This screen's quantity stepper (FR-4) uses `product.availableQuantity` as its max when present;
  when `null` (backend not yet updated, or a genuinely unknown quantity), falls back to a
  conservative default cap of **20** rather than being unbounded — a fixed, documented fallback,
  not a silent "no limit."
- This is a small, scoped contract addition to an already-approved service (MA-94/115/116), not a
  reopening of its functional behavior — flagged here per the Step 2 finding, ready to be picked
  up in Catalog Service's own implementation pass alongside or ahead of this screen's.

**Cart Service dependency:** `CartRepository.addItem(...)`'s request shape is defined jointly with
MA-96/MA-121's own spec (§6 there) — this spec does not duplicate that contract, only names the
fields this screen needs to send (product ID, quantity, frequency, start date).

**Pricing dependency:** `PricingRepository.quote(...)`'s request/response shape is defined jointly
with MA-101/MA-122's own spec (§6 there) — accepts a single-item list (per MA-101 §6's cardinality
decision), so this screen sends a one-element list even though it only ever configures one product
at a time.

## 8. Integration Considerations

- **Inventory:** not called directly by this screen — `availableQuantity` arrives via Catalog
  Service's response (§7), consistent with MA-115's own established decision that this app never
  calls Inventory Service directly.
- **Wallet:** balance read via the existing Wallet Service integration path established in
  MA-1/MA-100 (no new endpoint introduced by this spec — reuses whatever `AuthBloc`/profile
  refresh already exposes, or a direct `GET /wallet` call if that's what MA-100's contract
  provides; exact call site confirmed in implementation planning, not re-decided here).
- **Cart Service failure:** a `POST` failure surfaces via `ApiException` (FR-8) — no local queuing
  or offline retry; matches this app's existing online-only assumption (no story has introduced
  offline support).
- **Pricing Service failure:** degrades per FR-5 — the screen stays usable for browsing
  configuration options even when a quote can't be obtained, but confirming is blocked without one.

## 9. Edge Cases and Failure Modes

- Tapping a product whose stock has changed since the catalog screen last fetched it (stale
  `stockState`/`availableQuantity`) — this screen re-fetches the product's current state on open
  via a `CatalogRepository.getProduct(productId)` call (`GET /products/{id}`, which per §7's
  `availableQuantity` contract addition already returns current `stockState`/`availableQuantity`),
  not via `PricingRepository.quote` (MA-101's quote response carries price/tax data only, no stock
  fields — confirmed against MA-101/MA-122 §4 FR-1). So a customer never confirms against stale
  stock data. (Clarifies §6's routing note: the `Product` passed via `extra:` seeds the initial
  render only, it is not treated as ground truth for the confirm action — the fresh
  `getProduct` result replaces it once it resolves.)
- Quantity at the fallback cap of 20 when `availableQuantity` is genuinely higher — a customer is
  incorrectly blocked from ordering more than 20 units. Accepted as a known, documented limitation
  of the transitional fallback (§7), not silently ignored.
- Wallet balance fetch itself fails (network error, not just insufficient balance) — FR-7's gate
  fails closed (Subscribe Now stays disabled) with a distinct message ("Couldn't check your wallet
  balance — pull to retry") rather than either silently allowing the subscribe action or
  conflating this with the insufficient-balance message.
- Double-tapping the confirm CTA — prevented by FR-8's in-flight disable; no dependency on backend
  idempotency alone (though MA-96's own spec separately documents server-side idempotency per
  platform convention).
- Product becomes out-of-stock while this screen is open (a live update, not just stale-on-open) —
  out of scope for this pass; no live/push update mechanism exists anywhere in this app today
  (matches MA-22's own "poll/refresh-on-load, not live-push" resolution).

## 10. Testing Strategy

**Unit (bloc):** `ProductConfigBloc` — frequency/date/quantity change events update state
correctly; quantity clamps to `[1, availableQuantity ?? 20]`; a quote is requested on every
relevant state change and its result populates the price display; wallet-insufficient blocks
`AddToCartRequested` for subscription frequencies but not for one-time; add success clears
in-flight and surfaces a success result; add failure surfaces the backend's message.

**Widget:**
```
Scenario: Non-subscription-eligible product skips the frequency selector
Given: ProductConfigScreen pumped with a product where subscriptionEligible == false
Steps:
  1. Screen renders
Outcome: Key('frequency-daily') etc. are absent; CTA reads "Add to Cart"; no calendar visible

Scenario: Selecting a subscription frequency reveals the calendar and relabels the CTA
Given: ProductConfigScreen pumped with a subscription-eligible, in-stock product
Steps:
  1. Tap Key('frequency-daily')
Outcome: Key('start-date-calendar') becomes visible; primary CTA text is "Subscribe Now"

Scenario: Quantity stepper respects the max and shows a scarcity caption
Given: product.availableQuantity == 3
Steps:
  1. Tap Key('quantity-stepper-increase') three times (starting from 1)
Outcome: value shows 3; Key('quantity-stepper-increase') is disabled; a "Only 3 left"-style
  caption is visible

Scenario: Subscribe Now is disabled below the ₹500 wallet threshold
Given: a subscription-eligible product, wallet balance stubbed at ₹300, Daily selected
Steps:
  1. Frequency is Daily
Outcome: primary CTA is disabled; the ₹500-minimum inline message is visible

Scenario: Confirming a one-time add succeeds and returns to the catalog
Given: One Time selected, quantity 2, a FakeCartRepository that succeeds
Steps:
  1. Tap the primary CTA
Outcome: a "Added to cart" SnackBar appears; the screen pops
```

**Acceptance check:** `flutter test test/features/cart/` — all pass; `flutter analyze` clean;
manual walkthrough on the emulator against fakes (real backend not required to verify this
screen's own behavior, per §6's fake-first approach) covering every scenario above.

## 11. Risks and Trade-offs

- **Risk:** MA-96/MA-101 not yet implemented — this screen can be fully built and tested against
  fakes, but end-to-end verification (real price, real persisted cart) waits on both. Accepted
  trade-off, consistent with how MA-22 shipped ahead of/alongside MA-94/95.
- **Risk:** the Catalog Service contract addition (§7) is a dependency this spec doesn't control
  the timeline of — if it slips, this screen's quantity stepper falls back to the fixed 20-unit
  cap indefinitely rather than blocking the rest of the screen. Accepted as a documented, bounded
  degradation, not a launch blocker.
- **Trade-off:** re-fetching product state on screen-open (§9) instead of trusting the catalog
  card's data costs one extra round-trip but avoids confirming against stale stock — chosen
  deliberately over the cheaper-but-riskier alternative.
