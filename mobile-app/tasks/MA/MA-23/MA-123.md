## 2. Problem Statement

MA-120 shipped the product-configuration/add-to-cart screen but explicitly deferred a cart list/review
screen — named in MA-23's own ticket text ("view running subtotal, applicable taxes and delivery charge
preview... empty-cart and re-order-from-history shortcuts") but out of scope for that pass since no mockup
existed for it. Today, after adding an item, the customer sees a "Added to cart" SnackBar and is returned
to wherever they came from (Home or Catalog) — there is no way to see what's actually in the cart, change
a quantity, remove an item, or see the real payable total before checkout. The Home screen already carries
a non-functional cart icon (`Key('cart-fab')`, `onPressed: null`) waiting for exactly this. Without this
screen, MA-24 (Payment) has no real cart state to check out from.

## 3. Scope

**In scope:**
- A new `/cart` screen listing every line item currently in the customer's cart (product name/image/price
  joined from Catalog Service, quantity, frequency, start date where applicable).
- Quantity edit and per-item removal, persisted to Cart Service (already built, MA-96/MA-121).
- The live, aggregate subtotal/tax/delivery-fee/discount/net-payable breakdown, as already computed
  server-side by `GET /cart`'s embedded quote (Cart Service calls Pricing & Offer Service with the full
  item list — no client-side price math).
- Empty-cart state.
- Wiring the Home screen's existing cart FAB (`home_screen.dart:167-173`) to navigate here.
- `CartRepository` gains `getCart()`, `updateItem(...)`, `removeItem(...)` (interface + `DioCartRepository`
  impl + fake), alongside the existing `addItem(...)`.

**Out of scope:**
- Re-order-from-history — named in MA-23's ticket text, but no order-history concept exists anywhere in
  the app yet (MA-97 Order Service/screen not shipped). Flagged as a further follow-up, not silently
  dropped.
- Offers/coupon *application* UX (applying a promo code) — this screen only *displays* whatever
  `appliedOfferId`/`discountAmount` the quote already carries; there is no "enter a coupon code" affordance
  anywhere in Pricing & Offer Service's current contract (MA-101/MA-122 explicitly scoped out Offers — see
  that spec's own "Scope" section).
- Checkout/payment (MA-24) — this screen's primary CTA hands off to that flow once it exists; until then it
  is present but disabled (see FR-7).
- Cart Service backend changes — none needed. `GET /cart`, `PUT /cart`, `DELETE /cart/items/{id}` already
  exist and already return everything this screen needs (verified directly against
  `services/cart/src/handlers/dto.py` and `get_cart_handler.py`).
- Subscription lifecycle management (pause/resume/skip) — MA-25, unrelated to viewing/editing a cart.

## 4. Functional Requirements

### Screen structure

```
AppBar-equivalent: back arrow (left) · "Your Cart" title
Body:
  Empty state (no line items): illustration/icon + "Your cart is empty" + a "Browse Products" CTA
    routing to /catalog
  Non-empty state: scrollable list of cart line item cards, each showing:
    - product image + name (from Catalog Service GET /products/{id})
    - frequency + start date (subscription items only) or "One Time"
    - quantity stepper (-/+, same interaction pattern as MA-120's FR-4)
    - line-level unit price (product.price × quantity — display only; the payable total is the
      cart-level quote, never summed client-side from per-line prices, since tax/delivery/discount
      are computed once for the whole cart)
    - remove button (trash icon)
  Sticky bottom summary bar: Subtotal / Tax / Delivery Fee / Discount (if any) / Net Payable rows,
    sourced verbatim from GET /cart's quote — plus a primary CTA "Proceed to Checkout"
```

### FR-1: Navigation to the cart screen

- New `GoRoute(path: '/cart', builder: (context, state) => const CartScreen())` in `app_router.dart`,
  consistent with the existing flat-path convention (`/catalog`, `/home`).
- Home screen's `FloatingActionButton` (`Key('cart-fab')`, `home_screen.dart:167-173`) gains
  `onPressed: () => context.push('/cart')`, replacing its current `onPressed: null` — this is the only
  wiring change to `home_screen.dart` this spec makes.
- Reached via `push` (not `go`), so the back arrow simply returns to Home.

### FR-2: Loading the cart

- On screen open, dispatch a `CartStarted` event that calls `CartRepository.getCart()`
  (`GET {AppConfig.cartBaseUrl}/cart`).
- Response carries `items` (each with `id`, `productId`, `quantity`, `frequency`, `startDate`,
  `addedAt` — no product name/price), `cartVersion` (int, used for optimistic-concurrency on writes —
  see FR-4), and `quote` (nullable; `null` exactly when `items` is empty).
- For each line item, resolve display data via `CatalogRepository.getProduct(productId)` (already exists,
  added in MA-120 §6) — issued as parallel requests, not sequential, to keep load time flat regardless of
  cart size.
- Shows a loading skeleton (list-shaped placeholder rows, matching MA-120 FR-5's skeleton treatment) while
  both calls are in flight; a `getCart` failure shows a full-screen error with a "Retry" button (this is
  the screen's primary data source — unlike MA-120's quote, there is no partially-usable state without it);
  a per-item `getProduct` failure degrades that single row to a "Product unavailable" placeholder rather
  than failing the whole screen.

### FR-3: Empty cart

- `items.isEmpty` (equivalently, `quote == null`) renders the empty state (FR structure above) instead of
  the list/summary bar.
- `Key('cart-empty-state')` on the empty-state container; `Key('cart-browse-products-cta')` on its button.

### FR-4: Quantity edit

- `-`/`+` stepper per line item, same min-1 / disabled-at-1 behavior as MA-120 FR-4. No stock-max
  re-validation here — Cart Service's own `PUT /cart` is the enforcement point if a quantity now exceeds
  live stock (surfaces as an `ApiException`, handled per FR-6).
- Debounced 500ms after the last tap (longer than MA-120's 300ms quote-debounce, since this triggers a
  full authenticated write, not a read-only quote), then calls `CartRepository.updateItem(...)` →
  `PUT {AppConfig.cartBaseUrl}/cart` with the **full** current item list (Cart Service's `PUT /cart` is a
  replace, not a per-item patch — confirmed against `dto.py`'s `ReplaceCartRequestDto`) and the last-known
  `cartVersion` as `ifVersion`.
- On success, the response's fresh `cartVersion` and item list replace local state, then the screen
  re-fetches `GET /cart` to get the updated quote (matching Cart Service's own documented split — `PUT`
  doesn't return pricing, `GET` does, per `dto.py`'s `serialize_cart` comment).
- `Key('cart-item-quantity-decrease-{lineItemId}')` / `Key('cart-item-quantity-increase-{lineItemId}')` /
  `Key('cart-item-quantity-value-{lineItemId}')`, `Semantics(label: 'Decrease quantity')` /
  `Semantics(label: 'Increase quantity')` — same accessibility requirement as MA-120 FR-4.

### FR-5: Remove item

- Trash-icon button per line item, `Key('cart-item-remove-{lineItemId}')`,
  `Semantics(label: 'Remove item')`.
- Tapping shows a confirmation dialog ("Remove this item from your cart?" / Cancel / Remove) — a
  destructive action gets a confirm step, matching this codebase's general caution around irreversible
  actions elsewhere (no existing precedent to follow literally, since this is the first destructive-write
  UI in the app, but consistent with the Human Interaction guardrails this spec itself was produced under).
- Confirming calls `CartRepository.removeItem(id: lineItemId)` →
  `DELETE {AppConfig.cartBaseUrl}/cart/items/{id}`. On success, re-fetch `GET /cart` (same reasoning as
  FR-4 — a fresh quote is needed after any item-set change).
- Removing the last remaining item transitions the screen straight to the empty state (FR-3).

### FR-6: Write failures (quantity edit / remove)

- A `409` (stale `cartVersion` — another device or session changed the cart concurrently) triggers a
  silent `GET /cart` refetch and re-applies the user's last action against the fresh state, rather than
  surfacing a raw conflict error — the customer never needs to know optimistic concurrency exists.
- Any other `ApiException` shows an inline SnackBar with `exception.message` verbatim (matching MA-120
  FR-8's failure-surfacing pattern) and reverts the optimistic UI change (the stepper value / the removed
  row) back to its last known-good state.

### FR-7: Price summary and checkout CTA

- Bottom summary bar renders `quote.basePrice` (as "Subtotal"), `quote.taxAmount` (as "Tax
  ({quote.taxRate}%)"), `quote.deliveryFee`, `quote.discountAmount` (row omitted entirely when `null`,
  not shown as "₹0"), and `quote.netPayable` (as "Total", visually emphasized).
- `quote.monthlyEstimate`, when non-null (cart contains at least one subscription-frequency item per
  MA-101's contract), is shown as a secondary line ("≈ ₹{amount}/month") below the one-time total — same
  framing MA-120 FR-5 already uses on the configuration screen.
- Primary CTA "Proceed to Checkout" (`Key('cart-checkout-cta')`) is **present but disabled** with a
  tooltip/caption "Checkout coming soon" — MA-24 (Payment) doesn't exist yet, so this is a placeholder
  matching this codebase's established "present per mockup, not yet wired" treatment (Home screen's
  share/favourite icons, MA-120's own share/favourite icons) rather than omitting the element the mockup
  would eventually need.

### FR-8: Re-entering the screen after further edits elsewhere

- The cart is not cached across navigations — every `/cart` visit re-fetches `GET /cart` fresh (FR-2).
  Adding another item from the Product Config screen and returning to `/cart` always reflects the latest
  server state; no client-side cart cache to invalidate.

## 5. Non-Functional Requirements

- **Performance:** parallel per-item `getProduct` calls (FR-2) keep load time roughly constant regardless
  of cart size; no pagination in this pass (a customer's cart is not expected to exceed a handful of
  distinct products — matches Pricing & Offer Service's own single-quote-call design for the whole cart).
- **Reliability:** a Cart Service or Catalog Service outage degrades to a clear, retryable error state
  (FR-2) — never a silent failure or an uncaught exception crashing the screen.
- **Accessibility:** touch targets ≥ 48dp for stepper and remove buttons; `Semantics` labels on every
  icon-only control (FR-4, FR-5).
- **Testability:** every interactive element carries a `Key` (enumerated per-FR above), following this
  codebase's established selector convention.
- **Consistency:** never compute subtotal/tax/delivery/total client-side from per-line prices — always the
  server's `quote` object, verbatim (same principle MA-120 FR-5 already established for the single-product
  estimate).

## 6. Technical Design

- **State management:** a new `CartBloc` (events: `CartStarted`, `QuantityChanged`, `ItemRemoved`,
  `RemoveConfirmed`; states carry the resolved line items — each paired with its `Product` once resolved —
  `cartVersion`, current `quote`, and per-action in-flight/error status), mirroring `ProductConfigBloc`'s
  shape (a single bloc owning a multi-step, single-screen flow with several independent async operations).
- **Repositories:**
  - `CartRepository` (`lib/features/cart/data/cart_repository.dart`) gains three methods alongside the
    existing `addItem`:
    - `Future<CartView> getCart()` → `GET /cart`
    - `Future<CartView> updateItem({required List<CartLineItem> items, required int ifVersion})` →
      `PUT /cart`
    - `Future<void> removeItem({required String id})` → `DELETE /cart/items/{id}`
    - A new `CartView`/`CartLineItem`/`Quote` model set under `lib/features/cart/models/`, matching Cart
      Service's `serialize_cart_view`/`serialize_line_item`/`serialize_quote` field names exactly
      (`items`, `cartVersion`, `quote`; `id`, `productId`, `quantity`, `frequency`, `startDate`, `addedAt`;
      `basePrice`, `taxAmount`, `taxRate`, `deliveryFee`, `netPayable`, `monthlyEstimate`,
      `discountAmount`, `appliedOfferId`) — the existing `Quote` model in
      `lib/features/cart/models/quote.dart` (from MA-120, used for the single-product estimate) is reused
      here rather than duplicated, since the field shape is identical.
    - `FakeCartRepository` (`test/fakes/`) gains matching fakes, following this codebase's fake-first
      pattern.
  - `CatalogRepository.getProduct(productId)` (existing, from MA-120 §6) is reused as-is — no changes.
- **Routing:** `GoRoute(path: '/cart', builder: (context, state) => const CartScreen())` in
  `app_router.dart`, alongside the existing `/catalog` and `/product/:productId` entries. Unlike
  `/product/:productId`, no `extra:` payload — the screen always fetches its own state fresh (FR-2, FR-8).
- **Screen:** `lib/features/cart/presentation/cart_screen.dart`, `CartScreen`
  (`StatefulWidget` wrapping `BlocProvider<CartBloc>` + `BlocConsumer`), following the same `Card`-based
  layout conventions as `product_config_screen.dart`.
- **Home screen change:** `home_screen.dart:171`, `onPressed: null` → `onPressed: () => context.push('/cart')`.
  One-line change; no other modification to that file.

## 7. Data Considerations

- No new backend fields or endpoints. This spec consumes Cart Service's (MA-96/MA-121) existing contract
  verbatim — confirmed directly against `services/cart/src/handlers/dto.py`
  (`serialize_cart_view`/`serialize_line_item`/`serialize_quote`/`serialize_cart`) and
  `services/cart/src/handlers/get_cart_handler.py` (empty-cart → `200` with `items: []`, `cartVersion: 0`,
  `quote: null` — never a `404`, so FR-3's empty state is driven by an empty list, not an error response).
- `PUT /cart`'s request DTO (`ReplaceCartRequestDto`) requires the **full** item list plus `ifVersion` —
  confirmed there is no per-item `PATCH` endpoint, which is why FR-4 sends the whole current list on every
  quantity change, not a single-field patch.
- Mobile-side `CartLineItem`/`CartView`/`Quote` models are additive — no existing model changes beyond
  reusing MA-120's `Quote` model.

## 8. Integration Considerations

- **Cart Service:** `GET /cart` already internally calls Pricing & Offer Service with the full item list
  and the user's delivery-address state (via User Service) to build the aggregate `quote` — confirmed in
  `services/cart/src/domain/cart_service.py`'s `get_cart` method. This screen never calls Pricing directly;
  it only ever reads Cart Service's `GET /cart` response.
- **Catalog Service:** called once per distinct `productId` in the cart via the existing
  `GET /products/{id}` (no batch/bulk endpoint exists — acceptable per §5's NFR given expected cart sizes).
- **Cart Service write failures:** surfaced via `ApiException` (FR-6) — no local queuing or offline retry,
  matching this app's existing online-only assumption.
- **No new integration** with Payment, Wallet, or Inventory services — none of FR-1–FR-8 touches them.

## 9. Edge Cases and Failure Modes

- Cart becomes empty as the direct result of removing the last item (FR-5) — handled explicitly (empty
  state), not just as a side effect of the next `GET /cart` load.
- Concurrent edit from another device/session mid-visit (stale `cartVersion`) — handled via the `409`
  silent-refetch-and-reapply path (FR-6), not surfaced as a raw error.
- A line item's product has since been removed from the catalog or gone out of stock — `getProduct` for
  that `productId` either 404s or returns a changed `stockState`; this spec degrades that row to a
  "Product unavailable" placeholder (FR-2) with its remove button still functional, but does not attempt
  to auto-remove it or block the rest of the screen.
- Rapid repeated quantity taps — the 500ms debounce (FR-4) collapses them into a single write, same pattern
  as MA-120's 300ms quote debounce.
- Double-tapping "Remove" before the confirmation dialog dismisses — the dialog itself is modal, so this is
  prevented by the platform, not additional app logic.

## 10. Testing Strategy

**Unit (bloc):** `CartBloc` — `CartStarted` resolves items + products correctly and populates state;
`QuantityChanged` debounces and calls `updateItem` with the full item list and correct `ifVersion`;
`ItemRemoved`/`RemoveConfirmed` calls `removeItem` and triggers a refetch; a `409` on either write triggers
silent refetch-and-reapply rather than surfacing an error; any other write failure reverts optimistic state
and surfaces `ApiException.message`.

**Widget:**
```
Scenario: Empty cart shows the empty state
Given: CartScreen pumped with a FakeCartRepository returning items: []
Steps:
  1. Screen renders
Outcome: Key('cart-empty-state') is visible; the line-item list and summary bar are absent

Scenario: Non-empty cart shows the aggregate quote breakdown
Given: FakeCartRepository returns two line items and a quote with a non-null discountAmount
Steps:
  1. Screen renders
Outcome: Subtotal/Tax/Delivery/Discount/Total rows all show the quote's exact values, not a
  client-computed sum

Scenario: Increasing quantity calls updateItem with the full item list
Given: a cart with one line item, quantity 1
Steps:
  1. Tap Key('cart-item-quantity-increase-{id}')
  2. Wait past the 500ms debounce
Outcome: FakeCartRepository.updateItem was called once, with quantity 2 and the correct ifVersion

Scenario: Removing the last item returns to the empty state
Given: a cart with exactly one line item
Steps:
  1. Tap Key('cart-item-remove-{id}'), confirm the dialog
Outcome: Key('cart-empty-state') becomes visible

Scenario: A stale cartVersion silently refetches rather than showing an error
Given: FakeCartRepository.updateItem throws a 409 ApiException on first call, succeeds on retry
Steps:
  1. Trigger a quantity change
Outcome: no error SnackBar shown; the screen reflects the refetched state
```

**Acceptance check:** `flutter test test/features/cart/` — all pass; `flutter analyze` clean; manual
walkthrough against the real local Cart + Catalog services (both already running per
`services/local-dev/README.md`) covering every scenario above, since — unlike MA-120 — this spec's
dependency (Cart Service) is already fully implemented, so fake-only verification is not sufficient before
sign-off.

## 11. Risks and Trade-offs

- **Trade-off:** sending the full item list on every quantity change (FR-4), rather than a per-item patch,
  costs a slightly larger request payload but avoids requiring a new Cart Service endpoint — accepted since
  `PUT /cart` already exists and expected cart sizes are small.
- **Risk:** N parallel `getProduct` calls (FR-2) don't scale to a large cart — accepted per §5's NFR;
  a batch product-lookup endpoint would be a Catalog Service contract addition out of this spec's control,
  revisit only if real cart sizes prove this wrong.
- **Trade-off:** the checkout CTA is present-but-disabled (FR-7) rather than omitted, so the screen doesn't
  need a follow-up layout change once MA-24 ships — same reasoning already established for MA-120's
  share/favourite icons.
