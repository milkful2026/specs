## 2. Problem Statement

Registered/logged-in customers (MA-1, MA-21 — already shipped) land on a Home screen that is
currently an empty, role-aware placeholder. There is no way to browse what Milkful sells. This
spec covers the screen that replaces that placeholder: a category-grouped, real-time-stock-aware
product catalog, matching the attached wireframe (`FreshFarm` reference mockup — brand name in
the mockup differs from this app's actual branding; layout/structure is what's being matched, not
the brand string). Without this screen, no customer can proceed from "logged in" to "has something
to add to cart" (MA-23).

## 3. Scope

**In scope:**
- Replace `HomeScreen`'s current placeholder body with the catalog screen described here, behind
  the existing `/home` route (no new route needed).
- Category rail (left-side, per mockup), product cards (image, category tag, name, unit, price,
  stock state, subscription-eligible marker, Add button), search, filter, sort.
- Loading / empty / error states for the catalog fetch.
- A new `CatalogRepository` (interface + Dio-backed impl + hand-written fake), matching this
  codebase's existing `RegistrationRepository`/`AuthRepository`/`PlacesRepository` pattern.

**Out of scope:**
- Add to Cart behavior itself (MA-23) — the "Add" button exists visually and is tappable, but this
  spec only requires it to be present and enabled/disabled correctly; the actual cart-mutation
  logic belongs to MA-23's own spec.
- Product detail page — decided out of scope during Step 1; the catalog card is the entire
  interaction surface for this story.
- Payment, subscription creation/management (MA-24, MA-25).
- Catalog Service's own backend implementation (MA-94) and Inventory Service's (MA-95) — this spec
  defines the mobile app's consumption of Catalog's API, not Catalog/Inventory's own behavior.
- B2B-specific pricing display — MA-21's own spec already limited B2B to "indicator only, no
  B2B-specific screens"; this spec follows the same limit unless product overrides it later.

## 4. Functional Requirements

### Screen structure (matches attached mockup)

```
AppBar-equivalent: location/brand mark (left) · search icon · notification bell (right)
  — this app already has role-aware Home chrome (logout action); search/notification icons
    are additive to what's there today, not a replacement.
Left rail: vertical scrollable list of category circles (icon + label), one highlighted/selected
Main content: "{Category Name}" heading + "{n} items" count, then a scrollable list/grid of
  product cards
Bottom nav: existing app shell — this spec does not introduce a new bottom nav; Milkful's current
  IA is a single Home tab post-login (Schedule/Wallet/Profile shown in the mockup are NOT built
  yet anywhere in this app and are explicitly out of scope for this story)
```

### FR-1: Category rail

- Fetches categories from `GET /categories` on screen load.
- Renders each as a tappable circular icon + label (Material icon per category — no custom art
  asset pipeline assumed, matching how `welcome_screen.dart`'s logo badge already uses a plain
  `Icon` rather than an image asset).
- One category selected at a time; default selection is the first category returned.
- Selecting a category re-fetches/re-filters the product list for that category.
- `Key('category-rail')` on the rail's scrollable container; each item `Key('category-{id}')`.

### FR-2: Product list

- Fetches products for the selected category from `GET /products?categoryId=`.
- Each product card shows: image (network `Image.network` with a placeholder/error builder —
  no CDN-specific handling needed client-side, Catalog's API is assumed to return a directly
  usable URL), a small category/attribute tag overlay (e.g. "ORGANIC" — sourced from a
  `tag`/`badge` field on the product; renders nothing if absent, not a hardcoded value), name,
  unit (e.g. "1L Bottle"), price (₹ prefix, matching existing app convention — no other currency
  handled), and an "Add" button.
- `Key('product-card-{id}')` per card.

### FR-3: Stock state

- In-stock (default): "Add" button enabled, no extra state text.
- Out of stock: "Add" button disabled/replaced with a non-interactive "Out of Stock" label
  (`Key('out-of-stock-{id}')`); product card visually de-emphasized (reduced opacity), matching
  common e-commerce convention since the mockup itself doesn't show this state.
- Available from `<date>`: replaces the "Add" button with "Available from {date}" text
  (`Key('available-from-{id}')`), non-interactive. Date formatted via `intl`'s
  `DateFormat.yMMMd()` (already implicitly available via Flutter's `intl` transitive dependency
  through `google_maps_flutter`/other packages — confirm at implementation time whether an
  explicit `intl` dependency add is needed).

### FR-4: Subscription-eligible marker

- A small badge/icon (e.g. a repeat/subscription `Icon(Icons.autorenew)` in the corner of the
  card, `Key('subscription-badge-{id}')`) rendered only when the product's `subscriptionEligible`
  field is true. No subscription *action* — MA-25 owns actually starting one.

### FR-5: Search

- Tapping the search icon reveals a search text field (replacing or overlaying the category
  rail's header area) — `Key('catalog-search-field')`.
- Debounced (300ms) query against `GET /search?q=&filters=`.
- Empty query reverts to the category-filtered view (FR-2).
- No results: "No products found for '{query}'" message, `Key('search-empty-state')`.

### FR-6: Filters

- Filter affordance (icon/button) opens a bottom sheet with: category (multi-select, defaults to
  current rail selection), price (range slider or min/max fields), veg/organic (toggle/checkbox).
- "Apply" re-runs `GET /search` (or `/products`) with the selected filters as query parameters.
- Active filter count shown as a badge on the filter affordance (e.g. "Filters (2)"), matching the
  SDD skill's own guidance on observable, verifiable UI ("Filter button label updates to
  'Filter (1)'").

### FR-7: Sort

- Sort affordance (icon/button) opens a menu: Price: Low to High, Price: High to Low, Popularity
  (if the API supports a popularity/relevance field — otherwise omit at implementation time and
  flag as a spec-vs-API mismatch), Newest.
- Selected sort persists across category switches within the same screen session (not persisted
  across app restarts).

### FR-8: Loading / empty / error states

- **Loading:** skeleton placeholder cards (3, matching the mockup's typical count) or a centered
  `CircularProgressIndicator` on first load; a smaller inline indicator on category-switch re-fetch.
- **Empty:** a category with zero products shows "No products in this category yet" —
  `Key('category-empty-state')`.
- **Error:** network/API failure shows an inline error with a **Retry** button
  (`Key('catalog-retry-button')`), matching the existing `AddressScreen`'s
  `serviceabilityCheckFailed` retry pattern.

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| Performance | Initial category+product fetch renders within 2s on 4G; category switch re-fetch within 1s (assumes Catalog Service's own read-path latency budget, defined in MA-94's spec, is met) |
| Accessibility | All interactive elements (category items, product cards' Add button, search/filter/sort affordances) have semantic labels; touch targets ≥ 48dp; WCAG AA contrast — consistent with this app's existing `Semantics` usage throughout onboarding/auth screens |
| Offline / connectivity | No cached catalog for offline browsing in this pass (out of scope) — a connectivity failure surfaces the Error state (FR-8), not a silent blank screen |
| Security | Standard Cognito JWT via the existing shared `ApiClient` — no new auth pattern; no PII in this screen beyond what's already in the authenticated session |

## 6. Technical Design

### Architecture

- **State:** `CatalogBloc` (new, `flutter_bloc`), following `RegistrationBloc`'s event/state
  shape conventions.
- **Repository:** `CatalogRepository` (abstract) + `DioCatalogRepository` (impl, wraps the shared
  `ApiClient` — Catalog Service uses this app's own backend envelope, unlike `PlacesRepository`
  which had to bypass `ApiClient` for Google's external API).
- **Models:** `Product`, `Category` — `Equatable` + `fromJson`, mirroring `AddressDraft`'s existing
  pattern in `lib/features/onboarding/models/`.
- **DI:** `CatalogRepository` provided via `RepositoryProvider` in `main.dart`, alongside
  `PlacesRepository`; `CatalogBloc` provided via `BlocProvider`, scoped to the Home/Catalog screen
  (not app-global, since it's not needed before login).
- **Routing:** No new route — this replaces `HomeScreen`'s body content at the existing `/home`
  route.

### UI component map

| Component | Source | Pattern | Notes |
|-----------|--------|---------|-------|
| Category rail | Custom `ListView` + circular items | Vertical scroll | `Key('category-rail')` |
| Product card | Custom `Card`/`Container` | Matches mockup's rounded-card style, reuses `AppTheme`'s existing rounded/pill conventions | `Key('product-card-{id}')` |
| Add button | Material `FilledButton` (pill, via existing `AppTheme`) | Full pill, green | Label: "Add" |
| Search field | Material `TextField` | Debounced `onChanged` | `Key('catalog-search-field')` |
| Filter sheet | `showModalBottomSheet` | Category multi-select, price range, veg/organic toggle | |
| Sort menu | `PopupMenuButton` or bottom sheet | 3–4 options | |

### Responsive behavior (mobile only)

| Breakpoint | Behavior |
|------------|----------|
| Phone (< 600dp) | Single-column product list, as in the mockup |
| Tablet (≥ 600dp) | 2-column product grid; category rail unchanged |

## 7. Data Considerations

```dart
class Category extends Equatable {
  final String id;
  final String name;
  final String? iconName; // maps to a Material Icon at render time; no custom asset pipeline
}

class Product extends Equatable {
  final String id;
  final String categoryId;
  final String name;
  final String description;
  final String unit;          // e.g. "1L Bottle"
  final double price;
  final String? imageUrl;
  final String? tag;          // e.g. "ORGANIC" — optional, renders nothing if null
  final bool subscriptionEligible;
  final StockState stockState; // enum: inStock | outOfStock | availableFrom
  final DateTime? availableFrom; // set only when stockState == availableFrom
}
```

No local persistence for catalog data in this pass — always fetched fresh per screen visit/category
switch (see Risk #2 for the staleness trade-off this implies).

## 8. Integration Considerations

| API | When | Owning spec |
|-----|------|-------------|
| `GET /categories` | Screen load | MA-94 (MA-116) |
| `GET /products?categoryId=` | Screen load, category switch | MA-94 (MA-116) |
| `GET /search?q=&filters=` | Search, filter, sort | MA-94 (MA-117) |

New `AppConfig.catalogBaseUrl` — `String.fromEnvironment('CATALOG_BASE_URL', defaultValue: 'http://localhost:8003')`,
following the exact pattern of `identityAuthBaseUrl`/`userBaseUrl`/`inventoryBaseUrl`/
`inventoryBaseUrl` (port chosen as the next unused one after the existing `:8000`–`:8002` local
services; final port TBD against MA-94's own local-dev setup).

Errors mapped via the existing `ApiException`/`ApiClient` pattern; a Catalog Service outage surfaces
FR-8's Error state, not a crash.

## 9. Edge Cases and Failure Modes

| Case | Behavior |
|------|----------|
| Catalog Service unreachable | Error state (FR-8) with Retry |
| Category has zero products | Empty state (FR-8) |
| Product goes out-of-stock while screen is open (no live push in this pass) | Stale until next fetch (category switch, search, or pull-to-refresh — pull-to-refresh itself not yet specified as a gesture; flagged as open question) |
| Search query matches nothing | FR-5's empty-search state |
| Malformed/missing `imageUrl` | `Image.network`'s `errorBuilder` shows a placeholder icon, not a broken-image glyph |
| Filters applied that return zero results | Same empty state as FR-8's category-empty, reworded to reference active filters |

## 10. Testing Strategy

### Widget tests

- Category rail renders returned categories; tapping one re-fetches/filters the product list.
- Product card renders all required fields (name, unit, price, image placeholder) from a fake
  `CatalogRepository` response.
- Stock-state variants (in-stock / out-of-stock / available-from) render the correct
  button/label/key per FR-3.
- Subscription badge renders only when `subscriptionEligible: true`.
- Search: debounce behavior, empty-query revert, no-results state.
- Filter/sort: applying a filter re-issues the expected repository call with the right parameters.
- Loading/empty/error states each render their expected content and, for error, that Retry
  re-triggers the fetch.

### Integration test scenario: Browse and filter

**Given:** Authenticated session (post-MA-21 login), Catalog Service reachable with seeded
products across ≥2 categories.
**Steps:**
1. Land on Home (`/home`) — assert category rail visible (`find.byKey(Key('category-rail'))`).
2. Assert first category's products render (`find.byKey(Key('product-card-{id}'))` for a known
   seeded product).
3. Tap a second category (`find.byKey(Key('category-{id}'))`) — assert the product list changes.
4. Tap search icon, enter a known product name — assert exactly that product's card is shown.
5. Clear search — assert the category-filtered view returns.
6. Open filters, select veg/organic, apply — assert the filter badge shows "Filters (1)" and the
   list updates.

**Outcome:** Customer can browse, search, and filter to a specific product.

### Negative scenarios

- Catalog Service down at screen load → Error state + Retry, not a crash or blank screen.
- Search for a nonsense string → empty-search state, not an error.

## 11. Risks and Trade-offs

1. **Hard dependency on MA-94 (Catalog Service) actually existing** — this spec can be fully
   written and reviewed, but cannot be implemented/tested against a real backend until MA-94's own
   implementation lands. Mitigated at the mobile layer the same way `PlacesRepository` was tested
   (hand-written fake + repository-level unit tests), so mobile-side work isn't fully blocked, but
   true end-to-end verification is.
2. **No live stock updates while the screen is open** — accepted trade-off (see Edge Cases); a
   real-time push mechanism (WebSocket/polling) was not requested by the ticket and would be new
   scope.
3. **Mockup shows only the base state** — search, filter, sort, out-of-stock, and
   subscription-badge visuals were designed without a reference image; a design review before/
   during implementation is recommended.
