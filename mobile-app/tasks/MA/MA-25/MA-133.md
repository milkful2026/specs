## 2. Problem Statement

The bottom-nav **Schedule** tab (`home_screen.dart`'s `_HomeBottomNav`, index 1) is a
disabled stub — there is no screen to see or manage a subscription today. MA-23/MA-120
already let a customer *pick* a subscription frequency on `ProductConfigScreen`, but nothing
happens with that choice beyond adding a cart line item; there is no standing subscription,
nowhere to see it, and no way to pause/resume/stop/skip/edit it.

This spec delivers the **Schedule tab's real destination** exactly as drawn in the MA-25
ticket mock (`image-20260807-175447.png`): a "My Subscriptions" list, a Vacation Mode
toggle, and a CTA to subscribe to a new product — plus the per-subscription
pause(date-range)/resume/stop/skip-a-day/edit controls the mock doesn't depict but the
ticket text requires, built in this app's existing visual language.

Expected outcome: a customer can see every active subscription, pause all deliveries in one
tap (or a specific date range), and fully manage an individual subscription without leaving
the app.

## 3. Scope

### In scope

- Wiring the bottom-nav **Schedule** tab to a real screen (`context.go('/subscriptions')`,
  top-level destination — same pattern MA-125 used for Wallet).
- **My Subscriptions list** (mock): header "My Subscriptions" / "Manage your fresh recurring
  essentials.", a global **Vacation Mode** toggle ("Pause all deliveries"), an "Active
  Subscriptions" section with a count badge, one card per subscription (product name/image,
  status badge, quantity, frequency label, next-delivery date), and a promo CTA "Subscribe to
  New Product" routing to `/catalog`.
- **Per-subscription detail** (no mock — extrapolated): tapping a card opens a detail sheet/
  screen with Pause (date range picker), Resume, Stop, Skip next delivery, and Edit
  quantity/schedule — all not shown in the mock.
- Changing `ProductConfigScreen`'s confirm action (MA-120/MA-23, existing) for a
  subscription-frequency selection to call the new **Subscription Service** directly
  (MA-131 FR-1) instead of `CartRepository.addItem` — per MA-131 §6's parallel-hand-off
  design. A one-time-frequency confirm is **unchanged** (still calls `CartRepository.addItem`
  exactly as today).
- `SubscriptionRepository` (abstract + `DioSubscriptionRepository` + `FakeSubscriptionRepository`),
  `SubscriptionBloc`, models (`SubscriptionView`, `Schedule`, `SubscriptionStatus`).
- All UI states, `Key(...)` selectors, and accessibility per the `mobile-app` SDD conventions.

### Out of scope

- Order status/tracking detail beyond a minimal "delivered / payment failed" indicator on
  the subscription card's next-delivery line — full order tracking is MA-35/MA-36.
- Weekly/custom-day schedule picker's exact calendar widget design — a reasonable
  checkbox-per-weekday control is assumed (Mon–Sun toggles); MA-31's own "NR: Calendar View"
  is the larger, separate ordering-calendar concept and is not reused or blocked on here.
- Editing a subscription's product — matches MA-131's own scope cut (stop + recreate only).
- Low-balance push/SMS notification — no notification infra exists (MA-131 §3); this screen
  surfaces a low-balance state only if/when it next fetches subscription/order data showing a
  `PAYMENT_FAILED` order, not via a proactive alert.

### FR-1: Navigation & tab wiring

- New `GoRoute(path: '/subscriptions', builder: (_, __) => const SubscriptionsScreen())`,
  consistent with `/wallet`'s top-level-destination convention (MA-125 FR-1).
- The bottom-nav **Schedule** item (`_HomeBottomNav`, currently disabled) navigates via
  `context.go('/subscriptions')`. `/wallet`'s own bottom nav (`_WalletBottomNav`,
  `wallet_screen.dart`) gets the same Schedule wiring added for consistency (it currently
  only wires Home).
- No feature flag — unlike MA-125's `WALLET_ENABLED`, this ships live once merged (no
  external gateway dependency blocking it the way Razorpay credentials blocked Wallet).

### FR-2: Loading subscriptions

- On screen open, dispatch `SubscriptionsStarted` → `SubscriptionRepository.list()` →
  `GET /subscriptions/me`.
- Loading: skeleton list (`Key('subscriptions-loading-skeleton')`, mirrors
  `catalog_screen.dart`'s `_LoadingSkeleton` treatment).
- Failure: inline error + Retry (`Key('subscriptions-load-error')` /
  `Key('subscriptions-load-retry')`).
- Empty (no subscriptions yet): the "Active Subscriptions" section is replaced by an empty
  state (`Key('subscriptions-empty-state')`, "No active subscriptions yet") — the Vacation
  Mode row and promo CTA still render (vacation mode is meaningless with zero subscriptions,
  but hiding it entirely adds a conditional the mock gives no basis for; it simply has no
  effect until a subscription exists).

### FR-3: Vacation Mode (global pause)

- Toggle on: dispatches `VacationModeToggled(true)` →
  `SubscriptionRepository.pauseAll()` → one `POST /subscriptions/{id}/pause` per currently
  `ACTIVE` subscription (no `from`/`until` — open-ended, per MA-131 FR-2), executed
  concurrently. Toggle reflects the *aggregate* state: on if every subscription is currently
  paused-with-no-end-date, off otherwise (a per-subscription pause set via the detail sheet's
  date-range picker does **not** flip this toggle on, since it's a bounded, not open-ended,
  pause — the toggle specifically models "pause everything indefinitely," matching the mock's
  own binary on/off rendering).
- Toggle off: dispatches `VacationModeToggled(false)` → one `POST /subscriptions/{id}/resume`
  for **every currently-`PAUSED` subscription with no `pauseUntil`** — i.e. exactly the set
  `vacationModeOn`'s own aggregate definition (§6: "true iff every subscription is `PAUSED`
  with no `pauseUntil`") is already computed from, not a client-side-tracked subset. An
  earlier version of this spec scoped toggle-off to only the subscriptions "tracked
  client-side for this session" as vacation-paused — that both silently no-ops after any app
  restart (a fresh session has tracked nothing, so tapping the toggle off fires zero resume
  calls, yet the toggle correctly showed ON from the server-computed state) and was never a
  real distinction to begin with: a `PAUSED` subscription with no `pauseUntil` looks identical
  server-side whether it was paused via the Vacation Mode toggle or via its own detail sheet's
  "pause indefinitely" option (FR-5) — there is no `pausedBy`/reason field to tell them apart,
  so no client-side tracking scheme can be correct across devices/sessions even in principle.
  Resuming the same aggregate set that defines "on" is therefore not just simpler but the only
  approach an app restart can't break. The trade-off this accepts — a subscription
  individually, deliberately paused open-ended via its own detail sheet gets swept up and
  resumed by an unrelated Vacation Mode toggle-off — is a real UX cost, but is the honest
  behavior given the current data model, not a smaller bug traded for a bigger one; see the
  Risks section for the server-side field that would be needed to actually distinguish the two.
- A network failure reverts the toggle to its prior visual state and shows a snackbar with
  the error message — no optimistic-success assumption.

### FR-4: Subscription card

- Shows product name, a status badge (`Active`/`Paused`/`Stopped` — visually distinct
  colors, matching this app's existing badge conventions e.g. `catalog_screen.dart`'s
  out-of-stock styling), quantity, a human-readable frequency label (`Delivers Daily` /
  `Delivers Every Other Day` / `Delivers Weekly on {Day}` / `Delivers on {Day, Day, ...}`),
  and the next-delivery date (`nextDeliveryDate` from `GET /subscriptions/me` — or "Paused"/
  "Stopped" text in place of a date when not applicable).
- Tapping a card opens `SubscriptionDetailSheet` (FR-5).

### FR-5: Subscription detail — Pause / Resume / Stop / Skip / Edit

`showModalBottomSheet` (matches MA-125's own `_TopUpAmountSheet` pattern), `Key('subscription-detail-sheet')`:

- **Pause** (`Key('subscription-pause-button')`, shown when `ACTIVE`): opens a date-range
  picker (`Key('subscription-pause-range-picker')`) — "Pause indefinitely" (no dates) or a
  specific start/end date, matching MA-131 FR-2's three pause shapes. Confirms via
  `PauseRequested(id, from, until)`.
- **Resume** (`Key('subscription-resume-button')`, shown when `PAUSED`): confirms via
  `ResumeRequested(id)` immediately (no further input needed).
- **Stop** (`Key('subscription-stop-button')`, shown unless already `STOPPED`): a confirm
  dialog ("Stop this subscription? You'll need to subscribe again to resume it.") before
  dispatching `StopRequested(id)` — irreversible, per MA-131 FR-4.
- **Skip next delivery** (`Key('subscription-skip-button')`, shown when `ACTIVE` and a
  `nextDeliveryDate` exists): a confirm dialog naming the specific date, dispatches
  `SkipRequested(id, date)`. Disabled (not hidden — `Key('subscription-skip-button')` still
  present, `onPressed: null`) with caption "Too late to skip this delivery" once the cut-off
  has passed for that date (server is authoritative — MA-131 FR-5's `409 CUTOFF_PASSED` is
  also handled defensively if the client's own cut-off guess was stale).
- **Edit** (`Key('subscription-edit-button')`): opens a form (quantity stepper + schedule
  picker reusing the same weekday-toggle control the create flow uses — see FR-6) prefilled
  with current values. Submits `EditRequested(id, quantity?, schedule?)`. If the response's
  `effectiveFrom` is later than the very next delivery, shows a one-line notice ("Changes
  apply from {date}") rather than silently accepting.

### FR-6: Creating a subscription (ProductConfigScreen change)

- **`slotId` source (new UI, not in the mock)**: `ProductConfigScreen` has no delivery-slot
  picker today, and registration's own one-time `preferredSlotId` field is no longer even sent
  to the backend (confirmed in `registration_repository.dart` — "slot preference is now
  chosen later, from Home's own calendar picker") — so without this addition there is no value
  anywhere in the app to pass for FR-1's required `slotId`. This spec adds a compact slot chip
  row (`Key('product-config-slot-{slotId}')` per chip), visible only when
  `state.frequency.isSubscription` is `true`, reusing
  `RegistrationRepository.getDeliverySlots(zoneId)` — the exact same `GET /delivery/slots`
  call and `zoneId` source (`context.read<RegistrationBloc>().state.draft.zoneId`, the
  app-wide singleton bloc `home_screen.dart`'s own `_DeliverySlotPicker` already reads from)
  as the existing Home-screen picker, not a new endpoint or a new zone-resolution path.
  Defaults to the first `available` slot returned; the customer may change it before
  confirming. `ProductConfigState` gains a `slotId: String?` field (`copyWith`-able, same
  shape as the existing `startDate` field); `canConfirm` additionally requires
  `slotId != null` when `frequency.isSubscription`, mirroring `walletGateBlocks`'s existing
  gating pattern — the Subscribe Now CTA cannot be tapped with no slot selected.
- `ProductConfigBloc._onAddToCartRequested` (existing, MA-120/MA-23): when
  `state.frequency.isSubscription` is `true`, calls
  `SubscriptionRepository.create(productId, quantity, schedule, startDate, slotId,
  idempotencyKey)` (MA-131 FR-1) **instead of** `CartRepository.addItem(...)`. A one-time
  frequency confirm is unchanged.
- `ProductConfigScreen`'s existing frequency selector (`Frequency.daily`/
  `Frequency.alternateDays`) maps directly to `Schedule(type: DAILY)` /
  `Schedule(type: ALTERNATE_DAYS)`. `Frequency` itself is **not** extended with `WEEKLY`/
  `CUSTOM_DAYS` values in this pass — matches MA-131 §6's decision that Cart's `Frequency`
  stays narrow; a customer wanting a weekly/custom-day pattern uses the **My Subscriptions**
  screen's own create flow instead (see FR-7), not `ProductConfigScreen`. This keeps MA-120's
  already-tested `Frequency` enum and its wallet-gate logic completely untouched.
- On success: same `AddStatus.success` UI treatment `ProductConfigScreen` already has
  (confirmation + return to the previous screen) — no new UI needed here, just a re-pointed
  repository call.

### FR-7: Creating a weekly/custom-day subscription (new, from My Subscriptions)

- The "Subscribe to New Product" CTA (mock) routes to `/catalog` exactly as literally shown
  — reaching `ProductConfigScreen` for a `DAILY`/`ALTERNATE_DAYS` subscription (FR-6).
- A separate, smaller **"Custom schedule"** link on the same promo banner
  (`Key('subscriptions-custom-schedule-cta')`, not in the mock but necessary to reach
  `WEEKLY`/`CUSTOM_DAYS` at all) opens a lightweight product picker → weekday-toggle form →
  the same slot chip row FR-6 adds (same `getDeliverySlots(zoneId)` source) → calls
  `SubscriptionRepository.create` directly. This is the smallest addition that makes
  the full `Schedule` type set (MA-131 FR-1) reachable without redesigning
  `ProductConfigScreen`'s own, already-shipped frequency selector.

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| **Performance** | Subscriptions list interactive < 400ms after `list()` resolves; skeleton shown until then (matches MA-125's own target). |
| **Reliability** | Every write (pause/resume/stop/skip/edit/create) is a single, non-retried-by-the-client request — the server's own idempotency (MA-131) covers a genuine network retry; the client does not invent its own idempotency-key reuse logic beyond `create`'s (FR-6/FR-7). |
| **Accessibility** | Every icon-only control has a `Semantics` label; touch targets ≥ 48dp; status badges have a text equivalent, not color-only. |
| **Testability** | Every interactive element and result state carries a `Key(...)`. `SubscriptionBloc` is fully unit-testable against `FakeSubscriptionRepository`. |
| **Consistency** | Dates/times always rendered in the same relative style as the mock ("Tomorrow, 6:00 AM") via `intl`, matching this app's existing date-formatting conventions. |

## 6. Technical Design

### State management — `SubscriptionBloc`

Mirrors `WalletBloc`'s shape (one bloc owning a list screen with several async lifecycle
actions).

**Events:** `SubscriptionsStarted`, `SubscriptionsRefreshRequested`,
`VacationModeToggled(bool)`, `PauseRequested(id, from?, until?)`, `ResumeRequested(id)`,
`StopRequested(id)`, `SkipRequested(id, date)`, `EditRequested(id, quantity?, schedule?)`.

**State (`SubscriptionsState extends Equatable`):** `loadStatus`, `subscriptions:
List<SubscriptionView>`, `loadErrorMessage`, per-action status keyed by subscription id
(`Map<String, ActionStatus>` — so one subscription's pause-in-flight spinner doesn't disable
unrelated cards), `vacationModeOn` (computed: `true` iff every subscription is `PAUSED` with
no `pauseUntil`).

### Screen — `lib/features/subscriptions/presentation/subscriptions_screen.dart`

```
SubscriptionsScreen (StatelessWidget)
  └─ BlocProvider(create: SubscriptionBloc(repository: context.read())..add(SubscriptionsStarted()))
       └─ _SubscriptionsView
            ├─ BlocBuilder → switch on loadStatus: loading/failed/empty/loaded
            │     loaded → _SubscriptionsBody:
            │        ├─ _VacationModeRow(on, onToggle)
            │        ├─ _ActiveSubscriptionsHeader(count)
            │        ├─ _SubscriptionCard × N (onTap → _SubscriptionDetailSheet)
            │        └─ _NewProductPromo(onSubscribe, onCustomSchedule)
            └─ BlocListener → surfaces per-action failures as snackbars
```

### Repository — `lib/features/subscriptions/data/subscription_repository.dart`

```dart
abstract class SubscriptionRepository {
  Future<List<SubscriptionView>> list();                    // GET /subscriptions/me
  Future<SubscriptionView> create({...});                   // POST /subscriptions
  Future<void> pause(String id, {DateTime? from, DateTime? until});
  Future<void> resume(String id);
  Future<void> stop(String id);
  Future<void> skip(String id, DateTime date);
  Future<SubscriptionView> edit(String id, {int? quantity, Schedule? schedule});
}
```

`DioSubscriptionRepository(ApiClient)` — talks to a new `AppConfig.subscriptionBaseUrl`.
`FakeSubscriptionRepository` in `test/fakes/` — configurable list/create/action results,
matching `FakeWalletRepository`'s own established shape.

### Models — `lib/features/subscriptions/models/`

- `SubscriptionView { id, productId, productName, quantity, schedule (Schedule),
  status (SubscriptionStatus), nextDeliveryDate?, pauseFrom?, pauseUntil? }` + `fromJson`.
- `Schedule { type (ScheduleType), daysOfWeek?: List<int> }` — wire values match MA-131 §6
  exactly (`DAILY | ALTERNATE_DAYS | WEEKLY | CUSTOM_DAYS`).
- `SubscriptionStatus { active, paused, stopped }`.

### Config — `lib/core/config/app_config.dart`

```dart
static const subscriptionBaseUrl = String.fromEnvironment(
  'SUBSCRIPTION_BASE_URL', defaultValue: 'http://localhost:8008');
static const orderBaseUrl = String.fromEnvironment(
  'ORDER_BASE_URL', defaultValue: 'http://localhost:8009');
```

### `main.dart` / router wiring

- `RepositoryProvider<SubscriptionRepository>(create: (ctx) => DioSubscriptionRepository(ctx.read()))`.
- `GoRoute(path: '/subscriptions', builder: (_, __) => const SubscriptionsScreen())`.
- `home_screen.dart`'s `_HomeBottomNav.onTap`: index 1 (Schedule) → `context.go('/subscriptions')`.
- `wallet_screen.dart`'s `_WalletBottomNav.onTap`: add the same index-1 wiring (currently only
  wires index 0).

## 7. Data Considerations

- No local persistence — unlike Wallet's `pendingRecharge`, there is no client-side
  in-flight-attempt record to survive an app kill: every subscription action here is a
  single, non-multi-step request/response (no gateway sheet, no polling), so there's nothing
  analogous to persist.
- `wallet.lastPaymentMethod`-style local prefs are not needed here — no payment method
  choice exists on this screen (subscriptions are always Wallet-funded, MA-131 §3).

## 8. Integration Considerations

| System | Interaction | Failure behavior |
|--------|-------------|-------------------|
| **Subscription Service (MA-131)** | All of FR-2–FR-7's calls | `ApiException` → inline error (list) or snackbar (an action). |
| **Order Service (MA-132)** | Not called directly by this spec's screens — a `PAYMENT_FAILED` order would surface only via a future order-status affordance (out of scope, §3). | — |
| **Catalog / Cart (MA-23/MA-120)** | "Subscribe to New Product" → `/catalog` → existing `ProductConfigScreen` flow (FR-6, modified) | Unchanged failure handling from MA-120. |
| **User Service** | `GET /delivery/slots?zoneId=` for FR-6/FR-7's slot picker — same call `home_screen.dart`'s `_DeliverySlotPicker` already makes | Unavailable/empty → no default slot, Subscribe Now / the custom-schedule create button stays disabled (FR-6) rather than submitting a null `slotId`. |
| **Cognito / API Gateway** | JWT via shared `ApiClient` | `401` → existing `AuthBloc` path. |

## 9. Edge Cases and Failure Modes

| Case | Handling |
|------|----------|
| Vacation Mode toggled on with zero subscriptions | No-op (nothing to pause); toggle still visually flips (there is no subscription-dependent gate on the toggle itself per the mock). |
| Vacation Mode toggle-off after a subscription was independently stopped (not just paused) while vacation mode was on | Only `PAUSED` subscriptions are resumed (FR-3) — a `STOPPED` one stays `STOPPED`, matching MA-131 FR-4's terminal-state rule. |
| Vacation Mode toggle-off, app restarted since toggle-on (fresh session, no client-tracked pause history) | Still resumes every indefinitely-`PAUSED` subscription (FR-3) — toggle-off targets the same server-computed aggregate `vacationModeOn` is defined from, not a client-side-tracked list, so a fresh session behaves identically to a continuous one. |
| A subscription was individually paused open-ended (no `until`) via its own detail sheet, then Vacation Mode is toggled off | Also resumed — indistinguishable server-side from a vacation-mode pause (both are just "`PAUSED`, no `pauseUntil`"; no `pausedBy`/reason field exists to tell them apart). Accepted trade-off, not silently hidden — see §11 Risks. |
| Skip requested, but the server has already passed cut-off (race between client's stale cut-off assumption and server time) | `409 CUTOFF_PASSED` → inline message "Too late to skip this delivery," list refreshed to reflect the true current state. |
| Edit submitted with only `quantity` changed (schedule unchanged) | `schedule` omitted from the request body — server treats a missing field as "no change" (MA-131 FR-6). |
| Two devices open the same account's Subscriptions screen and one pauses a subscription the other is viewing | The second device's next `SubscriptionsRefreshRequested` (pull-to-refresh) picks up the change — no live sync/websocket in this pass, matching every other screen in this app. |
| A subscription's product becomes unavailable/out of stock | Not specially handled on this screen (MA-131 §9 — Order Service surfaces this as a failed order, not a subscription-level state); the card still shows the subscription as `ACTIVE`. |

## 10. Testing Strategy

### Unit — `SubscriptionBloc` (`test/features/subscriptions/bloc/subscription_bloc_test.dart`)

- `SubscriptionsStarted` loads the list; a failure → `loadStatus.failed` + message.
- `VacationModeToggled(true)` pauses every currently-`ACTIVE` subscription concurrently;
  `false` resumes every currently-`PAUSED`-with-no-`pauseUntil` subscription concurrently —
  including one seeded directly into that state (simulating a fresh app session with no
  client-tracked pause history, or a subscription paused open-ended via its own detail sheet
  rather than the toggle) to assert this is never scoped to a client-side-tracked subset
  (regression test for the exact gap this spec fixed).
- `PauseRequested`/`ResumeRequested`/`StopRequested`/`SkipRequested`/`EditRequested` each
  call the right repository method with the right arguments and update only that
  subscription's per-action status, leaving others untouched.
- A repository failure on one action doesn't affect other subscriptions' displayed state.

## 11. Risks and Trade-offs

- **A second, non-mock "Custom schedule" entry point (FR-7)** — the mock only shows one CTA;
  adding a second is a real UI decision beyond what the mock specifies. Accepted: without it,
  `WEEKLY`/`CUSTOM_DAYS` schedules (explicitly requested in the ticket text) would be
  unreachable from the app at all, which is a bigger gap than one extra small link on an
  already-existing banner.
- **A new slot-chip picker on `ProductConfigScreen` (FR-6)** — not in the mock or in MA-120's
  original scope, and not extrapolated from anywhere except necessity: FR-1's `slotId` is a
  required field on `POST /subscriptions` with no other value source anywhere in this app
  (registration's own `preferredSlotId` is deliberately unsent — see FR-6). Accepted for the
  same reason as the "Custom schedule" CTA above: the alternative is a required field with
  nothing to fill it, not a smaller/cleaner spec.
- **Vacation Mode toggle-off has no way to distinguish "paused because of vacation mode" from
  "paused indefinitely via its own detail sheet" (FR-3)** — both produce the identical
  `PAUSED`-with-no-`pauseUntil` state Subscription Service stores, so toggle-off resuming the
  full aggregate (matching how "on" itself is computed) will also resume a subscription the
  customer deliberately, individually paused open-ended, if they happen to also toggle
  Vacation Mode off later. A real fix needs a server-side `pausedBy: VACATION_MODE | MANUAL`
  field (or equivalent) on the pause record — a schema change to MA-131, out of scope for this
  pass; flagged as a follow-up if product confirms the distinction matters in practice (an
  indefinite manual pause seems like an unusual choice next to the ticket's own date-range
  pause affordance, but it is possible today via FR-5's picker).
- **`ProductConfigBloc` behavior change for subscription-frequency confirms** — a real,
  tested code path changes meaning (no longer touches Cart at all for a subscription). Risk
  mitigated by MA-120's own test suite catching any regression (extended, not replaced, per
  Testing Strategy) and by the one-time path being explicitly, separately verified unchanged.
- **No live sync between devices/sessions** — matches every other screen in this app; not a
  new gap introduced by this spec.
