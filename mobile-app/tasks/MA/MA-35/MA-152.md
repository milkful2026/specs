## 2. Problem Statement

MA-146 built the truthful subset of `order_details_inr`: header, items, total, delivery date,
payment method. It deliberately left off every action button, since none had a path to real
data or a real backend capability at the time. Two of those four buttons — **Reorder Items**
and **Support** — need no new backend capability at all: Reorder is a pure composition of the
order's own items against Cart Service's existing `addItem`, and Support only needs a contact
channel, not a ticketing system. This spec adds both to the existing `OrderDetailScreen`,
closing MA-35 as far as the current backend allows. The remaining two mock buttons (Download
Invoice, Leave Feedback) and the delivery address/slot/partner section stay out of scope,
each already owned by its own ticket (MA-38, MA-28, MA-102 respectively).

## 3. Scope

### In scope

- A new actions row at the bottom of `OrderDetailScreen`'s existing `ListView` (loaded state
  only): **Reorder Items** (primary) and **Support** (secondary).
- Reorder: re-adds every line of the current order to Cart as one-time purchases, with
  per-line success/failure handling and a result SnackBar.
- Support: opens the device's email client addressed to a configured support address, with
  the order's display ID pre-filled in the subject line.
- Loading / per-action disabled state while an action is in flight; errors that don't crash
  or lose the screen's content.

### Out of scope (other tickets / needs other work)

- Download Invoice (MA-38) — no invoice capability exists anywhere in the platform.
- Leave Feedback (MA-28) — a separate story with its own form/flow.
- Delivery address, "Delivered At" time, slot, delivery partner (MA-102) — MA-146's own
  decision, reconfirmed for this spec: showing the customer's *current* default address on a
  past order could misrepresent where it was actually delivered, so this waits for a real
  per-order address/slot source.
- Any cancel action — Order Service has no customer-facing cancel endpoint; `CANCELLED` is
  set only by the backend sweep (MA-143/144).
- Re-creating a subscription from Reorder — Reorder always adds a one-time cart line,
  regardless of the original order's source; starting a new subscription is `ProductConfigScreen`'s
  existing job, not this button's.
- Editing quantity before reordering — Reorder re-adds exactly what was originally ordered;
  the customer can adjust the line from the Cart screen afterward like any other cart item.

## 4. Functional Requirements

### Screen structure addition (loaded state only)

```
┌ Payment Method ───────────────────────┐   (existing, MA-146)
│ (wallet) Milkful Wallet                │
└────────────────────────────────────────┘
┌ Reorder Items ─────────────────────────┐   <- new, primary, full width
└────────────────────────────────────────┘
┌ Support ───────────────────────────────┐   <- new, secondary (outlined), full width
└────────────────────────────────────────┘
```

Both buttons render only in `OrderDetailLoaded` — never in loading, not-found, or error
states (consistent with MA-146's existing per-state rendering).

### FR-1: Reorder Items

- Button `Key('orderDetail.reorder')`, label **"Reorder Items"**, `FilledButton` (matches
  the mock's green full-width primary style and `ProductConfigScreen`'s own confirm-button
  styling).
- On tap: for every line in `order.items`, call
  `CartRepository.addItem(productId: line.productId, quantity: line.quantity, frequency:
  Frequency.oneTime, idempotencyKey: newHexId())` — a fresh key per line, run concurrently
  via `Future.wait` (mirrors `resolveProducts`'s own existing pattern in
  `order_detail_cubit.dart`).
- While in flight: the button shows a small inline spinner in place of its label and is
  disabled; **Support** stays enabled (the two actions are independent).
- **All lines succeed:** SnackBar **"Added {n} item{s} to cart"** (singular for one line)
  with a **"View Cart"** SnackBar action that navigates to `/cart`.
- **Some lines succeed, some fail** (e.g. a product now out of stock or no longer in
  Catalog): SnackBar **"Added {k} of {n} items to cart. Couldn't add {name}{, name2, …}."**
  (comma-joined failed product names; "Item" for any whose Catalog lookup also failed), still
  with the **"View Cart"** action, since partial success still put something in the cart.
- **All lines fail:** SnackBar **"Couldn't add items to cart. Try again."**, no "View Cart"
  action.
- Re-tapping after a partial or full failure retries **every** line again (not just the
  failed ones) — the simplest behavior, consistent with Cart Service's own idempotent
  `addItem` (a line that already succeeded and is retried harmlessly adds a second cart line
  for that product, same as if the customer tapped "Add to Cart" twice from the catalog —
  not a new failure mode this spec introduces).

### FR-2: Support

- Button `Key('orderDetail.support')`, label **"Support"**, `OutlinedButton` (matches the
  mock's secondary button style).
- On tap: launches `mailto:{AppConfig.supportEmail}?subject=Order%20{displayId}` via
  `url_launcher` (new dependency — not currently in `pubspec.yaml`), where `{displayId}` is
  the same short, uppercased ID `DetailHeaderCard` already computes and shows (e.g.
  `3F9A2C1B`), URL-encoded.
- If no email client can handle the intent (`canLaunchUrl` returns false — e.g. a device
  with no mail app configured, common on emulators): SnackBar **"No email app found. Contact
  us at {AppConfig.supportEmail}."**, so the customer isn't left with a silent no-op.
- `AppConfig.supportEmail` is a new config constant, not hardcoded inline — same pattern as
  every other `AppConfig.*BaseUrl` — defaulted to a clearly-labeled placeholder (see Open
  Questions; Product must confirm the real address before release).

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Performance | Reorder's `Future.wait` means wall-clock time is the slowest single line, not the sum |
| Correctness | Reorder never silently drops a failed line from the result message; Support never silently no-ops with no device feedback |
| Security | No new data leaves the device beyond what Cart's existing `addItem` already sends; the `mailto:` subject carries only the display ID, never the full order ID or any customer PII |
| Accessibility | Both buttons ≥48dp touch target; the in-flight spinner replaces the label text (not an overlay), so screen readers announce "Reorder Items, button, busy" via a wrapping `Semantics(button: true, enabled: false)` while loading |
| Maintainability | Reorder's per-line fan-out and message composition lives in the cubit, not the widget, matching `OrderDetailCubit`'s existing split |

## 6. Technical Design

**Modified files:**

| File | Change |
|------|--------|
| `lib/features/orders/bloc/order_detail_cubit.dart` | Add `reorder()`: fans out `CartRepository.addItem` calls, emits a result (success count / failed product names) the screen turns into a SnackBar. Add `_reordering: bool` to `OrderDetailLoaded` (or a sibling status field) so the button can disable itself without losing the loaded order. |
| `lib/features/orders/presentation/order_detail_screen.dart` | Append the two-button actions row after the Payment Method card; wire `reorder()` and a new `_openSupport(context)` method. |
| `lib/core/config/app_config.dart` | Add `supportEmail` constant. |
| `pubspec.yaml` | Add `url_launcher` (latest stable at implementation time). |

**New files:** none — both actions extend existing files; no new route, repository, or model.

**Reuse:** `CartRepository` (already provided app-wide via `main.dart`'s
`MultiRepositoryProvider` — confirmed present since `ProductConfigScreen` already reads it),
`newHexId()` (`core/utils/id_generator.dart`), `Frequency.oneTime`
(`features/cart/models/frequency.dart`).

## 7. Data Considerations

- No new persistence, no new wire schema, no backend change of any kind.
- Reorder's `Future.wait` calls are independent POSTs to Cart Service's existing
  `POST /cart/items` — no transactional relationship between lines (Cart Service has no
  multi-item atomic add endpoint, and none is needed here: a partial cart is still a useful
  cart).

## 8. Integration Considerations

| Dependency | Contract | Failure behaviour |
|------------|----------|-------------------|
| Cart Service `POST /cart/items` (existing) | One call per order line | Per-line `ApiException` caught and attributed to that line's product name in the result SnackBar |
| Device email client (via `url_launcher`) | `mailto:` URL | `canLaunchUrl` false → SnackBar with the support email as plain text instead |

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Order has a single item (every `SUBSCRIPTION` order, or a one-line `CHECKOUT` order) | Reorder still fans out through the same one-line `Future.wait` — no special-casing needed |
| A reordered product's Catalog lookup already failed on this screen (`products[id] == null`) | Reorder still attempts the add (Cart Service, not Catalog, is authoritative for addability); on failure it's reported as **"Item"** in the failure list, matching how the items card already labels an unresolved product |
| Reorder tapped twice in quick succession | The button is disabled while `_reordering` is true — a second tap is a no-op, not a second fan-out |
| Support tapped while Reorder is in flight | Allowed — the two actions don't share state |
| `CartRepository.addItem` throws a non-`ApiException` (e.g. a network timeout) | Treated the same as an `ApiException` for that line — caught, attributed, counted as a failure |
| Device has no mail app at all | Handled per FR-2 — SnackBar with the support address, not a crash or silent failure |

## 10. Testing Strategy

**Cubit tests (`order_detail_cubit_test.dart` additions, `FakeCartRepository`):**
- All lines succeed → result reports full success count, no failed names; `FakeCartRepository.requests` has one entry per order line, each with a distinct idempotency key.
- One of two lines fails (`FakeCartRepository.addItemException` targeted at one product) → result reports partial success with the failed product's name.
- All lines fail → result reports zero successes.
- `reorder()` while already reordering → a second call is a no-op (no additional `addItem` calls).
- A line whose product lookup already failed (`products[id] == null`) still attempts the add and, on failure, reports "Item" not a crash.

**Widget tests (`order_detail_screen_test.dart` additions):**
- **Scenario: successful reorder.**
  - Given a loaded CONFIRMED order with 2 items.
  - Tap `Key('orderDetail.reorder')`.
  - Expect the button shows a busy state during the call, then a SnackBar "Added 2 items to cart" with a "View Cart" action; tapping it navigates to `/cart`.
- **Scenario: partial reorder failure.**
  - One of two `addItem` calls fails.
  - Expect SnackBar "Added 1 of 2 items to cart. Couldn't add {product name}." with a "View Cart" action still present.
- **Scenario: full reorder failure.**
  - Expect SnackBar "Couldn't add items to cart. Try again." with no "View Cart" action.
- **Scenario: support tap, mail app available.**
  - Mock `url_launcher`'s `canLaunchUrl`/`launchUrl` (via its platform test harness); tap `Key('orderDetail.support')`; expect the launched URL's scheme is `mailto`, query contains the subject with the order's display ID.
- **Scenario: support tap, no mail app.**
  - `canLaunchUrl` stubbed false; expect SnackBar containing the configured support email address, no launch attempted.
- **Keys:** `Key('orderDetail.reorder')`, `Key('orderDetail.support')`.

**Integration (local-dev):** open a real order, tap Reorder, confirm the items appear in `GET /cart`.

## 11. Risks and Trade-offs

- **Retry-all vs retry-failed-only on a second Reorder tap.** Retrying every line again is
  simpler and matches Cart's own idempotent-by-click-not-by-order-line model; the trade-off
  is a possible duplicate cart line for an already-succeeded product if the customer retries
  after a partial failure. Accepted: duplicate cart lines are already a normal, correctable
  (removable) state in Cart, not a data-integrity problem.
- **`url_launcher` is a new dependency** purely for a stub support contact. Accepted as the
  standard, idiomatic way to open a mail client from Flutter; no lighter alternative exists
  for this exact need.
- **Support is a dead-end today** (just an email) — no ticket tracking, no in-app history of
  past support contacts. Acceptable for this ticket's scope; a real support/ticketing
  integration is a future story, not invented here.

## 12. Open Questions

- **The real support contact (email and/or phone) needs Product/Support sign-off before
  release.** This spec ships `AppConfig.supportEmail` with an obviously-placeholder value
  (e.g. `support@milkful.app`) — the same discipline `pricing-offer`'s `PRICING_SELLER_STATE`
  and `WALLET_LOW_BALANCE_THRESHOLD_PAISE` placeholders already use elsewhere in this
  codebase. Must be confirmed, not silently shipped as real.
- Whether "View Cart" should be the SnackBar's *only* way to reach the cart after a
  successful reorder, or whether the screen should also auto-navigate — resolved here as
  SnackBar-only (least surprising; the customer stays on the order they were looking at)
  but flagged in case Product wants the more aggressive auto-navigate behavior.
