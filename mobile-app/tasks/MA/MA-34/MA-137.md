## 2. Problem Statement

The cart screen (MA-123) shows a disabled "Proceed to Checkout — coming soon" button:
customers can fill a cart but never buy it. There's also no way to add more from the cart,
and a subscription picked on the product screen bypasses the cart entirely (MA-133 FR-6),
so a customer can't review a one-time purchase and a new subscription together.

Expected outcome: the cart becomes **Review Cart**. It shows what is paid now, what
subscriptions cost per delivery, the wallet balance and the delivery date. It has an
**Add more items** entry point and an enabled **Confirm Order** button that places
everything in one step and lands on a success screen.

## 3. Scope

### In scope

- Cart screen: title "Review Cart"; "Add more items"; split summary; wallet balance +
  shortfall/Top Up; delivery info with the full saved address; "Confirm Order" wired to `POST /orders/checkout`.
- Subscription lines on the cart card show schedule + start date.
- `ProductConfigBloc`: subscription-frequency confirm → `CartRepository.addItem` with
  `slotId` (reverts MA-133 FR-6); button copy and success SnackBar updated.
- New `checkout` feature: `CheckoutRepository` (+Dio, +Fake), `CheckoutResult` model,
  checkout state inside `CartBloc`, `OrderSuccessScreen` at `/order-success`.
- Persisted idempotency key for an in-flight Confirm (survives app kill).

### Out of scope

- A separate preview screen (PO-1: the cart *is* the review screen).
- Address selection/editing (the saved default address is shown read-only), slot choice for
  one-time items, offers/coupons, direct Razorpay payment at checkout.
- Order details/tracking screens (MA-35/MA-36).
- My Subscriptions' own create flow (MA-133 FR-7): unchanged, still creates directly.

## 4. Functional Requirements

### Screen structure (after this spec)

```
AppBar: back arrow · "Review Cart"
Body (scroll):
  Line-item cards (existing MA-123 card)
    + subscription lines: "Daily · starts 27 Sep" under the name (instead of "Daily")
  [+ Add more items]                             ← text button, left-aligned under the list
  Delivery card (Key('cart-delivery-card')):
    📍 "Deliver to"
       "Flat 402, Sai Heights, Baner Road"        (address lines joined with ", ")
       "Near Baner Gaon bus stop"                  (landmark, only if set)
       "Pune, Maharashtra 411045"
    "One-time items arrive Fri, 26 Sep"           (only if one-time lines exist)
Sticky bottom bar:
  PAY NOW                                         (only if payNowQuote != null)
    Subtotal / Tax (x%) / Delivery Fee / Discount? / Total
  SUBSCRIPTIONS                                   (only if perDeliveryQuote != null)
    "₹{perDelivery.netPayable} per delivery · charged from wallet"
    "≈ ₹{monthlyEstimate}/month"                  (only if non-null)
  Wallet balance ₹{balance}  [Top up]             (Top up shown only on shortfall)
  [ Confirm Order ]
```

### FR-1: Title

`AppBar` title → `Text('Review Cart')` (`cart_screen.dart:119`).

### FR-2: Add more items

- `TextButton.icon(key: Key('cart-add-more'), icon: Icons.add, label: Text('Add more items'))`
  rendered below the last line item whenever the cart is loaded and non-empty.
- Tap → `await context.push('/catalog')`; on return, dispatch `CartRefreshRequested`
  (re-fetch `GET /cart`, keeping the list visible, with no skeleton flash).
- The empty state's existing `cart-browse-products-cta` gets the same
  await-then-refresh behaviour, so returning from the Catalog shows the new item.

### FR-3: Subscriptions go into the cart (reverts MA-133 FR-6)

- `ProductConfigBloc._onAddToCartRequested`: for a subscription frequency, call
  `_cartRepository.addItem(productId, quantity, frequency, startDate, slotId, idempotencyKey)`
  instead of `_subscriptionRepository.create(...)`. The one-time branch is unchanged.
- `CartRepository.addItem` / `DioCartRepository` / `FakeCartRepository` gain
  `String? slotId` and send it as `slotId` (MA-135 FR-1).
- `CartLineItem` model gains `slotId` (nullable, parsed from `GET /cart`).
- All existing gates stay: wallet check (≥ ₹500), slot required, start date.
- Confirm button label on the product screen for a subscription: **"Add subscription to
  cart"**. Success SnackBar: "Subscription added to cart". One-time stays "Added to cart".
- `SubscriptionRepository` is no longer a dependency of `ProductConfigBloc`; remove it
  from its constructor and from `ProductConfigScreen`'s provider wiring.

### FR-4: Split summary

- `CartState` gains `payNowQuote`, `perDeliveryQuote` (parsed from MA-135 FR-2); the
  existing `quote` field is kept but no longer rendered.
- PAY NOW block = MA-123 FR-7's rows, sourced from `payNowQuote` (same `_SummaryRow`,
  `_formatRate`, and "Discount row omitted when null" rules).
- SUBSCRIPTIONS block as drawn above. Section headers are `labelSmall`, uppercase,
  `colorScheme.onSurfaceVariant`.
- A block is hidden entirely when its quote is `null`.

### FR-5: Wallet balance and shortfall

- On load/refresh the bloc also reads `WalletBalanceRepository.getBalance()` (existing,
  used by ProductConfig) in parallel with `GET /cart`. A failed balance read hides the
  wallet row but does **not** block Confirm (the server is authoritative).
- `requiredRupees = payNow.netPayable (or 0) + (hasSubscriptionLines ? 500 : 0)`.
  If `balance < requiredRupees`, show under the balance:
  `"Add ₹{required − balance} to confirm this order"` in `colorScheme.error`, plus a
  `TextButton(key: Key('cart-wallet-topup'), 'Top up')` → `await context.push('/wallet')`
  → refresh on return. Confirm stays enabled; the server decides (MA-136 FR-3.7).
- The ₹500 must come from one shared constant with ProductConfig's existing check
  (`product_config_bloc.dart`), not a second literal.

### FR-6: Delivery info

- Shows the **full default address** the customer saved on the onboarding Google Maps /
  Places screen, as returned by `GET /users/me`'s new `defaultAddress` (MA-135 FR-6):
  - `UserProfile` gains `DeliveryAddress? defaultAddress` (`id`, `lines`, `landmark`,
    `city`, `state`, `pincode`, `lat`, `lng`), parsed in `UserProfile.fromJson`.
  - The cart screen reads it from `AuthBloc`'s profile. If the profile has no
    `defaultAddress` (older cached profile, or a backend without MA-135 FR-6), the cart bloc
    re-fetches `GET /users/me` once on load via the existing profile repository and uses
    that; still `null` → the card shows "No delivery address on file" in
    `colorScheme.error` and Confirm stays enabled (the server answers
    `DELIVERY_ADDRESS_UNKNOWN`).
  - Layout: `Icons.location_on_outlined` + "Deliver to" (`labelMedium`), then the lines
    joined with ", " (`bodyMedium`, max 2 lines, ellipsis), landmark (`bodySmall`, only if
    set), then "{city}, {state} {pincode}" (`bodySmall`).
  - Read-only in this story. Changing the address is out of scope.
- "One-time items arrive {EEE, d MMM}" computed with MA-136 FR-8's rule (IST,
  cut-off 20:00, confirmed by Product for one-time deliveries) for display only. The
  success screen shows the server's date.

### FR-7: Confirm Order

- `FilledButton(key: Key('cart-checkout-cta'), child: Text('Confirm Order'))`. The
  "coming soon" copy is removed.
- **Enabled** when: `loadStatus == loaded`, items non-empty, no quantity update/removal
  in flight, and `checkoutStatus != submitting`.
- Tap → `CheckoutRequested`:
  1. Key = persisted pending key if one exists (FR-9), else `newHexId()` persisted
     before the call.
  2. `CheckoutRepository.checkout(cartVersion, expectedPayNowPaise, idempotencyKey)` where
     `expectedPayNowPaise = (payNowQuote?.netPayable ?? 0) × 100` rounded half-up.
  3. While submitting: button shows a 20 px `CircularProgressIndicator`
     (`Key('cart-checkout-progress')`), quantity controls and remove buttons disabled,
     back navigation allowed.
- Outcomes:

| Server result | App behaviour |
|---------------|---------------|
| `200 COMPLETED` | Clear the persisted key; `context.go('/order-success', extra: result)` |
| `402 INSUFFICIENT_BALANCE` | Clear key; dialog "Not enough wallet balance": "Add ₹{shortfall} to place this order." [Cancel] [Top up] → `/wallet`, refresh on return |
| `403 WALLET_NOT_ACTIVE` | Clear key; dialog "Your wallet isn't active yet. Please try again shortly." [OK] |
| `409 CART_CHANGED` / `CART_EMPTY` | Clear key; refresh cart; SnackBar "Your cart changed. Please review it and confirm again." |
| `409 PRICE_CHANGED` | Clear key; refresh cart; SnackBar "Prices were updated. Please review the new total." |
| `409 CHECKOUT_IN_PROGRESS` | Keep key; SnackBar "An order is already being placed…"; auto-retry per FR-8 |
| `422 LINE_INVALID` | Clear key; refresh; mark each listed line with an inline error: `SLOT_MISSING` → "Remove and add again to choose a delivery slot"; `START_DATE_PAST` → "Start date has passed. Remove and add again"; `PRODUCT_UNAVAILABLE` → "No longer available" |
| `422 DELIVERY_ADDRESS_UNKNOWN` | Clear key; dialog "Add a delivery address to continue" [OK] |
| `503 CHECKOUT_INCOMPLETE`, network error, timeout | **Keep key**; auto-retry per FR-8 |

### FR-8: Automatic retry of an incomplete checkout

- Up to 3 automatic retries with the **same key** at 1 s, 2 s, 4 s.
- Still failing → inline banner above the button (`Key('cart-checkout-incomplete')`):
  "We're finishing your order. Tap Confirm Order to try again." The key stays
  persisted, so the next tap resumes rather than starting over (no double charge; MA-136 FR-2).

### FR-9: Key persistence across app kill

- The pending key is stored in `SharedPreferences` under `checkout.pendingKey.{userId}`
  when a Confirm starts and removed on any terminal outcome (the rows in FR-7 that say
  "Clear key").
- On cart screen load, if a pending key exists, show the FR-8 banner immediately; the
  next Confirm tap reuses it.

### FR-10: Order success screen

- New `GoRoute(path: '/order-success')` → `OrderSuccessScreen(result: CheckoutResult)`.
  Reached with `go` (not `push`), so Back can't return to the confirmed cart.
  With no `extra` (deep link or restore) → redirect to `/home`.
- Content (top to bottom):
  - `Icons.check_circle` (64 px, `colorScheme.primary`), title "Order confirmed!"
  - If `order != null`: "Order ID {orderId}" (`Key('order-success-id')`, selectable),
    "Arriving {EEE, d MMM}", "₹{amount} paid from wallet".
  - If subscriptions were created: "Subscriptions started", one row per
    `status: CREATED` ("{product name} · starts {date}").
  - If any subscription `FAILED`: warning row "{product name} couldn't be subscribed.
    It's still in your cart."
  - "Wallet balance ₹{walletBalanceAfterPaise / 100}".
  - Buttons: `FilledButton('Back to Home')` → `/home`; `OutlinedButton('View
    subscriptions')` → `/subscriptions` (shown only if ≥1 subscription created).
- Product names come from the cart's already-joined `CartLineItemView.product`, passed
  alongside the result (no extra Catalog calls).

## 5. Non-Functional Requirements

- **No double submission:** button disabled while submitting; the persisted key makes
  any retry idempotent server-side.
- **Performance:** cart + balance load in parallel; Confirm feedback (spinner) within
  100 ms of tap.
- **Accessibility:** Confirm button `Semantics(label: 'Confirm order, pay ₹{x} now')`;
  spinner has `semanticsLabel: 'Placing order'`; success title is a live region
  (`Semantics(liveRegion: true)`); touch targets ≥ 48 dp; text scales to 1.3× without
  clipping the bottom bar (bar scrolls if needed).
- **Theming:** colors/typography from `Theme.of(context)` tokens only; no hex literals.
- **Observability:** existing `ApiClient` request-id header; log checkout outcome codes
  (no amounts or IDs in analytics events).

## 6. Technical Design

```
lib/features/checkout/
  data/checkout_repository.dart     abstract CheckoutRepository + DioCheckoutRepository + FakeCheckoutRepository
  data/pending_checkout_store.dart  SharedPreferences-backed pending key
  models/checkout_result.dart       CheckoutResult, CheckoutOrder, CheckoutSubscriptionResult
  models/checkout_failure.dart      sealed: InsufficientBalance(shortfallPaise), CartChanged, PriceChanged,
                                    LineInvalid(lines), AddressUnknown, WalletNotActive, InProgress, Incomplete
  presentation/order_success_screen.dart
```

- `DioCheckoutRepository` → `POST {orderBaseUrl}/orders/checkout` (`AppConfig.orderBaseUrl`
  already exists: `ORDER_BASE_URL`, default `:8009`), header `Idempotency-Key`; maps the
  error envelope's `errorCode` to `CheckoutFailure`.
- `CartBloc` gains events `CartRefreshRequested`, `CheckoutRequested`, and state fields
  `payNowQuote`, `perDeliveryQuote`, `walletBalance`, `walletStatus`, `checkoutStatus`
  (`idle | submitting | incomplete`), `checkoutFailure`, `lineErrors`, `checkoutResult`.
  Screen listens with `BlocListener` for navigation/dialogs.
- Providers: `RepositoryProvider<CheckoutRepository>` and `PendingCheckoutStore` in
  `main.dart`, same pattern as `RazorpayCheckout`.

## 7. Data Considerations

- `CartLineItem.slotId`, `CartView.payNowQuote/perDeliveryQuote` (nullable; old
  backends → null → the screen falls back to showing `quote` under PAY NOW so a stale
  backend never shows an empty summary).
- SharedPreferences key `checkout.pendingKey.{userId}`: string, cleared on logout.

## 8. Integration Considerations

| Dependency | Use | Failure |
|------------|-----|---------|
| Cart Service (MA-135) | `GET /cart` split quotes, `slotId` on add | Existing MA-123 error/retry states |
| Order Service (MA-136) | `POST /orders/checkout` | FR-7 table |
| Wallet Service | `GET /wallet/me` balance; `/wallet` screen for Top up | Balance row hidden |
| AuthBloc / User Service | `defaultAddress` (MA-135 FR-6), `userId` for key scope | One `GET /users/me` re-fetch, then the "No delivery address on file" card |

## 9. Edge Cases and Failure Modes

| Case | Behavior |
|------|----------|
| Customer backs out mid-submit | Request continues. Key persisted, so the next visit shows the banner and a tap resumes |
| App killed after server charged | Next Confirm reuses key → server replays COMPLETED → success screen |
| Quantity changed then Confirm tapped immediately | Confirm disabled until the update settles; `cartVersion` reflects it |
| Cart edited on another device | `409 CART_CHANGED` → refresh + SnackBar |
| All lines removed | Empty state; Confirm not shown |
| Subscription-only cart | PAY NOW hidden; Confirm label unchanged; success shows subscriptions only |
| Legacy subscription line without slot | Server `LINE_INVALID/SLOT_MISSING` → inline line error |
| Top up then return | Refresh recalculates shortfall; the stored key was already cleared, so a fresh Confirm starts |

## 10. Testing Strategy

**Bloc tests (`bloc_test`, fakes):**
- Load emits split quotes + balance; balance failure → `walletStatus.failed`, Confirm enabled.
- Confirm happy path persists key → calls repo with `cartVersion` + `expectedPayNowPaise`
  → clears key → `checkoutResult` set.
- Each failure code → expected state and key persisted/cleared per FR-7.
- `Incomplete` → 3 retries with the same key → `checkoutStatus.incomplete`.
- Pending key on load → `incomplete` banner state; next Confirm reuses it.
- `ProductConfigBloc`: subscription confirm calls `FakeCartRepository.addItem` with
  `slotId` and **not** `FakeSubscriptionRepository.create` (update the MA-133 test that
  asserts the opposite, rather than deleting it).

## 11. Risks and Trade-offs

- **Reverting MA-133 FR-6** changes a shipped behaviour: a subscription no longer starts
  the moment it's confirmed on the product screen; it starts at Confirm Order. This is
  intended (PO-4); the product-screen button copy change makes it visible.
- Displayed delivery date is computed client-side and may differ from the server's by a
  day around the cut-off; the success screen always uses the server's date.
- Client-side shortfall is advisory; the server can still return 402 (race), which is handled.

## 12. Open Questions

None blocking. Resolved by Product on 2026-09-25: show the full address captured on the
Google Maps onboarding screen (FR-6, backed by MA-135 FR-6); the 20:00 cut-off applies to
one-time items; a failed subscription line doesn't block the rest of the order.

Non-blocking design choice: "Add more items" sits below the list only, with no AppBar
action. Revisit if long carts make it hard to reach.
