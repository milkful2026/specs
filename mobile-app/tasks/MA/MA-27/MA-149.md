## 2. Problem Statement

The Wallet screen's **Passbook** and **View All Transactions**, and Profile's **Transactions**
row (MA-147), all open a "Transaction history coming soon" placeholder. Customers can't see
where their money went: which order took how much, when they topped up, and what their balance
was after each movement. Expected outcome: a passbook that lists every completed wallet
movement with its closing balance, filterable by type, with order payments linked to the order.

## 3. Scope

### In scope

- `/wallet/transactions` screen (replacing the placeholder):
  - a balance card with **ADD MONEY**;
  - month-grouped ledger rows, paged;
  - a type filter;
  - pull-to-refresh;
  - all loading, empty and error states.
- `WalletRepository.listTransactions` and the ledger entry model.
- Order-type chips for order payments, via the existing `OrderRepository.getById`.
- Order-payment rows open `/orders/{orderId}` (MA-146).

### Out of scope

- Search (the mock's search icon is **not shown**), date-range filter, export/share statement.
- Pending or failed top-ups (they aren't in the ledger; the Wallet screen's recharge flow keeps
  them).
- Gateway reconciliation; showing raw ledger refs or Razorpay ids.
- Any change to the Wallet screen beyond what already links here.

## 4. Functional Requirements

### Screen structure

```
AppBar: [←]  Transaction History                         [filter]
┌ Balance card ────────────────────────────────────────┐
│ Current Balance                         [ADD MONEY]  │
│ ₹6621.46                                             │
└──────────────────────────────────────────────────────┘
[Top-ups ×]                                (active-filter chip, only when filtered)
August                                     (month header, IST)
┌ row ─────────────────────────────────────────────────┐
│ (icon✓) Paid for Order                       − ₹367  │
│         Thu, 6th Aug 26, 07:29:15 AM                 │
│ [Subscription]          Closing balance: ₹6621.46    │
└──────────────────────────────────────────────────────┘
```

### FR-1: Route and entry points

- `GoRoute('/wallet/transactions')` builds `TransactionHistoryScreen`. If
  `AppConfig.walletEnabled` is false, it builds `WalletComingSoon` instead, the same gate as
  `/wallet`.
- It's a pushed screen: back arrow, title **"Transaction History"**, and **no bottom bar**.
  That's consistent with `/orders`; the mock's bottom bar belongs to the Wallet tab it's pushed
  from.
- Existing entry points are unchanged and now land here: the Wallet screen's Passbook and View
  All Transactions, and Profile's Transactions row.

### FR-2: Data loading

On open and on pull-to-refresh, these load **independently** (one failing never blanks the
other):

1. **Balance:** the existing `WalletRepository.getWallet()` (`GET /wallet/me`).
2. **First ledger page:** `WalletRepository.listTransactions(limit: 50, types: <current
   filter>)` → `GET /wallet/me/transactions?limit=50[&types=…]`.

Then the order lookups for order-payment rows (FR-6).

### FR-3: Balance card

- **"Current Balance"** and `balancePaise` formatted with two decimals (`₹6621.46`). The mock's
  "CD Money" is placeholder branding and is not used.
- **ADD MONEY** → `context.go('/wallet')`, where the top-up flow lives (MA-125). It's a filled
  button, 48dp high.
- Balance loading → a placeholder bar. Balance failed → **"—"** with a small **Retry** text
  button (the list is unaffected).
- Wallet status not ACTIVE (`CREATING`/`FAILED`): the card still shows the balance, but ADD
  MONEY is disabled. This matches the Wallet screen's existing "gate Top Up on ACTIVE" rule.

### FR-4: Rows

One row per ledger entry, newest first, grouped under **month headers** in IST. The header is
the month name ("August"), with the year added when it isn't the current IST year ("August
2025").

| Ledger `type` | Title | Icon | Chip |
|---------------|-------|------|------|
| `ORDER_DEBIT` | Paid for Order | cart | from the order (FR-6): **Subscription** / **One-time order** / **Order** |
| `RECHARGE` | Wallet Top-up | wallet + | **Top-up** |
| `REFUND` | Refund for Order if the entry has an `orderId` (ref `refund:{orderId}:{refundId}`, MA-148 FR-3), else Refund | cart | **Refund** |
| `CASHBACK` | Cashback | gift | **Cashback** |
| `REFERRAL_CREDIT` | Referral Credit | people | **Referral** |
| `ADJUSTMENT` | Adjustment | tune | **Adjustment** |
| `OPENING` | Wallet Opened | wallet | **Wallet** |
| unknown | the entry's `description` (fallback "Transaction") | receipt | neutral chip with the raw type, title-cased |

Each row also shows:

- **Timestamp:** `createdAt` in IST, formatted like the mock: `Thu, 6th Aug 26, 07:29:15 AM`
  (ordinal day suffix; 12-hour time with seconds).
- **Amount:** `amountPaise` is signed.
  - `> 0` → **`+ ₹45`**, in the theme's primary (green) colour.
  - `< 0` → **`− ₹367`**, with a Unicode minus, in the default text colour.
  - `0` (the opening entry) → **`₹0`**.
  - The digits are `formatPaise(amountPaise.abs())` (no `.00` for whole rupees). Format the
    **absolute** value: `formatPaise` already prefixes negatives with `-`, so passing the signed
    amount would render `− -₹367`. The `+ ` / `− ` above is the only sign shown.
- **Closing balance:** **`Closing balance: ₹6621.46`** from `balanceAfterPaise` (always two
  decimals).
- **Status icon:** a small check badge on the icon. Every ledger row is a completed movement;
  there is no status chip (MA-27 decision).

### FR-5: Type filter

- The filter icon in the app bar (semantics label "Filter transactions") opens a bottom sheet
  titled **"Show"**, with radio options:
  - **All transactions** (no `types`)
  - **Top-ups** → `RECHARGE`
  - **Order payments** → `ORDER_DEBIT`
  - **Refunds & credits** → `REFUND,CASHBACK,REFERRAL_CREDIT,ADJUSTMENT`
- Choosing an option:
  - closes the sheet;
  - discards the loaded ledger pages and cursor;
  - reloads the first page with the new `types` (MA-148);
  - doesn't reload the balance.
- When the filter isn't "All", a dismissible chip under the balance card names it (e.g.
  **"Top-ups ×"**); tapping × returns to All.
- The filter lives in the screen's state only and isn't persisted.

### FR-6: Order-type chips

- An entry's **`orderId`** comes from its `ref` (MA-148 FR-3):
  - `order:{orderId}` (an `ORDER_DEBIT`) → `orderId`;
  - `refund:{orderId}:{refundId}` (a `REFUND`) → the part after `refund:` up to the next `:`
    (or the end, if there is none);
  - anything else, or an empty ID → none.
- For each entry with an `orderId`, resolve the order once with
  `OrderRepository.getById(orderId)`. Calls are parallel and cached in the bloc
  for the screen's lifetime.
- `source == SUBSCRIPTION` → **Subscription**; `CHECKOUT` → **One-time order**. Before the
  lookup resolves, and if it fails (including a 404), the chip reads **Order**.
- Rows render immediately; the chips fill in later.

### FR-7: Tapping a row

- A row with an `orderId` (FR-6: order payments and order refunds) → `context.push('/orders/{orderId}')`.
- Other rows are not tappable (no ripple), and have no chevron.

### FR-8: Pagination

- When the list scrolls within 300 px of its end and `nextCursor` is non-null, fetch the next
  page with the same `types` and append it. Only one page request runs at a time.
- A bottom spinner shows while loading. A failed page shows a **"Couldn't load more. Retry"**
  row.
- A filter change or refresh discards any in-flight page result (generation counter, as in
  MA-145).

### FR-9: States

| Situation | UI |
|-----------|----|
| First load | Balance placeholder + 4 row skeletons |
| Ledger `404 WALLET_NOT_FOUND` | **"Your wallet is being set up."** + sub-text "Your transactions will appear here once it's ready." + **"Back to Wallet"** (`go('/wallet')`); no filter icon |
| Ledger failed (other) | Under the balance card: **"Couldn't load your transactions."** + **"Retry"** |
| No entries, filter All | **"No transactions yet"** + "Top up your wallet to get started." |
| No entries, filtered | **"No top-ups yet"** / **"No order payments yet"** / **"No refunds or credits yet"** + **"Show all transactions"** (resets to All) |
| Pull-to-refresh fails | Keep the data; SnackBar **"Couldn't refresh. Try again."** |

An empty state is shown only when the ledger request **succeeded** with zero items; a failed
request never shows "No transactions yet".

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Performance | Skeleton < 100 ms; rows render as soon as the ledger page returns (chips fill in later); smooth scrolling with 500 rows (`SliverList.builder`) |
| Network | 2 calls on open + ≤ 1 `GET /orders/{id}` per distinct order (cached); next pages on demand |
| Correctness | Signed amounts and balances exactly as the ledger says (integer paise); IST timestamps and months regardless of device time zone |
| Accessibility | Each row's semantics: "{title}, {amount spoken as plus/minus rupees}, {date}, closing balance {balance}"; 48dp targets; AA contrast (the green credit colour is the theme primary); the filter sheet's radios are labelled |
| Maintainability | Title/chip/icon mapping and the date format live in pure functions (`ledger_copy.dart`), unit-tested |

## 7. Data Considerations

- Read-only; nothing persisted.
- `createdAt` is ISO-8601 with an offset → converted to IST. `amountPaise` and
  `balanceAfterPaise` are integers (paise).
- An unknown ledger `type` never throws (FR-4 fallback).

## 8. Integration Considerations

| Dependency | Contract | Failure behaviour |
|------------|----------|-------------------|
| Wallet `GET /wallet/me` | `{balancePaise, status, …}` (existing `WalletView`) | Balance "—" + Retry |
| Wallet `GET /wallet/me/transactions` (+ `types`, MA-148) | `{items, nextCursor}` | 404 → being set up; other → Retry |
| Order `GET /orders/{id}` | `source` | Chip stays "Order" |

**Rollout:** the filter needs MA-148 deployed. Without it, the current Wallet ignores `types`
(FastAPI drops unknown query params), so a filter would show unfiltered data. **Ship MA-148
before, or with, this screen.**

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Opening entry only (new wallet) | One "Wallet Opened" row, `₹0`, chip "Wallet" |
| Same order appears as a debit (`order:{id}`) and (later) a refund (`refund:{id}:{refundId}`) | Both resolve to the same `orderId`: one `GET /orders/{id}` (cache); both rows link to it |
| Two partial refunds for one order | Two rows, each "Refund for Order", both linking to the order (distinct `refundId`s) |
| `REFUND` with a ref in no known format (e.g. a manual credit) | Title "Refund", no order chip, not tappable |
| Order lookup 404 (e.g. a deleted order) | Chip "Order"; tapping still pushes `/orders/{id}`, which shows its own "Order not found" (MA-146) |
| Entries spanning a year boundary | "January" then "December 2025" headers |
| Device time zone ≠ IST | Timestamps and months in IST |
| Filter changed during an in-flight page | The stale page is ignored |
| Large credit amounts (≥ ₹1,00,000) | Shown without grouping separators (consistent with app-wide `formatPaise`) |

## 10. Testing Strategy

- **Unit (`ledger_copy_test.dart`):**
  - every row of the FR-4 table, plus an unknown type;
  - a refund with an order ref (`refund:ord_1:rf_1` → "Refund for Order") and without one
    ("Refund");
  - `formatLedgerTimestamp`: 1st/2nd/3rd/4th/11th/12th/13th/21st/22nd/23rd suffixes; AM/PM;
    IST conversion across midnight UTC;
  - `formatMonthHeader` for the current and a previous year;
  - each `TransactionFilter.types`.
- **Model:** `LedgerEntry.fromJson` (signed amounts, unknown type) and `orderId`:
  `order:ord_1` → `ord_1`; `refund:ord_1:rf_1` → `ord_1`; `refund:ord_1` → `ord_1`;
  `refund::rf_1`, `recharge:…`, `manual-credit` → none.
- **Bloc (fakes, fixed clock):**
  - open → balance and ledger loaded independently; ledger 404 → wallet-not-ready;
  - ledger 500 → ledger failed, while the balance still loads;
  - a filter change resets the cursor and calls `listTransactions(types: [RECHARGE])`;
  - paging appends, and a duplicate request is dropped;
  - a filter change during a page discards the stale result;
  - order cache: one `getById` per distinct order across pages and refresh; a failed lookup
    leaves the chip "Order";
  - a refresh failure keeps the data.
- **Widget (GoRouter harness):**
  - mock-like data → "Transaction History", "Current Balance", "₹6621.46", "August", "Paid for
    Order", "− ₹367", "+ ₹45", "Closing balance: ₹6621.46", chip "Subscription", and **no**
    search icon, and **no** text containing "-₹" (no double sign on the `-36700` debit);
  - a refund row with ref `refund:ord_1:rf_1` reads "Refund for Order" and tapping it pushes
    `/orders/ord_1`;
  - the filter sheet → "Top-ups" → the request has `types=RECHARGE`, the chip "Top-ups ×"
    shows, and × resets;
  - the filtered empty state "No top-ups yet" + "Show all transactions";
  - the wallet-being-set-up state + "Back to Wallet" → `/wallet`;
  - tapping an order row pushes `/orders/ord_1`, and a top-up row isn't tappable;
  - ADD MONEY → `/wallet`; ADD MONEY disabled when the status is CREATING;
  - a ledger failure shows "Couldn't load your transactions." and never "No transactions yet".
- **Router:** `/wallet/transactions` builds the new screen with the wallet enabled, and
  `WalletComingSoon` when it's disabled. No existing test references the placeholder; its only
  use is the router builder being replaced.
- **Keys:** `Key('txn.row.{ledgerId}')`, `Key('txn.filter')`, `Key('txn.balance')`,
  `Key('txn.loadMoreRetry')`.

## 11. Risks and Trade-offs

- **N order lookups per page** for chips. They're cached and parallel, and the rows don't wait.
  A batch endpoint can come later if needed.
- **No bottom bar** (unlike the mock), for consistency with the other pushed screens.
- **The filter depends on MA-148** (rollout order in §8).
