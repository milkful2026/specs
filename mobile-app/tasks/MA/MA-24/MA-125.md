## 2. Problem Statement

The Milkful prepaid **Wallet** is the platform's settlement rail — it funds one-time "instant buy" orders and subscription auto-debit. Today the Wallet is auto-created at registration ([MA-1 `wallet-auto-provision`](https://github.com/milkful2026/specs/blob/main/services/tasks/MA/MA-1/wallet-auto-provision.md)) but the app has **no screen to see the balance or add money to it**: the bottom-nav "Wallet" tab (`home_screen.dart:944`) is a stub with no destination, and `StubWalletBalanceRepository` always fails closed. Nothing in the app can take a real payment.

This spec delivers the **Wallet tab** exactly as drawn in the MA-24 ticket mock (`image-20260806-182611.png`): the customer sees their balance, picks a top-up amount (quick chip or custom), picks a payment method (UPI or card), and pays through **Razorpay**; on success the wallet is credited and the balance updates. The passbook entry points route to Transaction History ([MA-27](https://milkfuldairyindia.atlassian.net/browse/MA-27)).

Expected outcome: a customer can fund their wallet in under a minute, sees an honest result for every payment outcome (success / failure / async-UPI pending), and is never double-charged.

## 3. Scope

### In scope

- A new `/wallet` screen and the wiring of the existing bottom-nav **Wallet** tab to it.
- **Balance card** — "Available Balance", `₹{amount}`, `Top Up` button, `Passbook` button; a "View All Transactions" link.
- **Quick Top Up** — three chips: `Add ₹500`, `Add ₹1000`, `Add ₹2000`.
- **Top Up (custom amount)** — a modal sheet with an amount field, min/max validation (bounds read from the service, not hard-coded).
- **Payment Methods** — a radio group: "UPI Payments" and "Credit / Debit Card"; one selected (default from last-used, else Card per the mock); remembered per user via `shared_preferences`.
- **Proceed to Payment** — creates a Razorpay order via Payment Service, opens the `razorpay_flutter` checkout sheet for the chosen amount, handles success / failure / cancel / **pending (async UPI)**.
- **Result handling** — success confirmation + balance refresh; inline failure reason + retry; non-blocking "processing" state for pending UPI that resolves via a balance re-fetch.
- **Passbook** / **View All Transactions** navigate to the MA-27 Transaction History route (`/wallet/transactions` placeholder until MA-27 ships).
- `WalletBloc`, `WalletRepository` (abstract + `DioWalletRepository` + `FakeWalletRepository`), `WalletBalance` / `RechargeIntent` / `PaymentMethod` models.
- New dependency `razorpay_flutter`; Razorpay **key id** supplied via `--dart-define=RAZORPAY_KEY_ID`.
- Retire `StubWalletBalanceRepository`; re-point MA-120's `ProductConfigBloc` wallet-balance gate at the new repository (semantics move from whole-rupees to paise — see §7).
- Feature flag `--dart-define=WALLET_ENABLED` (default `false`) so the tab can ship dark until MA-126/MA-127 are live.
- All UI states, `Key(...)` selectors, and accessibility per the `mobile-app` SDD conventions.

### Out of scope

- **Cart → order checkout** ("pay for this order"): the cart's `cart-checkout-cta` (MA-123 FR-7) stays disabled after this story.
- **Transaction History screen itself** — MA-27; this spec only links to it.
- **Recharge offers / cashback, low-balance auto-recharge, low-balance alerts** — NSMB row 14.0 extras, not in the mock; deferred (MA-33 repurposed / MA-103).
- **Custom "saved payment methods" management UI** — v1 uses Razorpay-native saved instruments inside its sheet.
- **Net-banking as a first-class method tile** — the mock shows only UPI and Card; net-banking remains reachable inside Razorpay's sheet but is not a top-level option.
- **Wallet debit / order payment / refund flows** — downstream (MA-25 / MA-97 / MA-32).
- **B2B / credit wallets** — B2C prepaid only.
- **Flutter web** — `razorpay_flutter` is Android/iOS only; the web build shows a fallback (see FR-9).

### FR-1: Navigation & tab wiring

- New `GoRoute(path: '/wallet', builder: (_, __) => const WalletScreen())` in `app_router.dart`, consistent with the existing flat-path convention (`/cart`, `/catalog`).
- The bottom-nav **Wallet** item (`_HomeBottomNav`, `home_screen.dart:944`) navigates to `/wallet` (via `context.go('/wallet')` so the tab acts as a top-level destination, not a push). The `Home` item continues to point at `/home`; `Schedule` and `Profile` remain stubs.
- Reached only from the bottom nav — it is not an auth-redirect target and carries no `extra:` payload; the screen fetches its own state (FR-2).
- When `WALLET_ENABLED` is `false`, the Wallet nav item is still visible but tapping it shows a "Coming soon" placeholder (`Key('wallet-coming-soon')`) instead of `WalletScreen`.

### FR-2: Loading the wallet

- On screen open, dispatch `WalletStarted` → `WalletRepository.getWallet()` → `GET {AppConfig.userBaseUrl-style wallet host}/wallet/me` (see §6 for the base URL).
- Response (per MA-127): `{ walletId, status, balancePaise, currency, rechargeMinPaise, rechargeMaxPaise }`.
- While in flight, show a **loading skeleton**: a grey placeholder balance card + shimmering chip row, matching `catalog_screen.dart`'s `_LoadingSkeleton` treatment. `Key('wallet-loading-skeleton')`.
- On failure, show a full-width inline error with a **Retry** button (`Key('wallet-load-error')` / `Key('wallet-load-retry')`) — never render `₹0` as if it were a real balance.
- If `status != ACTIVE` (`CREATING` / `FAILED` — from the MA-1 auto-provision flow), render the balance area as "Wallet setup in progress" and **disable `Proceed to Payment`**; if `FAILED`, show a "Retry setup" action calling `WalletRepository.retryProvision()` → `POST /wallet/me/retry` (MA-1 FR-3).

### FR-3: Choosing a recharge amount

- Tapping a Quick Top Up chip (`Add ₹500` / `Add ₹1000` / `Add ₹2000`) selects that amount; the chip shows a selected state; `Proceed to Payment` becomes enabled.
- Tapping `Top Up` opens `_TopUpAmountSheet` (`Key('wallet-topup-sheet')`): a numeric `TextField` (`Key('wallet-topup-amount-field')`, `keyboardType: TextInputType.number`, digits only), a "Continue" button, and inline validation (`Key('wallet-topup-amount-error')`):
  - empty / non-numeric → "Enter an amount"
  - `< rechargeMinPaise` → "Minimum top-up is ₹{min}"
  - `> rechargeMaxPaise` → "Maximum top-up is ₹{max}"
  - non-integer rupee (paise entered) → "Enter a whole rupee amount"
- "Continue" closes the sheet and sets the chosen amount (shown near the CTA, e.g. "Proceed to Payment · ₹750"); a Quick chip and a custom amount are mutually exclusive (choosing one clears the other).
- Selected amount is **UI state only** until `Proceed to Payment`; it is not persisted across screen exits.
- Changing the selected amount while **no** recharge attempt is in flight also discards any idempotency key still held in bloc memory (a new amount is a new attempt — prevents the stale key being reused at a different amount). While a pending attempt is unresolved the amount controls are disabled entirely (FR-6a), so this cannot happen mid-attempt.

### FR-4: Choosing a payment method

- Radio group with exactly two options: `UPI Payments` (subtitle "Google Pay, PhonePe, BHIM") and `Credit / Debit Card` (subtitle "Visa, Mastercard, RuPay").
- Default selection: the last method this user used (persisted key `wallet.lastPaymentMethod` in `shared_preferences`); if none, `Credit / Debit Card` (matches the mock).
- Each option is a ≥48dp touch target with `Semantics(label: 'UPI Payments, Google Pay PhonePe BHIM')` / `Semantics(label: 'Credit or Debit Card, Visa Mastercard RuPay')`.
- The selected method is passed to Razorpay checkout as the preferred method (`method: {upi: true}` or `{card: true}` in the `razorpay_flutter` options); the customer can still switch inside Razorpay's sheet — whatever Razorpay reports back is what gets recorded.

### FR-5: Proceed to Payment — creating the order

- `Proceed to Payment` is **disabled** until an amount is chosen and `status == ACTIVE`.
- On tap: show a spinner on the CTA (`Key('wallet-proceed-loading')`, CTA non-interactive) and dispatch `RechargeRequested(amountPaise, method)`.
- `WalletBloc` generates a fresh **idempotency key** (UUID v4) for this attempt — held in bloc state and **reused** across any retry of this same attempt (never regenerated on retry) — and calls `WalletRepository.createRecharge(amountPaise, method, idempotencyKey)` → `POST /payments` (MA-126 FR-1).
- Response: `{ paymentId, razorpayOrderId, razorpayKeyId, amountPaise, currency }`.
- On a non-2xx response, revert the CTA and show an inline error (FR-8).

### FR-6: Proceed to Payment — the Razorpay sheet

- With the created order, open the `razorpay_flutter` checkout: `{ key: razorpayKeyId, order_id: razorpayOrderId, amount: amountPaise, currency: 'INR', name: 'Milkful', description: 'Wallet top-up', prefill: { contact: <user mobile>, email: <user email if known> }, method: <from FR-4>, theme: { color: <brand green> } }`.
- **Razorpay `success`** callback `{ razorpay_payment_id, razorpay_order_id, razorpay_signature }` → dispatch `RechargeGatewaySucceeded(razorpayPaymentId, razorpayOrderId, razorpaySignature)` → `WalletRepository.confirmRecharge(paymentId, razorpayPaymentId, razorpayOrderId, razorpaySignature)` → `POST /payments/{id}/confirm` (MA-126 FR-2). `razorpayOrderId` is **required** in this call — MA-126 FR-2 rejects a body without it and 409s (`ORDER_MISMATCH`) if it does not match the order on the row. This call **does not credit the wallet** — it advances the payment to `CONFIRMING`; the credit is webhook-driven server-side.
  - On `confirm` success → enter the **pending-confirmation** state (FR-7): show `Key('wallet-recharge-pending')` "Payment received — updating your balance…", start polling `getPayment(paymentId)` (every 2s, up to 20s).
  - **Success is decided only by `getPayment(paymentId)` returning `status: CONFIRMED`** — never by inferring it from a `getWallet()` balance delta. An unrelated credit of the same amount landing in the poll window (a second device's recharge, a refund, a cashback) would otherwise false-positive. On `CONFIRMED` → issue one final `getWallet()` for the authoritative new balance, then switch to the **success** state (FR-7).
  - If `getPayment()` returns `status: FAILED` (the webhook or the reconciliation sweep recorded a failed capture) → stop polling and switch to the **failure** state (FR-8), showing `PaymentView.failureReason` (or a mapped friendly message); balance unchanged.
  - If 20s elapse with the payment still `CONFIRMING` → keep a non-blocking `Key('wallet-recharge-pending')` banner on the balance card ("We'll update your balance shortly"), stop the in-session poll, and **keep the persisted pending-attempt record** (§7) so a re-open resumes polling this same payment. The CTA stays in its pending affordance — it does **not** re-enable for a fresh amount while this attempt is unresolved (FR-6a).
- **Razorpay `error`** callback `{ code, description, ... }` → dispatch `RechargeGatewayFailed(code, description)` → show failure (FR-8). Also `POST /payments/{id}/confirm` is **not** called; Payment Service will mark it `FAILED` from the webhook or the reconciliation sweep.
- **Razorpay `external_wallet` / user dismissal / `PAYMENT_CANCELLED`** → treat as a benign cancel: return to the Wallet screen, CTA re-enabled, no error text, balance unchanged. `Key('wallet-recharge-cancelled')` (transient snackbar, optional).

### FR-6a: Resuming or abandoning a pending attempt

- On screen open (`WalletStarted`), if a persisted pending-attempt record exists (§7): the bloc enters the **pending** state for that `paymentId` and resumes polling `getPayment(paymentId)` (+ a `getWallet()` for display). The CTA shows the pending banner and stays disabled — the user cannot start a new, separately-chargeable recharge while a prior attempt is unresolved.
  - `getPayment()` = `CONFIRMED` → success state, record cleared.
  - `getPayment()` = `FAILED` → failure state, record cleared.
  - `getPayment()` = `CREATED` / `CONFIRMING` and the record is older than **30 minutes** (matches MA-126's reconciliation window) → keep the non-blocking banner and show a secondary `Key('wallet-recharge-abandon')` action ("Not you? Start over"). Tapping it opens a confirm dialog; on confirm, dispatch `PendingRechargeAbandoned` → clear the record, re-enable the CTA. (The server-side sweep still settles the abandoned payment independently — MA-126 FR-5.)
- The persisted record is written on `RechargeRequested` (before the Razorpay sheet opens) and cleared **only** on a terminal outcome (`CONFIRMED`, `FAILED`, user-confirmed abandon) — never on a bare in-session timeout.

### FR-7: Result states

| State | Trigger | UI |
|-------|---------|----|
| **Success** | `getPayment(paymentId)` = `CONFIRMED` (authoritative — never a bare `getWallet()` balance delta) | `Key('wallet-recharge-success')` — a confirmation (bottom sheet or snackbar) "₹{amount} added to your wallet", balance card animates to the value from a final `getWallet()`, method persisted to `shared_preferences`, the persisted pending-attempt record (§7) cleared. |
| **Pending** | `confirm` succeeded but `getPayment()` not yet `CONFIRMED` | `Key('wallet-recharge-pending')` — "Payment received — updating your balance…"; non-blocking; polling as FR-6. CTA stays disabled while the attempt is unresolved — including after the 20s in-session cutoff (a re-open resumes polling the same payment); it does **not** re-enable for a new amount until this attempt reaches `CONFIRMED`, `FAILED`, or is explicitly abandoned (FR-6a). |
| **Failure** | Razorpay `error`, `POST /payments` non-2xx, or `getPayment()` = `FAILED` during pending polling | `Key('wallet-recharge-error')` — inline card below the CTA with the gateway's `description` / `PaymentView.failureReason` (verbatim) or a mapped friendly message for known `ApiException.errorCode`s; the persisted pending-attempt record (§7) is cleared. **Retry** re-runs the flow **reusing the same idempotency key**, offered *only* for a Razorpay-`error` / non-2xx failure before a successful `confirm`; balance unchanged. |
| **Cancelled** | user dismissed the sheet before a Razorpay `success` | silent return; CTA re-enabled; no `POST /payments/{id}/confirm`; the persisted pending-attempt record is cleared (no payment was completed — MA-126's sweep settles the orphan `CREATED` row). |

### FR-8: Failure surfacing & retry

- `ApiException` from `POST /payments` / `POST /payments/{id}/confirm` → inline error (`Key('wallet-recharge-error')`) with `exception.message` verbatim (matches MA-120 FR-8 / MA-123 FR-6 conventions).
- Razorpay `error` → show `description`; map a few known codes to friendlier copy (`BAD_REQUEST_ERROR` → "Payment could not be started, try again"; `GATEWAY_ERROR` → "The payment provider is having trouble, try again in a bit").
- `getPayment()` = `FAILED` during pending polling → same failure card, message from `PaymentView.failureReason`.
- **Retry** button on the failure card re-dispatches `RechargeRequested` **with the same idempotency key** held in bloc state, so Payment Service resumes the same attempt (dedupes on the key / resumes `orders.create` per MA-126 FR-1) rather than minting a second Razorpay order. Retry is offered only for a `POST /payments` non-2xx or a Razorpay `error` **before** a successful `confirm` — never after `confirm` succeeded (that path only ever resolves to success or `getPayment()` = `FAILED`).
- No client-side retry loop / backoff; retry is user-initiated only.

### FR-9: Passbook navigation

- `Passbook` button and `View All Transactions` link both `context.push('/wallet/transactions')`.
- Until MA-27 ships, `/wallet/transactions` renders a minimal placeholder screen (`Key('wallet-transactions-placeholder')`, "Transaction history coming soon") — this spec adds the route and the placeholder; MA-27 replaces the builder.
- Both entry points navigate to the same route (the mock shows both; if MA-27's own spec later distinguishes a "recent" vs "full" view, that is MA-27's call).

### FR-10: Platform / web fallback

- `razorpay_flutter` supports Android and iOS only. On Flutter **web** (`kIsWeb`), the Wallet screen renders the balance card and passbook links normally but replaces `Proceed to Payment` with a disabled control + caption "Open the Milkful app on your phone to add money" (`Key('wallet-web-unsupported')`).
- Native config the implementation must add: Android — no extra permissions, but `minSdkVersion >= 19` (already met) and ProGuard keep rules for `com.razorpay.**`; iOS — add UPI app URL schemes (`tez`, `phonepe`, `paytmmp`, `bhim`, `credpay`) to `LSApplicationQueriesSchemes` in `Info.plist`.

### FR-11: Auth & session

- All `/wallet/*` and `/payments/*` calls go through the shared `ApiClient`, which attaches the Cognito access token; no wallet-specific token handling.
- A `401` from any wallet/payment call surfaces via the existing `ApiClient` → `AuthBloc` path (session expiry handling is not this spec's concern).

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| **Performance** | Wallet screen interactive < 400ms after `getWallet()` resolves; skeleton shown until then. No blocking spinner over the whole screen except first load. |
| **Reliability** | No client action can double-charge or double-credit: one idempotency key per attempt, reused on retry, **persisted to `shared_preferences` (§7) until the attempt reaches a terminal outcome** so an app kill or a pending-timeout resumes the *same* payment rather than starting a new, separately-chargeable one. The client never credits the wallet (server + webhook do). On next open, a persisted pending-attempt record drives a `getPayment()` resume; any completed credit shows via the subsequent `getWallet()`. |
| **Accessibility** | Every icon-only / compound control has a `Semantics` label; touch targets ≥ 48dp for chips, radio options, `Top Up`, `Passbook`, and `Proceed to Payment`; balance amount is announced ("Available balance, 450 rupees"); WCAG AA contrast on the green balance card (white text on brand green must pass 4.5:1 — verify the exact token). |
| **Testability** | Every interactive element and every result state carries a `Key(...)` (enumerated per FR). Bloc is fully unit-testable against `FakeWalletRepository`; the Razorpay sheet is abstracted behind a `RazorpayCheckout` wrapper interface so widget tests can inject a fake. |
| **Consistency** | Never compute or assume the post-recharge balance client-side beyond an optimistic display hint — the authoritative balance is always the next `getWallet()`. Money shown as `₹` with 2 decimals via `intl`'s `NumberFormat.currency(locale: 'en_IN', symbol: '₹')`. |
| **Security** | No PAN / CVV / card data is ever read, stored, or logged by the app. Only the Razorpay **key id** ships in the binary (via `--dart-define`, never committed — same pattern as `GOOGLE_MAPS_API_KEY` in `AppConfig`). The `razorpay_signature` from the success callback is forwarded to the server as-is and never trusted locally. |
| **Observability** | Bloc emits analytics-friendly state transitions (`recharge_initiated`, `recharge_gateway_opened`, `recharge_succeeded`, `recharge_failed{code}`, `recharge_pending_timeout`) for the app's telemetry layer; no PII in event props. |

## 6. Technical Design

### State management — `WalletBloc`

Mirrors `CartBloc` / `ProductConfigBloc`: one bloc owning a single screen with several async operations.

**Events (`sealed class WalletEvent`):**
- `WalletStarted` — initial load; also resumes a persisted pending-attempt record if one exists (FR-6a).
- `WalletRefreshRequested` — pull-to-refresh / poll tick / resume.
- `QuickAmountSelected(int amountPaise)` / `CustomAmountEntered(int amountPaise)` / `AmountCleared` — each, when no recharge attempt is in flight or unresolved, also clears any `idempotencyKey` / `pendingPaymentId` still held in bloc memory (a new amount is a new attempt). They are **rejected** (no-op) while a pending attempt is unresolved — the CTA is disabled then anyway (FR-6a).
- `PaymentMethodSelected(PaymentMethod method)`.
- `RechargeRequested` — build/keep the idempotency key, write the `wallet.pendingRecharge` record (§7), call `createRecharge`.
- `RechargeGatewaySucceeded(String razorpayPaymentId, String razorpayOrderId, String razorpaySignature)` — call `confirmRecharge` (all three ids + `paymentId`), enter pending.
- `RechargeGatewayFailed(String code, String description)` — enter failure.
- `RechargeGatewayDismissed` — benign cancel.
- `RechargePollTick` — internal (timer) → `getPayment` (authoritative) + `getWallet` (display only).
- `WalletProvisionRetryRequested` — `POST /wallet/me/retry`.
- `PendingRechargeAbandoned` — user confirmed "Start over" on a stale (>30 min) pending attempt (FR-6a): clear the persisted record, re-enable the CTA.

**State (`WalletState extends Equatable`):**
- `loadStatus: WalletLoadStatus { loading, loaded, failed }`, `loadErrorMessage`.
- `walletStatus: WalletStatus { active, creating, failed }`.
- `balancePaise`, `currency`, `rechargeMinPaise`, `rechargeMaxPaise`.
- `selectedAmountPaise` (nullable), `selectedMethod`.
- `rechargeStatus: RechargeStatus { idle, creatingOrder, awaitingGateway, confirming, pending, success, failed }`.
- `rechargeErrorMessage` (transient), `lastConfirmedAmountPaise` (for the success copy).
- `idempotencyKey` (nullable) — set on `RechargeRequested` and **mirrored to the `wallet.pendingRecharge` `shared_preferences` record** (§7); cleared (memory + persisted record) only on a terminal outcome: `success`, `failed`, or a user-confirmed abandon. An amount change clears it only when no attempt is in flight/unresolved.
- `pendingPaymentId` (nullable) — set on `RechargeRequested` / restored from `wallet.pendingRecharge` on `WalletStarted`; part of the persisted record.
- `props` includes all of the above.

**Transformers:** `RechargeRequested`, `RechargeGatewaySucceeded`, `WalletProvisionRetryRequested` use `droppable()` (ignore new triggers while one is in flight — a payment must not be re-initiated mid-flight). `RechargePollTick` uses `restartable()`.

### Screen — `lib/features/wallet/presentation/wallet_screen.dart`

```
WalletScreen (StatelessWidget)
  └─ BlocProvider(create: WalletBloc(walletRepository: context.read())..add(WalletStarted()))
       └─ _WalletView (StatefulWidget — owns the poll Timer, the RazorpayCheckout wrapper, and shared_preferences read/write)
            ├─ _WalletAppBarRow            (reuse Home's location/logo/bell row widgets if extractable; else local)
            ├─ BlocBuilder → switch on loadStatus:
            │     loading  → _WalletLoadingSkeleton   (mirror catalog_screen._LoadingSkeleton)
            │     failed   → _WalletLoadError(onRetry)
            │     loaded   → _WalletBody:
            │        ├─ _BalanceCard(balance, status, onTopUp, onPassbook)
            │        ├─ _ViewAllTransactionsLink()
            │        ├─ _QuickTopUp(selected, onSelect)
            │        ├─ _PaymentMethods(selected, onSelect)
            │        └─ (bottom, in a SafeArea) _ProceedButton(enabled, loading, amountLabel, onTap)
            └─ BlocListener → rechargeStatus:
                  creatingOrder/awaitingGateway → drive the CTA spinner / open the Razorpay sheet
                  confirming/pending            → show _PendingBanner + start poll Timer
                  success                       → _SuccessSheet, stop Timer, persist method, clear wallet.pendingRecharge
                  failed                        → _ErrorCard(message, onRetry)
```

- `_TopUpAmountSheet` — `showModalBottomSheet`, returns `int?` amountPaise; validation inline.
- `RazorpayCheckout` — thin wrapper: `Future<RazorpayResult> open(RazorpayOptions)` where `RazorpayResult` is `success | failed | dismissed`. Real impl wraps `Razorpay()` + its event callbacks; a `FakeRazorpayCheckout` is injected in widget tests. The wrapper is created in `_WalletView` and disposed with the state.

### Repository — `lib/features/wallet/data/wallet_repository.dart`

```dart
abstract class WalletRepository {
  Future<WalletView> getWallet();                       // GET /wallet/me
  Future<PaymentView> getPayment(String paymentId);     // GET /payments/{id}
  Future<RechargeOrder> createRecharge({
    required int amountPaise,
    required PaymentMethod method,
    required String idempotencyKey,
  });                                                    // POST /payments
  Future<void> confirmRecharge({
    required String paymentId,
    required String razorpayPaymentId,
    required String razorpayOrderId,
    required String razorpaySignature,
  });                                                    // POST /payments/{id}/confirm (MA-126 FR-2 — razorpayOrderId required; 409 ORDER_MISMATCH if it disagrees with the row)
  Future<void> retryProvision();                         // POST /wallet/me/retry
}
```

- `DioWalletRepository(ApiClient)` — talks to `AppConfig.walletBaseUrl` and `AppConfig.paymentBaseUrl` (new entries; see below).
- `FakeWalletRepository` in `test/fakes/` — configurable balance, `createRecharge` result, `confirmRecharge` exception, and a `creditAfter` toggle so a test can simulate the webhook landing between polls.

### Models — `lib/features/wallet/models/`

- `WalletView { walletId, status (WalletStatus), balancePaise (int), currency, rechargeMinPaise (int), rechargeMaxPaise (int) }` + `fromJson`.

## 7. Data Considerations

- **Persisted app data** — two `shared_preferences` keys, both local-only:
  - `wallet.lastPaymentMethod` (`"UPI"` / `"CARD"`) — read on `_WalletView.initState`, written on a successful recharge.
  - `wallet.pendingRecharge` — a small JSON blob `{ idempotencyKey, paymentId, amountPaise, method, createdAtIso }` for the **one** recharge attempt currently in flight or awaiting confirmation. Written on `RechargeRequested` (before the Razorpay sheet opens); read on `WalletStarted` to resume polling (FR-6a); cleared only on a terminal outcome (`CONFIRMED`, `FAILED`, user-confirmed abandon). This is what makes an app kill or a pending-timeout resume the *same* payment instead of allowing a second, separately-chargeable recharge for the same top-up.
- **`StubWalletBalanceRepository` retirement (backward-compat):** MA-120's `ProductConfigBloc` depends on `WalletBalanceRepository.getBalance() → Future<int>` in **whole rupees** (the ≥₹500 gate). This spec:
  1. Keeps the `WalletBalanceRepository` abstraction but adds `DioWalletBalanceRepository` implemented in terms of `WalletRepository.getWallet()` — returning `balancePaise ~/ 100` (whole rupees) to preserve MA-120's contract with zero change to `ProductConfigBloc`.
  2. Swaps `main.dart`'s `const StubWalletBalanceRepository()` for `DioWalletBalanceRepository(ctx.read<WalletRepository>())`.
  3. MA-120's "couldn't check balance" failure path still works — a `getWallet()` failure propagates as the same `ApiException`.
- **Amount handling:** the app collects rupees from the user, converts to paise (`× 100`) once at the boundary, and sends/stores only paise. No floating-point money anywhere.
- **Idempotency key** lifetime: generated per recharge attempt (`RechargeRequested`), held in `WalletBloc` memory **and** mirrored into `wallet.pendingRecharge`. It is reused verbatim across an in-session retry, an app relaunch, and a pending-timeout resume, so Payment Service (MA-126 FR-1) treats them all as the one attempt. It is discarded only when that attempt terminates (`CONFIRMED` / `FAILED` / user-confirmed abandon). A selected-amount change discards it **only** when no attempt is in flight or unresolved — changing the amount is otherwise blocked by the disabled CTA (FR-6a). The server-side reconciliation sweep (MA-126 FR-5) independently settles any payment the app never confirms.

| System | Interaction | Failure behavior |

Show "Payment received — updating your balance…" until resolved. |

## 9. Edge Cases and Failure Modes

| Case | Handling |
|------|----------|
| User taps `Proceed to Payment` twice quickly | `droppable()` on `RechargeRequested` + CTA disabled while `rechargeStatus != idle`. |
| Razorpay success callback fires, then the app is backgrounded before `confirm` completes | `wallet.pendingRecharge` was written before the sheet opened. On resume, `WalletStarted`/`WalletRefreshRequested` restores `pendingPaymentId` from it and resumes `getPayment()` polling (FR-6a); `getWallet()` refreshes the display. Credit shows up via the server webhook regardless; the `confirm` call is a best-effort signal, not required for correctness. |
| App killed during the Razorpay sheet (before or after the user pays) | `wallet.pendingRecharge` survives the kill. Next open: `WalletStarted` resumes polling `getPayment(paymentId)` for that exact payment (FR-6a) — success/failure resolves normally; a still-pending attempt keeps the banner and, past 30 min, offers "Start over". The user is **not** shown a fresh CTA that would create a second Razorpay order for the same top-up. Server reconciliation sweep (MA-126 FR-5) independently settles the payment. |
| `confirm` returns a signature-mismatch error | Enter failure with "We couldn't verify that payment — if money was deducted it'll be refunded or credited shortly"; do not retry automatically. |
| Webhook confirms the payment before `confirm` returns (fast webhook) | `getPayment()` poll returns `CONFIRMED` → success state (a final `getWallet()` refreshes the balance); `confirm`'s own response is ignored if it lands late. |
| `getPayment()` returns `FAILED` while the pending banner is showing | Stop polling, switch to the failure state (FR-8) with `PaymentView.failureReason`, clear `wallet.pendingRecharge`; balance unchanged. |
| Pending UPI never resolves within the 20s in-session window | Non-blocking `_PendingBanner` stays on the balance card; the in-session poll stops but `wallet.pendingRecharge` is retained and the CTA stays disabled for this attempt. A pull-to-refresh or re-open resumes `getPayment()` polling (FR-6a). Past 30 min, a "Start over" action appears. No error shown. |
| `rechargeMax` entered exactly | Allowed (`<=`). `rechargeMin` exactly → allowed (`>=`). |
| Custom amount with leading zeros / spaces | Trimmed and parsed; `"007"` → ₹7 → fails min. |
| Wallet `status == CREATING` on open, becomes `ACTIVE` while the screen is open | A `WalletRefreshRequested` (pull-to-refresh) picks it up; no auto-poll for provision status in this screen (MA-1's success screen owns that). |
| Two devices recharge simultaneously (or a refund / cashback of the same amount lands mid-poll) | Each device polls its **own** `paymentId` via `getPayment()`; success is per-payment and is **never** inferred from the shared wallet balance. Both credits apply; each device's screen resolves on its own payment's `CONFIRMED`. No false positive from a same-value credit. |
| `RAZORPAY_KEY_ID` empty in a build | `RazorpayCheckout.open` throws a guarded `StateError` caught by the bloc → failure state "Payments aren't configured in this build". (Prevents a confusing Razorpay SDK error.) |
| Network drops mid-`POST /payments` | `ApiException` → inline error, CTA restored, same idempotency key retained for retry. |

## 10. Testing Strategy

### Unit — `WalletBloc` (`test/features/wallet/bloc/wallet_bloc_test.dart`)

- `WalletStarted` populates balance/status/bounds from `getWallet()`; a failure → `loadStatus.failed` + message.
- `status != ACTIVE` → `Proceed to Payment` gate reflected in state; `WalletProvisionRetryRequested` calls `retryProvision()`.
- `QuickAmountSelected` / `CustomAmountEntered` are mutually exclusive; when no attempt is in flight they also clear a held idempotency key; `AmountCleared` resets. While a pending attempt is unresolved, all three are no-ops.
- `RechargeRequested` generates an idempotency key, writes `wallet.pendingRecharge`, calls `createRecharge` once, moves to `awaitingGateway`; a second `RechargeRequested` while in flight is dropped.
- `RechargeGatewaySucceeded` calls `confirmRecharge` with `paymentId` + `razorpayPaymentId` + `razorpayOrderId` + `razorpaySignature` and moves to `confirming`/`pending`; a `confirmRecharge` failure still moves to `pending` (not `failed`) when the gateway itself succeeded.
- `RechargeGatewayFailed` → `failed` with the description, `wallet.pendingRecharge` cleared; **Retry** re-dispatches with the **same** idempotency key (assert `createRecharge` called twice with an identical key).
- Poll: given `getPayment` returns `CONFIRMED` on the 2nd tick → `success` (and a final `getWallet` is issued); given `getPayment` stays `CONFIRMING` **and** `getWallet` shows a +sameAmount rise from an unrelated credit → **stays `pending`** (no false-positive success); given `getPayment` returns `FAILED` → `failed` + `wallet.pendingRecharge` cleared; given nothing resolves within the cutoff → stays `pending`, timer cancelled, `wallet.pendingRecharge` retained.
- Resume: with `wallet.pendingRecharge` seeded, `WalletStarted` enters `pending` and polls `getPayment(paymentId)`; a seeded record older than 30 min surfaces the "Start over" action; `PendingRechargeAbandoned` clears the record and re-enables the CTA.
- `RechargeGatewayDismissed` → back to `idle`, no error, `wallet.pendingRecharge` cleared (no payment was completed).

## 11. Risks and Trade-offs

- **`confirm` vs webhook race** — the app calls `POST /payments/{id}/confirm` after the Razorpay success callback, but the authoritative credit is the server webhook. Trade-off: the app cannot *know* the credit happened without polling `getPayment()`. Mitigation: bounded polling + a graceful non-blocking pending banner; the money is never at risk because the server settles it regardless. Accepted.
- **Holding the CTA for an unresolved pending attempt** — after a 20s pending-timeout the CTA does *not* re-enable for a new amount (it did in an earlier draft); the user waits for resolution or explicitly "Start over" after 30 min. Trade-off: a slightly stickier UI for a genuinely-pending UPI collect, in exchange for making a second, separately-chargeable recharge for the same top-up impossible (the `wallet.pendingRecharge` record + reused idempotency key). Accepted — double-charge protection outranks letting the user immediately retry a different amount.
- **New dependency `razorpay_flutter`** — adds native config surface (iOS URL schemes, Android ProGuard) and no web support. Mitigation: `RazorpayCheckout` wrapper + `kIsWeb` fallback (FR-10); the wrapper also keeps the SDK out of bloc/widget tests. Accepted — it is the standard Razorpay mobile integration.
- **Backend not yet implemented** — this spec is drafted and buildable against `FakeWalletRepository`, but end-to-end verification waits on MA-126 + MA-127. Mitigation: `WALLET_ENABLED` flag ships the tab dark; the implementation-plan sequences mobile after (or in parallel with a fake) the services. Same precedent as MA-120/MA-123.
- **Polling for the credit** rather than a push/websocket — simplest, acceptable for a ~seconds-long UPI capture; a future `WalletCredited`-driven push (MA-103) can replace it without changing this screen's contract.
- **Two base URLs (`walletBaseUrl`, `paymentBaseUrl`)** rather than one BFF path — matches the current per-service `AppConfig` convention (`cartBaseUrl`, `pricingBaseUrl`); a real API Gateway later collapses them without app changes.
