## 2. Problem Statement

Wallet Service (MA-127) can only **credit** a wallet (`credit_recharge`, driven by a
`PaymentConfirmed{purpose: WALLET_RECHARGE}` event). MA-25's subscription auto-debit needs
the wallet to also **debit** — moving money out to pay for a subscription-generated order —
with the exact same correctness bar the credit side already has: exactly-once, an immutable
ledger entry, never a negative balance, and a clear signal back to the caller (Order Service)
when the balance is insufficient so it can fail that order rather than silently losing money
or double-charging on retry.

The domain model already anticipates this: `LedgerType.ORDER_DEBIT` exists as an enum value
and `LedgerEntry.amount_paise`'s own doc comment says "signed: +credit / -debit" — this spec
is the first thing to actually use them.

Expected outcome: Order Service can call one idempotent operation to charge a wallet for an
order, and get back either a confirmed debit or a well-typed "insufficient balance" result —
never an ambiguous or retryable-into-double-charge outcome.

## 3. Scope

### In scope

- `POST /wallet/internal/debit` — an internal-only endpoint (network-level auth, matching
  Inventory Service's own internal/serviceability-check precedent — no public exposure)
  that debits a wallet by exactly `amountPaise` for a given `orderId`, idempotent on
  `orderId`.
- Insufficient-balance handling: returns a typed `INSUFFICIENT_BALANCE` result (not an
  exception the caller has to guess the meaning of) rather than debiting into a negative
  balance.
- A new ledger entry per debit: `type: ORDER_DEBIT`, negative `amountPaise`, `ref` unique on
  the order id (mirrors `credit_recharge`'s `ref` on the Razorpay payment id) — exactly-once
  under retry.
- Emits `WalletLowBalance` (per `milkful-well-architected.md` §7.1) when a debit succeeds but
  leaves the balance under a configurable threshold, **and** when a debit is refused for
  insufficient balance — both are "the customer should know their wallet needs money" signals.
  No consumer exists yet (Notification Service, MA-103, is out of scope for this story) —
  emitted anyway, matching this codebase's established "emit for a future consumer" pattern
  (e.g. `WalletCredited`).
- `GET /wallet/internal/balance` — a lightweight internal read Order Service can use for a
  pre-flight balance check before attempting a debit (optional fast-path; the debit call
  itself is still the authoritative, race-safe operation).

### Out of scope

- Any public-facing (mobile-app-callable) debit endpoint — debits are always internal,
  triggered by Order Service, never directly by the customer.
- Refunds (`LedgerType.REFUND`) — MA-32 (Order Cancellation) territory.
- Auto-recharge-on-low-balance — NSMB extra, deferred (matches MA-125's own precedent of
  deferring this exact item).
- Real push/SMS delivery of the low-balance signal — Notification Service (MA-103) doesn't
  exist; this spec only emits the event.
- Changing `credit_recharge`'s own behavior — untouched.

## 4. Functional Requirements

### FR-1: Debit endpoint

- `POST /wallet/internal/debit` — body `{ userId, orderId, amountPaise, correlationId? }`.
  All fields required except `correlationId`. `amountPaise` must be a positive integer
  (paise, matching every other money field in this codebase).
- Idempotency key is `orderId` itself (one order is debited at most once — no separate
  `Idempotency-Key` header needed, unlike Payment Service's `POST /payments`, since an order
  id is already a stable, caller-generated identifier for exactly this operation).
- On the **first** call for a given `orderId`: locks the wallet row (`SELECT ... FOR UPDATE`,
  same pattern as `credit_recharge`), checks `balance_paise >= amountPaise`:
  - **Sufficient** → writes a `ORDER_DEBIT` ledger entry (`amount_paise = -amountPaise`,
    `ref = f"order:{orderId}"`), decrements the wallet balance, enqueues a `WalletDebited`
    outbox event (new — Order Service consumes it to confirm the order; see MA-132 FR-1),
    all in the same transaction as `credit_recharge` uses. Returns
    `{ status: "DEBITED", balanceAfterPaise }`.
  - **Insufficient** → no ledger entry, no balance change. Enqueues `WalletLowBalance`
    (`reason: "DEBIT_REFUSED"`). Returns `{ status: "INSUFFICIENT_BALANCE",
    balancePaise, requiredPaise }` (a normal 200 response, not an error — the caller
    (Order Service) has well-defined behavior for this outcome, it isn't exceptional).
- On a **retried** call for an `orderId` already debited: returns the same `{ status:
  "DEBITED", balanceAfterPaise }` from the existing ledger entry — verbatim replay, no
  second debit (mirrors Payment Service's `POST /payments` idempotent-replay branch).
- On a **retried** call for an `orderId` previously refused (`INSUFFICIENT_BALANCE`): re-runs
  the balance check fresh (the wallet may have been recharged since) rather than replaying
  the stale refusal — this is the one case where "idempotent" means "safe to retry with a
  fresh answer," not "return the cached answer," because the whole point of a retry here is
  that circumstances may have changed. Guarded by the same `ref` scheme: a `DEBITED` result
  is permanently replayed, an `INSUFFICIENT_BALANCE` result is never persisted as a ledger
  row, so there is nothing to "replay" for it.
- `userId` on the request must match the wallet resolved for `orderId`'s owner — a mismatch
  is a `400 ORDER_USER_MISMATCH` (defensive; Order Service is the only caller and always
  passes the correct pair, but the check exists so a future integration bug fails loudly
  rather than silently debiting the wrong wallet).

### FR-2: Low-balance signal

- After any debit attempt (successful or refused) that leaves `balance_paise` under
  `WALLET_LOW_BALANCE_THRESHOLD_PAISE` (config, default ₹100 = `10000`), enqueue
  `WalletLowBalance{ userId, walletId, balancePaise, thresholdPaise, reason }` where
  `reason` is `"LOW_AFTER_DEBIT"` or `"DEBIT_REFUSED"`.
- At most one `WalletLowBalance` event per debit attempt (not per subsequent read) — this is
  a point-in-time signal, not a standing alert state Wallet Service tracks.

### FR-3: Internal balance read

- `GET /wallet/internal/balance?userId=` — returns `{ balancePaise, status }` (no ledger
  detail). Same network-level-only auth as FR-1. A convenience for Order Service to short-
  circuit an order it can already tell will fail, before spending a debit call on it — never
  the sole gate (a `TOCTOU` gap between this read and the actual debit is expected and
  handled correctly by FR-1's own row lock; this endpoint is an optimization, not a
  correctness dependency).

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| **Reliability** | A wallet balance can never go negative. Exactly one ledger entry per `orderId` ever, regardless of retry count — enforced by the `ref` UNIQUE constraint, same mechanism `credit_recharge` already uses. |
| **Consistency** | Ledger entry write, balance update, and outbox insert happen in one transaction — same pattern as `credit_recharge`; no separate reconciliation sweep needed since this is a synchronous, caller-driven operation (unlike Payment Service's webhook-driven confirm). |
| **Performance** | `POST /wallet/internal/debit` p99 < 200ms (internal, same-VPC caller) — matches this codebase's other internal-call NFRs (e.g. Wallet's own `wallet_limits_client` caller-side expectation in Payment Service). |
| **Security** | Internal-only network exposure (no public route, no Cognito JWT — matches Inventory Service's internal-endpoint precedent, security-group-restricted). |
| **Observability** | Structured-log metrics: `wallet.debit_succeeded`, `wallet.debit_refused_insufficient_balance`, `wallet.low_balance_signal_emitted` — this codebase's established CloudWatch substitute. |

## 6. Technical Design

### Domain — `wallet_service.py`

```python
class DebitResult(StrEnum):
    DEBITED = "DEBITED"
    INSUFFICIENT_BALANCE = "INSUFFICIENT_BALANCE"

@dataclass
class DebitOutcome:
    result: DebitResult
    balance_paise: int          # balance after (DEBITED) or current (INSUFFICIENT_BALANCE)
    required_paise: int | None  # set only for INSUFFICIENT_BALANCE

def debit_for_order(
    self, *, user_id: str, order_id: str, amount_paise: int, correlation_id: str | None,
) -> DebitOutcome: ...
```

Mirrors `credit_recharge`'s shape: a domain method wrapping one repository call that does the
lock-check-write-outbox sequence in a single transaction (the same pattern MA-125 round-2
review flagged as correct and MA-126's own review-fix commit reinforced — hold the lock
across the whole check-then-write, never release-then-write).

### Adapter — `wallet_repository.py`

New `debit_for_order(...)` method alongside the existing `credit_recharge(...)`:
1. `SELECT ... FOR UPDATE` the wallet row.
2. If an `ORDER_DEBIT` ledger row with `ref = f"order:{order_id}"` already exists → return
   its `balance_after_paise` as a `DEBITED` replay (no new write).
3. Else if `balance_paise < amount_paise` → return `INSUFFICIENT_BALANCE` (no write).
4. Else → insert the ledger row, update `wallets.balance_paise`, insert the `WalletDebited`
   outbox row, insert a `WalletLowBalance` outbox row if the post-debit balance is under
   threshold — all in the transaction opened at step 1.

### New outbox event — `WalletDebited`

Added to `shared/events/` alongside the existing `PaymentConfirmed`/`PaymentFailed`/
`WalletCredited` schemas:

```json
{
  "eventId": "uuid", "occurredAt": "iso8601", "correlationId": "string",
  "userId": "string", "walletId": "string", "orderId": "string",
  "amountPaise": "integer", "balanceAfterPaise": "integer"
}
```

### New outbox event — `WalletLowBalance`

```json
{
  "eventId": "uuid", "occurredAt": "iso8601",
  "userId": "string", "walletId": "string",
  "balancePaise": "integer", "thresholdPaise": "integer",
  "reason": "LOW_AFTER_DEBIT | DEBIT_REFUSED"
}
```

### Handlers — `internal_handlers.py`

Add `POST /wallet/internal/debit` and `GET /wallet/internal/balance` alongside the existing
`GET /wallet/internal/limits` — same file, same internal-only auth convention already
established there.

## 7. Data Considerations

- No schema migration needed — `ledger_entries.type` already accepts `ORDER_DEBIT` (an enum
  value with no DB-level CHECK constraint restricting it further beyond what
  `LedgerType` already declares), and `amount_paise` is already a signed `BigInteger`.
- `WALLET_LOW_BALANCE_THRESHOLD_PAISE` — new `Settings` field, default `10000` (₹100).
- Money: integer paise throughout, matching every other service in this codebase — no
  floats anywhere in this spec's data path.

## 8. Integration Considerations

| System | Interaction | Failure behavior |
|--------|-------------|-------------------|
| **Order Service (MA-132)** | Calls `POST /wallet/internal/debit` synchronously after creating an order row in `CREATED` status | A `DEBITED` result confirms the order; `INSUFFICIENT_BALANCE` fails it (MA-132's own FR defines the resulting order status); a transport failure (5xx/timeout) is retried by Order Service using the same `orderId` — safe because of FR-1's idempotency. |
| **Notification Service (MA-103, not built)** | Would consume `WalletLowBalance` | No consumer today — event is emitted and sits unread on its SQS queue's own retention window; this is intentional and matches `WalletCredited`'s own precedent. |
| **EventBridge** | `WalletDebited`/`WalletLowBalance` published via the same transactional-outbox publisher already running for `WalletCredited` | Outbox publish-lag metric already exists (`outbox.publish_lag_seconds`) and covers these new event types for free — no new publisher code needed, just new outbox rows. |

## 9. Edge Cases and Failure Modes

| Case | Handling |
|------|----------|
| Two concurrent debit calls for the same `orderId` (Order Service's own retry racing a slow first attempt) | The row lock (FR-1) serializes them; the second sees the first's ledger row already present and replays `DEBITED` — no double debit. |
| Debit call arrives for a wallet in `CREATING`/`FAILED` status (not yet `ACTIVE`) | Refused as `INSUFFICIENT_BALANCE`-shaped is wrong semantically — returns a distinct `WALLET_NOT_ACTIVE` error instead (Order Service treats this the same as a hard order failure, not a retryable one). |
| `amountPaise` is zero or negative | `400 INVALID_AMOUNT` — never silently accepted. |
| Balance exactly equals `amountPaise` | Allowed (`>=`), resulting balance is exactly `0` — not itself an error, though it will trip the low-balance signal (FR-2) if threshold `> 0`. |
| Wallet recharged between an `INSUFFICIENT_BALANCE` refusal and a retry of the same `orderId` | Handled correctly by design (FR-1) — the retry re-checks fresh, since no ledger row was ever written for the refusal. |
| `WalletLowBalance` outbox insert fails independently of the debit itself | Never blocks the debit — same "outer retry, not a blocking dependency" pattern this codebase already uses for `PaymentFailed`'s outbox insert relative to its own state transition. |

## 10. Testing Strategy

### Unit — `tests/unit/domain/test_wallet_service.py` (extends existing suite)

- `debit_for_order` with sufficient balance → `DEBITED`, correct `balance_after_paise`,
  ledger entry `amount_paise` negative, `WalletDebited` outbox row present.
- `debit_for_order` with insufficient balance → `INSUFFICIENT_BALANCE`, no ledger row, no
  balance change, `WalletLowBalance{reason: DEBIT_REFUSED}` outbox row present.
- Retried `debit_for_order` (same `orderId`, already `DEBITED`) → replays the same
  `balance_after_paise`, no second ledger row, no second outbox row.
- Retried `debit_for_order` (same `orderId`, previously `INSUFFICIENT_BALANCE`, wallet
  recharged since) → re-evaluates fresh, succeeds if now sufficient.
- Post-debit balance under threshold → `WalletLowBalance{reason: LOW_AFTER_DEBIT}` emitted;
  above threshold → not emitted.
- Wallet not `ACTIVE` → `WALLET_NOT_ACTIVE`, no ledger row.
- `amountPaise <= 0` → `INVALID_AMOUNT`, no repository call.

### Integration — `tests/integration/test_wallet_http.py` (extends existing suite)

- `POST /wallet/internal/debit` full round trip against the real HTTP app + SQLite-backed
  repository: sufficient balance, insufficient balance, replay.
- `GET /wallet/internal/balance` returns the current balance without mutating anything.

### Acceptance

- `pytest` green in `services/wallet`; `ruff check` clean.
- A `credit_recharge` (MA-127) followed by a `debit_for_order` for a smaller amount produces
  a wallet balance and ledger history consistent with both operations (no interaction bugs
  between the two ledger types sharing one table).

## 11. Risks and Trade-offs

- **Synchronous debit call, not event-driven** — unlike `credit_recharge` (event-driven off
  `PaymentConfirmed`), Order Service calls this endpoint directly and waits for the result.
  Accepted: the debit's own correctness (row lock, `ref` uniqueness) doesn't depend on this
  choice, and a synchronous call is simpler for Order Service to reason about than another
  async confirm-then-poll cycle stacked on top of the one it already has for creating the
  order itself. If a future story finds this line too chatty, it can move to event-driven
  without changing the debit's own idempotency contract.
- **No refund path in this spec** — a debited order that later needs to be cancelled has no
  symmetric "credit it back" operation yet. Accepted as MA-32's problem, explicitly, not
  silently.
- **Threshold is global, not per-user-configurable** — matches MA-125's own wallet NFRs
  precedent (no per-user config surface exists anywhere in this app yet).

## 12. Open Questions

- Exact `WALLET_LOW_BALANCE_THRESHOLD_PAISE` default (₹100 proposed) — confirm with product;
  trivial to change, not a design-affecting parameter.
- Should `WalletLowBalance` also fire from `GET /wallet/internal/balance` polling, or only
  from an actual debit attempt? This spec says only from a debit attempt (a poll is read-only
  and shouldn't have a side effect) — flagging in case Order Service's own daily-run design
  (MA-132) wants an earlier warning before attempting a doomed debit.
