## 2. Problem Statement

`services/order/` doesn't exist. Subscription Service (MA-131) can now decide *what's due*
(`SubscriptionOrderDue`) but nothing turns that into a real, payable, trackable Order. This
spec is the first real Order Service: it consumes a due-subscription signal, creates a dated
Order, gets it paid via Wallet Service's new debit capability (MA-130), and confirms or fails
it — the minimum viable slice of the platform's full envisioned "Order Saga"
(Reserve→Charge→Confirm), deliberately without the Reserve (inventory-hold) step, because
Inventory Service has no stock-quantity model anywhere in this platform to reserve against.

Expected outcome: every due subscription reliably becomes exactly one Order per day, paid
exactly once, with a status the customer's app can read.

## 3. Scope

### In scope

- Consume `SubscriptionOrderDue` (from `order-events-q`, per `milkful-messaging.drawio`) and
  create one `Order` row per event, idempotent on `(subscriptionId, deliveryDate)`.
- Call Wallet Service's `POST /wallet/internal/debit` (MA-130) synchronously to pay for the
  order at creation time.
- Order status lifecycle: `CREATED` → `CONFIRMED` (debit succeeded) or `PAYMENT_FAILED`
  (debit refused for insufficient balance) or `FAILED` (unexpected error, retryable).
- Emit `OrderConfirmed` / `OrderCancelled`-shaped failure signal (`OrderPaymentFailed`, new —
  see §6) per `milkful-messaging.drawio`'s producer list, for Wallet Service's own ledger
  read-model consistency and any future consumer (Notification, Reporting).
- `GET /orders/me` / `GET /orders/{id}` — read APIs for the mobile app to show order status
  (MA-133's "next delivery" card links a delivered/failed indicator here, minimally).

### Out of scope

- **The full checkout-driven Order Saga** (Reserve→Charge→Confirm for a one-time cart
  purchase) — `cart-checkout-cta` stays disabled; this spec only ever creates orders from
  `SubscriptionOrderDue`. Activating one-time checkout through this same service later is
  additive, not a rework of what's built here.
- Inventory reservation/stock decrement of any kind — no stock-quantity model exists to
  reserve against (confirmed reading `services/inventory` directly, MA-131 §2 repeats the
  same finding).
- Delivery assignment/tracking (`DeliveryStatusChanged` consumption) — Delivery Service
  (MA-102) territory, not built or consumed here.
- Order cancellation by the customer (MA-32) — this spec creates and confirms/fails orders;
  it does not expose a cancel endpoint.
- Refunds — a `PAYMENT_FAILED` order was never charged (see FR-2), so there's nothing to
  refund; a `CONFIRMED` order has no cancel path yet (previous bullet), so no refund trigger
  exists in this pass either.
- Invoice/GST generation (MA-38).

## 4. Functional Requirements

### FR-1: Consume `SubscriptionOrderDue`

- Polls `order-events-q` (SQS, per the messaging doc). For each message: parse
  `{ subscriptionId, userId, productId, quantity, deliveryDate, slotId, correlationId }`.
- Idempotency: a UNIQUE constraint on `(subscription_id, delivery_date)` in the `orders`
  table. A redelivered/duplicate message for a pair already materialized is acknowledged
  (deleted from the queue) without creating a second order or re-attempting payment —
  matches this codebase's established idempotent-consumer pattern (e.g. Wallet's own
  `UserRegistered` consumer).
- On receipt, fetches the product's current price from Catalog Service
  (`GET /products/{id}`) — the order's `amountPaise` is `price * quantity` at
  materialization time, not a price frozen when the subscription was created (matches how a
  recurring subscription is expected to track current pricing, absent any evidence the
  ticket wants price-locking).
- Creates the `Order` row in `CREATED` status, then immediately proceeds to FR-2 in the same
  logical operation (no separate "confirm later" step for this synchronous slice — unlike
  Payment Service's webhook-driven confirm, there's no external gateway round-trip here).

### FR-2: Pay via Wallet debit

- Calls `POST /wallet/internal/debit` (MA-130 FR-1) with `{ userId, orderId, amountPaise,
  correlationId }`.
- `DEBITED` response → order status → `CONFIRMED`, `confirmedAt` set, emits `OrderConfirmed`.
- `INSUFFICIENT_BALANCE` response → order status → `PAYMENT_FAILED`, `failureReason` set from
  the response's `balancePaise`/`requiredPaise`, emits `OrderPaymentFailed` (new event,
  distinct from `OrderCancelled` — this order was never confirmed, so there's nothing to
  "cancel," only to report as never-started).
- `WALLET_NOT_ACTIVE` response → same `PAYMENT_FAILED` treatment, different `failureReason`.
- A transport failure/timeout calling Wallet → order stays `CREATED`, message is **not**
  acked (left for SQS redelivery) — the retry is safe because of MA-130 FR-1's own
  idempotency on `orderId` (a debit call retried with the same `orderId` either replays a
  prior `DEBITED` result or re-evaluates fresh if it was never persisted).

### FR-3: Order read APIs

- `GET /orders/me?subscriptionId=&limit=&cursor=` — keyset-paginated list, newest first
  (mirrors Wallet Service's own transaction-list pagination convention).
- `GET /orders/{id}` — full detail: product, quantity, amount, status, delivery date,
  failure reason if applicable.

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| **Reliability** | Exactly one order per `(subscriptionId, deliveryDate)` ever, regardless of message redelivery count — UNIQUE constraint enforced at the DB level, not just application logic. |
| **Consistency** | Order creation + Wallet debit call + status update happen as one logical unit per message; a crash between "order created" and "debit called" leaves the order `CREATED` and the next redelivery (or a reconciliation sweep — see Risks) picks it up rather than silently stalling forever. |
| **Idempotency** | Consumer-level (message dedupe) and DB-level (UNIQUE constraint) — two independent guards, matching this codebase's now-established "don't rely on just one layer" lesson from Payment Service's own review-fix history (the lock-across-the-whole-sequence fix from PR #19). |
| **Performance** | One order materialization (Catalog price lookup + Wallet debit call) p99 < 500ms — dominated by the two synchronous internal calls. |
| **Observability** | Structured-log metrics: `order.created`, `order.confirmed`, `order.payment_failed`, `order.materialization_duration_ms`. |

## 6. Technical Design

### Domain model

```python
class OrderStatus(StrEnum):
    CREATED = "CREATED"
    CONFIRMED = "CONFIRMED"
    PAYMENT_FAILED = "PAYMENT_FAILED"
    FAILED = "FAILED"

@dataclass
class Order:
    id: str
    user_id: str
    subscription_id: str
    product_id: str
    quantity: int
    amount_paise: int
    delivery_date: date
    status: OrderStatus
    failure_reason: str | None
    created_at: datetime
    confirmed_at: datetime | None
```

### Consumer flow (`order_events_consumer.py`)

```
receive SubscriptionOrderDue
  -> if (subscription_id, delivery_date) already has an Order row: ack, done   # FR-1 dedupe
  -> fetch product price from Catalog (GET /products/{id})
  -> insert Order(status=CREATED) + outbox row for later OrderConfirmed/Failed, one transaction
  -> call POST /wallet/internal/debit(userId, orderId, amountPaise, correlationId)
       -> DEBITED: update Order.status=CONFIRMED, enqueue OrderConfirmed outbox row
       -> INSUFFICIENT_BALANCE / WALLET_NOT_ACTIVE: update Order.status=PAYMENT_FAILED,
          enqueue OrderPaymentFailed outbox row
       -> transport error: leave Order.status=CREATED, do NOT ack the SQS message
  -> ack SQS message only after the above completes (CONFIRMED or PAYMENT_FAILED)
```

The insert-then-call-then-update sequence intentionally does **not** try to wrap the Wallet
HTTP call inside the same DB transaction as the initial insert (an external HTTP call inside
a DB transaction is a latency/lock-hold anti-pattern this codebase avoids elsewhere too) —
instead, `(subscription_id, delivery_date)` UNIQUE at insert time is what makes re-entry
after a crash between insert and debit-call safe: the redelivered message finds its own
`CREATED` row and resumes from the debit-call step rather than re-inserting.

### New event — `OrderPaymentFailed`

```json
{
  "eventId": "uuid", "occurredAt": "iso8601", "correlationId": "string",
  "orderId": "string", "userId": "string", "subscriptionId": "string",
  "amountPaise": "integer", "reason": "INSUFFICIENT_BALANCE | WALLET_NOT_ACTIVE"
}
```

### API surface

| Method | Path | FR |
|--------|------|----|
| GET | `/orders/me` | FR-3 |
| GET | `/orders/{id}` | FR-3 |

(No public write endpoints — every order in this spec's scope is consumer-created from
`SubscriptionOrderDue`, never a direct client `POST`.)

## 7. Data Considerations

- New Aurora cluster/schema (`orders`) — first migration, `orders` table with the UNIQUE
  `(subscription_id, delivery_date)` constraint as its core correctness guarantee, plus a
  standard `outbox` table.
- Money: integer paise throughout, matching every other service.
- `amount_paise` is snapshotted at materialization time (FR-1) — never recomputed later, so
  a subsequent price change never retroactively alters an already-created order's amount.

## 8. Integration Considerations

| System | Interaction | Failure behavior |
|--------|-------------|-------------------|
| **Subscription Service (MA-131)** | Consumes `SubscriptionOrderDue` via `order-events-q` | Malformed/schema-invalid message → caught explicitly (matches the exact class of bug PR #19's review found and fixed in Wallet's own consumer — `jsonschema.ValidationError` must be caught, not left to crash the poll loop), left for DLQ. |
| **Catalog Service** | `GET /products/{id}` for current price at materialization time | Unavailable → order materialization fails closed (message not acked, redelivered later) rather than guessing a price. |
| **Wallet Service (MA-130)** | `POST /wallet/internal/debit` | See FR-2 — every outcome (DEBITED, INSUFFICIENT_BALANCE, WALLET_NOT_ACTIVE, transport failure) has defined handling; no outcome is left ambiguous. |
| **Mobile app (MA-133)** | `GET /orders/me`, `GET /orders/{id}` | Standard `ApiException` envelope. |
| **EventBridge** | Publishes `OrderConfirmed`/`OrderPaymentFailed` | Transactional outbox, same pattern as every other service. |

## 9. Edge Cases and Failure Modes

| Case | Handling |
|------|----------|
| `SubscriptionOrderDue` redelivered after the order already reached `CONFIRMED` | FR-1's UNIQUE-constraint check finds the existing row, acks immediately, no second debit attempt (the debit call itself is also independently idempotent on `orderId` — belt and suspenders, matching MA-130's own design). |
| Order stuck in `CREATED` because the process crashed between insert and the Wallet call, and the SQS message's visibility timeout hasn't yet expired | Genuinely stuck until either the visibility timeout expires (natural SQS redelivery) or an operational reconciliation sweep runs (see Risks — same shape as Payment Service's own `reconcile_once`, not built in this pass). |
| Catalog reports the product no longer exists (deleted) | `PAYMENT_FAILED`-shaped, `reason: "PRODUCT_UNAVAILABLE"` — the subscription itself is not auto-stopped by this service (that's a customer/ops decision, not implied by the ticket). |
| Two `SubscriptionOrderDue` events for the same subscription but different `deliveryDate`s arrive out of order | No conflict — the UNIQUE constraint is per `(subscription_id, delivery_date)` pair, not a global per-subscription serialization; each date is independent. |
| Wallet debit succeeds but the subsequent `OrderConfirmed` outbox insert fails | Never rolled back — the same transaction covers both the status update and the outbox insert (unlike the insert-then-call sequence in §6, this second half **is** one transaction, since it's a DB-only sequence with no external call in the middle). |

## 10. Testing Strategy

### Unit — `tests/unit/domain/test_order_service.py`

- Fresh `SubscriptionOrderDue` → order created, Wallet debit called with the right
  `orderId`/`amountPaise`, `DEBITED` → `CONFIRMED` + `OrderConfirmed` enqueued.
- `INSUFFICIENT_BALANCE` from Wallet → `PAYMENT_FAILED` + `OrderPaymentFailed` enqueued,
  reason recorded.
- Redelivered message for an already-`CONFIRMED` `(subscriptionId, deliveryDate)` → no
  second debit call, no duplicate outbox row (mock the Wallet client and assert call count).
- Wallet transport failure (simulated timeout) → order stays `CREATED`, message not acked.
- Catalog unavailable at materialization time → order not created, message not acked.

### Integration — `tests/integration/test_order_flow.py`

- End-to-end: seed a `SubscriptionOrderDue`-shaped SQS message → consumer processes it →
  `FakeWalletClient` returns `DEBITED` → assert `orders` table row is `CONFIRMED` and an
  `OrderConfirmed` event lands on the mocked EventBridge bus, schema-validated.
- Same flow with `FakeWalletClient` returning `INSUFFICIENT_BALANCE` → `PAYMENT_FAILED` +
  `OrderPaymentFailed`, schema-validated.

### Acceptance

- `pytest` green; `ruff check` clean.
- `GET /orders/me` reflects both a `CONFIRMED` and a `PAYMENT_FAILED` order correctly after
  the above flows.

## 11. Risks and Trade-offs

- **No reconciliation sweep for orders stuck in `CREATED`** — Payment Service has one
  (`reconcile_once`) because its `CONFIRMING` state can persist for real-world reasons
  (webhook latency); this service's `CREATED`→terminal transition is synchronous and should
  resolve in milliseconds under normal operation, so a stuck row implies a genuine crash, not
  a routine timing gap. Accepted for this pass; flagged as a natural addition once real
  operational experience shows it's needed (same "build the sweep when you have evidence you
  need it" restraint MA-126 itself didn't take, but that service's external-gateway
  dependency made the sweep obviously necessary from day one — this service's all-internal
  dependency chain does not obviously need one yet).
- **Price snapshotted at materialization, not subscription-creation** — a customer sees
  today's price when subscribing but may be charged a different (subsequently changed)
  price on a future delivery. Accepted: no evidence in the ticket or mock that price-locking
  is expected, and locking would require Order Service to track a price history it has no
  other reason to own.
- **Scoped away from the full Order Saga** — the eventual one-time-checkout flow will need
  its own spec to add the Reserve step and wire `cart-checkout-cta`; this spec's `Order`
  table/model is designed to be additive to that (no field here assumes "subscription-
  originated" is the only possible order source — `subscription_id` is a normal foreign key,
  not baked into every code path as if no other origin could exist).

## 12. Open Questions

- Should `PRODUCT_UNAVAILABLE` auto-pause the affected subscription rather than just failing
  one day's order? Left as manual/ops-driven for this pass — no ticket language supports an
  automatic pause.
- Retry/backoff count before a genuinely failed Wallet call is treated as `FAILED` (vs.
  indefinite SQS redelivery) — deferred to implementation, following this codebase's
  existing `retry.py` convention (already shared, per MA-24's own consolidation).
