## 2. Problem Statement

Nothing in this platform persists a recurring order intent beyond a single Cart line item.
`services/cart`'s `frequency` field only describes *the next* checkout, and Cart itself has
no checkout/order path at all yet (`cart-checkout-cta` is permanently disabled). MA-25 needs
a **standing Subscription entity** that outlives the cart: once created, it drives its own
future — a **daily scheduled run** decides which subscriptions are due today, respecting
each one's frequency, pause state, skip requests, and a platform-wide cut-off time, and
signals Order Service (MA-132) to materialize a real Order for each one.

This is also the first place in the platform that needs a schedule richer than Cart's own
`DAILY | ALTERNATE_DAYS` — MA-25's ticket text explicitly asks for weekly and custom-day
patterns, which Subscription Service defines and owns; it does not inherit Cart's narrower
enum.

Expected outcome: a customer creates a subscription once and it runs itself — generating a
correctly-timed order every due day, honoring pauses/skips/edits — until they stop it.

## 3. Scope

### In scope

- Subscription entity: product, quantity, a **Schedule** (daily / alternate days / weekly /
  custom days), start date, preferred delivery slot, status (`ACTIVE`, `PAUSED`, `STOPPED`).
- Lifecycle: **Create** (from a confirmed subscription intent — see §6), **Pause** (a date
  range: `pauseFrom`/`pauseUntil`, or open-ended until explicitly resumed — reconciles the
  mock's single "Vacation Mode" toggle, which is this same operation applied without an end
  date, with the ticket text's date-range requirement), **Resume**, **Stop/Cancel**
  (terminal — no resume from `STOPPED`, a stopped subscription must be recreated).
- **Skip-a-day**: mark exactly one upcoming due date as skipped without pausing the whole
  subscription.
- **Edit** quantity/schedule, enforced against a daily cut-off (an edit made after the
  cut-off for the next due date applies starting from the due date after that — the next
  delivery already "belongs" to the pre-edit schedule).
- **Daily Run**: an EventBridge-Scheduler-triggered job, once per cut-off, that computes
  every subscription due *tomorrow* (see §6 for why tomorrow, not today) and emits one
  `SubscriptionOrderDue` event per due subscription.
- Read APIs the Flutter app (MA-133) needs directly: list my subscriptions, get one, its
  next-delivery date.

### Out of scope

- Product/quantity/frequency/slot *selection UI* — that's MA-133 (Flutter); this spec is the
  API it calls once the customer has made those choices.
- Auto-generating the Order itself, or debiting the Wallet — Order Service (MA-132) and
  Wallet Service (MA-130) own those; this service only decides **what's due** and says so.
- Low-balance alerts, delivery-slot capacity/conflicts, inventory stock checks — other
  services' concerns, not re-validated here.
- Editing a subscription's *product* (swapping Cow Milk for Buffalo Milk) — only
  quantity/schedule are editable in this pass; a product swap requires stopping and
  recreating (simplest correct behavior; no evidence the ticket or mock needs same-
  subscription product swap).
- Multi-item subscriptions (one subscription = one product) — the mock shows one card per
  product; a "subscription bundle" concept isn't implied anywhere.

## 4. Functional Requirements

### FR-1: Create a subscription

- `POST /subscriptions` — body `{ productId, quantity, schedule, startDate, slotId,
  idempotencyKey }`. `schedule` is `{ type: DAILY|ALTERNATE_DAYS|WEEKLY|CUSTOM_DAYS,
  daysOfWeek?: int[] }` — `daysOfWeek` (ISO 1=Mon..7=Sun) required and non-empty for
  `WEEKLY`/`CUSTOM_DAYS` (`WEEKLY` also accepts exactly one day — it's `CUSTOM_DAYS` with a
  UI-level naming distinction, not a different validation rule), absent for `DAILY`/
  `ALTERNATE_DAYS`.
- Idempotent on `idempotencyKey` (same pattern as Payment Service's `POST /payments` and
  Cart's `Idempotency-Key`) — a retried create returns the original subscription, never a
  second one.
- Validates `productId` against Catalog Service (`GET /products/{id}`) — must exist and be
  `subscriptionEligible` (an existing Catalog field, per `milkful-app`'s own `Product` model
  precedent — confirmed reading `product_config_bloc.dart`'s wallet-gate logic, which already
  branches on subscription eligibility client-side; this is the server-side authority for
  the same fact).
- On success: subscription created `ACTIVE`, `startDate` must be today or later. Returns
  `{ subscriptionId, status: ACTIVE, nextDeliveryDate }`.
- This is the hand-off point from Cart: the mobile app's "Subscribe Now" confirm
  (`ProductConfigScreen`) calls this endpoint directly once the customer commits — it does
  **not** first add a subscription-frequency item to Cart and read it back. Cart's own
  `frequency` field remains for one-time-purchase-adjacent bookkeeping only (MA-120's
  existing scope); this is a parallel, not sequential, integration (see §6 for why).

### FR-2: Pause (vacation hold)

- `POST /subscriptions/{id}/pause` — body `{ from?: date, until?: date }`. Both optional:
  neither given → pauses starting immediately, open-ended (the mock's "Vacation Mode"
  toggle-on case); `until` given without `from` → pauses immediately through `until`; both
  given → pauses for exactly that range (the ticket text's "date range" case). `from` in the
  past is rejected (`400 INVALID_RANGE`); `until` before `from` is rejected.
- A subscription due date falling inside `[from, until]` (or from "now" onward if `until` is
  absent) is never emitted by the Daily Run.
- Status becomes `PAUSED` when the pause window has started; a **future-dated** pause
  (`from` in the future) keeps status `ACTIVE` until that date arrives (surfaced to the
  client via a `scheduledPauseFrom` field, not a status flip yet) — the Daily Run is the
  single source of truth for "is this due date affected," not the coarse status field alone.

### FR-3: Resume

- `POST /subscriptions/{id}/resume` — clears any pause window (past, current, or future)
  and returns status to `ACTIVE`. Allowed from `PAUSED` or `ACTIVE`-with-a-scheduled-future-
  pause; **not** allowed from `STOPPED` (`409 SUBSCRIPTION_STOPPED`).

### FR-4: Stop / Cancel

- `POST /subscriptions/{id}/stop` — terminal. Status becomes `STOPPED`. No future due dates
  are ever emitted again. Idempotent (stopping an already-stopped subscription is a no-op
  200, not an error).

### FR-5: Skip-a-day

- `POST /subscriptions/{id}/skip` — body `{ date }`. `date` must be a currently-scheduled
  future due date (per the subscription's own schedule) and must be **before** that date's
  cut-off (FR-7) — after cut-off, the Daily Run may have already fired; skipping is refused
  with `409 CUTOFF_PASSED` (the customer can't unmake an order-due decision already acted
  on; MA-32's cancellation flow is the only way to affect an already-materialized order).
- A skipped date is recorded (not deleted from history) so `GET /subscriptions/{id}` can show
  "skipped" distinctly from "delivered"/"upcoming."
- The subscription's ongoing cadence is unaffected — `ALTERNATE_DAYS`'s parity, `WEEKLY`'s
  day-of-week, etc. all continue counting as if the skipped day had simply not been due
  (matches Step 1's assumption: no "make-up day").

### FR-6: Edit quantity / schedule

- `PATCH /subscriptions/{id}` — body `{ quantity?, schedule? }`. Same cut-off rule as skip
  (FR-5/FR-7): if the next due date's cut-off has passed, the edit takes effect from the due
  date *after* next rather than the next one (returned as `effectiveFrom` in the response —
  the client must not assume "immediately").
- Re-validates `schedule` the same way FR-1 does.

### FR-7: Cut-off enforcement

- Cut-off is `SUBSCRIPTION_CUTOFF_HOUR_IST` (config, default `20` — 8 PM IST the evening
  before a due date; see Open Questions). All cut-off comparisons use IST
  (`Asia/Kolkata`) regardless of device/server timezone — a single authoritative timezone
  for an India-only delivery business (Step 2 risk, resolved here as a fixed constant, not a
  per-user setting).
- Applies uniformly to pause/resume/stop/skip/edit: any action affecting *tomorrow's*
  due date must be submitted before today's cut-off hour.

### FR-8: Daily Run

- Triggered by an EventBridge Scheduler rule at `SUBSCRIPTION_CUTOFF_HOUR_IST` sharp
  (the run *is* the cut-off moment — nothing between "cut-off" and "run" needs its own gap).
- For every `ACTIVE` subscription (not currently paused, not skipped for tomorrow), computes
  whether **tomorrow** is a due date per its `Schedule`:
  - `DAILY` → always.
  - `ALTERNATE_DAYS` → `(tomorrow - startDate).days % 2 == 0`.
  - `WEEKLY`/`CUSTOM_DAYS` → tomorrow's ISO weekday is in `daysOfWeek`.
- For each due subscription, emits `SubscriptionOrderDue{ subscriptionId, userId, productId,
  quantity, deliveryDate: tomorrow, slotId, correlationId }` (one event per due
  subscription — Order Service, MA-132, consumes these to create orders).
- **Why tomorrow, not today**: the run happens *at* the cut-off, which is the evening before
  — "today's" delivery already happened (or its order was already created by yesterday's
  run); the run is always producing the *next* day's due list.
- Idempotent: the run records `(subscriptionId, deliveryDate)` pairs it has already emitted
  (`subscription_run_log` table) so a retried/duplicate Scheduler invocation for the same
  cut-off never emits the same due-date twice — Order Service's own idempotency (MA-132 FR-1)
  is a second line of defense, not the only one.

### FR-9: Read APIs (for MA-133)

- `GET /subscriptions/me` — list the caller's subscriptions (any status), each with
  `nextDeliveryDate` (computed the same way FR-8 computes "due," projected forward to the
  soonest non-skipped, non-paused date) or `null` if `STOPPED`/indefinitely paused with no
  resume date.
- `GET /subscriptions/{id}` — one subscription's full detail including pause window, recent
  skip history, and `effectiveFrom` for any pending edit.

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| **Reliability** | The Daily Run must complete for all due subscriptions even if one subscription's computation throws — one bad row logs and continues, never aborts the whole run (same "isolate failures" principle as every SQS consumer in this codebase). |
| **Consistency** | A subscription's status/pause/skip state is read-your-writes consistent for the customer who just changed it (single Aurora instance, no read replica lag concern at this scale). |
| **Performance** | Daily Run must complete within its scheduling window (target: <5 min for the platform's current customer count) — batched due-date computation, not one query per subscription. |
| **Idempotency** | Every write endpoint (create, pause, resume, stop, skip, edit) plus the Daily Run itself is safe to retry — no duplicate subscriptions, no duplicate `SubscriptionOrderDue` events. |
| **Observability** | Structured-log metrics: `subscription.daily_run_due_count`, `subscription.daily_run_duration_ms`, `subscription.daily_run_row_errors`, `subscription.created`, `subscription.paused`, `subscription.stopped`, `subscription.skip_refused_cutoff`. |

## 6. Technical Design

### Why a parallel hand-off from Cart, not sequential

Cart's `Frequency` is a 2-value enum (`DAILY`/`ALTERNATE_DAYS`) scoped down for MA-23/MA-120,
which never needed weekly/custom-day patterns. Rather than widen Cart's own model (reopening
an already-shipped service for a concern it doesn't otherwise need — matches this codebase's
established preference, e.g. Pricing Service's own decision not to reopen Catalog for HSN/GST
fields) or lose fidelity by mapping a weekly pattern down into Cart's narrower shape, this
spec has the mobile app call Subscription Service directly with the full `Schedule` the
customer actually picked. Cart's cart-side `frequency` field stays exactly as-is, used only
for its existing one-time/near-term-checkout bookkeeping.

### Domain model

```python
class ScheduleType(StrEnum):
    DAILY = "DAILY"
    ALTERNATE_DAYS = "ALTERNATE_DAYS"
    WEEKLY = "WEEKLY"
    CUSTOM_DAYS = "CUSTOM_DAYS"

@dataclass
class Schedule:
    type: ScheduleType
    days_of_week: list[int] | None   # ISO 1-7; required for WEEKLY/CUSTOM_DAYS

class SubscriptionStatus(StrEnum):
    ACTIVE = "ACTIVE"
    PAUSED = "PAUSED"
    STOPPED = "STOPPED"

@dataclass
class Subscription:
    id: str
    user_id: str
    product_id: str
    quantity: int
    schedule: Schedule
    slot_id: str
    status: SubscriptionStatus
    start_date: date
    pause_from: date | None
    pause_until: date | None
    pending_edit: dict | None       # {quantity?, schedule?, effective_from}
    created_at: datetime
    updated_at: datetime
```

### Tables (Aurora `subscriptions` cluster)

- `subscriptions` — one row per subscription, columns matching the dataclass above
  (`schedule`/`pending_edit` as JSONB, matching Catalog/Payment's own established JSONB-for-
  structured-fields convention).
- `subscription_skips` — `(subscription_id, skipped_date)`, append-only history.
- `subscription_run_log` — `(subscription_id, delivery_date)` UNIQUE, the Daily Run's own
  idempotency guard (FR-8).
- `outbox` — same shape as every other service's transactional outbox.

### Daily Run entry point

A second process/thread in the same single-deployable `main.py` (matching Wallet/Payment's
own "one deployable, HTTP + background work" convention) — but triggered by an EventBridge
Scheduler `PutEvents`-equivalent HTTP hook (a `POST /internal/run-daily` the Scheduler rule
invokes) rather than an SQS poll loop, since this is a single point-in-time trigger, not a
continuous queue. Local-dev emulates the Scheduler with a cron-like local invocation script,
matching this repo's own "no moto-equivalent for X, documented fidelity gap" precedent
(e.g. Inventory's SQLite-for-Aurora gap) rather than inventing new local-dev infrastructure.

### API surface

| Method | Path | FR |
|--------|------|----|

| POST | `/subscriptions/{id}/pause` | FR-2 |

## 7. Data Considerations

- New Aurora cluster/schema (`subscriptions`) — first migration for this service, no
  existing data to migrate.
- `pending_edit` (JSONB, nullable) is applied by the Daily Run itself: when the run
  processes a subscription whose `pending_edit.effective_from <= tomorrow`, it applies the
  edit to the subscription row before computing due-ness, then clears `pending_edit` — this
  keeps "when does an edit actually take effect" logic in exactly one place (the run),
  rather than duplicated between the read APIs and the run.
- Money: none held by this service — quantity/schedule only, no paise-denominated field
  exists here.

## 8. Integration Considerations

| System | Interaction | Failure behavior |
|--------|-------------|-------------------|
| **Catalog Service** | `GET /products/{id}` at create-time (FR-1) to validate product + subscription-eligibility | Catalog unavailable → `503`, create fails closed (never create a subscription for an unverified product). |
| **Order Service (MA-132)** | Publishes `SubscriptionOrderDue`, consumed via `order-events-q` | Publish failure → same transactional-outbox retry every other service in this codebase already relies on; the Daily Run's own DB transaction (subscription state + outbox row) is atomic, so a crash before the outbox publisher drains it just means a delayed publish, never a lost or duplicated one. |
| **Mobile app (MA-133)** | All FR-1–FR-9 endpoints, via the shared `ApiClient` (Cognito JWT) | Standard `ApiException` envelope, matching every other service. |
| **EventBridge Scheduler** | Triggers `POST /internal/run-daily` once per cut-off | A missed/failed invocation needs an operational alert (out of this spec's testing scope, but the endpoint's own idempotency (FR-8) makes a manual re-trigger always safe). |

## 9. Edge Cases and Failure Modes

| Case | Handling |
|------|----------|
| Customer pauses a subscription, then the Daily Run fires for a date inside the pause window | Excluded from due computation — FR-2's own definition. |
| Customer resumes mid-pause-window on a date that would otherwise have been due | The very next Daily Run (for the day after resume) picks it back up normally; the paused-over dates are not "made up." |
| Two overlapping pause calls (a new `pause` while already paused) | The later call replaces the pause window entirely (not additive) — simplest, matches the mock's single-toggle mental model. |
| Skip requested for a date that isn't actually due (wrong day for this schedule) | `400 DATE_NOT_DUE`. |
| Edit changes `schedule` such that a previously-skipped future date no longer exists in the new schedule | The stale skip record is harmless (never referenced again since the due-date computation now never produces that date) — not actively cleaned up, not a correctness issue. |
| Daily Run invoked twice for the same cut-off (Scheduler retry) | `subscription_run_log`'s UNIQUE constraint makes the second invocation a no-op per subscription (FR-8). |
| Product becomes non-`subscriptionEligible` after a subscription using it was already created | Existing subscriptions are grandfathered — re-validation only happens at create/edit time (FR-1/FR-6), never retroactively invalidates a running subscription. |
| `startDate` is far in the future | Allowed — the subscription sits `ACTIVE` with no due dates until `startDate` arrives; the Daily Run's due-computation naturally excludes any `tomorrow < start_date`. |

## 10. Testing Strategy

### Unit — `tests/unit/domain/test_subscription_service.py`

- Create: valid schedule types (all four), invalid `daysOfWeek` (empty for `WEEKLY`),
  non-subscription-eligible product rejected, idempotent replay on `idempotencyKey`.
- Pause: no-args (open-ended, immediate), `until`-only, both-given, past `from` rejected,
  `until` before `from` rejected, overlapping pause replaces.
- Resume: from `PAUSED`, from a scheduled-future-pause, rejected from `STOPPED`.
- Stop: idempotent on repeat.
- Skip: valid future due date, refused for a non-due date, refused past cut-off.
- Edit: before cut-off (immediate next-cycle effect), after cut-off (`effectiveFrom` pushed
  one cycle out).
- Daily Run due-computation: one case per `ScheduleType`, a paused subscription excluded, a
  skipped date excluded, an edit with `effective_from` applied before due-check, duplicate
  run for the same cut-off emits nothing new (idempotency).

### Integration — `tests/integration/test_subscription_http.py`

- Full HTTP round trip: create → pause → resume → skip → edit → stop, each verified via a
  subsequent `GET`.
- `POST /internal/run-daily` against a seeded set of subscriptions (mixed schedules,
  pauses, skips) → asserts the exact set of `SubscriptionOrderDue` events published, schema-
  validated against `shared/events/SubscriptionOrderDue.schema.json` (new).

### Acceptance

- `pytest` green; `ruff check` clean.
- A subscription created via `POST /subscriptions`, run through several simulated Daily Runs
  (advancing a fake clock), produces exactly the due-date sequence its schedule predicts.

## 11. Risks and Trade-offs

- **New service, new compute pattern, no moto-equivalent for EventBridge Scheduler** — the
  Daily Run's trigger is emulated by a local invocation script rather than real Scheduler
  behavior in local-dev; flagged the same way Inventory flagged its own SQLite-for-Aurora gap.
- **`Schedule` as its own model, decoupled from Cart's `Frequency`** — two representations
  of "how often" now exist in the platform (Cart's narrow one, this service's fuller one).
  Accepted: reopening Cart to widen `Frequency` was rejected as unnecessary scope creep for
  an already-shipped service (§6); the two are allowed to diverge because they answer
  different questions (Cart: "what did the customer pick this one time," Subscription:
  "how does this recur forever").
- **Cut-off is a single global constant, not configurable per product/zone** — matches this
  platform's general "no per-user/per-zone config surface yet" precedent; a future need for
  zone-specific cut-offs is a schema-additive change, not a rewrite.
