## 2. Problem Statement

MA-22's catalog screen needs search-by-text and multi-facet filter/sort (category, price,
veg/organic) that a plain Aurora query can't serve well at scale or relevance. This spec covers
`GET /search`, backed by OpenSearch, kept in sync with the Aurora-owned product data from MA-116
(MA-116). Split out from MA-116 because it's a genuinely different technical concern: new
infrastructure (no service in this platform uses OpenSearch yet), a sync-consistency problem
(Aurora is system-of-record, OpenSearch is a derived index), and no existing local-dev emulation
story.

## 3. Scope

**In scope:**
- OpenSearch index design for products (denormalized, search/filter/sort-optimized).
- Aurora → OpenSearch sync mechanism (see Technical Design — outbox pattern).
- `GET /search?q=&filters=&sort=` endpoint.

**Out of scope:**
- The Aurora schema/system-of-record itself — MA-116 owns product/category data; this spec is
  purely the search-index layer on top of it.
- Personalized/ranked relevance beyond basic text-match + facet-filter + explicit sort — no
  ML-ranking, no "popular searches," nothing beyond what MA-22's ticket names.

## 4. Functional Requirements

### FR-1: `GET /search`

- Query params:
  - `q` — free-text match against product name/description.
  - `filters` — structured facet filters. **Contract (resolves Step 1 Q2):** repeated query
    params per facet, e.g. `?filters=category:milk&filters=veg:true&filters=price:0-100` — chosen
    over a single JSON blob because it's simpler to construct from Flutter's `Uri` query-param
    APIs (matching how `PlacesRepository` already builds `queryParameters` maps) and simpler to
    log/debug than an encoded JSON string.
  - `sort` — one of `price_asc`, `price_desc`, `newest` (see MA-115's Open Question Q1 on whether
    a `popularity` field is realistic — **not included in v1** of this spec absent a defined
    popularity signal; can be added without a breaking change later).
- Returns the same product shape as MA-116's `GET /products`, so the mobile client's `Product`
  model deserializes search results identically to category-browse results — no separate model
  needed client-side.
- Empty `q` with only `filters`/`sort` is valid (filter-only browsing, not just text search).

### FR-2: Aurora → OpenSearch sync

- **Chosen mechanism: transactional outbox**, matching the platform's own listed pattern
  (`milkful-well-architected.md` §3: "Transactional Outbox — Reliable event publishing from each
  service DB") and this repo's existing precedent (`services/user`'s outbox-publisher, seen in
  this session's local-dev work: a poller that reads an outbox table and republishes). MA-116's
  writes (product/category create/update, `StockChanged`-driven stock updates) insert an outbox
  row in the same Aurora transaction; a poller reindexes the affected document into OpenSearch.
- MA-116 commits to this on its own side (see MA-116 §4 FR-6 and §7's `catalog_outbox` table):
  every product/category write there, including FR-5-driven stock updates, inserts an outbox row
  in the same transaction. This was previously asserted only from this spec's (consumer) side; it
  is now a two-sided commitment recorded on both specs, matching how MA-116 ↔ MA-95's
  `StockChanged` dependency is documented.

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| Performance | `GET /search` p95 < 500ms (search is inherently heavier than a keyed read; looser budget than MA-116's plain `GET /products`) |
| Consistency | Outbox-driven sync targets < 5s staleness between an Aurora write and its OpenSearch reflection — not real-time, explicitly eventual |
| Reliability | A failed reindex attempt retries (poller re-reads unprocessed outbox rows); a permanently-failing document doesn't block the poller from processing others |
| Security | Same Cognito-JWT-at-API-Gateway requirement as MA-116; read-only |

## 6. Technical Design

### Architecture

- New `adapters/opensearch_adapter.py`-style component (following the existing hexagonal
  convention) wrapping OpenSearch's query DSL behind a plain Python interface the `handlers/`
  layer calls — mirrors how `services/inventory`'s `zone_repository.py` abstracts Postgres behind
  a domain-facing interface.
- Outbox poller: a separate long-running process (matching `services/user`'s
  `run_local_outbox_publisher.py` pattern for local dev; a scheduled ECS task or a small
  always-on Fargate sidecar for the real deployment — exact deployment shape is Step 4
  implementation-planning detail, not this spec's concern beyond stating the mechanism).

### Index design

```json
{
  "id": "uuid",
  "categoryId": "uuid",
  "categoryName": "text (denormalized, for filter-by-name without a join)",
  "name": "text, analyzed for search",
  "description": "text, analyzed for search",
  "unit": "keyword",
  "price": "float",
  "imageUrl": "keyword",
  "tag": "keyword",
  "isVeg": "boolean",
  "isOrganic": "boolean",
  "subscriptionEligible": "boolean",
  "stockState": "keyword",
  "availableFrom": "date (present only when stockState is AVAILABLE_FROM, matching MA-116's FR-1)"
}
```

Every field on MA-116's product record (§4 FR-1) that the mobile client's `Product` model needs is
denormalized into this index — `unit`, `imageUrl`, `tag`, and `availableFrom` were previously
missing here despite FR-1's promise that `GET /search` returns "the same product shape as
MA-116's `GET /products`"; the outbox document (§4 FR-2) now carries all of them so no per-result
Aurora hydration step is needed at query time.

`isVeg`/`isOrganic` — the ticket names "veg/organic" as one filter facet; modeled as two
independent booleans here since a product could plausibly be organic-but-not-veg-labeled (dairy
context) or vice versa. **Resolved with MA-116:** `is_veg`/`is_organic` are now part of MA-116's
`products` schema (see MA-116 §7) specifically so this spec's outbox consumer can denormalize them
into the OpenSearch index without a join.

## 7. Data Considerations

- Outbox table: `catalog_outbox` (id, aggregate_id, payload, created_at, processed_at) — additive
  migration on the same Aurora database MA-116 owns (same service, same database-per-service
  boundary — not a new datastore for MA-116's own writes, just a new consumer of them).

## 8. Integration Considerations

| Integration | Direction | Contract owner |

## 9. Edge Cases and Failure Modes

| Case | Behavior |
|------|----------|
| OpenSearch unavailable | `GET /search` returns 5xx; does not fall back to a degraded Aurora-only search in this pass (explicitly not required by the ticket) |
| Outbox poller falls behind (backlog) | Search results grow stale but don't error; a CloudWatch alarm on outbox-lag age is the operational signal |
| A document fails to index repeatedly (poison document) | Skipped after N retries, logged, does not block the poller from later rows — mirrors the DLQ pattern used elsewhere on the platform even though this isn't itself an SQS queue |
| `filters` param with an unrecognized facet key | Ignored (not a 400) — forward-compatible if the mobile client and this API drift slightly during parallel development |

## 10. Testing Strategy

### Unit tests

- Query-DSL construction from `q`/`filters`/`sort` params — a given input produces the expected
  OpenSearch query shape.
- Outbox → index document mapping.

### Integration tests (local-dev)

- Requires local OpenSearch emulation — **new local-dev tooling, not yet built** (Risk #1 in
  MA-94's Step 2 context). At minimum: a `docker-compose` service for OpenSearch, matching how
  `moto`/Postgres/Redis are already composed in `services/local-dev/docker-compose.yml`.
- Seed a few products via MA-116's API, assert they become searchable within the sync-latency
  budget (FR/NFR above).

### Negative scenarios

- Search for a term matching nothing → empty result list, not an error (same UX contract MA-22
  expects for its no-results state).
- Filter combination that excludes everything → empty result, not an error.

## 11. Risks and Trade-offs

1. **New infrastructure with no local-dev precedent** — the single biggest implementation risk in
   this whole spec set; flagged repeatedly (Step 2, here) rather than glossed over.
2. **Eventual consistency is a real, user-visible trade-off** — a just-created/updated product may
   not appear in search for up to the sync-latency budget. Accepted rather than engineering
   synchronous dual-writes (which would couple MA-116's write availability to OpenSearch's).
