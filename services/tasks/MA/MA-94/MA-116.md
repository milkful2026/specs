## 2. Problem Statement

No service in the platform owns product/category data today. The mobile app's catalog screen
(MA-22) has nothing to fetch from, and every downstream consumer (Cart, Order, Pricing) that
needs product identity/price/unit has no system of record to call. This spec stands up the
read-side data API: `GET /products`, `GET /products/{id}`, `GET /categories`. Search/filter/sort
(`GET /search`) is a separate spec (MA-117) given its distinct OpenSearch dependency.

## 3. Scope

**In scope:**
- Aurora schema for `products` and `categories`.
- `GET /products` (list, optionally filtered by `categoryId`), `GET /products/{id}`,
  `GET /categories`.
- Consuming `StockChanged` (from Inventory, MA-95) to keep each product's stock-state field
  current.
- Publishing `CatalogUpdated` on product/category change (for any future cache-invalidating
  consumer — no consumer exists yet, but the ticket names this event explicitly).

**Out of scope:**
- Product/category *authoring* (create/edit/deactivate) — admin console's Product & Catalog
  Management story (MA-42), unless product later decides this write-side belongs here too
  (open question).
- `GET /search` and any OpenSearch-backed behavior — MA-117.
- Image upload/CDN pipeline — this spec assumes `imageUrl` values already exist on product
  records (populated by whatever authoring path is eventually built), not how they got there.
- Actual stock quantities — Inventory (MA-95) owns those; this service only mirrors a
  stock-*state* summary via the `StockChanged` event, not quantities.

## 4. Functional Requirements

### FR-1: `GET /products`

- Query params: `categoryId` (optional filter), `page`/`pageSize` (pagination — no page size
  specified in the ticket; default 20, max 100, matching common REST convention absent a stated
  requirement).
- Returns products in this app's standard envelope: `{requestId, status, data: {products: [...],
  page, pageSize, total}}`.
- Each product includes: id, categoryId, name, description, unit, price (see FR-4 on B2B tiering),
  imageUrl, subscriptionEligible, isVeg, isOrganic, tag (optional), stockState (`IN_STOCK` |
  `OUT_OF_STOCK` | `AVAILABLE_FROM`), availableFrom (present only when stockState is
  `AVAILABLE_FROM`). `isVeg`/`isOrganic` exist on this record specifically so MA-117's
  OpenSearch index can denormalize them for the veg/organic filter facet without a join.

### FR-2: `GET /products/{id}`

- Single product, same shape as one element of FR-1's list. 404 (mapped to this app's
  `ApiException` convention) if the id doesn't exist.

### FR-3: `GET /categories`

- Returns all active categories: id, name, iconName (a stable string key the mobile client maps
  to a Material icon — not an image asset, per MA-22's own spec decision).
- No pagination — category count is expected to stay small (single digits to low tens), unlike
  products.

### FR-4: Pricing tiers (B2C/B2B)

- The ticket's own description names "pricing tiers (B2C/B2B)" as a Catalog responsibility.
  MA-22 (mobile) explicitly deferred B2B-specific pricing display, so this spec's minimum bar is:
  the product record *can* carry a B2B price alongside the B2C one, but the API always returns the
  B2C price in `price` unless/until a caller identifies as B2B (mechanism TBD — open question,
  since no B2B-aware caller exists yet).

### FR-5: `StockChanged` consumption

- Consumes `StockChanged` events (via a new `catalog-events-q` SQS queue, per
  `milkful-well-architected.md` §7.2) published by Inventory (MA-95/MA-118).
- **Agreed payload contract** (joint with MA-118):
  ```json
  {
    "eventId": "uuid",
    "productId": "uuid",
    "availableQuantity": 0,
    "stockState": "IN_STOCK | OUT_OF_STOCK | AVAILABLE_FROM",
    "availableFrom": "2026-09-01 | null",
    "occurredAt": "2026-08-16T10:00:00Z"
  }
  ```
- On receipt: update the named product's `stockState`/`availableFrom` in Aurora directly from the
  event's own fields (no re-derivation needed — Inventory has already computed the right state).
- Idempotent via `eventId`: this service tracks the last-processed `eventId` per product and
  ignores a redelivery of one it's already applied — redelivery (SQS at-least-once) must not
  corrupt state.

### FR-6: `CatalogUpdated` publication

- Published whenever a product or category record changes (via whatever authoring path exists —
  even if that path itself is out of scope here, this event fires from *this* service when its
  own data changes, including via FR-5's stock updates).

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| Performance | `GET /products`/`GET /categories` p95 < 300ms (hot-path read, per platform's own Fargate-for-latency-sensitive-services rationale) |
| Reliability | `StockChanged` consumption is idempotent; a poison message routes to the queue's DLQ, not a crash loop |
| Security | Cognito JWT required at API Gateway for all endpoints (platform-wide "authenticate every request" stance) — read-only, no per-user scoping needed beyond "is authenticated" |
| Observability | `X-Request-Id` correlation propagated end-to-end; CloudWatch metrics on request latency/error rate; X-Ray tracing across the `StockChanged` consume → Aurora write path |
| Scalability | ECS Fargate, auto-scaled behind the internal ALB per platform standard — no catalog-specific scaling need beyond default policy |

## 6. Technical Design

### Architecture

- Hexagonal structure matching `services/inventory`'s existing convention: `domain/` (Product,
  Category models + a `CatalogService` domain service), `adapters/` (Aurora repository via
  SQLAlchemy/psycopg2 matching the existing services' style, `StockChanged` SQS consumer adapter
  modeled on `services/inventory/src/adapters/zone_update_consumer.py`), `handlers/` (FastAPI
  routes + DTOs), `infra/` (CDK stack for Fargate + Aurora + the new SQS queue/EventBridge rule).
- Compute: ECS Fargate (per `milkful-well-architected.md` §6.1's rationale — steady, latency-
  sensitive hot path).

### API

```
GET /products?categoryId={id}&page={n}&pageSize={n}
GET /products/{id}
GET /categories
```

Response envelope matches every other service this app already calls
(`{requestId, status, data}`), so the mobile client's existing `ApiClient` needs no special-casing
for Catalog.

## 7. Data Considerations

```sql
-- products (Aurora)
id            uuid primary key
category_id   uuid references categories(id)
name          text not null
description   text
unit          text not null           -- e.g. "1L Bottle"
price_b2c     numeric(10,2) not null
price_b2b     numeric(10,2)           -- nullable; FR-4
image_url     text
tag           text                    -- optional, e.g. "ORGANIC"
subscription_eligible boolean not null default false
is_veg        boolean not null default true    -- MA-117's veg/organic filter facet reads these two
is_organic    boolean not null default false   -- independent booleans (a product can be one, both, or neither)
stock_state   text not null default 'IN_STOCK'  -- IN_STOCK | OUT_OF_STOCK | AVAILABLE_FROM
available_from date                   -- set only when stock_state = AVAILABLE_FROM
created_at    timestamptz not null default now()
updated_at    timestamptz not null default now()

-- categories (Aurora)
id          uuid primary key
name        text not null
icon_name   text not null
sort_order  int not null default 0
```

Migration convention: `migrations/0001_products_categories.sql`, tracked via `schema_migrations`,
applied by a `local-dev/apply_migrations.py`-style script matching every other service in this
repo.

## 8. Integration Considerations

| Integration | Direction | Contract owner |
|-------------|-----------|-----------------|
| Mobile app (MA-22) | Inbound (this API) | This spec |
| `StockChanged` event | Inbound (SQS consume) | Joint with MA-95 (MA-118) — payload shape agreed, see FR-5 |
| `CatalogUpdated` event | Outbound (publish) | This spec (no consumer yet) |

Dependency failure behavior: if Inventory (MA-95) is down/unreachable, this service is *not*
directly affected (it only consumes an async event, never calls Inventory's API synchronously) —
stock-state simply goes stale until the queue catches up once Inventory recovers.

## 9. Edge Cases and Failure Modes

| Case | Behavior |
|------|----------|
| `StockChanged` for a productId this service doesn't know about | Log and drop (not an error — could be a race with product creation, or a productId typo upstream); does not retry indefinitely |
| Duplicate `StockChanged` delivery (SQS at-least-once) | Idempotent update — same end state, no double-processing side effect |
| `GET /products/{id}` for a nonexistent id | 404 via standard `ApiException` mapping |
| Aurora unavailable | 5xx, surfaces as MA-22's Error state client-side; CloudWatch alarm on elevated 5xx rate |
| Category with `sort_order` collisions | Stable secondary sort by `name` — not a functional bug, just a determinism guarantee |

## 10. Testing Strategy

### Unit tests

- `CatalogService` domain logic: stock-state update from a `StockChanged` payload, idempotency
  check.
- DTO serialization matches the documented envelope shape.

### Integration tests (local-dev, matching existing services' `local-dev/` convention)

- `GET /products`/`GET /products/{id}`/`GET /categories` against a seeded local Postgres —
  mirroring `services/inventory/local-dev/seed_inventory_zones.py`'s seed-script pattern.
- `StockChanged` consumption: publish a fake event to the local queue, assert the product's
  `stock_state` updates.

### Negative scenarios

- Malformed `StockChanged` payload → logged, routed to DLQ, not a crash.
- `GET /products/{id}` for a deleted/nonexistent product → 404, not a 500.

## 11. Risks and Trade-offs

1. **No consumer of `CatalogUpdated` exists yet** — publishing it is low-cost/forward-compatible,
   but its actual contract can't be validated against a real consumer until one exists.
2. **B2B pricing mechanism (FR-4) is underspecified** — no caller identifies as B2B yet; this spec
   makes the data model B2B-ready without committing to how a caller signals B2B intent.
3. **Local-dev story for the new SQS queue/EventBridge rule** needs the same `bootstrap.py`-style
   provisioning as existing services — straightforward given the precedent, but real work, not
   assumed-free.
