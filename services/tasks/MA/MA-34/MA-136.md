## 2. Problem Statement

A customer can fill a cart but cannot buy it. Order Service creates orders only from
`SubscriptionOrderDue` (MA-132 §3 scoped the checkout saga out), and its schema is
subscription-shaped (`subscription_id NOT NULL`, one product per order). MA-34 needs one
**Confirm Order** action that charges the one-time items, starts the subscriptions in the
cart, and empties the cart, without ever double-charging and without leaving a
customer charged but missing a subscription.

Expected outcome: `POST /orders/checkout`, one idempotent, resumable call that turns
the current cart into (a) at most one paid one-time order and (b) one subscription per
subscription line.

## 3. Scope

### In scope

- `POST /orders/checkout` (Cognito JWT + `Idempotency-Key`).
- `checkouts` table: a resumable record of each checkout attempt.
- One-time **multi-line** orders (`source = CHECKOUT`) + `order_items` table; migration
  relaxing the subscription-only columns.
- `GET /orders/me` / `GET /orders/{id}` expose `source` and `items`.
- `OrderConfirmed` / `OrderPaymentFailed` schemas: `subscriptionId` nullable, add
  `source`, `checkoutId`, `items`.
- **Subscription Service:** `POST /internal/subscriptions`, a VPC-only wrapper
  over the existing `SubscriptionService.create` that takes `userId` in the body.
- New Order Service adapters: Cart internal client (SigV4), Subscription internal
  client, Wallet internal balance read.

### Out of scope

- Stock reservation / Inventory (no stock model exists; PO-5).
- Charging subscriptions at checkout: their deliveries keep being charged by the existing
  Daily Run → `SubscriptionOrderDue` → `materialize` path, unchanged.
- Razorpay at checkout (wallet-only; top-up is MA-24's screen).
- Offers/coupons, delivery slots for one-time orders, order cancellation/refunds.
- A background sweep for `IN_PROGRESS` checkouts abandoned by the client (see §11).

## 4. Functional Requirements

### FR-1: Request

```
POST /orders/checkout
Authorization: Bearer <Cognito JWT>
Idempotency-Key: <8–128 chars, client-generated, reused on every retry of the same Confirm>

{ "cartVersion": 7, "expectedPayNowPaise": 10820 }
```

- `userId` = the JWT's user (`shared.handlers.auth.current_user_id`, same as `GET /orders/me`).
- `cartVersion` required: the version the customer reviewed.
- `expectedPayNowPaise` optional (`null`/absent → no price check); it's the "Pay now"
  total the screen showed, in paise (`payNowQuote.netPayable × 100`, or `0` when there
  are no one-time lines).
- Missing/invalid `Idempotency-Key` → `400 VALIDATION_ERROR`.

### FR-2: Replay

If a `checkouts` row exists for `(userId, Idempotency-Key)`:

| Stored status | Response |
|---------------|----------|
| `COMPLETED` | The stored result, `200`, no side effects |
| `PAYMENT_FAILED` | The stored `402`/`403` error, no side effects. The client must use a **new** key after topping up |
| `IN_PROGRESS` | Handled as a live checkout (FR-2a) |

### FR-2a: Live checkouts: busy, discard, resume, adopt

A user has at most one `IN_PROGRESS` checkout. A request finds it either by its own key
(FR-2) or, with a different key, at FR-3.1. The key may differ when the app lost its
key (reinstall, or the other device).

- **Busy:** `updated_at` is within the last `CHECKOUT_BUSY_SECONDS` (default 30). Every
  step transition bumps `updated_at`, and one step takes at most ~12 s including
  retries, so a busy checkout is one that a running request still owns.
- **Claim:** a request takes over a non-busy checkout with a compare-and-set on
  `updated_at` (`UPDATE … WHERE id = ? AND updated_at = <value read>`). Only the winner
  continues; a loser gets `409 CHECKOUT_IN_PROGRESS`.

| Live checkout | Same key | Different key |
|---------------|----------|---------------|
| Busy | `409 CHECKOUT_IN_PROGRESS`, `details.retryAfterSeconds` = seconds until it stops being busy | Same |
| Not busy, `step = STARTED` (debit never called) | **Discard** it, then run this request as a new checkout (FR-3 onward, with this body) | Same |
| Not busy, `step ≥ CHARGING` | **Resume** from the first incomplete step (FR-5..FR-7) with the stored snapshot. The body is ignored | **Adopt:** resume it the same way and return its outcome (200 result, 402/403, or 503). The new key is not stored |

- **Discard** = one transaction that deletes the checkout row and its `CREATED` order and
  `order_items`. Nothing was charged and no event was emitted. The owner's
  `STARTED → CHARGING` transition is a compare-and-set (`WHERE step = 'STARTED'`), so a
  discarded attempt can never reach the debit.
- From `CHARGING` onward the snapshot wins over the body: the debit may already have
  moved the snapshot amount the customer confirmed. The app locks the cart while its key
  is pending and resends the same body (MA-137 FR-9), so the two only differ when the
  cart was edited on another device.
- As a result, an abandoned checkout blocks the user for at most `CHECKOUT_BUSY_SECONDS`.
  After that, a Confirm with any key finishes the checkout or discards it.

### FR-3: Validation (new checkout, before any side effect)

Evaluated in this order; each failure returns immediately and persists nothing (so a
retry with the same key re-evaluates, which is safe because nothing happened):

1. Another `IN_PROGRESS` checkout exists for this user → FR-2a (`409
   CHECKOUT_IN_PROGRESS` only while it is busy; otherwise discard it or adopt it).
2. Read the cart via Cart internal `GET /cart/internal/users/{userId}` (MA-135 FR-3).
   - No lines → `409 CART_EMPTY`.
   - `cartVersion` ≠ body `cartVersion` → `409 CART_CHANGED` (`details.cartVersion` = current).
3. Per-line subscription pre-check: a subscription line needs a `slotId` and
   `startDate ≥ today (IST)`. A line that fails does **not** fail the checkout (Product
   decision, §12). It goes into `subscription_results` up front as
   `{lineId, status: FAILED, reason: "SLOT_MISSING" | "START_DATE_PAST"}`, Subscription
   is never called for it, and it stays in the cart (FR-7). Carts sit for days, so
   stale start dates are expected. The request fails only if **nothing** would be
   checked out: no one-time lines and every subscription line fails. That returns
   `422 LINE_INVALID` with `details.lines: [{lineId, reason}]`.
4. Resolve delivery state via User Service (existing `get_delivery_address_state`).
   `None` → `422 DELIVERY_ADDRESS_UNKNOWN`. Transient → `503 DEPENDENCY_UNAVAILABLE`.
5. If one-time lines exist: quote them via Pricing (`frequency: ONE_TIME` for every line,
   one call) → `payNowPaise` (Decimal → paise, same rounding as `materialize`).
   Otherwise `payNowPaise = 0`. `ProductPricingUnknownError` → `422 LINE_INVALID`
   (`reason: "PRODUCT_UNAVAILABLE"`, line IDs from the error if available, else all one-time lines).
6. If `expectedPayNowPaise` is given and ≠ `payNowPaise` → `409 PRICE_CHANGED`
   (`details.payNowPaise`).
7. Balance pre-check via Wallet internal `GET /wallet/internal/balance`:
   `requiredPaise = payNowPaise + (validSubscriptionLines ? SUBSCRIPTION_MIN_BALANCE_PAISE : 0)`
   (`validSubscriptionLines` = the lines that passed step 3).
   `balance < requiredPaise` → `402 INSUFFICIENT_BALANCE` with
   `details: {balancePaise, requiredPaise, shortfallPaise}`. This check is advisory. The
   debit in FR-5 is authoritative. `SUBSCRIPTION_MIN_BALANCE_PAISE` must equal Cart's
   `wallet_minimum_balance` (same env value, converted to paise).

### FR-4: Start the checkout (one DB transaction)

- Insert `checkouts(status = IN_PROGRESS)` with the **line snapshot** (every cart line:
  id, productId, quantity, frequency, startDate, slotId), `cart_version`,
  `pay_now_paise`, `delivery_date` (FR-8), and the FR-3.3 pre-check failures in
  `subscription_results`.
- If **any one-time line exists** (whatever its price): insert `orders(source = CHECKOUT,
  checkout_id, amount_paise = payNowPaise, delivery_date)` + one `order_items` row per
  one-time line; store `order_id` on the checkout.
  - `payNowPaise > 0` → order `CREATED`, checkout `step = STARTED`.
  - `payNowPaise = 0` (every one-time line priced at 0) → no debit, because Wallet
    rejects debits ≤ 0. The order is inserted directly `CONFIRMED` with its
    `OrderConfirmed` outbox row in this same transaction, and the checkout starts at
    `step = PAID`. This is the only `CONFIRMED` order with `amount_paise = 0`.
    `materialize`'s "every CONFIRMED order has a positive amount" invariant still holds
    for `SUBSCRIPTION` orders.
- No one-time lines → no order; checkout starts at `step = PAID`.

### FR-5: Charge (only if the order is `CREATED`)

First move the checkout `STARTED → CHARGING` with a compare-and-set
(`WHERE id = ? AND step = 'STARTED'`, bumping `updated_at`). If 0 rows change, another
request discarded or took over this attempt (FR-2a) → `409 CHECKOUT_IN_PROGRESS`. Then
call `POST /wallet/internal/debit {userId, orderId, amountPaise, correlationId}`
(existing, idempotent on `order:{orderId}`; a replay returns the original entry's
balance):

| Outcome | Effect | Response |
|---------|--------|----------|
| `DEBITED` | Order → `CONFIRMED` + `OrderConfirmed` outbox row, and checkout step `PAID` + `balance_after_paise` = Wallet's `balancePaise` (one transaction) | continue to FR-6 |
| `INSUFFICIENT_BALANCE` | Order → `PAYMENT_FAILED(INSUFFICIENT_BALANCE)` + `OrderPaymentFailed` outbox; checkout → `PAYMENT_FAILED` | `402 INSUFFICIENT_BALANCE` with the **same `details` shape as FR-3.7**: `balancePaise` (from Wallet), `requiredPaise` (FR-3.7 formula), `shortfallPaise = requiredPaise − balancePaise` (always > 0 here, because `balancePaise < payNowPaise ≤ requiredPaise`) |
| `WALLET_NOT_ACTIVE` | Same, reason `WALLET_NOT_ACTIVE`; checkout → `PAYMENT_FAILED` | `403 WALLET_NOT_ACTIVE` |
| Transport failure after retries | Nothing changes; checkout stays `IN_PROGRESS` | `503 CHECKOUT_INCOMPLETE` |

On `PAYMENT_FAILED` **no subscription is created and the cart is untouched**.

### FR-6: Start subscriptions

For each subscription line in snapshot order that has no recorded result yet (FR-3.3
failures are already recorded), call Subscription
`POST /internal/subscriptions` with:

```json
{ "userId": "...", "productId": "...", "quantity": 2,
  "schedule": { "type": "DAILY" | "ALTERNATE_DAYS" },
  "startDate": "2026-09-27", "slotId": "...",
  "idempotencyKey": "checkout:{checkoutId}:{lineId}", "correlationId": "..." }
```

- Frequency → schedule: `DAILY → DAILY`, `ALTERNATE_DAYS → ALTERNATE_DAYS`.
- `2xx` → record `{lineId, subscriptionId, status: CREATED, nextDeliveryDate}` on the checkout.
- `422` (e.g. `PRODUCT_NOT_ELIGIBLE`, `INVALID_SCHEDULE`) → record
  `{lineId, status: FAILED, reason: <errorCode>}`, continue with the next line. The
  one-time order stands. These are independent purchases.
- Transient failure after retries → stop; checkout stays `IN_PROGRESS`;
  `503 CHECKOUT_INCOMPLETE`. A retry re-calls every not-yet-recorded line, and the
  derived idempotency key makes a line that actually succeeded return the same
  subscription.

### FR-7: Clear the cart

- Remove the lines that were **checked out successfully** (every one-time line if the
  order is `CONFIRMED`, plus every subscription line with `status: CREATED`) via Cart
  internal `remove-items` with `ifVersion = snapshot cart_version`, `reason: CHECKOUT`,
  `checkoutId`.
- `409 CART_VERSION_MISMATCH` (Cart's existing code; the customer edited the cart from
  another device mid-checkout) → re-read the cart and retry once with its current version.
  The retry removes only snapshot lines that are **still present and unchanged**: same
  `productId`, `quantity`, `frequency`, `startDate` and `slotId` as the snapshot. Cart
  keeps a line's ID across quantity edits, so a snapshot line that changed may hold
  units the customer added after the snapshot. Such a line stays in the cart and its ID
  goes into the result's `linesChangedDuringCheckout`. A second `409` counts as
  transient (below).
- Lines recorded `FAILED` in FR-3.3 or FR-6 stay in the cart so the customer can see and fix them.
- Transient failure → checkout stays `IN_PROGRESS`, `503 CHECKOUT_INCOMPLETE` (retry resumes here).
- Success → checkout `COMPLETED`, result stored.

### FR-8: Delivery date for the one-time order

`now` in IST; `cutoff = CHECKOUT_CUTOFF_HOUR_IST` (defaults to, and must equal,
Subscription Service's `cutoff_hour_ist`, currently **20**, i.e. 8 PM, confirmed by
Product 2026-09-25 to apply to one-time deliveries).
`delivery_date = today + 1` if `now < today@cutoff`, otherwise `today + 2`.

### FR-9: Success response (`200`, also stored for replay)

```json
{
  "checkoutId": "chk_…",
  "status": "COMPLETED",
  "order": {
    "orderId": "ord_…", "status": "CONFIRMED", "amountPaise": 10820,
    "deliveryDate": "2026-09-26",
    "items": [ { "productId": "p_buffalo_milk", "quantity": 1 } ]
  },
  "subscriptions": [
    { "lineId": "li_2", "productId": "p_cow_milk", "status": "CREATED",
      "subscriptionId": "sub_…", "nextDeliveryDate": "2026-09-27" },
    { "lineId": "li_3", "productId": "p_paneer", "status": "FAILED",
      "reason": "PRODUCT_NOT_ELIGIBLE" },
    { "lineId": "li_4", "productId": "p_curd", "status": "FAILED",
      "reason": "START_DATE_PAST" }
  ],
  "linesChangedDuringCheckout": [],
  "walletBalanceAfterPaise": 34180
}
```

- `order` is `null` for a subscription-only cart.
- `walletBalanceAfterPaise`: if the checkout debited, it's the stored
  `balance_after_paise`. A resumed checkout has it too: either the row already has it,
  or the resumed debit call (a Wallet replay) returns it. If nothing was debited (no
  order, or a zero-amount order), Order reads `GET /wallet/internal/balance` once when
  it completes. If that read fails, the value is `null` and the checkout still
  completes. The value is stored in `result`, so replays return the same number.

### FR-10: Read APIs

`GET /orders/me` and `GET /orders/{id}` add `source` (`SUBSCRIPTION | CHECKOUT`) and
`items: [{productId, quantity}]` (for subscription orders, one item built from
`product_id`/`quantity`). `subscriptionId` is `null` for checkout orders. The
`subscriptionId` filter keeps working, and checkout orders never match it.

### FR-11: Subscription Service internal create

`POST /internal/subscriptions`, network-level protection identical to the
existing `POST /internal/run-daily` (VPC-only, no JWT). Body = the public
`CreateSubscriptionRequest` + `userId` + optional `correlationId`. It calls the same
`SubscriptionService.create(...)` and returns the same response and error codes as the
public route. No business-logic change.

## 5. Non-Functional Requirements

- **Money safety:** never more than one debit per checkout (DB-level `UNIQUE(user_id,
  idempotency_key)` on `checkouts`, `UNIQUE(checkout_id)` on `orders`, Wallet's
  ledger-ref idempotency). Never a subscription created after a failed debit.
- **Latency:** p95 ≤ 2.5 s for a cart of ≤ 10 lines (User + Pricing + Wallet balance +
  debit + N subscription creates + cart clear, all sequential except where noted).
  Dependency timeouts: 3 s each, 2 retries with backoff (existing `call_with_retry`).
- **Concurrency:** partial unique index `checkouts(user_id) WHERE status = 'IN_PROGRESS'`
  → at most one live checkout per user.
- **Security:** `userId` only from the JWT; internal clients use SigV4 (Cart) or VPC-only
  (Wallet, Subscription), matching each target's existing convention.
- **Observability:** structured logs `checkout.started|paid|subscription_created|
  subscription_failed|cart_cleared|completed|payment_failed|incomplete` with
  `checkoutId`, `userId`, `orderId`, `correlationId`; metric `checkout_incomplete_count`
  with an alarm on > 0 for 15 min.

## 6. Technical Design

```
App ──POST /orders/checkout──▶ Order Service
                                 │ replay? ── checkouts(user,key) ──▶ return / resume
                                 ├─▶ Cart   GET  /cart/internal/users/{id}        (SigV4)
                                 ├─▶ User   delivery-address-state                 (SigV4, existing)
                                 ├─▶ Pricing POST /pricing/quote  (one-time lines)  (existing)
                                 ├─▶ Wallet GET  /wallet/internal/balance          (existing)
                                 │   [txn] insert checkout IN_PROGRESS + order CREATED + items
                                 ├─▶ Wallet POST /wallet/internal/debit             (existing)
                                 │   [txn] order CONFIRMED + OrderConfirmed outbox
                                 ├─▶ Subscription POST /internal/subscriptions × N     
                                 ├─▶ Cart   POST /cart/internal/users/{id}/remove-items (SigV4)
                                 └── checkout COMPLETED ──▶ 200 result
```

- `domain/checkout_service.py` (new `CheckoutService`), kept separate from
  `OrderService.materialize`, sharing the repository and the Pricing/Wallet/User ports.
- Resumability: the checkout row stores `step ∈ {STARTED, CHARGING, PAID,
  SUBSCRIPTIONS_DONE}` plus per-line subscription results. Each step from `CHARGING` on
  is idempotent, so resume = "run from the first incomplete step". A `STARTED` attempt
  is discarded rather than resumed (FR-2a).
- No external HTTP call happens inside a DB transaction (existing codebase rule).
- New adapters: `cart_client_adapter.py` (SigV4 via `shared.adapters.sigv4`, with a
  POST signer added if only GET exists), `subscription_client_adapter.py`, and
  `WalletClientPort.get_balance`.
- Handler: `handlers/checkout_handlers.py`, router registered in `handlers/app.py`.

## 7. Data Considerations

Migration `0002_checkout.sql`:

```sql
ALTER TABLE orders ALTER COLUMN subscription_id DROP NOT NULL;
ALTER TABLE orders ALTER COLUMN product_id      DROP NOT NULL;
ALTER TABLE orders ALTER COLUMN quantity        DROP NOT NULL;
ALTER TABLE orders ADD COLUMN source      VARCHAR(16) NOT NULL DEFAULT 'SUBSCRIPTION';
ALTER TABLE orders ADD COLUMN checkout_id VARCHAR(64) UNIQUE;
ALTER TABLE orders ADD CONSTRAINT orders_source_shape CHECK (
  (source = 'SUBSCRIPTION' AND subscription_id IS NOT NULL AND product_id IS NOT NULL AND quantity IS NOT NULL)
  OR (source = 'CHECKOUT' AND checkout_id IS NOT NULL AND subscription_id IS NULL)
);

CREATE TABLE order_items (
  order_id   VARCHAR(64) NOT NULL REFERENCES orders(id),
  line_no    INTEGER     NOT NULL,
  product_id VARCHAR(64) NOT NULL,
  quantity   INTEGER     NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (order_id, line_no)
);

CREATE TABLE checkouts (
  id              VARCHAR(64) PRIMARY KEY,
  user_id         VARCHAR(64) NOT NULL,
  idempotency_key VARCHAR(128) NOT NULL,
  cart_version    INTEGER     NOT NULL,
  status          VARCHAR(16) NOT NULL,          -- IN_PROGRESS | COMPLETED | PAYMENT_FAILED
  step            VARCHAR(24) NOT NULL,          -- STARTED | CHARGING | PAID | SUBSCRIPTIONS_DONE
  lines           JSONB       NOT NULL,          -- snapshot (shared JSONColumn type)
  pay_now_paise   BIGINT      NOT NULL CHECK (pay_now_paise >= 0),
  delivery_date   DATE        NOT NULL,
  order_id        VARCHAR(64),
  balance_after_paise BIGINT,                    -- from the debit (FR-5); NULL if no debit
  subscription_results JSONB  NOT NULL DEFAULT '[]',
  result          JSONB,                         -- stored FR-9 body or error for replay
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, idempotency_key)
);
CREATE UNIQUE INDEX checkouts_one_live_per_user ON checkouts(user_id) WHERE status = 'IN_PROGRESS';
```

- The existing `UNIQUE(subscription_id, delivery_date)` keeps working: Postgres treats
  NULLs as distinct, so checkout orders never collide.
- `Order` dataclass: `subscription_id`, `product_id`, `quantity` become optional; add
  `source`, `checkout_id`, `items`.
- Existing rows backfill to `source = 'SUBSCRIPTION'` via the column default.
- JSON columns use the shared `JSONColumn` type (commit `d2afde0`), not raw
  `json.dumps`, which avoids the double-encoding bug that commit fixed.

## 9. Edge Cases and Failure Modes

| Case | Behavior |
|------|----------|
| Double tap (same key) | Second call replays or resumes, one order |
| Retry with a **new** key after success | Cart was cleared → version bumped → `409 CART_CHANGED`/`CART_EMPTY`; no second order |
| Two devices confirm at once | Partial unique index → the second gets `409 CHECKOUT_IN_PROGRESS` while the first is busy (FR-2a) |
| App killed after debit, before response | Next Confirm reuses the persisted key (MA-137) → resume → same result |
| App lost its key mid-checkout (logout, reinstall, other device) | After `CHECKOUT_BUSY_SECONDS`, a Confirm with a new key adopts (`≥ CHARGING`) or discards (`STARTED`) the old checkout (FR-2a); never blocked for good |
| App killed before the debit, cart then edited | The attempt is still `STARTED` → discarded; the new body is validated from scratch, so the customer is charged what they now see |
| Debit OK, Subscription Service down | `503 CHECKOUT_INCOMPLETE`; order stays CONFIRMED; retry creates subscriptions idempotently |
| One subscription line ineligible | That line `FAILED` and kept in cart; everything else completes |
| Subscription line with a past start date or no slot | That line `FAILED` (`START_DATE_PAST` / `SLOT_MISSING`) and kept in cart; everything else completes. `422 LINE_INVALID` only if nothing else would be checked out |
| One-time lines all priced at 0 | Order created `CONFIRMED` with `amount_paise = 0`, no debit; lines cleared from the cart |
| Cart line quantity edited on another device mid-checkout | That line is left in the cart and listed in `linesChangedDuringCheckout`; unchanged lines are cleared |
| Price changed between review and confirm | `409 PRICE_CHANGED` before any side effect |
| Wallet balance changes between pre-check and debit | Debit is authoritative → `402` with `shortfallPaise`, order `PAYMENT_FAILED`, nothing else happens |
| Subscription-only cart | No order, no debit; subscriptions created; min-balance pre-check still applies |
| Client abandons an `IN_PROGRESS` checkout | Blocks new checkouts for at most `CHECKOUT_BUSY_SECONDS`. The paid part waits until the next Confirm, or the sweep in §11 |

## 10. Testing Strategy

- **Unit (`CheckoutService`, fakes for every port):** each FR-3 rejection; one-time-only,
  subscription-only, mixed; each debit outcome; subscription `422` vs transient;
  cart-clear `409` retry path (changed line kept and listed, unchanged lines removed);
  replay for each stored status; resume from each `step`; FR-2a matrix (busy → 409 with
  `retryAfterSeconds`; `STARTED` discarded and re-validated against the new body;
  `CHARGING` resumed with the snapshot; different key adopts); the `STARTED → CHARGING`
  compare-and-set loses after a discard; zero-amount one-time order (no debit call,
  `CONFIRMED` + outbox); FR-3.3 per-line failures alongside a successful checkout, and
  `422` when every line fails; debit `402` carries `requiredPaise`/`shortfallPaise`;
  `walletBalanceAfterPaise` on a resume past `PAID` and on a subscription-only cart.
- **Repository (SQLite in-memory, existing fidelity note):** migration applies on top of
  `0001`; `orders_source_shape` rejects invalid combinations; `UNIQUE(user_id,
  idempotency_key)`; partial unique index (SQLite supports partial indexes).
- **Integration (FastAPI TestClient, stubbed HTTP deps):** full happy path writes one
  order + items + outbox row, calls debit once, N subscription creates with derived
  keys, one remove-items call; kill-and-resume simulated by raising after debit, then
  replaying the same key → no second debit call.
- **Contract:** events validate against the updated schemas; `GET /orders/me` returns
  `source`/`items` for both order kinds.
- **Subscription Service:** internal create returns the same body as public create for
  the same input; idempotent on key; not reachable through the JWT API route.

## 11. Risks and Trade-offs

- **Server-side orchestration vs. client saga:** chosen so one idempotent record owns
  the whole flow; cost is Order Service taking three new dependencies.
- **Abandoned `IN_PROGRESS` checkouts** block the user for at most
  `CHECKOUT_BUSY_SECONDS`. After that, any Confirm adopts or discards them (FR-2a). A
  paid checkout whose customer never returns still waits with subscriptions uncreated
  and the cart uncleared. A reconciliation sweep that resumes checkouts stale > 10 min
  is deferred, the same deferral MA-132 §11 made for stuck `CREATED` orders. **Must land
  before production launch.**
- **Zero-amount one-time orders** skip Wallet entirely and are `CONFIRMED` with
  `amount_paise = 0`. No 100%-off offers exist yet, so today this only happens when a
  product is priced at 0.
- **Min-balance rule for subscriptions** is duplicated between Cart and Order (same env
  value); drift risk is noted in both specs.
- Stock isn't reserved, so an out-of-stock product can be ordered; accepted per PO-5.
