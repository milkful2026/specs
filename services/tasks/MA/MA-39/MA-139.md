## 2. Problem Statement

Today `services/user`'s `users` table has no account-lifecycle concept at all — every account is implicitly and permanently usable once registered. There is no way for an admin to stop a fraudulent, abusive, or requested-closure customer account from logging in, having orders fulfilled, or being auto-debited, short of a manual database edit. As the platform scales past its initial cohort, operations staff need a safe, audited, reversible way to suspend or deactivate a customer account from the admin console.

**Expected outcome:** A backend capability that lets an authorized admin change a customer account's status (Active / Suspended / Deactivated), immediately blocks further logins for a non-Active account, publishes a durable audit trail and a domain event that Subscription Service reacts to (see the paired spec, MA-140), while leaving order history and wallet balance untouched.

## 3. Scope

### In Scope

- `status` lifecycle on the `users` table: `Active` (default) → `Suspended` (temporary, has an end date) or `Deactivated` (indefinite) → back to `Active` via explicit reactivation, or automatically for `Suspended` once its end date passes
- Durable `user_status_history` audit trail (who, what, when, why) — this service's own fallback source of truth until MA-50's audit pipeline exists
- Admin-only APIs: list/search/filter-by-status, get-detail-with-history, suspend, deactivate, reactivate (single + bulk)
- Extending `CognitoAttributePort` with `disable_user` / `enable_user` (consumer-pool `AdminDisableUser` / `AdminEnableUser`) so a blocked account cannot complete a new login
- A background sweep that auto-lifts `Suspended` accounts whose end date has passed
- Publishing `user.status.changed` via the existing transactional-outbox pattern (this spec owns the event's contract; MA-140 consumes it)

### Out of Scope

- Any Subscription-service behavior triggered by the event — owned by the paired spec [MA-140](https://milkfuldairyindia.atlassian.net/browse/MA-140)
- Wallet Service — confirmed no change needed (Step 2 finding: pausing the subscription already prevents the orders that would trigger a debit)
- `portal-ui` screens — covered by the paired spec [MA-141](https://milkfuldairyindia.atlassian.net/browse/MA-141)
- KYC capture/verification, fraud scoring, or filtering by either — nothing in the platform stores this data yet; the list filters by status and searches by name/phone/email only
- B2B-specific behavior — `account_type` (MA-21) is orthogonal to `status`; both B2C and B2B accounts (once B2B exists) share the same status lifecycle
- Automatic disable on repeated payment failures or fraud signals — deferred; v1 is manual, admin-initiated only
- Hard delete / GDPR-style erasure
- Any change to the existing consumer Cognito pool's OTP registration/login *flows* themselves (MA-1/MA-21) — this is additive; `AdminDisableUser` changes account state, not the OTP mechanism

## 4. Functional Requirements

### FR-1: List / Search / Filter Customer Accounts

`GET /v1/admin/customers` — admin-authorized (Ops or SuperAdmin role claim; see §5 Security and MA-141 §4). Paginated list with `status` filter and free-text search over name/mobile/email. Returns each account's `id`, `name`, `mobile`, `email`, `accountType`, `status`, `statusReason`, `lastStatusChangeAt` (the most recent `user_status_history.created_at` for this account — a `timestamptz`, deliberately not `users.status_effective_from`, which is only a `DATE` and loses the time-of-day precision a "last changed" display needs; `NULL` for an account that has never had a status change).

### FR-2: Account Detail with Status History

`GET /v1/admin/customers/{id}` — returns the account's current profile plus its full `user_status_history` (previous status, new status, reason, effective date, actor, timestamp), newest first. `404 CUSTOMER_NOT_FOUND` if no matching row.

### FR-3: Suspend

`POST /v1/admin/customers/{id}/suspend` — accepts `{ reason, until }` (`until`: required, a future date). Sets `status = Suspended`, `status_reason = reason`, `suspended_until = until`, `status_effective_from = now`. Calls Cognito `AdminDisableUser` on the consumer pool for this account's `cognito_sub`. Writes a `user_status_history` row and publishes `user.status.changed` (both in the same DB transaction as the status write, via the outbox). Returns `409 INVALID_STATUS_TRANSITION` if the account is already `Deactivated` (deactivation must be explicitly reactivated first, not silently downgraded to a suspension).

### FR-4: Deactivate

`POST /v1/admin/customers/{id}/deactivate` — accepts `{ reason }`. Sets `status = Deactivated`, `status_reason = reason`, `status_effective_from = now`, `suspended_until = NULL`. Same Cognito `AdminDisableUser` call, history row, and event publish as FR-3. Idempotent: deactivating an already-`Deactivated` account returns `200` with the existing state unchanged (not an error) rather than requiring the caller to check current status first — bulk actions (FR-6) rely on this.

### FR-5: Reactivate

`POST /v1/admin/customers/{id}/reactivate` — accepts `{ reason }` (optional; recorded for the audit trail). Sets `status = Active`, `suspended_until = NULL`. Calls Cognito `AdminEnableUser`. Writes history + publishes the event with `newStatus = Active`. **Does not** touch any of the customer's subscriptions — per D2 (resolved in Step 1), a subscription paused by this story's own deactivation flow stays paused until the customer or an admin resumes it explicitly; reactivating the account is not resuming its subscriptions.

### FR-6: Bulk Status Change

`POST /v1/admin/customers/bulk-status` — accepts `{ customerIds: string[], action: "suspend"|"deactivate"|"reactivate", reason, until? }`. Applies FR-3/4/5's single-account logic once per ID, independently — **no shared transaction across rows**, so one account's failure (e.g. a Cognito timeout) does not roll back the others. Returns a per-ID result array: `{ customerId, success, errorCode? }`. Matches AC-6's "one failure doesn't roll back others" requirement by construction, not by special-casing.

### FR-7: Auto-Lift Expired Suspensions

A scheduled sweep (EventBridge Scheduler, mirrors Subscription's own Daily Run shape — new schedule, not shared infrastructure) queries `users WHERE status = 'Suspended' AND suspended_until <= today`, and for each: sets `status = Active`, `suspended_until = NULL`, calls `AdminEnableUser`, writes a `user_status_history` row with `actor = "system:suspension-sweep"`, publishes `user.status.changed`. Runs once daily; exact time is an implementation choice (recommend outside the Subscription Daily Run's own cut-off window to avoid resource contention — flagged, not fixed, in §12).

## 5. Non-Functional Requirements

- **Performance:** List/search p95 < 500ms for up to 50,000 customer accounts (indexed on `status`, and on `name`/`mobile`/`email` via existing lookup patterns); single status-change action p95 < 400ms including the Cognito call.
- **Security:** All `/v1/admin/customers*` endpoints require a valid admin JWT (MA-129's admin authorizer) with an Ops or SuperAdmin role claim, checked server-side — never trust a client-supplied role. `AdminDisableUser`/`AdminEnableUser` calls use IAM credentials scoped only to the consumer pool ARN (least privilege, no broader Cognito access granted).
- **Reliability:** A status change must not partially apply — the `users` row update, the `user_status_history` insert, and the outbox row are one DB transaction; the Cognito call happens synchronously in the same request (compensating: if `AdminDisableUser` fails after the DB commit, the handler returns a `502` but the DB state is retried-safe on the next attempt to the same account, since FR-4/FR-3 are idempotent on status).
- **Scalability:** No special scaling design beyond User Service's existing Lambda/Aurora defaults — customer accounts are the platform's largest user_id-keyed table but this feature adds indexed reads/writes, not a new access pattern class.
- **Observability:** CloudWatch metric on `user.status.changed` volume by `newStatus`; alarm on an unusual spike in `Deactivated` (bulk-action misuse or automation error) — mirrors MA-129's `admin.login.failed` alarm precedent. Structured logs with correlation ID on every status-change call.

## 6. Technical Design

### Architecture Approach

Extend User Service (Lambda, per `services/README.md`'s service inventory) with:
1. New `status`/`status_reason`/`status_effective_from`/`suspended_until` columns on `users`, plus a new `user_status_history` table — both in User Service's existing Aurora `users` cluster.
2. New admin-only handlers behind the existing admin JWT authorizer path (MA-129's authorizer, already role-aware — extended, not duplicated).
3. `CognitoAttributePort` (`cognito_attribute_adapter.py`) gains `disable_user(cognito_sub)` / `enable_user(cognito_sub)`, calling `AdminDisableUser`/`AdminEnableUser` against the **consumer** pool (the same pool `sync_profile_attributes`/`get_mobile_by_sub` already target) — no new adapter file, this is an additive method on the existing one.
4. A new scheduled Lambda (or an extension of an existing scheduled entrypoint, implementer's choice) for FR-7's sweep.

### Component Responsibilities

- **Admin customer handlers** (`src/handlers/admin_customers/`) — thin, map HTTP ↔ domain
- **Customer status domain** (`src/domain/customer_status_service.py`) — status-transition rules (§9's table), bulk orchestration, history-row construction
- **Adapters** — extended `cognito_attribute_adapter.py` (consumer pool disable/enable), `user_repository.py` (extended with status read/write + history + outbox), existing `outbox_event_publisher.py` (reused, no change)

### Workflow (Deactivate)

```
POST /admin/customers/{id}/deactivate {reason}
  → load user by id → 404 if missing
  → if already Deactivated: return 200 unchanged (idempotent)
  → DB transaction: UPDATE users SET status=Deactivated, status_reason, status_effective_from
                    INSERT user_status_history (previous, new, reason, actor, now)
                    INSERT outbox_events (user.status.changed, payload)
  → commit
  → call Cognito AdminDisableUser(cognito_sub)
      → on failure: log error, return 502 (DB state already committed and is
        idempotent-safe to retry — the next deactivate call for this account
        is a no-op per the idempotency rule above, so a retry naturally
        re-attempts only the Cognito call's effect, not a duplicate history row)
  → return 200 with the updated account
```

### API/Interface Definitions

See §4 for endpoints. All responses use the standard envelope (`services/README.md` §5).

### Data Flow

`portal-ui` (MA-141) → API Gateway (admin JWT authorizer, MA-129) → User Service Lambda → Aurora `users`/`user_status_history` + consumer Cognito Pool → EventBridge default bus → `subscription-events-q` (new, consumed by MA-140).

## 7. Data Considerations

### Schema: `users` (Aurora, extends the existing table — additive migration)

```sql
ALTER TABLE users ADD COLUMN status TEXT NOT NULL DEFAULT 'Active'
  CHECK (status IN ('Active', 'Suspended', 'Deactivated'));
ALTER TABLE users ADD COLUMN status_reason TEXT;
ALTER TABLE users ADD COLUMN status_effective_from DATE;
ALTER TABLE users ADD COLUMN suspended_until DATE;  -- NULL unless status = 'Suspended'
```

Backfill: existing rows get `status = 'Active'` via the column default — same additive-migration shape as MA-21's `account_type` column (no separate backfill script, no downtime).

### Schema: `user_status_history` (new table, same Aurora cluster)

| Column | Type | Notes |
|--------|------|-------|
| `id` | uuid, PK | |
| `user_id` | uuid, FK → `users.id` | indexed |
| `previous_status` | text, nullable | null only for a row's very first status (never occurs post-migration, since the default backfill doesn't write history — first real row is the first admin action) |
| `new_status` | text | |
| `reason` | text, nullable | |
| `effective_from` | date, nullable | set for `Suspended`/`Deactivated`; null for `Active` (reactivation) |
| `actor_admin_id` | text | admin's id from the JWT, or `"system:suspension-sweep"` for FR-7 |
| `created_at` | timestamptz | default now() |

**Validation rules:** `reason` required (non-empty) for suspend/deactivate; `until` (suspend) must be a future date; a `Suspended` row without `suspended_until` is invalid — enforced at the domain layer, not just a DB constraint, so the error message is actionable (`400 VALIDATION_ERROR`, not a raw constraint violation).

## 8. Integration Considerations

- **Upstream:** `portal-ui` (MA-141) is the only caller of the admin endpoints in this spec.
- **Downstream:** EventBridge (default bus) → new `subscription-events-q` (+DLQ) → Subscription Service's consumer (MA-140, this story's paired spec — **the event contract below is authoritative; MA-140 must not redefine it**). No other consumer exists yet; `user.status.changed` is published regardless (fire-and-forget is correct — this spec should not block on MA-140 or MA-50 existing).
- **Cognito consumer pool:** `AdminDisableUser`/`AdminEnableUser` calls wrapped in the existing adapter retry/backoff pattern (`services/README.md` §3.7); a Cognito outage surfaces as a `502` per the workflow in §6, mapped per the standard error table.
- **Identity & Auth (checklist item, not a spec — see MA-39's decomposition notes):** confirm `login_otp_send_handler.py`/`login_otp_verify_handler.py` (or the underlying Cognito SDK call chain) map a `UserDisabledException` to a clean client-facing error (e.g. `403 ACCOUNT_DEACTIVATED`) rather than an unhandled `5xx`. If it doesn't already, this is a small, additive fix inside `services/identity-auth`, tracked as an implementation note on this spec rather than its own Task — see §12.
- **No cross-service DB reads** — Subscription Service must never query User Service's Aurora directly; it only consumes `user.status.changed`'s payload.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| Suspend/deactivate an account that is already in that exact status | Idempotent `200`, no duplicate history row, no duplicate event (FR-4) |
| Suspend an already-`Deactivated` account | `409 INVALID_STATUS_TRANSITION` — must reactivate first (FR-3) |
| Deactivate an already-`Suspended` account | Allowed — `Deactivated` supersedes `Suspended`; `suspended_until` is cleared |
| `AdminDisableUser` succeeds but the DB transaction that preceded it already committed, then a later step fails | Cannot happen by construction — the DB transaction commits *before* the Cognito call (§6), so the only failure mode is "DB committed, Cognito call failed," never the reverse; see the compensating-retry note in §6 |
| Suspension sweep (FR-7) runs while an admin concurrently reactivates the same account manually | Last write wins at the DB layer; whichever transaction commits second determines final `status` — acceptable given low concurrent-edit likelihood on a single account, consistent with MA-129's own accepted-risk precedent for concurrent admin edits |
| Bulk action includes a customer ID that doesn't exist | That row's result is `{success: false, errorCode: "CUSTOMER_NOT_FOUND"}`; other rows proceed normally (FR-6) |
| Cognito `AdminDisableUser` called for a `cognito_sub` that no longer exists (edge case, e.g. manual Cognito console deletion) | Adapter surfaces this as a retryable `502`, not silently swallowed — an orphaned Aurora-without-Cognito state must be visible to the caller, not hidden |
| Reactivating an account whose subscriptions were paused by this feature | Subscriptions remain paused (D2) — this endpoint only changes `users.status` and Cognito state, never touches Subscription Service directly or indirectly |

## 10. Testing Strategy

- **Unit:** status-transition validation (the table in §9), idempotency-on-repeat-action, bulk per-row independence, history-row construction, CIDR-free validation of `reason`/`until`.
- **Integration:** `moto`-mocked Cognito (consumer pool) + EventBridge, SQLite/Aurora-compatible in-memory DB, following the exact offline-testing pattern already established in `user`/`identity-auth` (no AWS credentials, no Docker) — same precedent MA-129 §10 cites.
- **Contract:** `user.status.changed` payload shape verified against what MA-140's consumer expects (shared fixture/schema, not independently re-derived in each spec).
- **E2E:** at least one full journey — admin deactivates a customer, that customer's next login attempt is refused, admin reactivates, login succeeds again — before merge, per `services/README.md` §6.
- **Negative scenarios required:** deactivate-already-deactivated (idempotent), suspend-already-deactivated (409), bulk action with one bad ID, missing `reason`, past-dated `until`, Cognito call failure after DB commit.

## 11. Risks and Trade-offs

1. **DB-commit-then-Cognito-call ordering** (§6, §9) — chosen over the reverse (Cognito-then-DB) because a DB-committed status change that failed to reach Cognito is safely retried by re-issuing the same idempotent request, whereas a Cognito-succeeded-but-DB-failed state would leave Cognito and Aurora disagreeing with no natural retry trigger (the caller sees an error and doesn't know the Cognito half already happened). This mirrors MA-129 FR-3's saga-with-compensation pattern in spirit, but as ordering rather than an explicit compensating delete (deactivation has nothing analogous to "delete the orphaned Cognito user" — disabling an already-disabled user is itself idempotent).
2. **No optimistic locking on concurrent status changes** (§9) — accepted given the same low-concurrent-edit-likelihood reasoning MA-129 already established for admin-account edits; revisit if incidents actually occur.
3. **Suspension sweep is a new scheduled job**, not reused infrastructure — a small new operational surface (one more EventBridge Scheduler rule + Lambda), but keeping it separate from Subscription's own Daily Run avoids coupling two unrelated schedules' failure domains together.
4. **`actor_admin_id` is stored as the raw JWT-derived id, not a foreign key to `admin_user`** — because `admin_user` lives in Identity & Auth's database (database-per-service), a cross-service FK is impossible; this is a deliberate denormalization, consistent with how MA-129's own events carry admin identity by value, not by reference.

## 12. Open Questions

1. **Identity & Auth error-mapping** (§8) — needs a human/implementer check: does `UserDisabledException` already surface cleanly from the existing login handlers, or does it need an explicit catch? Flagged as a small implementation-time spike, not blocking this spec's drafting.
2. **Exact sweep schedule time** (FR-7) — needs a decision to avoid colliding with Subscription's Daily Run cut-off window; not blocking, a reasonable off-peak default (e.g. 3 AM IST) can be chosen at implementation time and revised later.
3. Should Ops role alone be sufficient for suspend/deactivate/reactivate, or should deactivate (the more consequential, indefinite action) require SuperAdmin specifically? Recorded here as an open question for the portal-ui spec (MA-141) and this spec's authorizer check to agree on before implementation — see MA-141 §12.
