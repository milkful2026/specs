# Subscription Service — Admin-Triggered Pause Consumer

## 1. Overview

- **Title:** Subscription Service — Admin-Triggered Pause Consumer

- **Related JIRA Task:** [MA-140](https://milkfuldairyindia.atlassian.net/browse/MA-140)
- **Author:** SDD Agent (spec-driven-designer)
- **Date:** 2026-09-28
- **Stakeholders:** Backend engineering (Subscription Service owner), User Service owner (event producer), Admin/Ops engineering

> **Owning service:** Subscription Service (MA-98). This spec adds one new EventBridge consumer to the existing service — no schema change, no new domain rule, reuses `pause()` exactly as MA-131 built it.
>
> **Process note:** Same as MA-139/MA-141 — Task left at its default status.

## 2. Problem Statement

MA-39 requires that deactivating (or suspending) a customer account stops future deliveries and charges for that customer's active subscriptions, without a human having to separately go pause each one. Subscription Service already has a complete, correct pause mechanism (`SubscriptionStatus.PAUSED`, `pause_from`/`pause_until`, and a Daily Run that already excludes paused subscriptions from due-computation) — but it is reachable only by the owning customer today (`pause()` requires the calling `user_id` to match the subscription's owner). There is no admin- or system-initiated path.

**Expected outcome:** Every active subscription belonging to a customer whose account transitions to `Suspended` or `Deactivated` is paused indefinitely (`until=None`), automatically and reliably, shortly after that transition — without widening the existing customer-facing `pause()` endpoint's authorization.

## 3. Scope

### In Scope

- A new, idempotent EventBridge consumer for `user.status.changed` (contract owned by [MA-139](https://milkfuldairyindia.atlassian.net/browse/MA-139) — this spec does not redefine it)
- A new internal domain entrypoint that pauses every active subscription for a given `user_id`, distinct from and not widening the existing customer-owned `pause()` method
- New SQS queue `subscription-events-q` + DLQ, and the EventBridge rule routing `user.status.changed` (where `newStatus` is `Suspended` or `Deactivated`) to it

### Out of Scope

- Reacting to `newStatus = Active` (reactivation) — per D2 (resolved in MA-39's Step 1), paused-by-admin subscriptions stay paused until explicitly resumed by the customer or an admin; this consumer is one-directional (pause only)
- Any change to the customer-facing `pause()`/`resume()` endpoints, their request/response shapes, or their ownership check
- Any change to the Daily Run's due-computation logic — it already correctly excludes paused subscriptions (confirmed in MA-39 Step 2); this spec only adds a new way to *reach* the existing `PAUSED` state
- Wallet Service — no interaction; this spec's only effect is on `subscriptions.status`
- Un-pausing on account reactivation (see "Out of Scope" above — explicitly not built here)

## 4. Functional Requirements

### FR-1: Consume `user.status.changed`

A new Lambda (or an extension of the existing subscription event-consumption entrypoint, implementer's choice — mirrors the shape of Subscription's existing outbox-consumer precedent) polls `subscription-events-q`. For each message where `payload.newStatus` is `Suspended` or `Deactivated`:
1. Look up all subscriptions for `payload.userId` with `status = ACTIVE` (or `PAUSED` with a still-future `pause_from`, per the existing Daily Run's own "non-STOPPED" filter precedent — a not-yet-started pause should also be caught here rather than left to independently resolve).
2. For each, call the new internal pause entrypoint (FR-2) with `reason = "account_" + newStatus.lower()` (e.g. `"account_deactivated"`) for traceability distinct from a customer-initiated pause.
3. Delete the message from the queue only after all subscriptions for that user have been paused successfully (partial failure leaves the message for redrive, per the idempotent-consumer guardrail).

### FR-2: Internal Admin-Pause Entrypoint

A new domain method, e.g. `pause_for_account_status_change(subscription_id: str, reason: str)` — **not** a parameter added to the existing `pause(subscription_id, user_id, from_, until, now)`, which stays exactly as MA-131 built it (still requires `user_id` ownership, still customer-only). The new method:
- Skips the ownership check (this is an internal, system-initiated call, not exposed via any public API route)
- Calls `_repo.update_pause(sub.id, pause_from=today, pause_until=None, status=SubscriptionStatus.PAUSED)` — the exact same repository call the existing `pause()` makes, just invoked from a different, narrowly-scoped caller
- Is idempotent: pausing an already-`PAUSED` subscription is a no-op (checked before calling the repository), so redelivery of the same event never double-writes or errors

### FR-3: Idempotency and Redelivery

The consumer as a whole is idempotent per FR-1/FR-2: redelivering the same `user.status.changed` event (EventBridge/SQS at-least-once delivery) re-derives the same target subscription set and re-applies the same (already-applied) pause, which FR-2 makes a no-op. No separate dedupe table is needed — this differs from MA-126/MA-127's payment-idempotency precedent (which needs a dedupe key because *crediting money* is not naturally idempotent); pausing a subscription is naturally idempotent by construction.

## 5. Non-Functional Requirements

- **Performance:** Not customer-facing — no p95 latency target in the usual sense; target end-to-end freshness (event published → subscriptions actually paused) of **under 5 minutes** under normal queue conditions, consistent with D7's accepted "short eventually-consistent delay" trade-off.
- **Reliability:** Idempotent consumer (FR-3); DLQ + CloudWatch alarm on `subscription-events-q` depth > 0, matching every other consumer queue in the messaging topology (`milkful-messaging.drawio` §7.2's existing pattern).
- **Security:** No new external-facing surface — this is a queue consumer only, invoked by EventBridge, not reachable by any client. IAM role scoped to read `subscription-events-q` and write to `subscriptions` (already-owned data), no new cross-service permission.
- **Observability:** CloudWatch metric on subscriptions paused via this path (`subscription.admin_pause.count`), tagged by `reason`; alarm on DLQ depth > 0.

## 6. Technical Design

### Architecture Approach

Add one new EventBridge rule (`UserStatusChangedRule`, matching `source: "user"`, `detail-type: "user.status.changed"`, `detail.newStatus` in `["Suspended", "Deactivated"]`) routing to a new `subscription-events-q` (+ DLQ), consumed by a new handler inside the existing Subscription Service deployable — same compute (Lambda, per `services/README.md`'s inventory), no new service.

### Component Responsibilities

- **New handler** (`src/handlers/user_status_changed_handler.py`) — thin, maps the SQS/EventBridge message to a call into the domain
- **`subscription_service.py`** — gains `pause_for_account_status_change(...)` (FR-2), sitting alongside the existing `pause`/`resume`/`stop` methods, sharing their repository call but not their public-facing signature or ownership check

### Workflow

```
User Service: users.status → Deactivated (MA-139)
  → outbox → EventBridge → UserStatusChangedRule
      → subscription-events-q
          → Subscription Service consumer:
              for each ACTIVE/not-yet-started-PAUSED subscription of userId:
                already PAUSED? → skip (idempotent no-op)
                else → pause_for_account_status_change(sub.id, reason="account_deactivated")
                       (internally: same update_pause() call the customer-facing
                        pause() already makes — until=None, pause_from=today)
          → delete message only once every subscription for that user is handled
```

### API/Interface Definitions

No public API — this spec adds no HTTP routes. The only "interface" is the consumed event contract, owned by MA-139 §8 (reproduced here for reference, not redefined):

```json
{ "eventType": "user.status.changed",
  "payload": { "userId", "previousStatus", "newStatus", "reason", "effectiveFrom", "actorAdminId" } }
```

### Data Flow

EventBridge → `subscription-events-q` (new) → Subscription Service Lambda → Subscription Service's own Aurora `subscriptions` cluster (existing, no schema change) → (Daily Run already respects the resulting `PAUSED` status, unchanged).

## 7. Data Considerations

**No schema change.** This spec reuses `subscriptions.status`, `pause_from`, `pause_until` exactly as they exist today (`services/subscription/src/domain/models.py`). The only new persisted concept is the `reason` string passed into the pause call, which — per the existing `pause()` implementation — is **not currently persisted on the subscription row at all** (MA-131's `pause()` takes no `reason` parameter). Two options for Step 3/implementation to settle, flagged here rather than decided:
- (a) extend the subscription's own schema/repository call to accept and store a `pause_reason`, or
- (b) leave the reason out of the subscription row entirely and rely solely on User Service's `user_status_history` (MA-139 §7) as the durable record of *why*, since the subscription row only needs to know *that* it's paused, not why.

**Recommend (b)** — avoids a schema change in this already-small spec, and the "why" is fully answered by querying the source event's origin (the customer's status history), not duplicated into a second table. Flagged as an explicit open question in §12 rather than silently decided.

## 8. Integration Considerations

- **Upstream:** User Service (MA-139) is the sole producer of the event this spec consumes. Contract is owned there; this spec must be updated if MA-139's event shape changes during implementation.
- **Downstream:** none — this spec has no consumers of its own. The Daily Run (existing, unchanged) is the only other code path that reads the `PAUSED` status this spec writes.
- **No cross-service DB reads** — this consumer only ever reads `payload.userId` off the event; it never queries User Service's `users` table.
- **Retries/timeouts:** standard SQS visibility-timeout + DLQ redrive pattern, consistent with every other consumer in the messaging topology; no new retry logic needed since the operation is naturally idempotent (§5 FR-3).

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| Customer has zero active subscriptions when their account is deactivated | Consumer finds no matching subscriptions, does nothing, deletes the message — not an error |
| Event redelivered for a user whose subscriptions are already paused | No-op per FR-2/FR-3 — safe, no duplicate state, no error |
| A subscription is customer-paused (with a real `until` date) at the same time the account is deactivated | The admin pause overwrites `pause_until` to `None` (indefinite) — deactivation is a stronger, indefinite override; the customer's original end date is lost, which is the correct behavior (an indefinite account block should not have a subscription silently un-pause on the customer's original schedule while the account is still deactivated) |
| Consumer fails partway through pausing a user's multiple subscriptions | Message is not deleted (per FR-1 step 3); redelivery retries the whole set, which is safe because already-paused ones are no-ops (FR-3) |
| `user.status.changed` event for `newStatus = Active` (reactivation) reaches this queue | Filtered out at the EventBridge rule level (§6) — never reaches the consumer at all, so there's no code path to accidentally auto-resume anything |
| Subscription Service's Daily Run runs concurrently with this consumer pausing a subscription mid-cycle | The Daily Run's existing `is_due` check already re-reads the pause window per subscription at run time (per MA-39 Step 2's own finding); a race either includes or excludes that day's order, never double-creates one — no new concurrency handling needed beyond what MA-131 already built |

## 10. Testing Strategy

- **Unit:** `pause_for_account_status_change` idempotency (already-paused no-op), reason-string construction, the "not-yet-started-PAUSED" inclusion rule (FR-1 step 1).
- **Integration:** `moto`-mocked EventBridge/SQS, SQLite/Aurora-compatible in-memory DB seeded with subscriptions in various states, following the same offline pattern as the rest of Subscription Service's existing test suite.
- **Contract:** consumed-event shape verified against MA-139's published contract (shared fixture, not independently re-derived).
- **E2E:** one full journey spanning both specs — User Service deactivates a customer with two active subscriptions → both end up `PAUSED` with `pause_until = None` within the test's polling window — before merge, per `services/README.md` §6.
- **Negative scenarios required:** redelivered event (no double-pause), customer with zero subscriptions, event for an unknown `userId` (no subscriptions found — not an error), malformed event payload (logged, sent to DLQ, not silently dropped).

## 11. Risks and Trade-offs

1. **Reason not persisted on the subscription row** (§7) — deliberate minimal-scope choice; revisit if support/ops ever need to see "why is this subscription paused" without cross-referencing the customer's own status history.
2. **One-directional consumer (no auto-resume on reactivation)** — a direct consequence of D2, not an oversight; a customer whose account is reactivated must explicitly resume their subscriptions, same as they would after any other manual pause, avoiding a surprise resumed-delivery/charge the day their account happens to be reactivated.
3. **New queue + DLQ + alarm is a small new operational surface** — the alternative (routing through an existing shared queue) was rejected because `user.status.changed` is semantically unrelated to Subscription's other event sources (`SubscriptionOrderDue`'s own Step Functions trigger), and sharing a queue across unrelated event types couples their failure/redrive domains for no benefit.

## 12. Open Questions

1. **Persist a pause reason on the subscription row, or not?** (§7) — recommends (b) "don't," but flagged for the implementer/architect to confirm, since it's the one place this spec makes a call not explicitly directed by the human-approved decomposition.
2. Exact SQS visibility timeout and DLQ redrive-count threshold — standard implementation-time tuning, not a design decision this spec needs to pin down.
