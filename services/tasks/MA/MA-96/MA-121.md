## 2. Problem Statement

No cart persistence exists anywhere in the platform. MA-23's product-configuration screen needs a
durable, cross-device, cross-session home for "what a customer has added" — without it, every add
is lost on app restart or device switch, directly contradicting the source ticket's own
requirement. This spec defines that service: CRUD on cart line items, stock-bound validation,
price/tax/delivery preview (via Pricing & Offer Service, MA-101/MA-122, spec'd in parallel), and a
one-time-vs-subscription distinction per item.

## 3. Scope

**In scope:**
- `GET /cart`, `PUT /cart`, `POST /cart/items`, `DELETE /cart/items/{id}` — contracts, validation,
  and behavior.
- DynamoDB `cart` table design (key structure, TTL).
- Synchronous calls to Inventory Service (stock re-validation) and Pricing & Offer Service (price
  quote) on relevant operations.
- `CartUpdated` EventBridge domain event, published via the platform's existing transactional
  outbox pattern.
- Response envelope + Cognito JWT auth, matching every other already-shipped service.

**Out of scope:**
- Re-order-from-history's data source (needs Order Service, MA-97, unbuilt) — this spec defines
  the shape only where it doesn't depend on Order Service; the actual "recreate my cart from a
  past order" flow is deferred until MA-97 exists.
- The Subscription lifecycle engine (MA-98) — this service only stores a line item's frequency/
  start-date attributes; it never generates recurring orders itself.
- Payment/checkout (MA-99/MA-24).
- Offer/coupon data ownership — this service calls Pricing & Offer for a quote; it never stores
  offer/coupon definitions itself.
- Mobile client behavior — MA-23/MA-120 defines how the app consumes this API.

## 4. Functional Requirements

### FR-1: `GET /cart`

- Returns the authenticated caller's full cart: all line items, each with product ID, quantity,
  frequency (`ONE_TIME` / `DAILY` / `ALTERNATE_DAYS`), start date (subscription frequencies only),
  and a per-item + cart-level price/tax/delivery breakdown sourced from a live
  `POST /pricing/quote` call to Pricing & Offer Service (MA-101/MA-122) — never a cached/stale
  price baked into the stored cart record itself (prices must reflect current catalog pricing and
  any currently-eligible offers, not the price at add-time).
- Also returns `cartVersion` (a monotonic integer, incremented on every mutation — see §7), which
  callers echo back on `PUT /cart` for optimistic-concurrency (FR-3).
- No cart yet for this caller → `200` with an empty line-item list and `cartVersion: 0` (not a
  `404`) — "no cart" and "empty cart" are the same state from the caller's perspective.

### FR-2: `POST /cart/items`

- Request: `productId`, `quantity`, `frequency`, `startDate` (required when `frequency !=
  ONE_TIME`, rejected as a validation error when present for `ONE_TIME`).
- Validates `quantity` against Inventory Service's current available quantity for `productId`
  (server-side re-validation — never trusts a client-supplied "I checked the stock already" claim,
  per standard defense-in-depth; MA-120's own client-side check at add-time is a UX convenience,
  not the source of truth).
- Assigns a new, stable line-item ID (`{id}` used by `DELETE /cart/items/{id}`) — **not** the
  product ID, since a caller may have more than one line item for the same product with different
  configurations (e.g. a one-time buy and a separate subscription of the same item) — the API must
  not silently collapse these into one row.
- On success: persists the line item, publishes `CartUpdated` (FR-5), returns the created line
  item (including its assigned ID) with `201`.
- Idempotency: accepts an optional client-supplied `Idempotency-Key` header; a repeated request
  with the same key within a bounded window (24h) returns the original result rather than creating
  a duplicate line item — matches the platform's documented idempotent-writes convention
  (`milkful-well-architected.md` §5).

### FR-3: `PUT /cart`

- Full-cart replace: accepts a complete list of desired line items (each either an existing
  line-item ID with an updated quantity, or a new item to add), and reconciles the stored cart to
  match — any existing line item not present in the request is removed. This is the bulk-edit path
  a future cart-review screen would use (out of MA-23's own scope, but this service's contract
  must not block that future consumer) — resolves Step 1 open question #1 (`PUT` = bulk replace,
  `POST /cart/items` = single-item add, are two distinct, both-needed operations, not redundant).
- Same stock re-validation as FR-2, applied per line item in the replacement set.
- **Optimistic concurrency:** `GET /cart` returns a `cartVersion` (a monotonic integer, see §7).
  `PUT /cart` requires an `ifVersion` field matching the caller's last-read `cartVersion`; if the
  stored version has since advanced (another device wrote in between), the request is rejected
  with `409 CART_VERSION_MISMATCH` and no write occurs, rather than silently overwriting the other
  device's change — this is the cross-device cart's actual conflict guard (§2 Problem Statement),
  not just its optimistic-happy-path replace semantics.

### FR-4: `DELETE /cart/items/{id}`

- Removes the specified line item. `404` if the ID doesn't exist or doesn't belong to the caller
  (never leaks whether an ID belongs to a different caller — same-shaped `404` either way).
- Publishes `CartUpdated` (FR-5) on success.

### FR-5: `CartUpdated` event

- Published via the transactional outbox pattern already established in `user`'s service
  (`adapters/outbox_event_publisher.py`, `run_local_outbox_publisher.py`) — write-to-outbox-table
  in the same transaction as the cart mutation, background publisher drains it to EventBridge, at
  least once delivery.
- Payload, following the platform's established event envelope (`stock_changed_consumer.py`'s
  `{"payload": {...}}` shape, `services/catalog`):
  ```json
  {
    "eventId": "uuid",
    "userId": "uuid",
    "cartId": "uuid",
    "changeType": "ITEM_ADDED | ITEM_REMOVED | CART_REPLACED",
    "occurredAt": "2026-08-20T10:00:00Z"
  }
  ```
  Deliberately thin (IDs + change type, not the full cart body) — consumers that need current cart
  state call `GET /cart`, avoiding a large/stale event payload; matches the "events signal, APIs
  serve state" convention implied by every other producer in this platform (e.g. `StockChanged`
  carries just enough to act on, not a full product record).

### FR-6: Wallet-balance-≥-₹500 gate (server-side)

- `POST /cart/items` and `PUT /cart` reject (with a distinct, documented error code —
  `WALLET_BALANCE_TOO_LOW`) a subscription-frequency line item when the caller's Wallet balance is
  `< ₹500` at write time — this is the server-side source of truth backing MA-120's own
  client-side FR-7 check; the mobile UI's check is a convenience, this is the enforcement point.
  Calls Wallet Service (already shipped, MA-100) synchronously to read the current balance — exact
  call site not yet confirmed against MA-100's actual contract, see §8/§12 (matches MA-120's own
  open question, rather than treating this as settled).
- **`PUT /cart` scoping:** the gate is evaluated only against line items being newly added or
  having their quantity/frequency/start-date changed by this request — a subscription line item
  that is unchanged from the currently-stored cart and simply being carried forward in the full
  replacement list (FR-3) is not re-checked. Otherwise a balance that later drops below ₹500 would
  block any unrelated cart edit (e.g. adding a one-time item) for as long as a previously-approved
  subscription item remains in the cart, which is not this gate's intent (see §9).

## 5. Non-Functional Requirements

- **Performance:** `POST /cart/items`/`PUT /cart` involve up to four synchronous downstream calls
  (Inventory stock check, Wallet balance for subscription line items, `user` service for the
  delivery-address state, and Pricing & Offer's `POST /pricing/quote`) plus the outbox write —
  target p99 under 1s, consistent with a Lambda-hosted, low-complexity write path. `GET /cart`
  makes two of these unconditionally (address lookup + pricing quote) on every call.
- **Reliability:** a downstream Inventory/Wallet/Pricing/`user`-service outage must fail the
  request cleanly (a `5xx` with a clear error code, see §9) rather than silently skipping
  validation or returning a cart with no price/tax breakdown.
- **Scalability:** stateless Lambda, DynamoDB on-demand capacity — no server-side session
  affinity, consistent with `milkful-well-architected.md` §5.
- **Observability:** correlation ID propagated from API Gateway through to Inventory/Wallet calls
  and the `CartUpdated` event; CloudWatch + X-Ray per `services/README.md`'s standard.

## 6. Technical Design

- **Compute:** Lambda, one function per route (`handlers/get_cart_handler.py`,
  `handlers/put_cart_handler.py`, `handlers/add_item_handler.py`, `handlers/delete_item_handler.py`),
  following `identity-auth`/`user`'s established layering: `handlers/dto.py` (Pydantic DTOs +
  envelope helpers, `extract_jwt_claims`), `domain/` (framework-free business rules —
  `cart_service.py`, `models.py`), `adapters/` (`cart_repository.py` — DynamoDB,
  `inventory_client_adapter.py`-style HTTP client for Inventory, a new `pricing_client_adapter.py`
  for MA-101, `wallet_client_adapter.py` for the FR-6 balance check,
  `outbox_event_publisher.py`).
- **`POST /pricing/quote` contract** (called from FR-1/FR-2/FR-3): request accepts a list of
  `{productId, quantity, frequency}` **plus the caller's delivery-address state and an optional
  cart-level `offerCode`**, matching MA-101/MA-122 FR-1's request shape exactly (that spec requires
  the state field for CGST/SGST vs. IGST determination, and added `offerCode` so a
  manually-validated offer/coupon code can actually be applied rather than only auto-applied) —
  Cart Service always sends its full line-item list in one call, whether that list has one item
  (mirroring an MA-23 single-add) or many (a full `GET /cart` read). The delivery-address state is
  resolved server-side via a synchronous call to `user`'s service (`GET`-profile-by-sub, already
  shipped — the `User`/`Address` domain model already carries `default_address_id` and each
  `Address.state`, `services/user/src/domain/models.py`), not supplied by the mobile client — a
  caller with no default address set is a distinct failure mode, see §9. `offerCode`, by contrast,
  has no source yet in this pass: this service doesn't currently store or accept a caller-supplied
  offer code anywhere (offer/coupon UX is explicitly out of scope, §3), so Cart Service always
  forwards `offerCode` as absent today, which lets Pricing's auto-apply run — matching this shared
  contract's shape now (so no future drift) without inventing offer-application functionality this
  spec doesn't otherwise cover. A future cart-review/offers screen would be the one to add a way
  for the caller to set and persist a chosen code, at which point this service starts forwarding
  it.
- **DynamoDB `cart` table:** partition key `userId` (Cognito sub), sort key a prefixed `SK` (see §7
  for the three item shapes it holds); TTL attribute `expiresAt` on line items, set to **30 days
  from last write** on every mutation (a concrete, documented value — resolves Step 1 open question
  #2; chosen to comfortably exceed a realistic browse-to-purchase window without indefinitely
  retaining abandoned carts). A returning customer inside that window sees their cart intact across
  devices/sessions; outside it, `GET /cart` simply returns empty — no special "your cart expired"
  messaging required, consistent with treating "no cart" and "empty cart" identically (FR-1).
- **Redis — flagged, not yet approved:** a read-through cache in front of the Inventory
  stock-check and Pricing quote calls (short TTL, e.g. 30s) to keep `GET /cart` latency low under
  repeated polling — **not** a second copy of cart-of-record data; DynamoDB remains the sole source
  of truth for cart contents. **Correction:** `milkful-well-architected.md` §6's database-per-service
  table currently lists Cart Service's owned datastore as DynamoDB only (Redis is scoped there to
  Pricing & Offer Service); this spec's Redis addition is a genuine change to that authoritative
  table, not something already sanctioned by the generic §5 "hot cache & rate limits → Redis"
  principle. Flagged as a risk requiring Platform/Architecture lead sign-off (§11) before
  implementation, matching how the sibling Pricing spec (MA-101/MA-122 §11) flags its own new
  cross-service dependencies rather than assuming them pre-approved.

## 7. Data Considerations

- **Line-item ID scheme:** server-generated UUID, distinct from `productId` (FR-2) — allows
  multiple line items per product with different configurations, which the data model must support
  even though MA-23's own mobile screen doesn't yet expose an editing path for it (§3 of MA-120).
- **DynamoDB schema:**
  ```
  cart (table)
    PK: userId (S)
    SK: lineItemId (S)                    -- line items: SK = "ITEM#{uuid}"
    productId (S)
    quantity (N)
    frequency (S)          -- ONE_TIME | DAILY | ALTERNATE_DAYS
    startDate (S, nullable) -- ISO date, only for subscription frequencies
    addedAt (S)             -- ISO timestamp
    expiresAt (N)           -- TTL attribute, epoch seconds

    -- one meta item per user, SK = "META", holding the FR-3 concurrency version:
    cartVersion (N)          -- monotonic, incremented on every mutation (FR-1/FR-3)

    -- one item per in-flight/completed idempotency key, SK = "IDEMPOTENCY#{key}" (FR-2):
    idempotencyKey (S)
    responseBody (S)         -- the original 201 response, serialized, replayed on a repeat request
    expiresAt (N)            -- TTL attribute, 24h from write, same attribute/mechanism as line items
  ```
  All three item shapes share the `cart` table (single-table design, distinguished by `SK` prefix)
  rather than a separate table each, consistent with `milkful-well-architected.md` §6's
  database-per-service boundary being per-*service*, not per-item-type.
- No cross-service DB reads (`milkful-well-architected.md` §6) — `productId` is stored as an
  opaque reference; product name/image/current price are never denormalized into this table (the
  mobile client already holds product display data from Catalog; price is always a live quote, per
  FR-1).

## 8. Integration Considerations

- **Inventory Service (already shipped):** stock-check call on every write (FR-2/FR-3) — exact
  endpoint TBD against Inventory's actual current API surface at implementation time (this spec
  assumes a per-product quantity lookup exists or is added as a small Inventory-side addition,
  mirroring MA-120's own Catalog Service contract addition — flagged, not blocking this spec).
- **Pricing & Offer Service (MA-101/MA-122, spec'd in parallel):** `POST /pricing/quote` — the two
  specs' request/response shapes are kept in sync in this same drafting pass; any future change to
  one must be checked against the other.
- **`user` service (already shipped):** new synchronous call to resolve the caller's delivery-
  address state (§6) for every `POST /pricing/quote` call — a new dependency this spec introduces,
  not previously called out; `user`'s existing profile-by-sub read already carries
  `default_address_id`/`Address.state`, so this is a small, additive consumer of an existing
  capability, not a new endpoint on `user`'s side.
- **Wallet Service (already shipped, MA-100):** balance read for FR-6. **Not yet confirmed:**
  MA-100 has no spec of its own in this repo yet, and the sibling mobile spec (MA-120 §8/§12)
  explicitly lists the exact wallet-balance read call site as an open question rather than an
  established contract — this spec's assumption that Cart Service can call Wallet Service
  synchronously for a balance read should be treated the same way (open, not settled) until
  MA-100's actual contract is reviewed.
- **EventBridge:** `CartUpdated` publication (FR-5) — no confirmed consumer yet (flagged, not
  blocking); likely candidates are Pricing & Offer (cache invalidation) and, later, Order Service
  at checkout — to be confirmed when those consumers are themselves spec'd.

## 9. Edge Cases and Failure Modes

- Concurrent `POST /cart/items` calls for the same product from two devices — both succeed as
  separate line items (per FR-2's ID scheme); no merge-on-write behavior in this pass — a future
  cart-review screen (or this service's own later iteration) may add "same product, same
  frequency → merge quantities" logic, deliberately not assumed here.
- Inventory stock check fails mid-request (Inventory outage) — the write fails with a `5xx` and a
  distinct error code (`STOCK_CHECK_UNAVAILABLE`), not a silent pass-through that risks
  overselling.
- Wallet balance check fails mid-request — same treatment, `WALLET_CHECK_UNAVAILABLE`, distinct
  from `WALLET_BALANCE_TOO_LOW` (FR-6) so the mobile client (MA-120's FR-7) can distinguish
  "you don't have enough" from "we couldn't check."
- Pricing & Offer Service call fails or times out — since `GET /cart` depends on it unconditionally
  (FR-1) for every response, this fails the whole request with `5xx` and a distinct error code
  (`PRICING_UNAVAILABLE`), not a cart returned with missing/zero price fields — the mobile client
  falls back to its own "Price unavailable" state (MA-120 FR-5) rather than being handed unpriced
  data.
- `user` service call to resolve the delivery-address state fails, or the caller has no default
  address set yet — fails with a distinct error code (`DELIVERY_ADDRESS_REQUIRED` for "no default
  address," `ADDRESS_LOOKUP_UNAVAILABLE` for a `user`-service outage) rather than guessing a state
  or omitting it from the Pricing call, since Pricing can't compute CGST/SGST-vs-IGST without it.
- `PUT /cart` sent with a stale `ifVersion` (another device wrote first) — rejected with
  `409 CART_VERSION_MISMATCH` (FR-3); the caller must re-fetch `GET /cart` for the current
  `cartVersion` and reconcile before retrying, rather than the write silently discarding the other
  device's change.
- Wallet balance drops below ₹500 after a subscription item was already added, and the caller later
  sends an unrelated `PUT /cart` edit — the unchanged subscription item is not re-gated (FR-6's
  scoping), so the unrelated edit is not blocked by a balance change that has nothing to do with it.
- `PUT /cart` request omits a line item that exists server-side — treated as an intentional
  removal (FR-3's full-replace semantics), not an error — callers building a partial-update UI
  must fetch the current cart first and include everything they want to keep.
- Duplicate `POST /cart/items` without an `Idempotency-Key` (client retry after a timeout, no key
  supplied) — creates a second line item; this is accepted as the caller's responsibility per
  standard idempotency-key semantics (the key is optional but its absence forfeits dedup
  protection) — documented, not silently fixed server-side.

## 10. Testing Strategy

**Unit (domain):** quantity validation against a stubbed Inventory response; line-item ID
generation and uniqueness; TTL calculation (30 days from last write, recalculated on every
mutation, not just creation); wallet-gate logic (FR-6) for each frequency value, including the
unchanged-item scoping rule; `cartVersion` increment/mismatch logic (FR-3); idempotency-key
lookup/replay logic (FR-2).

**Integration:** `POST /cart/items` → `GET /cart` round-trip against a real DynamoDB-local/moto
instance (matching this platform's existing moto-based local-dev pattern); outbox → `CartUpdated`
publication verified against a local EventBridge/SQS emulation, matching `user`'s own outbox test
pattern.

**Contract:** a fixture-based test asserting `POST /pricing/quote` request/response shapes match
MA-101/MA-122's spec exactly (single source of truth for the shared contract, run in both
services' test suites).

**Acceptance check:** `pytest services/cart/tests/` — all pass, including the wallet-gate and
stock-validation negative-path tests.

## 11. Risks and Trade-offs

- **Risk:** Pricing & Offer Service (MA-101) not yet built — `GET /cart`'s live-quote requirement
  (FR-1) can't be verified end-to-end until MA-101 ships; both specs are being drafted in the same
  pass specifically to keep their contracts in sync ahead of that.
- **Risk:** Inventory Service's exact per-product stock-quantity endpoint is assumed, not
  confirmed against its current real API surface — flagged in §8, to be resolved before
  implementation, not before this spec is approved.
- **Trade-off:** thin `CartUpdated` payload (FR-5) trades a second `GET /cart` call by consumers
  for avoiding stale/oversized event bodies — deliberate, matches platform convention.
- **Trade-off:** 30-day TTL (§6) is a judgment call, not derived from a stated business
  requirement — flagged for reviewer confirmation (§13).
- **Risk:** the Redis read-through cache (§6) is a new addition to Cart Service's datastore
  footprint that `milkful-well-architected.md` §6's database-per-service table doesn't currently
  reflect (that table lists Cart Service as DynamoDB-only). Needs Platform/Architecture lead
  sign-off, and the architecture doc updated, before implementation — not assumed pre-approved by
  the generic §5 caching principle.
- **Risk:** the Wallet Service synchronous-balance-read integration (FR-6/§8) is assumed, not
  confirmed — MA-100 has no spec of its own yet in this repo. If MA-100's actual contract doesn't
  support a synchronous per-request balance read the way FR-6 assumes, this FR needs rework.
