## 2. Problem Statement

Catalog Service (MA-94/MA-116/MA-117) is fully built but **read-only** — confirmed directly from the code: `products_handler.py`/`categories_handler.py` expose only `GET` routes, and `product_repository.py` has no create/update method at all. Today, the *only* way to create a product or change its price is editing `services/local-dev/_catalog_seed_data.py` and re-running `seed_catalog_products.py`, or a direct SQL `UPDATE` — not a real operational path. Catalog's own README names this gap and attributes it to this story by name. This spec closes it.

**Expected outcome:** An admin (Ops or SuperAdmin role) can create a product with full pricing/tax/eligibility detail, edit any field on an existing one, activate/deactivate it, and manage categories — every action audited, and a new product automatically provisioned in Inventory via a real `CatalogUpdated` event instead of silently requiring a second manual step there.

## 3. Scope

### In Scope

- `POST /products` — create a product (all fields incl. new `isActive`/`hsnCode`/`taxRate`), writes `catalog_audit_log`, publishes `CatalogUpdated`.
- `PATCH /products/{id}` — edit any subset of fields, including `isActive` (activate/deactivate), writes `catalog_audit_log`.
- `POST /categories` / `PATCH /categories/{id}` — create/edit categories.
- `GET /admin/products` — paginated admin list, includes inactive products (unlike the public `GET /products`), optional `categoryId`/`isActive` filters.
- New `is_active`, `hsn_code`, `tax_rate` columns on `products`.
- New `catalog_audit_log` table.
- `is_active = true` filter added to the existing `GET /products`, `GET /products/{id}` (list-context only, see FR-6), and `GET /search` — a real behavior change to shipped code.
- Admin-authorizer wiring (Ops + SuperAdmin), near-direct port of Inventory's `admin_context.py`/`local_admin_auth.py` (MA-48).
- Adopting `shared.adapters.outbox_event_publisher.EventBridgeOutboxPublisher` for a direct `CatalogUpdated` publish on product creation (mirrors Inventory's own `EventBridgeStockEventPublisher` — a direct publish, not a polling-outbox table; see §6).
- A new CDK stack for Catalog (`infra/catalog/catalog_stack.py`), mirroring Inventory's.

### Out of Scope

- Image upload/CDN pipeline — `imageUrl` stays a plain string field; an admin pastes an already-hosted URL. A real upload pipeline is new infrastructure, flagged as future work (MA-42 Step 1).
- Scheduled/future-effective price changes — needs its own effective-dating design, closer in shape to Inventory's `available_from` batch scheduling than a field edit. Not built here.
- CSV bulk import/export — a materially separate capability (file parsing, validation, partial-failure handling). Not built here.
- B2B-aware pricing callers — `priceB2b` becomes admin-editable, but no caller signals B2B intent yet (MA-116's own still-open Q2, unchanged).
- Any change to `GET /search`'s underlying query engine, sort options, or filter facets beyond adding the `is_active` predicate — MA-117's own territory, untouched otherwise.
- Pricing & Offer Service (MA-101) — unaffected; it keeps reading `price_b2c` from Catalog exactly as today.

## 4. Functional Requirements

### FR-1: `POST /products`

- Body: `{ categoryId, name, description, unit, priceB2c, priceB2b?, imageUrl?, tag?, subscriptionEligible, isVeg, isOrganic, hsnCode?, taxRate? }`. `isActive` is not settable on create — always `true` (a product is created active; deactivation is a deliberate separate action, FR-2).
- Validates `categoryId` exists (`404 CATEGORY_NOT_FOUND` if not — a new, distinct error code from `PRODUCT_NOT_FOUND`); `priceB2c > 0` (`400 VALIDATION_ERROR`); `name`/`unit` non-empty.
- One Aurora transaction: `INSERT products (..., is_active=true)` → `INSERT catalog_audit_log (admin_id, product_id, action='CREATE', previous_value=NULL, new_value=<full new row as JSON>, reason)`.
- After the transaction commits: publish `CatalogUpdated` — `{"payload": {"productId": "..."}}`, `Source: "catalog"`, `DetailType: "CatalogUpdated"` (the exact contract already wired in `local-dev/bootstrap.py`'s `CatalogUpdatedRule` and consumed by Inventory's `catalog_updated_consumer.py` — no new agreement to strike, just the first real producer for an existing one). A publish failure is logged but does **not** roll back the already-committed product row (same "commit the write, best-effort the event" posture `StockEventPublisherPort` already established — the alternative, failing product creation because EventBridge is briefly unavailable, is worse).
- Returns `201` with the full serialized product.

### FR-2: `PATCH /products/{id}`

- Body: any subset of `POST /products`'s fields, plus `isActive` (boolean) — this is how activate/deactivate works, not a separate endpoint (one fewer route, one audited code path for every product field change).
- `404 PRODUCT_NOT_FOUND` for an unknown id (reuses the existing error code/status).
- One transaction: `UPDATE products SET <changed fields>` → `INSERT catalog_audit_log (action='UPDATE', previous_value=<changed fields' old values as JSON>, new_value=<changed fields' new values as JSON>, reason)`. Only *changed* fields are recorded in `previous_value`/`new_value` — not the whole row — so an audit entry reads as "what actually changed," matching the specificity Inventory's own adjustment audit row already has.
- No `CatalogUpdated` publish on edit — FR-8's consumer only cares that a product *exists* (to provision a `stock` row once); it has no use for a product-detail-changed signal, and inventing one here would be scope creep past what any real consumer needs today.

### FR-3: `POST /categories` / `PATCH /categories/{id}`

- Body (`POST`): `{ name, iconName, sortOrder? }`. Body (`PATCH`): any subset. `404 CATEGORY_NOT_FOUND` on an unknown id for `PATCH`.
- No audit log entry — categories are lower-risk, purely organizational metadata; Inventory's own precedent (MA-119) only audits stock-affecting admin actions, not every admin-adjacent write. Flagged as a deliberate scope line, not an oversight (§11).

### FR-4: `GET /admin/products`

- Paginated: `id, categoryId, name, priceB2c, priceB2b, isActive, stockState, createdAt, updatedAt` — includes inactive products (the public `GET /products` never does, FR-6). Optional `categoryId` and `isActive` query filters.
- This is the admin product-list screen's (MA-157) sole data source — distinct from the public `GET /products`, which **requires** `categoryId` and never returns inactive rows.

### FR-5: Admin authorization

- All five endpoints above require a valid admin identity with role `Ops` or `SuperAdmin` (same set this session confirmed for Inventory, not a fresh decision) — `401` if missing/malformed, `403` for any other role.
- `adminId` for every audit row comes from the verified admin context, never the request body — same anti-spoofing rule as MA-119/MA-150.

### FR-6: `is_active` filtering on existing public endpoints

- `GET /products?categoryId=`, `GET /search` — both add `WHERE is_active = true` (or equivalent `and_()` condition) to their existing query. An inactive product silently stops appearing in either.
- `GET /products/{id}` — **does not** filter on `is_active`; a direct-id lookup still resolves regardless of active status. Resolved explicitly (MA-42 Step 3): a product already referenced by an existing cart/order/subscription line must not start 404ing the moment an admin deactivates it — only *discovery* (list/search) should hide it, not *resolution* of an id a caller already has.

## 5. Non-Functional Requirements

- **Performance:** `GET /admin/products` p95 < 500ms for up to 10,000 products (indexed on `category_id`, already present per `0001_products_categories.sql`); writes p95 < 300ms including the audit insert — same latency class as Inventory's own admin writes.
- **Security:** all five admin endpoints behind the authorizer (FR-5); never trust a client-supplied `adminId` or role.
- **Reliability:** `POST /products` and `PATCH /products/{id}` are each one Aurora transaction — the product write and its audit row are never applied independently of each other.
- **Auditability:** 100% of successful product creates/edits produce exactly one `catalog_audit_log` row — same bar MA-119/MA-150 hold themselves to.
- **Observability:** CloudWatch metric `catalog.admin.product_write.count`, tagged by `action` (create/update).

## 6. Technical Design

### Architecture Approach

Extends `services/catalog`'s existing hexagonal structure (FastAPI/Fargate, same shape as Inventory):
1. New domain methods on `CatalogService`: `create_product(...)`, `update_product(product_id, **changes)`, `create_category(...)`, `update_category(category_id, **changes)`, `list_products_admin(category_id, is_active, page, page_size)`.
2. New FastAPI routes: `APIRouter(prefix="/v1", tags=["catalog-admin"])` — mirrors `products_handler.py`'s existing router style exactly.
3. New `handlers/admin_context.py` — **a near-direct port of `services/inventory/src/handlers/admin_context.py`**, same `{"Ops", "SuperAdmin"}` `ALLOWED_ROLES` set, same `X-Admin-Id`/`X-Admin-Email`/`X-Admin-Role` header contract (API Gateway's Lambda authorizer + parameter mapping populates these in production, same cross-stack `admin_authorizer_fn_arn` pattern MA-139/MA-48 both use).
4. New `handlers/local_admin_auth.py` — **a direct port of `services/inventory/src/handlers/local_admin_auth.py`**, same env-var-gated (`CATALOG_LOCAL_ADMIN_AUTH`, mirrors `CATALOG_CORS_ALLOW_ALL`'s existing pattern in `app.py`) local-dev ASGI middleware translating the browser's real `Authorization: Bearer` token into those same three headers. Without this, every admin call 401s locally exactly the way Inventory's did before MA-48's own fix — ported here proactively, not rediscovered.
5. New adapter: `CatalogAuditLogRepository` (or extends `SqlAlchemyProductRepository` directly, implementer's choice) — `insert_audit_log(admin_id, product_id, action, previous_value, new_value, reason)`.
6. New `adapters/catalog_event_publisher.py` — **mirrors `inventory/src/adapters/stock_event_publisher.py`'s own shape**: wraps `shared.adapters.outbox_event_publisher.EventBridgeOutboxPublisher` for a *direct* publish (not a polling-outbox table — Inventory's own docstring explains why a direct wrap is correct here: the publisher's retry/backoff is exactly the behavior a direct publish needs, no reason to duplicate it as a second hand-rolled boto3 wrapper).
7. CDK: new `infra/catalog/catalog_stack.py` — Fargate service + ALB + Aurora, mirroring `inventory/infra/inventory/inventory_stack.py`'s structure; new API Gateway route integrations for the five admin endpoints referencing the existing admin authorizer Lambda by ARN, same pattern as MA-139/MA-48 (including their already-disclosed placeholder-ARN gap — inherited, not introduced).

### Component Responsibilities

- **Admin catalog handlers** (`src/handlers/admin_catalog_handler.py`) — thin FastAPI routes, map HTTP ↔ domain, mirror `products_handler.py`'s shape.
- **`CatalogService`** (extends the existing domain service, not a new class) — five new methods (above).
- **`SqlAlchemyProductRepository`** — extends with `create_product()`, `update_product()`, `create_category()`, `update_category()`, `list_products_admin()`; `products_table`/`categories_table` gain the three new columns.

### Workflow (`POST /products`)

```
POST /products {categoryId, name, ..., priceB2c, ...}
  → get_caller_admin(request) → 401 if missing/malformed
  → role not in {Ops, SuperAdmin} → 403
  → categoryId unknown → 404 CATEGORY_NOT_FOUND
  → priceB2c <= 0 or name/unit empty → 400 VALIDATION_ERROR
  DB transaction:
    INSERT products (..., is_active=true)
    INSERT catalog_audit_log (admin_id, product_id, action='CREATE',
                               previous_value=NULL, new_value=<row as JSON>, reason)
  commit
  → publish CatalogUpdated {"payload": {"productId": "..."}} via
    EventBridgeOutboxPublisher(event_bus_name, event_source="catalog", region).publish(
      "CatalogUpdated", {"payload": {"productId": product_id}}
    )
    — failure logged, does not roll back the already-committed product
  → return 201 with the new product
```

### API/Interface Definitions

| Method | Path | Purpose |
|--------|------|---------|
| POST | `/v1/products` | Create product (FR-1) |
| PATCH | `/v1/products/{id}` | Edit / activate-deactivate (FR-2) |
| POST | `/v1/categories` | Create category (FR-3) |
| PATCH | `/v1/categories/{id}` | Edit category (FR-3) |
| GET | `/v1/admin/products` | Admin product list, incl. inactive (FR-4) |

All responses use the standard envelope (`services/README.md` §5), consistent with Catalog's existing endpoints.

### Data Flow

`portal-ui` (MA-157) → API Gateway (admin JWT authorizer, cross-stack ref to Identity & Auth) → Catalog Service (Fargate, FastAPI) → Aurora `milkful_catalog` (`products`/`categories`/new `catalog_audit_log`) → EventBridge → Inventory's existing `catalog_updated_consumer.py`.

## 7. Data Considerations

```sql
-- Additive, all nullable or defaulted — no backfill migration needed
-- for existing seeded rows:
ALTER TABLE products ADD COLUMN is_active BOOLEAN NOT NULL DEFAULT true;
ALTER TABLE products ADD COLUMN hsn_code  VARCHAR(16);
ALTER TABLE products ADD COLUMN tax_rate  NUMERIC(5, 2);

-- New table, same shape/intent as Inventory's inventory_audit_log
-- (MA-119 §7) — a proven pattern, not a new design:
CREATE TABLE catalog_audit_log (
    id              VARCHAR(64) PRIMARY KEY,
    product_id      VARCHAR(64) NOT NULL REFERENCES products(id),
    admin_id        VARCHAR(64) NOT NULL,
    action          VARCHAR(16) NOT NULL,   -- 'CREATE' | 'UPDATE'
    previous_value  JSONB,
    new_value       JSONB,
    reason          TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_catalog_audit_log_product_id ON catalog_audit_log (product_id);
```

The `src/adapters/product_repository.py` SQLAlchemy Core table definitions must be extended column-for-column to match, same hand-sync discipline that file's own header comment already documents for `0001`/`0002`.

## 8. Integration Considerations

- **Upstream:** `portal-ui` (MA-157) is the only caller of the five new endpoints.
- **Downstream:** EventBridge → Inventory's existing `catalog_updated_consumer.py` (MA-118 FR-8) — this spec is its first real producer. **Must be live-verified**, not just schema-checked (§10) — same "don't trust the paper contract" discipline MA-48 applied to `StockChanged` in the other direction.
- **Contract ownership:** Inventory's `catalog_updated_consumer.py` already pins the payload shape (`{"payload": {"productId": "..."}}`) and the EventBridge rule filter (`source: ["catalog"]`, `detail-type: ["CatalogUpdated"]`, already wired in `local-dev/bootstrap.py`) — this spec conforms to that existing contract, does not redefine it.
- **Identity & Auth:** reuses the existing admin authorizer Lambda, same cross-stack ARN pattern as MA-139/MA-48 — no change to Identity & Auth itself.
- **No cross-service DB reads** — this spec never queries Inventory's or any other service's database.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| `POST /products` with an unknown `categoryId` | `404 CATEGORY_NOT_FOUND`, no row written |
| `POST /products` with `priceB2c <= 0` | `400 VALIDATION_ERROR`, no row written |
| `PATCH /products/{id}` for an unknown id | `404 PRODUCT_NOT_FOUND` |
| `CatalogUpdated` publish fails after the product row commits | Product creation still succeeds (`201` returned); failure logged; Inventory never provisions a `stock` row for it until manually reconciled — flagged as a real, accepted gap (§11), not solved by a retry queue in this pass |
| A deactivated product is looked up by direct id (e.g. an old order's line item) | `200`, full product returned — `isActive: false` visible in the payload, but the call does not 404 (FR-6) |
| Same deactivated product appears in `GET /products?categoryId=` or `GET /search` | Does not appear — filtered out |
| Two admins edit the same product concurrently | Last write wins at the API layer; no row-level locking needed here (unlike Inventory's stock numbers, product metadata has no concurrent-decrement risk to protect against) |
| `POST /categories` with a duplicate `name` | Not constrained at the DB level today (no unique index on `categories.name`) — allowed through; flagged as a possible future constraint, not blocking (§12) |

## 10. Testing Strategy

- **Unit:** `create_product`/`update_product`'s validation (positive price, non-empty name/unit, unknown category), the audit-row previous/new-value diffing (`PATCH` only records *changed* fields), `list_products_admin`'s `isActive`/`categoryId` filters, `get_product`/`get_products`/`search`'s `is_active` filtering behavior (including that `get_product` does **not** filter, FR-6).
- **Integration (local-dev):** full `POST /products` against local Postgres asserting the product row + audit row land in one transaction; `PATCH /products/{id}` with `isActive: false` then confirming `GET /products/{id}` still 200s while `GET /products?categoryId=` no longer lists it.
- **Contract — mandatory live verification, not just a schema-shape check:** publish a real `CatalogUpdated` event via `POST /products` against the running local-dev stack and confirm Inventory's `catalog_updated_consumer.py` actually provisions a `stock` row for the new `productId` — the first time this consumer will have run against a genuine producer instead of a manually-published test event.
- **Negative scenarios required:** unknown category, non-positive price, unknown product on edit, non-{Ops,SuperAdmin} caller, `CatalogUpdated` publish failure (product still created, failure logged, not silently swallowed without a trace).

## 11. Risks and Trade-offs

1. **`CatalogUpdated` publish failure does not roll back product creation** (§4 FR-1, §9) — accepted because the alternative (failing a product create due to a transient EventBridge blip) is worse, and matches `StockEventPublisherPort`'s own established posture; the real cost is a product that exists in Catalog but has no `stock` row in Inventory until someone notices and reconciles manually. No automated reconciliation job is built in this pass — flagged, not solved.
2. **Categories have no audit log** (§4 FR-3) — a deliberate scope line (lower-risk than product/pricing changes), not an oversight; revisit if category mismanagement ever becomes a real operational problem.
3. **No CDK/infra stack existed for Catalog before this spec** — real, non-trivial supporting work bundled in here, same category of estimate-risk MA-48 flagged for MA-118/MA-119's size.
4. **Inherits the same placeholder-authorizer-ARN gap** MA-139/MA-48 both already carry (§6) — not newly introduced here.

## 12. Open Questions

1. Should `categories.name` get a uniqueness constraint? Not required for this spec; flagged as a plausible, low-risk future addition if duplicate categories prove to be a real operational annoyance.
2. Should a failed `CatalogUpdated` publish (§11 Risk 1) eventually get a retry/reconciliation mechanism (e.g. a periodic job that finds Catalog products with no matching Inventory `stock` row)? Not required for v1; flagged for a future iteration if manual reconciliation proves too error-prone in practice.
