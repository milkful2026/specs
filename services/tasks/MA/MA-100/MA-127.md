## 2. Problem Statement

MA-1 seeded the Wallet Service: a `wallet` row per user is auto-created from `UserRegistered`, with a zero-balance opening ledger entry, and a `GET /wallet/me/status` endpoint. That is **all** that exists — the MA-1 spec explicitly deferred "Recharge, ledger transactions, admin adjustments".

MA-24 now needs the customer to **add money** (via Razorpay, handled by Payment Service — MA-126) and to **see** their balance and history (the Wallet screen — MA-125 — and later the passbook, MA-27). For that, Wallet Service must:

- expose the **balance** and the **recharge limits** the app reads,
- consume the **`PaymentConfirmed`** event Payment Service emits for a recharge and **credit the ledger exactly once**, updating the running balance atomically,
- expose the **transaction ledger** (paged, newest-first) that MA-27 will render,
- publish **`WalletCredited`** so downstream (Notification, Reporting) can react.

Expected outcome: within seconds of a Razorpay capture, the user's `GET /wallet/me` balance reflects the top-up, the ledger has one immutable `RECHARGE` entry with a running-balance snapshot, and a duplicate or replayed event never credits twice.

## 3. Scope

### In scope

- **Extend the `wallet` schema** (MA-1's `wallets` + `ledger_entries`): switch money columns to integer paise, add `balance_after_paise` and a `UNIQUE` `ref` to `ledger_entries`, add `correlation_id`, add recharge-limit config.
- **`GET /wallet/me`** — balance, status, currency, and recharge min/max bounds (supersedes / augments MA-1's `GET /wallet/me/status`).
- **`GET /wallet/me/transactions`** — paged, newest-first ledger (the contract MA-27 consumes).
- **`GET /wallet/internal/limits`** — service-to-service (SigV4), returns `{ rechargeMinPaise, rechargeMaxPaise }` for Payment Service (MA-126 FR-6).
- **`wallet-events-q` consumer extension** — handle `PaymentConfirmed` where `detail.purpose = WALLET_RECHARGE`: idempotent `RECHARGE` credit + balance snapshot in one transaction, then publish `WalletCredited`.
- **`WalletCredited`** domain event (schema per MA-126 §8.4).
- **Recharge-limit rule** — min/max, config-driven, integer rupees.
- **Observability, DLQ, alarms** for the recharge consumer path.
- **A note / migration** aligning the event vocabulary (`WalletCreated`/`WalletCredited`/`WalletDebited`/`WalletLowBalance`) and the `/wallet/me/*` endpoint style, per MA-126 §8.5.

### Out of scope

- **Wallet creation** — owned by MA-1 (`UserRegistered` consumer, `WalletCreated`); unchanged here beyond the schema migration.
- **Debits** (`ORDER_DEBIT`) and the `OrderConfirmed` consumer path — the ledger `type` enum includes `ORDER_DEBIT` for schema-stability, but the debit *behaviour* (and `WalletDebited`) is MA-97 / MA-25's Order Saga slice.
- **Refunds / cashback / referral credits** — MA-32, MA-30; enum values reserved, behaviour deferred.
- **Auto-recharge, low-balance alerts (`WalletLowBalance`)** — MA-33 extras / MA-103; not triggered here.
- **Admin wallet adjustments** — MA-40.
- **The Transaction History screen** — MA-27; this spec provides its data endpoint only.
- **Statement export / PDF** — MA-27 / MA-38.
- **The Razorpay integration** — entirely MA-126; Wallet Service never talks to Razorpay.
- **`GET /wallet/{userId}` (id-in-path style)** — rejected in favour of `/wallet/me/*` (MA-126 §8.5).

## 4. Functional Requirements

### FR-1: `GET /wallet/me`

**Auth:** Cognito JWT (`sub` → resolve the caller's `wallet` row).
**Response 200:**
```json
{
  "walletId": "uuid",
  "status": "ACTIVE",                 // ACTIVE | CREATING | FAILED  (from MA-1)
  "balancePaise": 45000,
  "currency": "INR",
  "rechargeMinPaise": 10000,
  "rechargeMaxPaise": 10000000
}
```
- `balancePaise` is `wallets.balance_paise` — an O(1) read, never a ledger sum at request time.
- If no wallet row yet (auto-create event not processed) → `status: "CREATING"`, `balancePaise: 0` (MA-1 FR-2 behaviour, preserved).
- Replaces MA-1's `GET /wallet/me/status` shape by superset; MA-1's `/status` path MAY be kept as an alias returning the same body, or 301'd — decided in implementation (non-breaking either way since MA-1's mobile consumer is the registration success screen).

### FR-2: `GET /wallet/me/transactions`

**Auth:** Cognito JWT.
**Query:** `limit` (default 20, max 100), `cursor` (opaque, from a prior response's `nextCursor`).
**Response 200:**
```json
{
  "items": [
    { "id": "led_...", "type": "RECHARGE", "amountPaise": 50000, "balanceAfterPaise": 95000,
      "ref": "razorpay_payment:pay_XXX", "description": "Wallet top-up",
      "createdAt": "2026-09-11T18:30:00Z" }
  ],
  "nextCursor": "eyJ0cyI6..."          // null when no more
}
```
- Newest-first, keyed on `(created_at DESC, id DESC)`; `cursor` encodes the last seen `(created_at, id)`.
- `description` is a server-rendered human string per `type` (`RECHARGE` → "Wallet top-up"; `OPENING` → "Wallet created"; future types get their own).
- This is the contract **MA-27** renders. MA-125's `Passbook` / `View All Transactions` navigate to MA-27, which calls this endpoint.
- Amounts are **signed** (`+` credit, `−` debit); `RECHARGE` is always positive.

### FR-3: `GET /wallet/internal/limits`

**Auth:** service-to-service **SigV4 / mTLS** (not Cognito JWT); callable only from within the VPC (Payment Service).
**Response 200:** `{ "rechargeMinPaise": 10000, "rechargeMaxPaise": 10000000 }`
- Values from the recharge-limit config (FR-6). Cheap; Payment Service caches it 5 min (MA-126 FR-6).

### FR-4: Recharge credit — `wallet-events-q` consumer

**Trigger:** an SQS message on `wallet-events-q` whose body is an EventBridge envelope with `detail-type = "PaymentConfirmed"` and `detail.purpose = "WALLET_RECHARGE"` (delivered by the new rule defined in MA-126 §8.3).

**Message shape (`detail`):** per MA-126 §8.1 — `{ eventId, occurredAt, correlationId, paymentId, userId, purpose, amountPaise, currency, method, razorpayPaymentId, razorpayOrderId }`.

**Processing (idempotent, single DB transaction):**
1. `ref = "razorpay_payment:" + razorpayPaymentId`.
2. `SELECT ... FOR UPDATE` the `wallets` row for `user_id = detail.userId`.
   - No wallet row → **do not** drop the message: this is a rare race (recharge before `UserRegistered` processed). Re-queue with a visibility-timeout backoff (or send to DLQ after N attempts with an alarm) — a recharge must never be silently lost. (Practically near-impossible: the user had to register, get a wallet, and open the app to recharge.)
   - Wallet `status != ACTIVE` → same handling (re-queue / DLQ + alarm).
3. `INSERT INTO ledger_entries (wallet_id, type='RECHARGE', amount_paise=+amountPaise, balance_after_paise = wallets.balance_paise + amountPaise, ref, correlation_id) ON CONFLICT (ref) DO NOTHING`.
   - **0 rows inserted** (conflict) → this event was already processed; **ack the message and stop** (no balance change, no `WalletCredited`).
4. `UPDATE wallets SET balance_paise = balance_paise + amountPaise, updated_at = now() WHERE id = wallet_id`.
5. Insert an `outbox` row for `WalletCredited` (MA-126 §8.4 schema): `{ eventId: <new uuid>, occurredAt, correlationId, userId, walletId, amountPaise, balanceAfterPaise, type: "RECHARGE", ref, paymentId }`.
6. Commit. The outbox poller publishes `WalletCredited` to `milkful-events`.
7. Ack the SQS message.

**Idempotency guarantee:** the `ledger_entries.ref` `UNIQUE` constraint + `ON CONFLICT DO NOTHING` inside the `FOR UPDATE` transaction means N deliveries of the same `PaymentConfirmed` (SQS at-least-once, Payment Service replay, DLQ redrive) produce **exactly one** credit and **exactly one** `WalletCredited`.

**Currency:** `detail.currency` must be `INR`; anything else → DLQ + alarm (should be impossible).

### FR-5: `WalletCredited` publication

- Published from the `outbox` (transactional outbox pattern, same as MA-126) — never a direct `PutEvents` inside the consumer transaction.
- `detail-type = "WalletCredited"`, `source = "milkful.wallet"`, `detail` per MA-126 §8.4.
- Consumers (not built here): `notification-events-q` (optional "₹X added" push), `reporting-events-q` (catch-all). No consumer is required for MA-24 to function.

### FR-6: Recharge-limit rule

- Config-driven: `WALLET_RECHARGE_MIN_PAISE` (default `10000` = ₹100), `WALLET_RECHARGE_MAX_PAISE` (default `10000000` = ₹1,00,000).
- Surfaced via `GET /wallet/me` (FR-1) and `GET /wallet/internal/limits` (FR-3).
- **Enforcement** of the range on a recharge request is Payment Service's (MA-126 FR-1) — Wallet Service only *owns and publishes* the numbers. (Rationale: the amount is validated before any Razorpay order is created; Wallet Service never sees a recharge request, only a confirmed `PaymentConfirmed`.)
- If a `PaymentConfirmed` somehow arrives with `amountPaise` outside the range (e.g. limits changed mid-flight), **still credit it** — the money was really captured; log `recharge_outside_current_limits` for finance visibility. Never reject real money.

### FR-7: MA-1 alignment

- The schema migration (FR in §7) is **backward-compatible** with MA-1's `UserRegistered` consumer and `WalletCreated` publication: `balance` → `balance_paise` (opening value `0` unchanged), `ledger_entries.amount` → `amount_paise`, opening entry `type='OPENING'` gains `balance_after_paise = 0` and `ref = 'opening:' + wallet_id`.
- MA-1's `POST /wallet/me/retry` and `GET /wallet/me/status` are untouched (status alias per FR-1).
- Event vocabulary: this spec's implementation adopts `WalletCredited` (new) alongside MA-1's `WalletCreated`; `WalletDebited` / `WalletLowBalance` are reserved for later slices. Architect to update `milkful-well-architected.md` §7.1 (acceptance item, per MA-126 §8.5).

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| **Performance** | `GET /wallet/me` p95 < 100ms (single indexed row read). `GET /wallet/me/transactions` p95 < 200ms for a 20-item page (covering index on `(wallet_id, created_at DESC, id DESC)`). Recharge consumer: credit committed < 1s after message receipt p95; end-to-end (Razorpay capture → balance visible) < 5s p95. |
| **Reliability** | Exactly-once credit under at-least-once delivery (ledger `ref` UNIQUE + `FOR UPDATE`). A recharge event is **never** dropped — unprocessable messages go to `wallet-events-q`'s DLQ with an alarm, not `/dev/null`. Outbox guarantees `WalletCredited` publication survives an EventBridge outage. |
| **Consistency** | Balance and ledger are updated in **one** transaction; `balance_paise` always equals the latest entry's `balance_after_paise`. A DB check/constraint or a periodic invariant job asserts `wallets.balance_paise == SUM(ledger_entries.amount_paise)` per wallet. |
| **Security** | Cognito JWT for `/wallet/me/*`; SigV4/mTLS for `/wallet/internal/*` (VPC-only, not routable from API Gateway's public side). Least-privilege IAM: `sqs:ReceiveMessage/DeleteMessage` on `wallet-events-q`, `events:PutEvents` on the bus, `rds` connect — nothing else. KMS at rest on Aurora `wallet`; TLS 1.2+. No PII beyond `user_id`. Ledger + wallet rows are append-only / balance-only-increases-via-entry (no direct balance writes outside FR-4 step 4). |
| **Scalability** | Stateless Fargate; the consumer scales on `wallet-events-q` depth; read APIs scale on request count behind the ALB. Aurora Serverless v2 + RDS Proxy. The 6 AM subscription-debit burst (well-architected §2.3) is a *future* debit-path concern; recharge traffic is diffuse. |
| **Observability** | `correlationId` from the event carried into logs and into `WalletCredited`. Metrics: `wallet.recharge.credited`, `wallet.recharge.duplicate` (ON CONFLICT hits), `wallet.recharge.no_wallet_retry`, `wallet.credit.consumer_lag_seconds`, `wallet-events-q` DLQ depth, `wallet.balance_invariant_violations`. Alarms: DLQ depth > 0, `consumer_lag_seconds > 60`, any invariant violation. X-Ray on the consumer transaction. |
| **Maintainability** | `handler → domain → adapter`. The ledger transaction lives in `domain/wallet_service.credit_recharge()`; SQS/EventBridge are adapters. The `type` enum and signed `amount_paise` make debits/refunds pure additions. |

## 6. Technical Design

### Component responsibilities

```
API Gateway (Cognito JWT)                       EventBridge milkful-events
   │  GET /wallet/me                                │  rule: PaymentConfirmed & purpose=WALLET_RECHARGE
   │  GET /wallet/me/transactions                   ▼
   ▼                                             wallet-events-q (SQS + existing DLQ)
Wallet Service (Fargate)                            │
 ├─ handlers/
 │   ├─ http/       GET /wallet/me, /wallet/me/transactions, (MA-1) /wallet/me/status, /wallet/me/retry
 │   ├─ internal/   GET /wallet/internal/limits  (SigV4)
 │   └─ sqs/        wallet-events consumer  → domain.on_event(envelope)
 ├─ domain/
 │   ├─ wallet_service.py   get_wallet / list_transactions / credit_recharge / (MA-1) create_wallet
 │   └─ models.py           Wallet, WalletStatus, LedgerEntry, LedgerType
 ├─ adapters/
 │   ├─ wallet_repository.py   Aurora (wallets, ledger_entries) — SELECT ... FOR UPDATE, keyset pagination
 │   ├─ outbox_repository.py   outbox insert (same tx) + poller publish (WalletCreated | WalletCredited)
 │   └─ limits_config.py       recharge min/max
```

### `credit_recharge` — the core transaction

```
def credit_recharge(evt):                 # evt = PaymentConfirmed.detail, purpose == WALLET_RECHARGE
  ref = f"razorpay_payment:{evt.razorpayPaymentId}"
  with tx():                              # single Aurora transaction
    w = repo.lock_wallet_by_user(evt.userId)          # SELECT ... FOR UPDATE
    if w is None or w.status != ACTIVE:
        raise RetryableError("wallet-not-ready")       # -> SQS retry / DLQ, never ack-drop
    inserted = repo.insert_ledger_entry(
        wallet_id=w.id, type=RECHARGE, amount_paise=+evt.amountPaise,
        balance_after_paise=w.balance_paise + evt.amountPaise,
        ref=ref, correlation_id=evt.correlationId)      # ON CONFLICT (ref) DO NOTHING
    if not inserted:
        return                                          # duplicate -> ack, no event
    repo.set_balance(w.id, w.balance_paise + evt.amountPaise)
    outbox.enqueue("WalletCredited", {
        eventId=uuid(), occurredAt=now(), correlationId=evt.correlationId,
        userId=evt.userId, walletId=w.id, amountPaise=evt.amountPaise,
        balanceAfterPaise=w.balance_paise + evt.amountPaise,
        type="RECHARGE", ref=ref, paymentId=evt.paymentId})
  # tx committed -> ack SQS; poller publishes WalletCredited
```

## 7. Data Considerations

**Aurora `wallet` cluster — migration extending MA-1's schema (`services/wallet/migrations/`):**

```sql
-- MA-1 baseline:
--   wallets(id, user_id UNIQUE, balance, currency, status, created_at)
--   ledger_entries(id, wallet_id, type, amount, ref, created_at)

-- MA-24 migration:
ALTER TABLE wallets
  ADD COLUMN balance_paise BIGINT NOT NULL DEFAULT 0,
  ADD COLUMN updated_at   TIMESTAMPTZ NOT NULL DEFAULT now();
UPDATE wallets SET balance_paise = COALESCE(balance, 0) * 100;   -- MA-1 stored rupees; none in prod yet
ALTER TABLE wallets DROP COLUMN balance;

CREATE TYPE ledger_type AS ENUM
  ('OPENING','RECHARGE','ORDER_DEBIT','REFUND','CASHBACK','REFERRAL_CREDIT','ADJUSTMENT');

ALTER TABLE ledger_entries
  ALTER COLUMN type TYPE ledger_type USING type::ledger_type,
  ADD COLUMN amount_paise         BIGINT NOT NULL DEFAULT 0,
  ADD COLUMN balance_after_paise  BIGINT NOT NULL DEFAULT 0,
  ADD COLUMN correlation_id       TEXT;
UPDATE ledger_entries SET amount_paise = COALESCE(amount,0) * 100;
ALTER TABLE ledger_entries DROP COLUMN amount;
ALTER TABLE ledger_entries
  ALTER COLUMN ref SET NOT NULL,
  ADD CONSTRAINT ledger_entries_ref_key UNIQUE (ref);
-- backfill opening-entry refs for any existing rows:
UPDATE ledger_entries SET ref = 'opening:' || wallet_id WHERE type = 'OPENING' AND (ref IS NULL OR ref = '');

CREATE INDEX ledger_entries_wallet_created_idx
  ON ledger_entries (wallet_id, created_at DESC, id DESC);

CREATE TABLE outbox (
  id BIGSERIAL PRIMARY KEY, aggregate_id TEXT NOT NULL, event_type TEXT NOT NULL,
  payload JSONB NOT NULL, published_at TIMESTAMPTZ, created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX outbox_unpublished_idx ON outbox (created_at) WHERE published_at IS NULL;
```

- **Money:** integer paise, `BIGINT`. `amount_paise` signed (credits `+`, debits `−`). `balance_paise` and `balance_after_paise` are non-negative (a `CHECK (balance_paise >= 0)` is safe now — recharge only increases; revisit when debits land).
- **Invariant:** `wallets.balance_paise == (SELECT SUM(amount_paise) FROM ledger_entries WHERE wallet_id = wallets.id)`. Enforced by construction (FR-4) + a nightly check job emitting `wallet.balance_invariant_violations`.
- **Immutability:** `ledger_entries` is append-only — no `UPDATE`/`DELETE` in application code; a DB role without those grants on the table is recommended.
- **Retention:** ledger + outbox retained per finance policy (assume 7y); PITR on the cluster.
- **PII:** `user_id` (Cognito sub) only. `ref` embeds a Razorpay payment id — not PII.
- **Cross-service:** Wallet Service reads **no other service's DB**; it learns of payments only via `PaymentConfirmed`. Payment Service reads Wallet's limits only via `GET /wallet/internal/limits` (API, not DB).

| **User Service** | `UserRegistered` (MA-1) — unchanged | — |
| **MA-27 (Transaction History screen)** | Calls `GET /wallet/me/transactions` | MA-27's concern; this endpoint is stable and paged. |

## 9. Edge Cases and Failure Modes

| Case | Handling |
|------|----------|
| Duplicate `PaymentConfirmed` (SQS at-least-once, or Payment replay/DLQ) | `ledger_entries.ref` UNIQUE + `ON CONFLICT DO NOTHING` → one credit, one `WalletCredited`. Metric `wallet.recharge.duplicate`. |
| `PaymentConfirmed` arrives before the wallet exists (`UserRegistered` not yet processed) | `RetryableError` → SQS visibility-timeout backoff; after N attempts → DLQ + alarm. **Never acked-and-dropped.** |
| Wallet `status = FAILED` (MA-1 provision failed) but a recharge confirmed | Same retry/DLQ path + alarm; ops replays after fixing provisioning (MA-1's `POST /wallet/me/retry`), then re-drives the DLQ message → credits. |
| Two consumer tasks get the same message | `SELECT ... FOR UPDATE` serializes; the second sees the `ref` conflict → no-op ack. |
| `PaymentConfirmed.amountPaise` outside current recharge limits | Still credited (real money); `recharge_outside_current_limits` log. FR-6. |
| `PaymentConfirmed.currency != INR` | DLQ + alarm (should be impossible; Payment enforces INR). |
| Poller publishes `WalletCredited` but a consumer NACKs | Not Wallet Service's problem — downstream (Notification/Reporting) dedupe on `eventId`; SQS redrive there. |
| `GET /wallet/me/transactions` with a stale/garbled `cursor` | 400 `INVALID_CURSOR`; the app restarts from page 1. |
| Large ledger (thousands of entries) | Keyset pagination on the covering index — constant-time pages; no `OFFSET`. |
| Migration on a `wallets`/`ledger_entries` table that (in prod) has only opening entries | `balance * 100` / `amount * 100` is exact for `0`; `ref` backfill handles the opening rows. Zero data risk (Wallet Service isn't in prod yet). |
| Clock skew | `created_at` / `occurredAt` are server-generated. |
| `balance_after_paise` disagreeing with a later recomputation | Nightly invariant job flags it; `balance_after_paise` is a snapshot for display, `wallets.balance_paise` + `SUM(amount_paise)` are the truth. |

## 10. Testing Strategy

### Unit (domain — no AWS)

- `credit_recharge`: fresh event → one `ledger_entries` row (`type=RECHARGE`, `amount_paise=+A`, `balance_after_paise = old+A`), `wallets.balance_paise` bumped by `A`, one `outbox` `WalletCredited` with the right `ref`/`balanceAfterPaise`.
- Duplicate event (same `razorpayPaymentId`) → `ON CONFLICT` no-op: no balance change, **no** second `outbox` row; returns cleanly (ack).
- No wallet row → `RetryableError` (assert the message is **not** acked in the handler-level test).
- Wallet `status != ACTIVE` → `RetryableError`.
- `amountPaise` outside limits → still credits; asserts the `recharge_outside_current_limits` log/metric.
- `list_transactions`: newest-first ordering; `nextCursor` round-trips; `limit` clamped to 100; empty ledger → `items: [], nextCursor: null`.
- `get_wallet`: existing wallet → balance + bounds; missing wallet → `status: CREATING, balancePaise: 0`.
- Signed amounts: a hand-inserted `ORDER_DEBIT` of `−1000` makes `get_wallet` and the invariant still consistent (proves the schema is debit-ready).

### Integration (test containers + local EventBridge/SQS)

- Publish a `PaymentConfirmed` (purpose=WALLET_RECHARGE) to a local `wallet-events-q` → assert the ledger row, the balance, and a `WalletCredited` on the local bus.
- Fire the **same** event 5× → one credit, one `WalletCredited`, 5 message receipts (4 conflict-noops).
- Publish with `purpose = ORDER` → consumer acks + logs "unhandled", no credit (proves the discriminator).
- Publish with no wallet row → message ends in the DLQ after the configured attempts; create the wallet, redrive → credit succeeds.
- `GET /wallet/me` and `/wallet/me/transactions` over HTTP against the seeded row.

## 11. Risks and Trade-offs

- **Schema migration of MA-1's tables** — changing `balance`→`balance_paise` and `amount`→`amount_paise` is a breaking column change, mitigated entirely by the fact that Wallet Service is **not in production** (no data at risk). If MA-1 ships to an environment first, coordinate the migration order. Accepted.
- **Balance as a stored column** (vs always summing the ledger) — O(1) reads and a simple `GET /wallet/me`, at the cost of a consistency invariant to guard. The `FOR UPDATE` + single-transaction write plus a nightly check keeps it honest. The alternative (sum-on-read) is simpler to reason about but scales badly and complicates the passbook's running-balance column. Accepted.
- **Reusing `wallet-events-q` for a new message type** (vs a dedicated `wallet-recharge-q`) — fewer queues/rules to operate, and the consumer already multiplexes `UserRegistered`. Downside: one poison recharge message shares a DLQ with provisioning events. Acceptable given both are low-volume and idempotent; flagged for the reviewer (MA-126 §13c).
- **`RetryableError` for a missing wallet** — trades a (near-impossible) tail latency for a guarantee that real money is never dropped. A recharge landing before provisioning would need a user to recharge in the sub-second window between registration and the wallet-create event — effectively never. Accepted.
- **Limits owned here but enforced in Payment Service** — a single rule, two locations (owner + enforcer). Chosen because the amount must be validated *before* a Razorpay order exists, and Wallet Service never sees the request. Documented; MA-126 caches + falls back.
- **`type` enum with reserved-but-unused values** (`ORDER_DEBIT`, `REFUND`, …) — mild YAGNI, but it makes the debit/refund slices pure additions with no migration. Accepted.

## 12. Open Questions

- **`GET /wallet/me/status` (MA-1) disposition** — keep as a permanent alias of `GET /wallet/me`, or 301-redirect, or deprecate with a sunset date? (Non-breaking either way; MA-1's only consumer is the registration success screen.) Leaning: keep as an alias.
- **`OrderConfirmed` / `OrderCancelled` on `wallet-events-q`** — the consumer currently acks + logs them as unhandled. Confirm MA-97's Order Saga slice will *add* those handlers here (vs a separate consumer). Leaning: same consumer, added by MA-97.
- **Nightly invariant job placement** — an in-service scheduled task vs a separate ops Lambda. Leaning in-service (same as MA-126's reconciliation sweep decision).
- **`description` localisation** — server renders "Wallet top-up" in English; is i18n of ledger descriptions in scope for MA-27, or should the API return a `typeCode` and let the client localise? Leaning: return both `type` (code) and `description` (English default); MA-27 decides.
- **Dedicated `wallet-recharge-q`** — see Risks; reviewer call.
