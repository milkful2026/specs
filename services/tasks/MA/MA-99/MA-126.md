## 2. Problem Statement

There is **no Payment Service** yet — `services/payment/` is unimplemented, and the app has no way to take money. MA-24 needs a customer to fund their prepaid wallet through **Razorpay** (UPI / card) from the Flutter Wallet screen (MA-125). That requires a service that: creates a gateway order server-side for an exact amount, verifies the payment authoritatively via Razorpay's **webhook** (never trusting the mobile client), is **idempotent** so retries and duplicate callbacks never double-charge, persists a **reconciliation reference**, and emits a domain event the Wallet Service consumes to credit the ledger.

This spec is the **first slice of Payment Service**, deliberately scoped to `purpose = WALLET_RECHARGE`. The generic `purpose = ORDER` path (checkout for a cart) is designed-for but **not built here** — it is a later story's extension of the same tables and endpoints.

It also **owns the cross-service contract**: the `PaymentConfirmed` / `PaymentFailed` event schemas, the new EventBridge rule that routes recharge confirmations to `wallet-events-q`, and the resolution of two naming discrepancies found during context-building (see §8). MA-127 consumes this contract.

Expected outcome: a mobile client can initiate a recharge, complete it in Razorpay, and — driven by the webhook — have `PaymentConfirmed` published within seconds, exactly once, with a durable audit trail.

## 3. Scope

### In scope

- **Payment Service scaffold** in `services/payment/` following the repo's `handler → domain → adapter` structure (mirroring `services/cart/`), its own Dockerfile, IAM role, Aurora migrations, and CDK/Terraform wiring for the ALB target, EventBridge rule, and Secrets Manager entries.
- **Endpoints** (behind API Gateway + Cognito JWT, except the webhook):
  - `POST /payments` — create a Razorpay order for a recharge (`Idempotency-Key` header).
  - `POST /payments/{id}/confirm` — accept the mobile client's signed Razorpay callback; advance to `CONFIRMING`.
  - `POST /payments/webhook` — **public**, Razorpay-signature-verified; authoritative `CONFIRMED` / `FAILED`.
  - `GET /payments/{id}` — read a payment's current state (owner-scoped).
- **Razorpay integration adapter** — Orders API (`orders.create`), webhook signature verification, `payments/{id}` fetch (for the reconciliation sweep). Circuit breaker + retry/backoff.
- **Idempotency** at three points (§6): client key on `POST /payments`, Razorpay `order_id` uniqueness, and a stable `paymentId`/`razorpay_payment_id` the Wallet Service dedupes on.
- **Reconciliation sweep** — a scheduled job that resolves `CONFIRMING` payments older than a threshold by polling Razorpay.
- **Transactional outbox** → `PaymentConfirmed` / `PaymentFailed` on the `milkful-events` EventBridge bus, carrying the `purpose` discriminator.
- **New EventBridge rule** matching `PaymentConfirmed` where `detail.purpose = WALLET_RECHARGE` → `wallet-events-q`.
- **Data model** — `payments`, `payment_events`, `outbox` in Aurora `payments`.
- **Secrets** — Razorpay `key_id` + `key_secret` + `webhook_secret` in Secrets Manager (rotation-enabled).
- **Observability** — structured logs with `correlationId`, CloudWatch metrics + alarms, X-Ray.
- **Cross-service contract doc** (this spec's §8) — `PaymentConfirmed` / `PaymentFailed` / `WalletCredited` schemas and the endpoint/event naming rulings; MA-127 references it.

### Out of scope

- `purpose = ORDER` payment flows (cart checkout) — designed-for, not built. No `POST /orders` orchestration here.
- **Refunds** (`POST /payments/{id}/refund`, `RefundIssued`) — MA-32 / MA-16.
- **Wallet-first split-tender** (charge some to wallet, rest to gateway in one payment) — not needed for a recharge (a recharge is 100% gateway); the "wallet-first" behaviour lives in the Order Saga (MA-97), out of scope.
- **Saved-card / customer-token management APIs** — v1 relies on Razorpay-native saved instruments; Payment Service stores only whatever token/customer ref Razorpay returns, no CRUD API.
- **Paytm / PhonePe / other gateways** — Razorpay only.
- **Admin reconciliation UI** — MA-40; this spec sets the data contract, not the console.
- **Wallet crediting itself** — MA-127 owns the ledger write; this service only emits the event.
- **Net-banking / EMI / pay-later** as distinct server concepts — Razorpay reports the actual method; we store it, we don't special-case it.

## 4. Functional Requirements

### FR-1: `POST /payments` — create a recharge order

**Auth:** Cognito JWT (`sub` → `userId`).
**Headers:** `Idempotency-Key` (required, client-generated UUID; 400 if missing), `X-Correlation-Id` (optional; generated if absent).
**Body:**
```json
{ "purpose": "WALLET_RECHARGE", "amountPaise": 50000, "currency": "INR", "method": "UPI" }
```
**Rules:**
- `purpose` must be `WALLET_RECHARGE` for this slice (400 `UNSUPPORTED_PURPOSE` otherwise).
- `amountPaise` integer, `> 0`, within `[rechargeMinPaise, rechargeMaxPaise]` — the bounds are **owned by Wallet Service** (MA-127); Payment Service fetches them once via `GET /wallet/internal/limits` (SigV4) and caches (TTL 5 min), or accepts a `limits` config fallback. Out-of-range → 422 `AMOUNT_OUT_OF_RANGE` with the min/max echoed.
- `currency` must be `INR`.
- `method` ∈ `{UPI, CARD}` — a hint passed to Razorpay; not authoritative.
- **Idempotency:** keyed on `(user_id, idempotency_key)`.
  - **Row exists with a `razorpay_order_id`** → return that row's create-response verbatim (200, not a new order); never create a second Razorpay order for the same key.
  - **Row exists without a `razorpay_order_id`** (a prior attempt inserted the row but `orders.create` failed — see *Failure* below) → resume: call `orders.create` once, persist the `razorpay_order_id`, return the create-response. This is the retry path, not a second order.
  - **Body mismatch on a reused key** → if a row exists for the key but the incoming `amountPaise`, `purpose`, or `currency` differ from the stored row, return **409 `IDEMPOTENCY_KEY_REUSED`** with the stored `amountPaise`/`purpose` echoed. Never return an order for a different amount than the caller now asks for.
**Behaviour:**
1. Insert `payments` row `status = CREATED`, `purpose`, `amount_paise`, `user_id`, `idempotency_key`, `correlation_id`.
2. Call Razorpay `orders.create({ amount: amountPaise, currency: 'INR', receipt: paymentId, notes: { userId, purpose } })` via the adapter (circuit-breaker guarded).
3. Persist `razorpay_order_id` (UNIQUE) on the row.
4. Append a `payment_events` row `source = INTERNAL_CREATE` with the request/response snapshot.
**Response 200/201:**
```json
{ "paymentId": "pay_int_...", "razorpayOrderId": "order_...", "razorpayKeyId": "rzp_live_...",
  "amountPaise": 50000, "currency": "INR", "status": "CREATED" }
```
**Failure:** Razorpay unavailable after retries → 503 `GATEWAY_UNAVAILABLE`, row left `CREATED` with no `razorpay_order_id` (a later identical idempotent call retries the `orders.create`).

### FR-2: `POST /payments/{id}/confirm` — client callback

**Auth:** Cognito JWT; the `payment.user_id` must match `sub` (else 404, not 403 — don't leak existence).
**Body:** `{ "razorpayPaymentId": "pay_...", "razorpayOrderId": "order_...", "razorpaySignature": "hex" }`
**Rules:**
- Verify `razorpaySignature == HMAC_SHA256(razorpayOrderId + "|" + razorpayPaymentId, key_secret)`. Mismatch → 400 `SIGNATURE_INVALID`; append `payment_events` `source = CLIENT_CONFIRM_REJECTED`; **do not** change status.
- `razorpayOrderId` must equal the row's `razorpay_order_id` (else 409 `ORDER_MISMATCH`).
- Idempotent: if already `CONFIRMED` / `FAILED`, return the current state (200). If `CONFIRMING`, return 200 (no-op).
**Behaviour on valid signature:**
1. Set `status = CONFIRMING`, persist `razorpay_payment_id`, `razorpay_signature`.
2. Append `payment_events` `source = CLIENT_CONFIRM`.
3. **Do not** emit `PaymentConfirmed` and **do not** trigger crediting — that is the webhook's job (FR-3). This endpoint exists only so the app can show an accurate "processing" state quickly.
**Response 200:** `{ "paymentId", "status": "CONFIRMING" }`
> Rationale: a signed client callback proves the user *reached* a Razorpay success screen, but not that funds settled (UPI can still fail post-collection). Only `payment.captured` is trusted.

### FR-3: `POST /payments/webhook` — authoritative confirmation

**Auth:** **no JWT.** Gated by: (a) Razorpay webhook signature `X-Razorpay-Signature == HMAC_SHA256(rawBody, webhook_secret)` — reject 400 on mismatch, increment `webhook.signature_invalid`; (b) source IP in the Razorpay allowlist (WAF / SG). The handler never parses the body before the signature check passes.
**Events handled:** `payment.captured`, `payment.failed`, `order.paid` (treat as `captured`). Others → 200 ack, no-op.
**Behaviour (`payment.captured` / `order.paid`):**
1. Resolve the `payments` row by `razorpay_order_id` (from `payload.payment.entity.order_id`). Unknown → 200 ack + log `orphan_webhook` (could be an ORDER-purpose payment once that exists; for now, alert if `notes.purpose == WALLET_RECHARGE` and no row).
2. Idempotent / terminal-state handling:
   - Row already `CONFIRMED` → append `payment_events` `source = WEBHOOK_DUP`, 200 ack, no further work.
   - Row `FAILED` with `failure_code = TIMEOUT` (our own provisional sweep failure, FR-5) → treat as **not** terminal: continue to step 3 and settle it `CONFIRMED`, appending `payment_events` `source = LATE_CAPTURE_RECOVERED` and emitting `PaymentConfirmed` (the money is real). Metric `recharge.late_capture_recovered`.
   - Row `FAILED` with any other `failure_code` (a Razorpay-reported failure) → append `payment_events` `source = WEBHOOK_DUP`, raise `late_capture_after_fail` alert, 200 ack, **no** state change (genuinely contradictory — ops decides).
3. Verify `payload.payment.entity.amount == amount_paise` and `order_id` match. Mismatch → status `FAILED`, `failure_code = AMOUNT_MISMATCH`, alert, 200 ack.
4. In **one DB transaction**: set `status = CONFIRMED`, persist `razorpay_payment_id`, `method` (from `payload.payment.entity.method`), `captured_at`; append `payment_events` `source = WEBHOOK`; insert an `outbox` row for `PaymentConfirmed` (§8 schema).
5. The outbox poller publishes `PaymentConfirmed` to `milkful-events`.
**Behaviour (`payment.failed`):**
1. Resolve row; if not already terminal, set `status = FAILED`, `failure_code`/`failure_reason` from the payload; append `payment_events`; insert `outbox` row for `PaymentFailed`.
**Response:** always `200` with `{"status":"ok"}` once the signature is valid and the event is recorded (Razorpay retries non-2xx — we ack fast and process idempotently).

### FR-4: `GET /payments/{id}` — read state

**Auth:** Cognito JWT; owner-scoped (404 if not the caller's).
**Response 200:**
```json
{ "paymentId", "purpose", "status", "amountPaise", "currency", "method",
  "razorpayOrderId", "razorpayPaymentId", "failureReason", "createdAt", "updatedAt" }
```
Used by the app's pending-state polling (MA-125 FR-6) and by support.

### FR-5: Reconciliation sweep

- A scheduled task (EventBridge Scheduler → the service, or an internal cron on the Fargate task) runs every **2 minutes**.
- For each `payments` row `status = CONFIRMING` (or `CREATED` with a `razorpay_order_id`) older than **3 minutes**, call Razorpay `orders/{razorpay_order_id}/payments` and branch on what Razorpay reports:
  - **A captured payment exists** → run the FR-3 `captured` path (idempotent) → `CONFIRMED` + `PaymentConfirmed`.
  - **The order is no longer payable** (all payment attempts failed, or the order has expired) → `FAILED` `failure_code = GATEWAY_FAILED` + `PaymentFailed`.
  - **The order is still payable** (e.g. a UPI collect the customer has not yet acted on — Razorpay's `orders` API still shows it open) → **leave the row `CONFIRMING`**. Do not force-fail it. Keep sweeping. Emit `payment.confirming_over_30m` once it passes 30 minutes and alarm — but only mark `FAILED` `failure_code = TIMEOUT` when either Razorpay's order status itself becomes non-payable **or** a hard cap of **6 hours** is reached (well beyond any real UPI-collect window).
- A `TIMEOUT` failure is **provisional**, not a settled "no money moved": the row stays eligible for a late `payment.captured` webhook, which recovers it to `CONFIRMED` (see §9). Only a Razorpay-reported failure (`GATEWAY_FAILED`, or a `payment.failed` webhook) is terminal.
- Rationale: an uncaptured **card** authorization is auto-voided by Razorpay; a **UPI collect** has nothing captured to void — it simply expires. Real money only ever moves on a `captured` event, so the sweep must never declare failure ahead of Razorpay for a still-open collect.
- Emits metric `recharge.reconciled{outcome}`; alarms on `payment.confirming_over_30m > 0` and on every `TIMEOUT` failure (finance visibility).

### FR-6: Internal limits fetch

- `GET /wallet/internal/limits` (SigV4, service-to-service) → `{ rechargeMinPaise, rechargeMaxPaise }` from Wallet Service (MA-127). Cached 5 min. On failure, fall back to a config default (`WALLET_RECHARGE_MIN_PAISE` / `_MAX_PAISE`, defaults ₹100 / ₹1,00,000) and log `limits_fallback`.

## 6. Technical Design

### Component responsibilities

```
API Gateway (Cognito JWT)                Razorpay
   │  POST /payments                        ▲  orders.create / orders/{id}/payments
   │  POST /payments/{id}/confirm           │
   │  GET  /payments/{id}                   │
   ▼                                        │
Payment Service (Fargate)                   │
 ├─ handlers/          thin: authn, DTO map, error translation
 ├─ domain/
 │   ├─ payment_service.py   create / confirm / apply_webhook / reconcile — all business rules, idempotency
 │   └─ models.py            Payment, PaymentStatus, Purpose, PaymentEvent
 ├─ adapters/
 │   ├─ payment_repository.py   Aurora (payments, payment_events) — SELECT ... FOR UPDATE on the row
 │   ├─ outbox_repository.py    outbox insert (same tx) + poller publish
 │   ├─ razorpay_gateway.py     PaymentGateway port impl (orders.create, verify_webhook_sig, verify_client_sig, fetch_order_payments)
 │   └─ wallet_limits_client.py SigV4 GET /wallet/internal/limits (cached)
 └─ jobs/reconcile.py           scheduled sweep (FR-5)

Public (no JWT):
   POST /payments/webhook  ──►  handlers/webhook.py  ──► domain.apply_webhook()
```

### Payment lifecycle

```
CREATED ──(orders.create ok)──► CREATED(+order_id)
   │                                  │  client pays in Razorpay
   │                                  ▼
   │                          POST /confirm (valid sig)  ──► CONFIRMING
   │                                  │
   ├──────────── webhook payment.captured / sweep ───────► CONFIRMED  ──► outbox: PaymentConfirmed
   └──────────── webhook payment.failed / sweep timeout ─► FAILED     ──► outbox: PaymentFailed
```

`CONFIRMING` is optional — a payment can go `CREATED → CONFIRMED` directly if the webhook beats the client `confirm` (or the client never calls it). `confirm` never advances past `CONFIRMING`. A row the reconciliation sweep marked `FAILED` `failure_code = TIMEOUT` (FR-5) is **provisionally** failed — a later `payment.captured` recovers it to `CONFIRMED`; a Razorpay-reported failure (`GATEWAY_FAILED` / `payment.failed`) is terminal.

### Idempotency — the three layers

1. **Client key** — `UNIQUE(user_id, idempotency_key)` on `payments`. `POST /payments` on a dup key returns the stored create-response; no second Razorpay order.
2. **Gateway order** — `razorpay_order_id UNIQUE`. `orders.create` is only ever called for a row without one.
3. **Confirmation** — `apply_webhook` / `apply_confirm` / `reconcile` all take `SELECT ... FOR UPDATE` on the row and no-op if already terminal. The downstream credit is deduped by MA-127 on `razorpay_payment_id` (ledger `ref` UNIQUE). Result: **at most one `PaymentConfirmed` per payment**, and at most one credit.

### API definitions

| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| `POST` | `/payments` | JWT + `Idempotency-Key` | Create a recharge order (FR-1) |
| `POST` | `/payments/{id}/confirm` | JWT (owner) | Record the client's signed callback → `CONFIRMING` (FR-2) |
| `POST` | `/payments/webhook` | Razorpay HMAC + IP allowlist | Authoritative `CONFIRMED`/`FAILED` (FR-3) |
| `GET` | `/payments/{id}` | JWT (owner) | Read state (FR-4) |
| `GET` | `/wallet/internal/limits` | *(consumed, owned by MA-127)* | Recharge bounds (FR-6) |

### Data flow (recharge, happy path)

```
Flutter → POST /payments {WALLET_RECHARGE, 50000, UPI, Idempotency-Key:k1}
Payment: insert payments(CREATED, k1) → razorpay.orders.create(50000) → save order_id → 200 {paymentId, orderId, keyId}
Flutter → Razorpay sheet → success {payment_id, order_id, signature}
Flutter → POST /payments/{id}/confirm {razorpayPaymentId, razorpayOrderId, razorpaySignature} → verify(order_id|payment_id, key_secret) ok, order_id matches row → status CONFIRMING → 200
Razorpay → POST /payments/webhook  payment.captured {order_id, payment_id, amount:50000, method:upi}
Payment: verify HMAC(rawBody, webhook_secret) ok → row by order_id → tx{ status=CONFIRMED, method=UPI, captured_at,
         payment_events+=WEBHOOK, outbox+=PaymentConfirmed{purpose:WALLET_RECHARGE, ...} }
Outbox poller → events.PutEvents(milkful-events, PaymentConfirmed)
EventBridge rule (detail.purpose=WALLET_RECHARGE) → wallet-events-q → Wallet Service (MA-127) credits ledger
```

## 7. Data Considerations

**Aurora `payments` cluster — new schema (migrations under `services/payment/migrations/`):**

```sql
CREATE TYPE payment_purpose AS ENUM ('WALLET_RECHARGE', 'ORDER');
CREATE TYPE payment_status  AS ENUM ('CREATED', 'CONFIRMING', 'CONFIRMED', 'FAILED');
CREATE TYPE payment_method  AS ENUM ('UPI', 'CARD', 'NETBANKING', 'WALLET', 'OTHER');

CREATE TABLE payments (
  id                  TEXT PRIMARY KEY,               -- app-generated, e.g. 'pay_' + uuid
  user_id             TEXT NOT NULL,
  purpose             payment_purpose NOT NULL,
  amount_paise        BIGINT NOT NULL CHECK (amount_paise > 0),
  currency            CHAR(3) NOT NULL DEFAULT 'INR',
  status              payment_status NOT NULL DEFAULT 'CREATED',
  method              payment_method,
  razorpay_order_id   TEXT UNIQUE,
  razorpay_payment_id TEXT,
  razorpay_signature  TEXT,
  idempotency_key     TEXT NOT NULL,
  failure_code        TEXT,
  failure_reason      TEXT,
  correlation_id      TEXT NOT NULL,
  captured_at         TIMESTAMPTZ,
  created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, idempotency_key)
);
CREATE INDEX payments_status_updated_idx ON payments (status, updated_at);   -- reconciliation sweep

CREATE TABLE payment_events (              -- immutable audit of every state-affecting input
  id           BIGSERIAL PRIMARY KEY,
  payment_id   TEXT NOT NULL REFERENCES payments(id),
  source       TEXT NOT NULL,             -- INTERNAL_CREATE | CLIENT_CONFIRM | CLIENT_CONFIRM_REJECTED
                                          -- | WEBHOOK | WEBHOOK_DUP | LATE_CAPTURE_RECOVERED | RECONCILE | ...
  raw_payload  JSONB NOT NULL,
  received_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE outbox (
  id             BIGSERIAL PRIMARY KEY,
  aggregate_id   TEXT NOT NULL,           -- payment id
  event_type     TEXT NOT NULL,           -- PaymentConfirmed | PaymentFailed
  payload        JSONB NOT NULL,          -- the full EventBridge 'detail'
  published_at   TIMESTAMPTZ,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX outbox_unpublished_idx ON outbox (created_at) WHERE published_at IS NULL;
```

- **Money:** `BIGINT` paise, `CHECK > 0`. No numeric/float.
- **Retention:** `payments` + `payment_events` + `outbox` retained per finance policy (assume 7 years); PITR on the cluster.
- **PII:** `user_id` only (a Cognito sub). No name/email/phone stored; `raw_payload` from Razorpay is card-data-free by SAQ-A (verify the webhook payload shape in implementation and redact if Razorpay ever includes `card.last4` beyond what's needed).
- **Migration impact:** none on other services — new cluster, new tables. The `ORDER` enum value is present but unused.

## 8. Integration Considerations (cross-service contract — owned here)

### 8.1 `PaymentConfirmed` (EventBridge `milkful-events`)

```json
{
  "version": "0", "id": "<eventbridge id>", "detail-type": "PaymentConfirmed",
  "source": "milkful.payment", "time": "<iso8601>",
  "detail": {
    "eventId": "<uuid>",                 // dedupe key for consumers
    "occurredAt": "<iso8601>",
    "correlationId": "<uuid>",
    "paymentId": "pay_...",
    "userId": "<cognito sub>",
    "purpose": "WALLET_RECHARGE",        // discriminator — consumers filter on this
    "amountPaise": 50000,
    "currency": "INR",
    "method": "UPI",
    "razorpayPaymentId": "pay_...",
    "razorpayOrderId": "order_..."
  }
}
```

### 8.2 `PaymentFailed`

Same envelope; `detail` adds `failureCode`, `failureReason`; omits `method` if unknown.

### 8.3 EventBridge routing (new)

- **New rule** `payment-confirmed-wallet-recharge` on `milkful-events`:
  `{ "detail-type": ["PaymentConfirmed"], "detail": { "purpose": ["WALLET_RECHARGE"] } }` → target **`wallet-events-q`** (existing SQS queue + its existing DLQ).
- `wallet-events-q` currently receives `UserRegistered` / `OrderConfirmed` / `OrderCancelled` (well-architected §7.2). This adds recharge `PaymentConfirmed` to it. The Wallet consumer (MA-127) branches on `detail-type` + `purpose`.
- `PaymentFailed` for recharges is routed to **`notification-events-q`** only (already subscribed to `PaymentFailed`) — the app learns of failure synchronously via `GET /payments/{id}`; no wallet action needed.
- **`milkful-messaging.drawio` update:** this recharge path is not currently drawn. The spec's acceptance includes a note for the architect to add it; the spec itself does not edit the `.drawio`.

### 8.4 `WalletCredited` (published by MA-127 — schema agreed here for coherence)

```json
{ "detail-type": "WalletCredited", "source": "milkful.wallet",
  "detail": { "eventId", "occurredAt", "correlationId", "userId", "walletId",
              "amountPaise", "balanceAfterPaise", "type": "RECHARGE",
              "ref": "razorpay_payment:pay_...", "paymentId": "pay_..." } }
```

### 8.6 Dependency failure behaviour

| Dependency | Failure | Behaviour |
|------------|---------|-----------|
| Razorpay `orders.create` | timeout / 5xx | retry ×3 w/ backoff → circuit-open → `POST /payments` 503 `GATEWAY_UNAVAILABLE`; row stays `CREATED`, retryable via the same idempotency key. |
| Razorpay (webhook not received) | lost webhook | reconciliation sweep (FR-5) polls Razorpay and settles the row within ~3 min. |
| EventBridge `PutEvents` | throttle / error | outbox row stays unpublished; poller retries with backoff; `outbox.publish_lag_seconds` alarm. |
| `wallet-events-q` consumer down | MA-127 unavailable | events queue in SQS; DLQ after redrive; no data loss; balance is eventually consistent; `GET /payments/{id}` still shows `CONFIRMED`. |
| Wallet `GET /wallet/internal/limits` | unavailable | config fallback bounds + `limits_fallback` log. |

## 9. Edge Cases and Failure Modes

| Case | Handling |
|------|----------|
| Duplicate `POST /payments` (same key, same body, order already created) | Return the stored create-response; no new order. |
| `POST /payments` retried after `orders.create` failed (row `CREATED`, no `order_id`) | Same key + same body → resume `orders.create` once, then persist. |
| `POST /payments` reuses a key with a different `amountPaise` / `purpose` / `currency` | 409 `IDEMPOTENCY_KEY_REUSED`, stored values echoed; no order, no state change. |
| Webhook arrives before `POST /payments/{id}/confirm` | `CREATED → CONFIRMED` directly; a later `confirm` is a 200 no-op. |
| `confirm` with a valid sig but for a different `order_id` | 409 `ORDER_MISMATCH`; no state change; `payment_events` records the attempt. |
| Webhook `payment.captured` with `amount != amount_paise` | `FAILED` `AMOUNT_MISMATCH`, alert, 200 ack. (Should be impossible — Razorpay order was created server-side for the exact amount.) |
| Duplicate webhook (Razorpay retries) | `WEBHOOK_DUP` audit row, 200 ack, no state change, no second `outbox` row. |
| Late `payment.captured` after our own sweep set the row `FAILED` `TIMEOUT` | The `TIMEOUT` failure is provisional — the `captured` webhook runs the FR-3 `captured` path idempotently → `CONFIRMED` + `PaymentConfirmed`; `payment_events` `source = LATE_CAPTURE_RECOVERED`; metric `recharge.late_capture_recovered`. |
| Razorpay-reported `payment.failed`, then a later `payment.captured` for the same payment | Contradictory, should be impossible. `WEBHOOK_DUP` + `late_capture_after_fail` alert; **not** auto-handled — ops decides (manual credit + refund). Distinguished from the row above by `failure_code` (`TIMEOUT` = ours/provisional; anything else = Razorpay-reported/terminal). |
| Payment `CONFIRMING` past 30 min, Razorpay still shows the order payable (UPI collect open) | Not force-failed; `payment.confirming_over_30m` alarm; sweep continues until Razorpay marks the order non-payable or the 6-hour hard cap (FR-5). |
| Payment `CONFIRMING`, Razorpay reports the order failed / expired | `FAILED` `GATEWAY_FAILED` + `PaymentFailed`. |
| Signature-invalid webhook flood | 400 + `webhook.signature_invalid` metric + alarm; WAF rate-limit; body never parsed. |
| Orphan webhook (`order_id` not in `payments`) | 200 ack + `orphan_webhook` log; alert only if `notes.purpose == WALLET_RECHARGE`. |
| `outbox` row published but consumer never acks (SQS) | SQS redrive → DLQ + alarm; replay is idempotent (consumer dedupes on `eventId`/`razorpayPaymentId`). |
| Two Fargate tasks process the same webhook concurrently | `SELECT ... FOR UPDATE` on the `payments` row serializes them; the second sees terminal state → `WEBHOOK_DUP`. |
| Clock skew on `time` fields | All timestamps server-generated (`now()` / event `occurredAt` from the service), not client-supplied. |

## 10. Testing Strategy

### Unit (domain — no AWS, no real Razorpay)

- `create`: new key → inserts row + calls `gateway.orders_create` once + persists `order_id`; dup key with an `order_id` already stored → returns stored response, `orders_create` **not** called; dup key on a row with **no** `order_id` → resumes `orders_create` once then persists; dup key with a different `amountPaise` → 409 `IDEMPOTENCY_KEY_REUSED`, no order created; amount out of range → `AMOUNT_OUT_OF_RANGE`; `orders_create` raises → 503, row `CREATED` no `order_id`.
- `confirm`: valid sig → `CONFIRMING` + `CLIENT_CONFIRM` event; bad sig → `SIGNATURE_INVALID`, no state change, `CLIENT_CONFIRM_REJECTED` event; already `CONFIRMED` → 200 no-op; `order_id` mismatch → `ORDER_MISMATCH`.
- `apply_webhook(captured)`: `CREATED → CONFIRMED` + exactly one `outbox` `PaymentConfirmed` with `purpose=WALLET_RECHARGE`; second call → `WEBHOOK_DUP`, no new outbox; amount mismatch → `FAILED` `AMOUNT_MISMATCH`.
- `apply_webhook(failed)`: → `FAILED` + `outbox` `PaymentFailed`.
- late `captured` after `FAILED` `TIMEOUT` (our sweep) → `CONFIRMED` + `PaymentConfirmed` + `LATE_CAPTURE_RECOVERED` event; late `captured` after a Razorpay-reported `FAILED` → `WEBHOOK_DUP` + `late_capture_after_fail` alert, no state change.
- `reconcile`: `CONFIRMING` + Razorpay shows captured → `CONFIRMED` path; Razorpay shows the order non-payable → `FAILED` `GATEWAY_FAILED`; Razorpay still shows the order payable, < 6 h → **untouched** (alarm only past 30 min); Razorpay still payable at the 6 h hard cap → `FAILED` `TIMEOUT` (provisional).
- Webhook signature verification: known-vector HMAC test (fixed body + secret → expected signature); tampered body → reject.

### Integration (Localstack / test containers + Razorpay **test mode**)

- `POST /payments` → real Razorpay test `orders.create` → row has a real `order_id`.
- Simulate Razorpay webhook (signed with the test webhook secret) → row `CONFIRMED` → an `outbox` row → poller `PutEvents` to a local EventBridge → the new rule delivers to a test `wallet-events-q`.
- Idempotency: fire the same signed webhook 5×; assert one `CONFIRMED`, one outbox row, 5 `payment_events` (1 `WEBHOOK` + 4 `WEBHOOK_DUP`).
- Reconciliation: create a payment, capture it in Razorpay test dashboard/API but **drop** the webhook; run the sweep; assert `CONFIRMED` + event.

### Contract

- JSON-schema the `PaymentConfirmed` / `PaymentFailed` `detail`; MA-127's consumer tests validate against the same schema file (shared under `services/shared/events/`).

### Acceptance

- All unit + integration green; `POST /payments` → Razorpay test UPI (`success@razorpay`) → webhook → `PaymentConfirmed` observed on the bus, end to end, in a local stack.
- Negative: `failure@razorpay` → `PaymentFailed`; tampered webhook → 400 + metric; duplicate webhook → single credit downstream (verified with MA-127's consumer).
- Security review sign-off: no secret in logs/env/image; webhook rejects unsigned/mis-signed; no card data persisted.

## 11. Risks and Trade-offs

- **First service scaffold** — no `services/payment/` prior art. Mitigation: mirror `services/cart/` structure exactly (handler→domain→adapter, outbox, idempotency table); it is in the canonical 13-service inventory so **no new-service architect gate** — but report the scaffold + tests per the repo's "extend before you create" rule.
- **Webhook as source of truth adds latency** to the user's "it worked" moment vs trusting the client callback. Trade-off accepted: trusting the client callback risks crediting a wallet for a UPI collection that later fails. The `CONFIRMING` state + the app's pending UI bridge the gap.
- **Event-driven crediting** (vs a synchronous Payment→Wallet call) — chosen for decoupling per the well-architected guardrails, at the cost of a new EventBridge rule and a `purpose` discriminator. A sync call would be simpler but couples the two services and loses the outbox/replay safety. Flagged and accepted in the decomposition.
- **Reconciliation sweep polling Razorpay** — a periodic cost and a dependency on Razorpay's `orders/{id}/payments` API. Alternative (rely solely on webhooks) is fragile to a single lost webhook. Accepted; 2-min cadence is cheap.
- **Amount limits owned by Wallet Service** — Payment fetches them (FR-6), adding a cross-service read on `POST /payments`. Cached 5 min + config fallback keeps it non-blocking. Alternative (Payment owns limits) would split a single business rule across two services. Accepted.
- **`purpose` enum with an unused `ORDER` value** — mild YAGNI, but it makes the ORDER slice a pure addition (no migration, no event-schema change). Accepted.

## 12. Open Questions

- **Reconciliation scheduler mechanism** — EventBridge Scheduler invoking an endpoint vs an in-task cron (APScheduler-style) on the Fargate service. Leaning in-task (simpler, no extra IAM); confirm with platform.
- **Razorpay account / entity** — is there an existing Milkful Razorpay merchant account, and one account for both recharge and future order payments, or Razorpay Route sub-accounts per concern? (Affects `key_id` provisioning and settlement reporting.) Needs a business answer before go-live; does not block the spec.
- **Webhook IP allowlist source** — Razorpay publishes webhook source IPs; confirm whether we pin them at the WAF, the SG, or rely on signature-only. Leaning signature + WAF rate-limit, IP allowlist as defence-in-depth if the list is stable.
- **`payment_events.raw_payload` redaction** — confirm the exact Razorpay `payment.captured` payload fields and redact anything beyond `id/order_id/amount/method/status/created_at` if present.
- **Shared event-schema location** — proposing `services/shared/events/*.schema.json`; confirm the `services/` repo wants a `shared/events/` folder (the README allows transport/envelope helpers in `shared/`).
