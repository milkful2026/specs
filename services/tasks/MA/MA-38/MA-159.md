## 2. Problem Statement

An order records only its grand total (`orders.amount_paise`). `order_items` holds `product_id` and `quantity`, and subscription orders keep their single product on `orders` itself. Nothing records what each line cost, how it was taxed, what the delivery fee was, or where the order was delivered.

Since a GST invoice must show exactly what was charged, those facts must be captured **at order creation**, when the price is quoted and charged. They cannot be reconstructed later, because prices, tax rates and addresses all change over time.

**Expected outcome:**
- Every new order stores an immutable bill: per-line price and tax, the delivery-fee line, supply type, place of supply, and a billing-address snapshot.
- The customer API returns a `bill` summary.
- The Invoice Service can read the day's confirmed orders with their full breakdown through an internal endpoint, without touching Order's database.

## 3. Scope

### In Scope

- **User Service:** add `name`, `mobile` and `defaultAddress` to `GET /v1/internal/users/address-state` (additive).
- **Order — user client:** read those fields in the same single call it already makes.
- **Order — pricing client:** parse MA-158's `lines`, `deliveryFeeLine`, `supplyType`, `placeOfSupplyState`, `netPayablePaise`.
- **Migration `0005_bill_snapshot.sql`:** new nullable columns on `orders` and `order_items`.
- **Snapshot on both creation paths:**
  - Subscription orders (MA-132, `order_service.py`).
  - Checkout one-time orders (MA-136, `checkout_service.py`).
- **Subscription orders also write one `order_items` row** (line 1), so every priced order has a uniform breakdown.
- **`bill` object** on `GET /orders/{id}` and `GET /orders/me`.
- **New internal endpoint** `GET /orders/internal/confirmed`: confirmed orders for a delivery date, with full breakdown and billing address.

### Out of Scope

- Invoice generation, numbering and PDF (MA-160).
- Mobile UI (MA-161).
- Backfilling bills for existing orders: they stay `bill: null`.
- Address editing, or a per-order delivery address chosen at checkout. The snapshot is the default address at creation time, which is what the order was actually delivered to today.
- Changing how `amount_paise` is charged. It now comes from `netPayablePaise` but must equal the old `round(netPayable × 100)`.

## 4. Functional Requirements

### FR-1: User internal endpoint — billing fields (User Service)

`GET /v1/internal/users/address-state?cognitoSub=…` keeps `defaultAddressState` and adds:

```json
{
  "defaultAddressState": "Karnataka",
  "name": "Asha Rao",
  "mobile": "+919800000000",
  "defaultAddress": {
    "lines": ["Flat 4B, Green Residency", "12th Main"],
    "landmark": "Near City Park",
    "city": "Bengaluru", "state": "Karnataka", "pincode": "560038"
  }
}
```

- `defaultAddress` is `null` when no default address exists (the same condition under which `defaultAddressState` is null today).
- The data comes from `UserProfile` (`name`, `mobile`, `default_address`), which `get_my_profile` already loads, so there are no new queries.
- `lat`/`lng`/`zoneId` are **not** returned (not needed; minimises PII).

### FR-2: Order user client

- `UserClientPort.get_delivery_address_state` is replaced by `get_billing_profile(cognito_sub) -> BillingProfile | None`.
- `BillingProfile` has `state`, `name`, `mobile` and `address` (lines, landmark, city, state, pincode).
- It returns `None` exactly when today's method returns `None` (no default address), keeping the existing `DELIVERY_ADDRESS_UNKNOWN` behaviour.
- Retries, SigV4 signing and `AddressLookupUnavailableError` are unchanged.

### FR-3: Order pricing client

- `Quote` (Order's domain copy) gains `lines: list[QuoteLine]`, `fee_line: FeeLine`, `supply_type`, `place_of_supply_state` and `net_payable_paise`.
- **If Pricing's response lacks `lines`** (an older Pricing build), the client returns a `Quote` with `lines=[]` and `fee_line=None`. The order is then created **without** a bill snapshot (columns null) and the metric `order.bill_snapshot.missing` is emitted. This makes the deploy order Pricing → Order safe, and never blocks ordering.

### FR-4: Amount charged

- `amount_paise = quote.net_payable_paise` when present; otherwise the existing `round_half_up(net_payable × 100)`.
- An assertion (log at error level plus metric, never fail the order) checks that the two agree whenever both are available.

### FR-5: Snapshot at creation

Written in the **same transaction** that inserts the order (status `CREATED`), on both paths.

**`order_items`, one row per quote line, in request order:**

| Column | Source |
|---|---|
| `product_name` | `lines[i].productName` |
| `hsn_code` | `lines[i].hsnCode` |
| `unit_price_paise` | `lines[i].unitPricePaise` |
| `discount_paise` | `lines[i].discountPaise` |
| `taxable_paise` | `lines[i].taxablePaise` |
| `tax_rate` | `lines[i].taxRatePercent` |
| `cgst_paise` / `sgst_paise` / `igst_paise` | `lines[i]` |
| `line_total_paise` | `lines[i].totalPaise` |

- **Subscription orders** insert one `order_items` row (`line_no = 1`, `product_id`, `quantity`) carrying the same columns. `orders.product_id`/`quantity` stay populated as today, so existing readers are unaffected.

**`orders`:**

| Column | Source |
|---|---|
| `delivery_fee_paise` | `deliveryFeeLine.grossPaise` |
| `delivery_fee_taxable_paise` | `deliveryFeeLine.taxablePaise` |
| `delivery_fee_tax_rate` | `deliveryFeeLine.taxRatePercent` |
| `delivery_fee_cgst_paise` / `_sgst_paise` / `_igst_paise` | `deliveryFeeLine` |
| `delivery_fee_sac` | `deliveryFeeLine.sacCode` |
| `supply_type` | `supplyType` |
| `place_of_supply_state` | `placeOfSupplyState` |
| `billing_address` (JSONB) | `{name, mobile, lines, landmark, city, state, pincode}` from FR-2 |
| `bill_version` | `1` (lets later shapes evolve) |

- Orders recorded with `amount_paise = 0` before a price exists (`DELIVERY_ADDRESS_UNKNOWN`, `PRODUCT_UNAVAILABLE`) get **no** snapshot.
- **Immutability:** no code path updates these columns after insert.

### FR-6: `bill` on customer reads

`GET /orders/{id}` and each item of `GET /orders/me` gain:

```json
"bill": {
  "itemTotalPaise": 11300,
  "deliveryFeePaise": 2000,
  "taxPaise": 225,
  "grandTotalPaise": 13525,
  "lines": [
    { "productId": "cow-milk", "productName": "Cow Milk", "quantity": 1,
      "unitPricePaise": 6800, "discountPaise": 0, "taxablePaise": 6800,
      "taxRatePercent": 0.0, "taxPaise": 0, "totalPaise": 6800 }
  ]
}
```

- `itemTotalPaise` = Σ `taxable_paise`.
- `taxPaise` = Σ line (cgst + sgst + igst). This excludes the delivery fee's inclusive tax, matching the "Taxes & Fees" row.
- `deliveryFeePaise` = `delivery_fee_paise`.
- `grandTotalPaise` = `amount_paise`.
- **Invariant:** `itemTotalPaise + taxPaise + deliveryFeePaise == grandTotalPaise`.
- `bill` is `null` when the order has no snapshot: created before this release, the FR-3 fallback, or an unpriced failure.
- The customer response does **not** include the billing address or tax split, to keep the existing payload lean.

### FR-7: Internal read for invoicing

`GET /orders/internal/confirmed?deliveryDate=YYYY-MM-DD&cursor=<opaque>&limit=<1..200, default 100>`

- **Access:** internal only (SigV4/mTLS, VPC-only, not on the public API Gateway), following the Wallet `/wallet/internal/*` convention.
- **Selection:** orders with `status = 'CONFIRMED'` and that `delivery_date`, including those with `bill_version IS NULL`, ordered by `seq` (keyset pagination like `/orders/me`).
- **Response:**

```json
{ "orders": [ {
    "orderId": "ord_…", "userId": "<cognito sub>", "source": "SUBSCRIPTION",
    "deliveryDate": "2026-11-27", "amountPaise": 13525, "confirmedAt": "…",
    "hasBill": true,
    "supplyType": "INTRA_STATE", "placeOfSupplyState": "Karnataka",
    "billingAddress": { "name": "…", "mobile": "…", "lines": ["…"], "landmark": null,
                        "city": "…", "state": "…", "pincode": "…" },
    "lines": [ { "lineNo": 1, "productId": "…", "productName": "…", "hsnCode": "0401",
                 "quantity": 1, "unitPricePaise": 6800, "discountPaise": 0,
                 "taxablePaise": 6800, "taxRatePercent": 0.0,
                 "cgstPaise": 0, "sgstPaise": 0, "igstPaise": 0, "totalPaise": 6800 } ],
    "deliveryFee": { "sacCode": "996813", "grossPaise": 2000, "taxablePaise": 1695,
                     "taxRatePercent": 18.0, "cgstPaise": 152, "sgstPaise": 153, "igstPaise": 0 }
  } ],
  "nextCursor": null }
```

- `hasBill: false` orders return `lines: []`, with `deliveryFee`, `billingAddress` and `supplyType` set to null, so Invoice can skip them and log them as `NO_BREAKDOWN`.
- Errors: 400 `INVALID_DELIVERY_DATE` or `INVALID_CURSOR`.

## 5. Non-Functional Requirements

- **Atomicity:** the snapshot and the order row commit together; there is never a half-written bill.
- **Performance:**
  - Order creation adds no network calls: the same one User call and one Pricing call, with only larger payloads.
  - `GET /orders/{id}` adds one indexed read of `order_items`.
  - The internal endpoint p95 < 300 ms per page of 100 at 10k orders/day, using the new index `(delivery_date, status, seq)`.
- **Privacy:**
  - The billing address, name and mobile are stored only on `orders.billing_address`, and returned only by the internal endpoint.
  - They are never logged. Log lines carry `orderId` and the correlation ID only.
- **Backward compatibility:** every existing response field is unchanged; `bill` is additive. Old orders are unaffected.
- **Observability:**
  - Metrics `order.bill_snapshot.written`, `order.bill_snapshot.missing` and `order.amount_mismatch`.
  - X-Ray subsegments for the internal endpoint.

### Workflow (both creation paths)

```

        │
        ▼

        │

  INSERT order_items (… breakdown columns …)          -- 1 row for SUBSCRIPTION, N for CHECKOUT

        │
        ▼

```

## 7. Data Considerations

`0005_bill_snapshot.sql` (Postgres/Aurora; the SQLAlchemy tables must stay column-compatible):

```sql
ALTER TABLE order_items
  ADD COLUMN product_name      VARCHAR(200),
  ADD COLUMN hsn_code          VARCHAR(16),
  ADD COLUMN unit_price_paise  BIGINT CHECK (unit_price_paise >= 0),
  ADD COLUMN discount_paise    BIGINT CHECK (discount_paise >= 0),
  ADD COLUMN taxable_paise     BIGINT CHECK (taxable_paise >= 0),
  ADD COLUMN tax_rate          NUMERIC(5,2),
  ADD COLUMN cgst_paise        BIGINT CHECK (cgst_paise >= 0),
  ADD COLUMN sgst_paise        BIGINT CHECK (sgst_paise >= 0),
  ADD COLUMN igst_paise        BIGINT CHECK (igst_paise >= 0),
  ADD COLUMN line_total_paise  BIGINT CHECK (line_total_paise >= 0);

ALTER TABLE orders
  ADD COLUMN bill_version              SMALLINT,
  ADD COLUMN delivery_fee_paise        BIGINT CHECK (delivery_fee_paise >= 0),
  ADD COLUMN delivery_fee_taxable_paise BIGINT,
  ADD COLUMN delivery_fee_tax_rate     NUMERIC(5,2),
  ADD COLUMN delivery_fee_cgst_paise   BIGINT,
  ADD COLUMN delivery_fee_sgst_paise   BIGINT,
  ADD COLUMN delivery_fee_igst_paise   BIGINT,
  ADD COLUMN delivery_fee_sac          VARCHAR(8),
  ADD COLUMN supply_type               VARCHAR(12) CHECK (supply_type IN ('INTRA_STATE','INTER_STATE')),
  ADD COLUMN place_of_supply_state     VARCHAR(100),
  ADD COLUMN billing_address           JSONB;

CREATE INDEX orders_delivery_status_seq_idx ON orders (delivery_date, status, seq);
```

- Everything is nullable, so existing rows stay valid (AC-9). The application enforces "all bill columns set, or none" when `bill_version = 1`.
- **Subscription orders:** pre-existing subscription orders have no `order_items` row. The read path keeps using `orders.product_id`/`quantity` for `items` (unchanged `item_list()`), and uses `order_items` only for the breakdown.
- **Retention:** these columns are part of the order record; there is no separate retention.

## 8. Integration Considerations

- **Pricing (MA-158):** new fields required for a snapshot; absent fields fall back per FR-3.
- **User:** additive response. The old Order build ignores the new fields; the new Order build tolerates their absence by treating `defaultAddress: null` as no snapshot, while the order still proceeds using `defaultAddressState`.
- **Invoice (MA-160):** sole consumer of FR-7. Its contract is the JSON in FR-7; any field change needs a coordinated version bump of `bill_version`.
- **Deploy order:** User and Pricing first (both additive), then Order. Any order works without errors; only snapshot completeness depends on it.

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|---|---|
| No default address | Existing `DELIVERY_ADDRESS_UNKNOWN` path; no snapshot |
| User returns state but `defaultAddress` null (old User build) | Order proceeds; `billing_address` null, `bill_version` null; metric `missing` |
| Pricing without `lines` | Order proceeds; no snapshot (FR-3) |
| `netPayablePaise` ≠ legacy rounding | Charge `netPayablePaise`; log an error plus metric `order.amount_mismatch` |
| Quote `lines` count ≠ requested items | Treat as a Pricing contract violation: no snapshot, error log, order proceeds |
| Checkout replay (same Idempotency-Key) | Existing resume logic; the snapshot was written with the original insert and is never rewritten |
| Sweep re-prices a stuck order (MA-143) | Re-pricing only happens before the order row exists; once inserted, the snapshot is final |
| Customer later changes address | The snapshot keeps the address at order time |
| Internal endpoint called with a future date | Returns whatever is CONFIRMED (normally none) |

## 10. Testing Strategy

- **Unit (User):** handler serializes the new fields, `defaultAddress: null` when no default, and never includes `lat`/`lng`.
- **Unit (Order):**
  - Pricing client parses the full and the legacy response.
  - User client parses the full and the legacy response.
  - Snapshot built correctly for subscription (1 line) and checkout (N lines).
  - The `bill` invariant holds.
  - `bill` is null for an old or unpriced order.
  - FR-4 mismatch logging.
- **Repository (Postgres via the existing test DB fixture):**
  - Migration applies to a DB containing pre-existing orders.
  - Insert and read round-trip.
  - The CHECK constraints reject negatives.
  - `list_confirmed_for_date` pagination and filtering (excludes CANCELLED and PAYMENT_FAILED; includes `hasBill: false`).
- **Integration (local-dev compose):** create a subscription order and a checkout order against real Pricing and User, then assert `GET /orders/{id}` `bill` values and `GET /orders/internal/confirmed` content.
- **Negative:** malformed cursor; a bad date; Pricing returning mismatched line counts.

## 11. Risks and Trade-offs

- **PII on orders.** Billing name, mobile and address are now stored in the Order DB. This is needed for invoice correctness (the address at the time of supply). Mitigations: KMS at rest, never logged, internal-only exposure.
- **Subscription `order_items` dual source.** Product and quantity live both on `orders` and on the new `order_items` row. Accepted, to avoid rewriting existing readers; a later clean-up can drop the `orders` columns.
- **Bundling the User change into an Order spec.** It's small and additive, and the reviewers include the User owner.
- **No backfill.** Historical orders never get invoices; accepted under MA-38's scope.
