# Invoice Service — Daily GST Invoice Generation, Numbering, PDF & Download API

## 1. Overview

- **Title:** Invoice Service — Daily GST Invoice Generation, Numbering, PDF & Download API
- **Related User Story:** [MA-38](https://milkfuldairyindia.atlassian.net/browse/MA-38) — Invoice Generation (GST, Discounts, Offers)
- **Related JIRA Task:** [MA-160](https://milkfuldairyindia.atlassian.net/browse/MA-160)
- **Author:** SDD Agent (spec-driven-designer)
- **Date:** 2026-11-26
- **Stakeholders:** Backend engineering, Finance (seller details, numbering, retention), Mobile team (MA-161, the API consumer), Architecture (adds a 14th service)

> **Owning service:** a **new Invoice Service**, `services/invoice`. It uses **Lambda** compute (a daily burst plus a low-traffic read API, the same profile as Subscription's daily run), **Aurora PostgreSQL `invoices`** (database-per-service), and **S3 `milkful-invoices`** for PDFs. This is the platform's 14th service, so the HLD table in `milkful-app/docs/design/milkful-well-architected.md` §6 needs a new row (follow-up doc change; see §13).
>
> **Depends on:** MA-159 (Order's internal read and stored breakdown). **Consumed by:** MA-161 (Mobile).
>
> **Size note:** decomposition flagged this as possibly more than one sprint. It was approved as a single spec. FR-4 (PDF) is designed so it can be implemented and released after FR-1 to FR-3: invoices are recorded with `pdf_status = PENDING`, and the API returns `INVOICE_NOT_READY` until rendering ships.

## 2. Problem Statement

Milkful has no invoice anywhere: no numbering, no document, no record finance can reconcile. GST requires a tax invoice or bill of supply for every supply. The ticket asks for an invoice per order, generated each day after delivery, downloadable as a PDF from the app, with sequential numbering and a feed for accounting.

**Expected outcome:**
- Every day, after the last delivery slot, every `CONFIRMED` order for that day gets exactly one immutable invoice.
- Each invoice has a gapless, per-financial-year number, is rendered to PDF in the reference layout (`CountryDelight_09-08-2026.pdf`), and is stored durably.
- An `InvoiceGenerated` event is published.
- The order's owner can fetch a short-lived download link from the app.

## 4. Functional Requirements

### FR-1: Daily run

- **Trigger:** EventBridge Scheduler, `cron(30 5 * * ? *)` UTC = **11:00 IST** daily (`INVOICE_RUN_TIME_IST`, configurable), which is after the last delivery slot. Locally, `POST /invoice/internal/run` (internal-only) is called by `local-dev/run_invoices_local.py`.
- **Window:** delivery dates from `today_IST − INVOICE_CATCHUP_DAYS` (default 7) through `today_IST`. Missed runs self-heal: an order not invoiced yesterday is picked up today.
- **For each date in the window:** page through Order's `GET /orders/internal/confirmed?deliveryDate=…` (MA-159 FR-7) and apply FR-2 to each order.
- **Concurrency:** a run takes a Postgres advisory lock (`pg_try_advisory_lock(<const>)`). A second concurrent run exits immediately with `status: SKIPPED_LOCKED`.
- **Result:**
  - Returned to the caller: `{runId, window: [from, to], counts: {issued, alreadyIssued, skipped: {NO_BREAKDOWN, INVARIANT_FAILED, MISSING_HSN}, pdfRendered, pdfFailed}}`.
  - Also logged with `runId` as the correlation ID.
- After issuing, the run renders PDFs for every invoice with `pdf_status IN ('PENDING','FAILED')` and `pdf_attempts < 5` (FR-4).

### FR-2: Issue rules (per order)

1. **Already issued?** If an invoice exists for `order_id`, count it `alreadyIssued` and stop. `UNIQUE(order_id)` enforces this too.
2. **No breakdown?** If `hasBill: false`, skip with `NO_BREAKDOWN`.
3. **Missing HSN?** If any product line has a null `hsnCode`, skip with `MISSING_HSN`. A tax invoice must show HSN.
4. **Invariant:** `Σ lines.totalPaise + deliveryFee.grossPaise == amountPaise`. Also, per product line, `taxablePaise + cgst + sgst + igst == totalPaise`; for the fee line, `taxablePaise + cgst + sgst + igst == grossPaise`. On failure, skip with `INVARIANT_FAILED` and log an error with `orderId`.
5. **Issue, in one DB transaction:**
   - allocate a number (FR-3);
   - insert `invoices`, then `invoice_lines` (products, plus one `DELIVERY_FEE` line);
   - insert an outbox row (FR-6);
   - commit.
   - `issued_on` = the order's `delivery_date` (date of supply). The financial year comes from `issued_on`.
6. All data is **copied** from Order's response. The invoice never re-reads Order after issue, so it is immutable.

Skipped orders are retried on every run within the catch-up window, and then dropped from it. A skip alarms (§5).

### FR-3: Gapless numbering

- **Format:** `{INVOICE_NUMBER_PREFIX}/{FY}/{seq:06d}`. The prefix defaults to `MF` and FY is `YY-YY`, e.g. `MF/26-27/000123`, which is 15 characters. Start-up fails if the prefix would make the number exceed GST's 16-character limit.
- **Financial year:** 1 April to 31 March, from `issued_on`.
- **Allocation** (inside the FR-2 transaction): `INSERT INTO invoice_counters (fy, last_no) VALUES (:fy, 0) ON CONFLICT DO NOTHING`, then `UPDATE invoice_counters SET last_no = last_no + 1 WHERE fy = :fy RETURNING last_no`.
- The row lock serializes allocators. Because allocation and the invoice insert commit or roll back together, **no number is ever consumed without an invoice**, so there are no gaps.
- Numbers are never reused, and invoices are never deleted.

### FR-4: PDF rendering

- **Library:** **ReportLab** (pure Python, no native system libraries, so it is Lambda-friendly. WeasyPrint was rejected because it needs cairo and pango.)
- **Layout** mirrors the reference PDF, A4 portrait:
  1. **Header:** seller legal name; CIN; registered address; GST address; GSTIN; FSSAI registration number.
  2. **Title:** "TAX INVOICE/BILL OF SUPPLY".
  3. **Meta box:** Invoice No.; Date (`issued_on`, `YYYY-MM-DD`); Place Of Supply.
  4. **Bill To / Ship To:** name, mobile, address lines, landmark, city, state, pincode. Both show the same snapshotted address.
  5. **Line table columns:** SR No, Item & Description, HSN (SAC for the fee line), Qty, Unit Price, Disc %, Taxable Amt., CGST%, SGST%, CGST Amount, SGST Amount, IGST%, IGST Amount, Cess%, Cess Amount, Total Amt. Then a **Total** row with the summed tax and total columns.
     - **Unit Price** replaces the reference's "MRP": Milkful's catalog price is pre-tax (MA-158).
     - **Disc %** = `discountPaise / (unitPricePaise × qty) × 100`, 2 decimal places.
     - **Delivery fee line:** "Delivery Charges", SAC, qty 1, unit price = its taxable value, total = gross.
     - Cess is always 0.00.
  6. **Footer amounts:** "Item Total" (Σ product line totals), "Delivery Charges" (fee gross), "Invoice Value" (= `amountPaise`), "Paid via Milkful Wallet".
  7. **Declarations:** "Whether GST is Payable on Reverse Charge - NO."; "This is a computer-generated invoice issued in accordance with the Information Technology Act, 2000; no physical signature is required."; "The goods sold are intended for end-user consumption and not for resale."
- Amounts print as rupees with 2 decimals, from paise (no float maths).
- **Storage:**
  - Key `invoices/{fy}/{invoice_no with "/" → "-"}.pdf`, e.g. `invoices/26-27/MF-26-27-000123.pdf`.
  - `ContentType: application/pdf`, SSE-KMS, private bucket.
  - On success: `pdf_status = READY`, `s3_key` set, `pdf_rendered_at`.
  - On failure: `pdf_status = FAILED`, `pdf_attempts += 1`, error logged. Retried next run, up to 5 attempts, then alarm.
- A rendered PDF is **never overwritten**. A re-render happens only when `pdf_status ≠ READY`.

### FR-5: Customer API — `GET /orders/{orderId}/invoice`

- **Auth:** Cognito JWT at API Gateway; `shared.handlers.auth.current_user_id` gives the caller's `sub`.
- **Responses:**

| Condition | Status | Body |
|---|---|---|
| No invoice for `orderId`, **or** it belongs to another user | 404 | `INVOICE_NOT_FOUND` |
| Invoice belongs to the caller, `pdf_status ≠ READY` | 404 | `INVOICE_NOT_READY` |
| Invoice belongs to the caller and is READY | 200 | `{invoiceId, invoiceNo, issuedOn, invoiceValuePaise, downloadUrl, urlExpiresAt}` |

- `downloadUrl` is an S3 pre-signed GET URL with TTL `INVOICE_URL_TTL_SECONDS` (default 300) and `ResponseContentDisposition: attachment; filename="Milkful-Invoice-MF-26-27-000123.pdf"`.
- A non-owner always gets `INVOICE_NOT_FOUND`, so the response never reveals that an invoice exists.
- The route path lives under `/orders/…` for client ergonomics. API Gateway routes `GET /orders/{orderId}/invoice` to this Lambda; all other `/orders/*` routes stay with Order Service.

### FR-6: `InvoiceGenerated` event

- Outbox row in the FR-2 transaction; published to the `milkful-events` bus by `invoice-outbox` (shared `outbox_event_publisher`, the same pattern as order, user and cart).
- `detail`:

```json
{ "invoiceId": "inv_…", "invoiceNo": "MF/26-27/000123", "orderId": "ord_…",
  "userId": "<sub>", "issuedOn": "2026-11-27", "financialYear": "26-27",
  "invoiceValuePaise": 13525, "taxablePaise": 12995,
  "cgstPaise": 264, "sgstPaise": 266, "igstPaise": 0,
  "supplyType": "INTRA_STATE", "placeOfSupplyState": "Karnataka",
  "correlationId": "…" }
```

- It carries no address or name (PII stays in the Invoice DB).
- The schema is added at `shared/events/InvoiceGenerated.schema.json`.
- It is published at issue time, independent of the PDF.

### FR-7: Seller configuration

- **Required:** `INVOICE_SELLER_LEGAL_NAME`, `INVOICE_SELLER_CIN`, `INVOICE_SELLER_GSTIN`, `INVOICE_SELLER_FSSAI`, `INVOICE_SELLER_REG_ADDRESS`, `INVOICE_SELLER_GST_ADDRESS`, `INVOICE_SELLER_STATE`.
  - Read from SSM Parameter Store in AWS, and from env or `.env.local` locally.
- **Validation:** GSTIN format `^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]$`.
- **Outside local:** any missing or invalid value fails start-up, so the run reports an error rather than issuing legally invalid invoices.
- **Locally:** clearly fake placeholders are allowed (e.g. legal name "Milkful Dairy (LOCAL TEST)").
- **Seller details are snapshotted** onto each invoice row at issue time, so later configuration changes never alter an issued invoice's content.
- `INVOICE_SELLER_STATE` must equal Pricing's `PRICING_SELLER_STATE` (MA-158). The run logs a warning if an order's `supplyType` contradicts this state.

## 5. Non-Functional Requirements

- **Correctness:**
  - Integer paise throughout.
  - FR-2's invariant before every issue.
  - `UNIQUE(order_id)` and `UNIQUE(invoice_no)` at the database level.
- **Performance:**
  - A run issues 10k invoices in under 10 minutes. Issuing is one transaction per order; PDFs render at roughly 50 ms each.
  - The Lambda timeout is 15 minutes. If the backlog exceeds one run, the remainder rolls to the next run (idempotent).
  - The API p95 is under 150 ms (one indexed lookup plus a local pre-sign; no S3 round trip).
- **Reliability:**
  - Advisory lock against overlapping runs.
  - A catch-up window for missed runs.
  - PDF retries.
  - Outbox delivery is at-least-once, so consumers must de-duplicate on `invoiceId`.
- **Security:**
  - Private, KMS-encrypted bucket; access only through pre-signed URLs.
  - The internal run endpoint is never on the public gateway.
  - A least-privilege IAM role (`s3:PutObject`/`GetObject` on the bucket, `events:PutEvents`, SSM read on `/milkful/invoice/*`).
- **Retention:** GST requires records for 6 years from the end of the financial year (the due date of the annual return). Use an S3 lifecycle with **no expiry**, plus Object Lock (governance mode, 8 years) in production. DB rows are never deleted.
- **Observability:**
  - Metrics: `invoice.issued`, `invoice.already_issued`, `invoice.skipped{reason}`, `invoice.pdf.rendered`, `invoice.pdf.failed`, `invoice.run.duration`, `invoice.api.{2xx,4xx,5xx}`.
  - Alarms:
    - no successful run by 12:00 IST;
    - `invoice.skipped > 0` for `INVARIANT_FAILED` or `MISSING_HSN`;
    - a PDF still failing after 5 attempts.
  - Correlation ID: `runId` for runs, the request ID for API calls.

## 6. Technical Design

### Architecture Approach

```
EventBridge Scheduler (11:00 IST)
        │
        ▼
run_handler (Lambda) ──SigV4──► Order GET /orders/internal/confirmed?deliveryDate=D   (pages)
        │
        ├── per order: BEGIN; allocate no.; INSERT invoices + lines + outbox; COMMIT
        │
        └── render pending PDFs ──► S3 milkful-invoices (SSE-KMS)
                                         ▲
invoice-outbox ──► EventBridge milkful-events (InvoiceGenerated)
                                         │
API Gateway (Cognito JWT) GET /orders/{orderId}/invoice ──► api_handler (Lambda) ──► pre-signed URL
```

### Component Responsibilities

| Component | Responsibility |
|---|---|
| `adapters/order_client.py` | SigV4 client for MA-159 FR-7, with the shared `retry` |
| `adapters/invoice_repository.py` | SQLAlchemy Core: counters, invoices, lines, outbox |
| `adapters/pdf_renderer.py` | ReportLab layout (FR-4); pure function `render(invoice) -> bytes` |
| `adapters/s3_store.py` | Put object; pre-sign |
| `domain/invoice_service.py` | FR-1 to FR-3 orchestration and rules |
| `domain/numbering.py` | FY derivation; number formatting and validation |
| `handlers/run_handler.py` | Scheduler / internal trigger |
| `handlers/api_handler.py` | FR-5 |
| `handlers/outbox_publisher.py` | Shared outbox poller entry point |
| `config/env.py` | `INVOICE_*` settings and FR-7 validation |

### API / Interface Definitions

| Endpoint | Auth | Purpose |
|---|---|---|
| `GET /orders/{orderId}/invoice` | Cognito JWT | FR-5 |

## 7. Data Considerations

Migration `0001_invoices.sql` (Aurora `invoices`):

```sql
CREATE TABLE invoice_counters (
    fy       VARCHAR(5) PRIMARY KEY,      -- '26-27'
    last_no  BIGINT NOT NULL DEFAULT 0
);

CREATE TABLE invoices (
    id                    VARCHAR(64) PRIMARY KEY,         -- inv_<uuid>
    invoice_no            VARCHAR(16) NOT NULL UNIQUE,
    fy                    VARCHAR(5)  NOT NULL,
    seq                   BIGINT      NOT NULL,
    order_id              VARCHAR(64) NOT NULL UNIQUE,
    user_id               VARCHAR(64) NOT NULL,
    issued_on             DATE        NOT NULL,
    supply_type           VARCHAR(12) NOT NULL,
    place_of_supply_state VARCHAR(100) NOT NULL,
    bill_to               JSONB       NOT NULL,            -- name, mobile, address (snapshot)
    seller                JSONB       NOT NULL,            -- FR-7 snapshot
    taxable_paise         BIGINT NOT NULL,
    cgst_paise            BIGINT NOT NULL,
    sgst_paise            BIGINT NOT NULL,
    igst_paise            BIGINT NOT NULL,
    invoice_value_paise   BIGINT NOT NULL,
    pdf_status            VARCHAR(8)  NOT NULL DEFAULT 'PENDING',  -- PENDING | READY | FAILED
    pdf_attempts          SMALLINT    NOT NULL DEFAULT 0,
    s3_key                VARCHAR(200),
    pdf_rendered_at       TIMESTAMPTZ,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (fy, seq)
);
CREATE INDEX invoices_pdf_pending_idx ON invoices (created_at) WHERE pdf_status <> 'READY';

CREATE TABLE invoice_lines (
    invoice_id        VARCHAR(64) NOT NULL REFERENCES invoices(id),
    line_no           INTEGER     NOT NULL,
    line_type         VARCHAR(12) NOT NULL,               -- PRODUCT | DELIVERY_FEE
    product_id        VARCHAR(64),
    description       VARCHAR(200) NOT NULL,
    hsn_sac           VARCHAR(16)  NOT NULL,
    quantity          INTEGER      NOT NULL,
    unit_price_paise  BIGINT NOT NULL,
    discount_paise    BIGINT NOT NULL,
    taxable_paise     BIGINT NOT NULL,
    tax_rate          NUMERIC(5,2) NOT NULL,
    cgst_paise        BIGINT NOT NULL,
    sgst_paise        BIGINT NOT NULL,
    igst_paise        BIGINT NOT NULL,
    total_paise       BIGINT NOT NULL,
    PRIMARY KEY (invoice_id, line_no)
);

CREATE TABLE outbox ( /* identical to order/user/cart outbox */ );
```

- **Immutability:** the application never issues `UPDATE` on invoice content columns. Only `pdf_*` and `s3_key` change.
- The invoice-level `taxable_paise` and tax totals include the delivery-fee line. These are the GST reporting figures.
- **PII:** `bill_to` holds name, mobile and address; KMS at rest; never logged.

## 8. Integration Considerations

- **Order (MA-159 FR-7):**
  - SigV4 GET with the shared `retry`: 3 attempts with backoff on 5xx and timeouts.
  - If Order is unavailable for a date, that date is abandoned for this run (logged); the next run retries via the catch-up window.
- **S3:** put failures go to `pdf_status = FAILED`, retried next run.
- **EventBridge:** through the outbox, so a bus outage delays the event but never loses it.
- **API Gateway:** add the `GET /orders/{orderId}/invoice` route to the Invoice Lambda, which needs an infra follow-up. Locally, the mobile app calls Invoice on port 8010 directly (MA-161 `AppConfig.invoiceBaseUrl`).
- **Contract with Mobile:** the FR-5 table is the contract.

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|---|---|
| Run invoked twice at the same time | The second gets `SKIPPED_LOCKED` |
| Run crashes mid-way | Committed invoices stand; the rest are issued next run; no gaps (FR-3) |
| Order cancelled after confirmation but before the run | Not `CONFIRMED`, so not returned and never invoiced |
| Order CONFIRMED but older than the catch-up window | Never invoiced; the `skipped` alarm will have fired on earlier runs. Operators re-run with an explicit window (`POST /invoice/internal/run {fromDate}`, internal only) |
| FY boundary (31 Mar → 1 Apr) | The number series comes from `issued_on`; a catch-up on 2 Apr of a 31 Mar order uses the old FY series |
| Product line with 0% tax | Issued normally (bill of supply portion); CGST/SGST 0.00 |
| PDF render throws for one invoice | That invoice goes to `FAILED`; the others proceed |
| Mobile asks before the run | 404 `INVOICE_NOT_READY` (owner) or `INVOICE_NOT_FOUND` (no record yet) |
| Pre-signed URL expires before tap | The app re-fetches (MA-161) |
| Seller config missing in prod | Start-up fails; the run alarm fires; nothing invalid is issued |

## 10. Testing Strategy

- **Unit:**
  - **FY derivation:** 31 Mar vs 1 Apr; number format and the 16-character check.
  - **Issue rules:** each skip reason, the invariant maths, already-issued handling.
  - **Seller config validation:** GSTIN regex; missing value outside local.
  - **Disc % and amount formatting.**
- **Repository (Postgres):**
  - The concurrency test: N threads allocating in the same FY produce 1..N with no gaps or duplicates.
  - A rollback after allocation leaves no gap.
  - `UNIQUE(order_id)` prevents a double issue.
- **PDF:**
  - Render a fixture invoice (intra-state, mixed 0% and 5%, plus the fee line), then extract its text with `pypdf` and assert every required field: header, title, number, place of supply, HSN/SAC, the totals row, invoice value.
  - Inter-state fixture: the IGST columns are populated.
- **API:**
  - Owner READY → 200 with a URL whose host is the bucket.
  - Owner PENDING → `INVOICE_NOT_READY`.
  - Another user → `INVOICE_NOT_FOUND`.
  - Unknown order → `INVOICE_NOT_FOUND`.
- **Integration (local-dev):**
  - Create orders via Order (MA-159), run `run_invoices_local.py`, and assert the invoices, the moto S3 object, and the outbox row. A re-run issues nothing new.
- **Acceptance (MA-38):**
  - AC-4: one invoice per confirmed order; a re-run creates none.
  - AC-5: sequential, ≤16 characters.
  - AC-6: the PDF matches the layout and totals equal the charge.
  - AC-7: owner-only.

## 11. Risks and Trade-offs

- **A 14th service.** It adds ops surface, mitigated by Lambda (scale-to-zero) and the shared libraries. The rejected alternative, a module inside Order, would put PDF rendering, S3 and numbering on Order's hot Fargate service and couple invoice retention to order schema changes.
- **Pull at 11:00 IST vs delivery truth.** An order is invoiced because it is CONFIRMED (paid), not because it was proven delivered. This is accepted until MA-102 provides `DELIVERED`; the switch is a one-line filter change in MA-159 FR-7.
- **No CDK stack in this spec.** Following the cart and pricing precedent, production deployment needs the follow-up stack before go-live.
- **Seller and fee values unconfirmed.** Mitigated by FR-7's fail-closed start-up and Finance sign-off.

## 12. Open Questions

- **Finance:** the real seller details (FR-7), and confirmation of the number prefix `MF` and the format `MF/YY-YY/NNNNNN`.
- **Finance:** whether retention of 6 years after the end of the FY, enforced by S3 Object Lock for 8 years, matches the company's policy.
- **Ops:** confirm the run time of 11:00 IST against the real last delivery slot.
