## 2. Problem Statement

Today the only identity system in Milkful is a single Cognito User Pool built for **consumer** OTP-based login (MA-92/MA-1/MA-21) — it has no concept of a staff/admin identity, no password+2FA flow, no roles, and no session/IP restriction. Admin, Ops, Finance, Support, and Marketing staff need their own authenticated identity, scoped by role to least-privilege access, with every privileged action attributable for audit and immediately revocable when a role changes or an account is deactivated.

**Expected outcome:** A backend capability that authenticates admin users (password + TOTP 2FA), issues JWTs carrying a role claim, enforces session/IP restrictions, and emits a domain event for every privileged admin action — consumed later by MA-50's audit pipeline.

## 3. Scope

### In Scope

- A dedicated **Admin Cognito User Pool**, separate from the existing consumer pool
- Admin authentication API: password login (step 1) + TOTP 2FA challenge (step 2), JWT issuance/refresh/logout
- `admin_user` profile storage (Aurora, owned by this service): name, email, role, status, session/IP config, audit metadata
- CRUD APIs for admin accounts: create (invite), list, edit role, deactivate, reactivate
- Fixed 5-role model: Ops, Finance, Support, Marketing, SuperAdmin — modeled as Cognito Groups, surfaced in the JWT as `cognito:groups`
- Session/IP restriction enforcement at the API Gateway authorizer / login layer
- Emission of `admin.*` domain events for every privileged action (create, role change, deactivate, reactivate, login, login lockout)
- Invitation email trigger (delegates actual delivery to the existing SNS/SES pattern used elsewhere — no new notification channel invented)

### Out of Scope

- Persisted, queryable audit log storage or any audit viewer UI — owned by MA-50; this spec only emits the event
- Custom/configurable roles or a permission-matrix engine — the 5 roles and their permission sets are fixed
- `portal-ui` screens — covered by the paired spec [MA-128](https://milkfuldairyindia.atlassian.net/browse/MA-128)
- Any change to the existing consumer Cognito pool or its OTP flows (MA-1/MA-21) — this is additive, isolated infrastructure

## 4. Functional Requirements

### FR-1: Admin Login — Password Step

`POST /v1/admin/auth/login` — accepts `{ email, password }`. On valid credentials for an **Active** admin, returns a short-lived `challengeToken` requiring 2FA completion (not a usable session token). On invalid credentials, returns a generic 401 (`"Incorrect email or password"`) regardless of whether the email exists (no user enumeration). On a **Pending** or **Deactivated** account, returns 403 with a status-specific message.

### FR-2: Admin Login — 2FA Verification

`POST /v1/admin/auth/2fa/verify` — accepts `{ challengeToken, code }`. On a correct TOTP code, returns Cognito-issued access/ID/refresh tokens with `cognito:groups` populated from the admin's assigned role. On an incorrect code, increments a per-`challengeToken` failure counter; after 5 failures within 15 minutes, the account is locked for 15 minutes (401 with a lockout-specific error code) and an `admin.session.blocked` event is emitted.

### FR-3: Admin Account Creation (Invite)

`POST /v1/admin/users` — Super-Admin-only (enforced via JWT group claim). Accepts `{ name, email, role }`. Creates an admin in **Pending** status in both the Admin Cognito Pool (`AdminCreateUser`, no password set) and the `admin_user` table, triggers a TOTP-enrollment + password-set invitation email, and emits `admin.user.created`. Returns 409 if the email already exists in the Admin pool.

### FR-4: List / Edit / Deactivate / Reactivate

- `GET /v1/admin/users` — Super-Admin-only; paginated list with role/status filter and name/email search.
- `PATCH /v1/admin/users/{id}` — Super-Admin-only; updates role and/or session/IP config. A role change emits `admin.role.assigned` and invalidates the target admin's current refresh token (forces re-login on next token refresh — see §9 for the exact timing trade-off).
- `POST /v1/admin/users/{id}/deactivate` — sets status to Deactivated, revokes all active refresh tokens for that admin (`AdminUserGlobalSignOut`), emits `admin.user.deactivated`. A Super-Admin cannot deactivate their own account (400).
- `POST /v1/admin/users/{id}/reactivate` — sets status back to Active, emits `admin.user.reactivated`. Does not restore any previously-revoked session; the admin must log in again.

### FR-5: Session / IP Restriction Enforcement

- If an admin's `admin_user` record has a non-empty IP allowlist, every request bearing that admin's JWT is checked against it at the API Gateway custom authorizer; a request from a disallowed IP is rejected with 403 and emits `admin.session.blocked` with reason `ip_not_allowed`.
- If `maxConcurrentSessions` is set, a new successful 2FA verification beyond the limit revokes the oldest active refresh token for that admin (LRU eviction), consistent with "least surprising" behavior over silently rejecting new logins.

### FR-6: Domain Event Emission

Every action in FR-2–FR-5 that changes admin state or blocks access emits one event from the `admin.*` family, following the standard envelope (`services/README.md` §5):

```json
{
  "eventId": "uuid",
  "eventType": "admin.user.created",
  "eventVersion": "1.0",
  "source": "identity-auth",
  "timestamp": "ISO-8601",
  "correlationId": "uuid",
  "payload": { "adminId": "uuid", "email": "string", "role": "string", "createdBy": "uuid" }
}
```

Event types: `admin.user.created`, `admin.user.deactivated`, `admin.user.reactivated`, `admin.role.assigned`, `admin.login.succeeded`, `admin.login.failed`, `admin.session.blocked`.

## 5. Non-Functional Requirements

- **Performance:** Login (password step) p95 < 500ms; 2FA verify p95 < 300ms — consistent with the existing OTP verify NFR precedent in `identity-auth`.
- **Security:** Passwords never logged; TOTP secrets stored only in Cognito, never in application logs or the `admin_user` table; all admin-management endpoints require the `SuperAdmin` group claim, checked server-side (never trust a client-supplied role).
- **Reliability:** Role/deactivation changes must take effect for new requests within one API Gateway authorizer cache TTL (recommend disabling or minimizing authorizer caching for admin JWTs given the security sensitivity of stale role claims — flagged in §11).
- **Scalability:** Admin pool sized for low hundreds of accounts (staff, not consumers) — no special scaling design needed beyond existing Cognito/Lambda defaults.
- **Observability:** Structured logs with correlation ID on every admin auth/management call; CloudWatch alarm on `admin.login.failed` rate spikes (potential credential-stuffing signal) and on repeated `admin.session.blocked` for the same admin (potential compromised-account signal).

## 6. Technical Design

### Architecture Approach

Extend the existing Identity & Auth service (Lambda compute, per `services/README.md`'s service inventory) with:
1. A second Cognito User Pool ("Admin Pool") — `UsernameAttributes = [email]` only (no phone, unlike the consumer pool), native password auth enabled, TOTP MFA **required** (not optional) at the pool level.
2. Cognito Groups: `Ops`, `Finance`, `Support`, `Marketing`, `SuperAdmin` — one per fixed role — group membership drives the `cognito:groups` JWT claim.
3. A new `admin_user` table in the service's existing Aurora database (same instance as any future roles/permissions table already anticipated in MA-92's own service description — see MA-92 Story description: "Aurora (roles/permissions)").
4. A new API Gateway custom authorizer path (or an extension of the existing one) that additionally checks the IP allowlist for admin JWTs specifically — consumer JWTs are unaffected.

### Component Responsibilities

- **Admin auth handlers** (`src/handlers/admin_auth/`) — thin, map HTTP ↔ domain
- **Admin auth domain** (`src/domain/admin_auth/`) — login/2FA orchestration, lockout counting, session eviction logic
- **Admin user management domain** (`src/domain/admin_users/`) — CRUD business rules, role-change side effects
- **Adapters** — `admin_cognito_adapter` (new pool operations), `admin_user_repository` (Aurora), `event_publisher` (existing EventBridge adapter, reused)

### Workflow (Login)

```
POST /admin/auth/login → validate creds against Admin Pool → issue challengeToken (5 min TTL, single-use)
POST /admin/auth/2fa/verify → validate TOTP against challengeToken's user → on success:
  AdminInitiateAuth-equivalent → tokens with cognito:groups → emit admin.login.succeeded
  on 5th consecutive failure → lock 15 min → emit admin.session.blocked (reason: lockout)
```

### API/Interface Definitions

See §4 for endpoints. All responses use the standard envelope (`services/README.md` §5).

### Data Flow

`portal-ui` → API Gateway (public, unauthenticated for `/admin/auth/*`; Cognito JWT authorizer for everything else) → Identity & Auth Lambda → Admin Cognito Pool + Aurora `admin_user` table → EventBridge default bus (no dedicated bus exists yet — consistent with existing precedent in `identity-auth`'s README).

## 7. Data Considerations

### Schema: `admin_user` (Aurora, owned by Identity & Auth)

| Column | Type | Notes |
|--------|------|-------|
| `id` | uuid, PK | |
| `cognito_sub` | text, unique | Admin Pool's `sub` claim |
| `name` | text | |
| `email` | text, unique | Also the Admin Pool username |
| `role` | enum(Ops, Finance, Support, Marketing, SuperAdmin) | Mirrors the Cognito Group; kept in Aurora for query/list performance (avoids a Cognito `ListUsersInGroup` call per list request) |
| `status` | enum(Pending, Active, Deactivated) | |
| `ip_allowlist` | text[], nullable | CIDR ranges |
| `max_concurrent_sessions` | int, nullable | |
| `created_by` | uuid, FK → `admin_user.id`, nullable | null for the first bootstrap Super-Admin |
| `created_at`, `updated_at` | timestamptz | |

**Migration note:** the very first Super-Admin account has no `created_by` — must be seeded via a one-time migration/bootstrap script requiring human execution (per `services/README.md` §3.6, production migrations require human approval), not a self-service API call, since no Super-Admin exists yet to authorize creating one.

**Validation rules:** `email` format validated and lowercased before uniqueness check; `role` must be one of the 5 fixed values (no free text); `ip_allowlist` entries validated as CIDR before persisting.

## 8. Integration Considerations

- **Upstream:** `portal-ui` (MA-128) is the only caller.
- **Downstream:** EventBridge (default bus) → future MA-50 audit consumer. No consumer exists yet; events are published regardless (fire-and-forget is correct here — MA-129 should not block on MA-50 existing).
- **Contract with MA-128:** this spec is the source of truth for request/response shapes; MA-128 must be updated if this contract changes during implementation.
- **Retries/timeouts:** Cognito SDK calls wrapped in the existing adapter retry/backoff pattern (`services/README.md` §3.7); a Cognito outage surfaces as a 502 to `portal-ui`, mapped per the standard error table (§5c).
- **No cross-service DB reads** — if MA-50's audit consumer needs admin names/emails for display, it must consume that data from the `admin.*` events' payloads, never query this service's Aurora table directly.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| Login attempt for an email that doesn't exist in the Admin Pool | Generic 401, same message as wrong password (no enumeration) |
| 2FA verify with an expired `challengeToken` | 401, distinct error code `CHALLENGE_EXPIRED`, prompting the UI to restart from password step |
| Role changed while admin has an active session | Existing access token remains valid until its own expiry (short-lived, per standard Cognito token TTLs) but the refresh token is invalidated — the stale role claim can persist for at most one access-token lifetime. **This is a deliberate, documented trade-off** (see §11), not silently accepted as ideal |
| Deactivation while admin has an active session | `AdminUserGlobalSignOut` immediately revokes all refresh tokens; however the same short-access-token-window caveat above applies until Gateway authorizer caching is addressed (§11) |
| Concurrent role-change requests for the same admin from two Super-Admins | Last write wins at the DB layer (single-row update); both requests succeed at the HTTP layer, no optimistic-locking conflict surfaced — acceptable given low admin headcount and low concurrent-edit likelihood, but noted as accepted risk |
| Duplicate `POST /admin/users` with the same email (double-click) | Second request returns 409, idempotency achieved via the unique constraint on `email`, not an explicit idempotency key (volume is low enough that this is sufficient — contrast with payment/order idempotency-key requirements elsewhere) |
| IP allowlist misconfigured to lock out the only Super-Admin | No automated safeguard in this spec — flagged as an open question (§12); a manual Aurora fix would be required today |

## 10. Testing Strategy

- **Unit:** lockout counter logic, CIDR validation, role-claim mapping, DTO validation for every endpoint's negative paths.
- **Integration:** `moto`-mocked Cognito (Admin Pool) + EventBridge, SQLite/Aurora-compatible in-memory DB for `admin_user`, following the exact offline-testing pattern already established in `identity-auth` and `user` services (no AWS credentials, no Docker).
- **Contract:** response shapes verified against the DTOs `portal-ui` (MA-128) depends on (§7 of that spec).
- **E2E:** at least one full journey — Super-Admin creates an admin, that admin logs in with 2FA, is deactivated, and can no longer log in — before merge, per `services/README.md` §6.
- **Negative scenarios required:** wrong password, wrong 2FA code, lockout threshold, deactivated-account login attempt, self-deactivation attempt, duplicate email, malformed CIDR, IP-blocked request.

## 11. Risks and Trade-offs

1. **Second Cognito Admin Pool vs. extending the consumer pool.** Chosen per explicit human decision (2026-09-15, recorded on MA-47). Trade-off: more infrastructure to maintain (two pools), but avoids retrofitting password+MFA onto a pool architected for phone/email OTP usernames — a cleaner security boundary for a small number of highly-privileged accounts. **This is the kind of decision `services/README.md`'s "Human approval gate" principle exists for — confirm the architect has actually signed off, not just the requester in this chat, before implementation begins.**
2. **API Gateway authorizer caching vs. stale role claims.** Standard Cognito JWT authorizers commonly cache decisions for a TTL (e.g., 5 minutes) for performance. For admin JWTs specifically, this directly conflicts with the "role/deactivation takes effect quickly" NFR (§5). Recommend disabling authorizer caching for the admin JWT path specifically (accepting a latency cost) rather than accepting a multi-minute window where a deactivated admin's requests still pass authorization. **Not yet decided — flagged for architect input, see §12.**
3. **`admin_user.role` duplicates the Cognito Group membership** (§7) for query performance. Trade-off: two sources of truth that must be kept in sync on every role change (Cognito `AdminAddUserToGroup`/`AdminRemoveUserFromGroup` + Aurora update in the same transaction/saga). Alternative (Cognito as sole source of truth, `ListUsersInGroup` per list call) was rejected for latency and Cognito API rate-limit reasons.
4. **No optimistic locking on concurrent role-change/deactivate requests** (§9) — accepted given low admin headcount; revisit if concurrent-admin-editing incidents actually occur.

## 12. Open Questions

1. **Architect sign-off required** for the second-Cognito-pool decision (§11.1) — recorded here as resolved-in-chat with the requester, but this spec should not be treated as fully approved until an architect has actually reviewed it, per `services/README.md`'s explicit gate.
2. Should the API Gateway authorizer disable caching for admin JWTs (§11.2), or is a short cache TTL (e.g., 30s) an acceptable compromise? Needs a latency-vs-security-freshness call from the architect.
3. What is the bootstrap procedure for the very first Super-Admin account (§7 migration note) — a one-time seed script, a manual Cognito console step, or a CDK custom resource? Needs a decision before this is implementable, not just a "someone will figure it out."
4. Is there a safeguard needed against an admin locking out the only Super-Admin via a misconfigured IP allowlist (§9)? E.g., disallow IP-restricting the last remaining active Super-Admin account.
5. Exact Cognito access-token TTL to use for admin sessions (shorter than the consumer pool's, given the stale-role-claim trade-off in §11.2, is recommended but not yet a number).
