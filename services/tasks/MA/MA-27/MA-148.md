## 2. Problem Statement

The Transaction History screen (MA-149) filters the passbook by type: All, Top-ups, Order
payments, Refunds & credits. `GET /wallet/me/transactions` has no filter, so the app could only
filter the pages it has already loaded. A customer with many order payments would then see "No
top-ups" even though older top-ups exist. The filter has to apply on the server, inside the same
keyset query that pages the ledger.

## 3. Scope

### In scope

- An optional `types` query parameter on `GET /wallet/me/transactions`: comma-separated ledger
  types.
- Validation (`400 VALIDATION_ERROR` for an unknown or empty type).
- The filter applied in `SqlAlchemyWalletRepository.list_ledger_entries`, keeping the existing
  keyset on `id`.
- Tests at the service, repository and HTTP levels.

### Out of scope

- Search, date-range filters, export.
- Any change to the response shape, the ledger, or the other wallet routes.
- New indexes (see §7).

## 4. Functional Requirements

### FR-1: Request

`GET /wallet/me/transactions?limit=&cursor=&types=RECHARGE,ORDER_DEBIT`

- `types` is optional. When absent, the behaviour is exactly today's (all types).
- The value is comma-separated, case-sensitive and whitespace-trimmed. Each element must be a
  `LedgerType`: `OPENING`, `RECHARGE`, `ORDER_DEBIT`, `REFUND`, `CASHBACK`, `REFERRAL_CREDIT`,
  `ADJUSTMENT`. Duplicates are allowed and collapsed.
- An unknown element, an empty element (`types=RECHARGE,,X` / `types=`), or more than 7 distinct
  values → `400 VALIDATION_ERROR` with `details: {field: "types", invalid: [<values>]}`. Nothing
  is read.

### FR-2: Filtering and paging

- Only ledger entries whose `type` is in the set are returned, newest first. Ordering is by `id
  DESC`, as today.
- Keyset paging is unchanged: `cursor` encodes the last returned `id`, and the next page returns
  matching entries with `id < cursor`. `nextCursor` is set only when more **matching** entries
  exist; the service's existing `limit + 1` probe runs on the filtered query.
- A cursor is only meaningful with the same `types`. The server doesn't bind a cursor to a
  filter, and a cursor reused with a different filter still returns a correct, gap-free sequence
  for the new filter starting below that id. The app resets the cursor whenever the filter
  changes (MA-149).

### FR-3: Response

Unchanged: `{items: [entry], nextCursor}`, with entry `{id, type, amountPaise,
balanceAfterPaise, ref, description, createdAt}`. An empty match returns `{items: [],
nextCursor: null}`, never 404.

### FR-4: Errors (unchanged otherwise)

- No wallet for the user → `404 WALLET_NOT_FOUND` (as today).
- A malformed cursor → `400 INVALID_CURSOR` (as today).
- DB unavailable → `503`.

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Performance | p99 < 100 ms for a page of 50, for wallets up to 10k ledger entries (filter on the per-wallet range of the existing `(wallet_id, created_at, id)` index) |
| Compatibility | Callers without `types` see byte-identical responses |
| Security | Same JWT route and ownership (the caller's own wallet only); no new data exposed |
| Observability | Existing request logging only; no new metrics (a `400` is visible in API logs) |

| File | Change |

| `wallet/src/adapters/interfaces.py` | Port signature updated |
| `wallet/README.md` | Endpoint table: `types` parameter |

## 7. Data Considerations

- No migration. The filter is on the existing `type` column within a single wallet's rows. A
  per-wallet ledger is small (one entry per top-up or order), so a type filter over the
  `wallet_id` range is cheap.
- A `(wallet_id, type, id)` index is **not** added now. Revisit if wallets exceed about 10k entries.

## 8. Integration Considerations

| Counterparty | Contract | Failure behaviour |
|--------------|----------|-------------------|
| Flutter app (MA-149) | Sends `types` per filter group: Top-ups `RECHARGE`; Order payments `ORDER_DEBIT`; Refunds & credits `REFUND,CASHBACK,REFERRAL_CREDIT,ADJUSTMENT`; All → no param | `400` would be a client bug; the app shows its generic error |
| Existing callers (none in the app today; the passbook screen is a placeholder) | No `types` → unchanged | — |

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| `types=REFUND` and no refunds exist | `200 {items: [], nextCursor: null}` |
| `types=RECHARGE,RECHARGE` | Same as `RECHARGE` |
| `types=recharge` (lower case) | `400 VALIDATION_ERROR` (case-sensitive) |
| `types=` (empty) | `400 VALIDATION_ERROR` |
| Filtered page exactly fills `limit` and no more matches | `nextCursor: null` (the probe runs on the filtered query) |
| Matching entries are sparse among many others | Pages still contain `limit` matches when available (the filter is in SQL, not post-filtered) |

## 10. Testing Strategy

- **Unit (service, `tests/unit/domain/test_wallet_service.py`):**
  - `_parse_types` accepts each type, trims spaces and collapses duplicates;
  - it rejects unknown, empty and lower-case values (`InvalidTransactionTypeError` with
    `invalid` listed);
  - `list_transactions` with `types=None` equals today's output.
- **Repository (SQLite):**
  - seed 3 RECHARGE, 5 ORDER_DEBIT and 1 OPENING;
  - `types={RECHARGE}` returns 3, newest first;
  - paging with `limit=2` → 2, then 1 with `nextCursor: null`;
  - `types={ORDER_DEBIT, RECHARGE}` returns 8 in id order;
  - an empty result for an absent type.
- **HTTP (TestClient, `tests/integration/test_wallet_http.py`):**
  - `?types=RECHARGE` → only top-ups;
  - `?types=BOGUS` → 400 `VALIDATION_ERROR` with `details.field == "types"`;
  - no param → unchanged body;
  - `?types=ORDER_DEBIT&limit=1` then `cursor=` → continues within order debits only.

## 11. Risks and Trade-offs

- **Cursor isn't bound to the filter.** It's simpler and stateless. The app resets it on a
  filter change, and reuse with another filter is still correct, just starting mid-history.
- **No new index.** This is acceptable at current volumes; it's flagged in §7.
