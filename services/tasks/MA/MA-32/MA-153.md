## 2. Problem Statement

When a customer cancels a paid order (MA-32), the money must go back to their Milkful Wallet.

What exists today:
- Wallet can debit an order (`POST /wallet/internal/debit`, ref `order:{orderId}`).
- Wallet can fence a debit that hasn't happened yet (MA-142 void).
- **Nothing can credit money back for an order that was debited.** The `REFUND` ledger type
  exists, and the app's Transaction History already renders it, but no code writes it.

**Expected outcome:** an internal, idempotent refund that credits the order's debited amount
back to the same wallet, exactly once, however many times it's called.

## 3. Scope

### In scope

- `POST /wallet/internal/refunds`, an internal, service-to-service route. It credits a `REFUND`
  ledger entry against an existing `ORDER_DEBIT`.
- Idempotency on the ledger `ref` `refund:{orderId}:{refundId}`.
- Validation against the original debit: it must exist, belong to the same user, and the
  refund must not exceed what was debited.
- A new `WalletRefunded` event (`shared/events/WalletRefunded.schema.json`), published
  through the existing outbox.
- Order Service's `HttpWalletClient.refund(...)`, the typed client used by MA-154.

### Out of scope

- Any public (JWT) refund route, or customer-initiated refunds.
- Refunds to a card or bank (the money only goes back to the Wallet).
- Partial-refund *policy*. This API supports refunding less than the debit; MA-32 always
  refunds in full (decided 2026-10-07).
- Cashback, referral credits and admin adjustments (other ledger types, other stories).

## 4. Functional Requirements

### FR-1: Route and auth

- `POST /wallet/internal/refunds`, under the existing `/wallet/internal/*` prefix.
- Same service-to-service auth as `POST /wallet/internal/debit`: SigV4 / VPC-only in prod, not
  routed through the public API Gateway.
- Request body (JSON):

| Field | Type | Rules |
|-------|------|-------|
| `userId` | string | Required, non-empty (Cognito sub) |
| `orderId` | string | Required, `^[A-Za-z0-9_-]{1,64}$` (same `_validate_order_id` rule as the debit routes) |
| `refundId` | string | Required, `^[A-Za-z0-9_-]{1,32}$`. MA-32 always sends `cancel` |
| `amountPaise` | integer | Required, `> 0` |
| `correlationId` | string | Optional; minted if absent (same as `DebitRequest`) |

### FR-2: Behaviour

Run everything in one transaction with the same lock-check-write shape as `debit_for_order`:

1. `SELECT … FOR UPDATE` the wallet row for `userId`. If there's none →
   `404 WALLET_NOT_FOUND`.
2. **Replay:**
   - If a ledger entry with ref `refund:{orderId}:{refundId}` exists, return it as `200
     REFUNDED` with `replayed: true`, and write nothing.
   - If that entry belongs to a different wallet → `409 ORDER_USER_MISMATCH`.
3. **Original debit:**
   - Load the ledger entry with ref `order:{orderId}`.
   - If it's missing → `409 DEBIT_NOT_FOUND` (nothing to refund; this includes a voided
     order).
   - If its wallet isn't the locked wallet → `409 ORDER_USER_MISMATCH`.
4. **Amount cap:** `amountPaise` plus the sum of existing `REFUND` entries whose ref starts with
   `refund:{orderId}:` must be ≤ `abs(debit.amount_paise)`. The match is a literal prefix match
   (§7), never an unescaped `LIKE`. Otherwise → `409
   REFUND_EXCEEDS_DEBIT`, with `details: {debitedPaise, alreadyRefundedPaise}`.
5. **Wallet status:** refunds credit the wallet **whatever its status** (`ACTIVE`, `CREATING`
   or `FAILED`). It's the customer's own money coming back, and blocking it would strand
   funds. This deliberately differs from debits, which require `ACTIVE`.
6. **Write, all in this one transaction:**
   - insert the ledger row: `type = REFUND`, `amount_paise = +amountPaise`, `ref =
     refund:{orderId}:{refundId}`, `balance_after_paise`, `description` from the existing
     `_DESCRIPTIONS` ("Refund");
   - increment `wallets.balance_paise`;
   - insert a `WalletRefunded` outbox row.
7. **Concurrent identical requests:**
   - The `ref` UNIQUE constraint is the serialization point, as for `debit`.
   - An `IntegrityError` on insert is resolved by re-reading the ref in a fresh transaction
     and returning it as a replay.

### FR-3: Response

`200`, wrapped in the existing `success_envelope`:

```json
{ "orderId": "ord_…", "refundId": "cancel", "status": "REFUNDED",
  "amountPaise": 15500, "balanceAfterPaise": 677646,
  "ledgerEntryId": 812, "refundedAt": "2026-10-07T09:12:03+00:00", "replayed": false }
```

A replay returns the **original** entry's values, with `replayed: true`.

### FR-4: Errors

These use the existing Wallet error envelope (`error_code` + `details` spread into `data`).

| Condition | HTTP | `errorCode` |
|-----------|------|-------------|
| Body invalid / bad `orderId` or `refundId` | 400 | `VALIDATION_ERROR` |
| `amountPaise <= 0` | 400 | `INVALID_AMOUNT` |
| No wallet for `userId` | 404 | `WALLET_NOT_FOUND` |
| No `ORDER_DEBIT` for the order | 409 | `DEBIT_NOT_FOUND` |
| Debit or prior refund on another wallet | 409 | `ORDER_USER_MISMATCH` |
| Would exceed the debited amount | 409 | `REFUND_EXCEEDS_DEBIT` |
| Database failure | 503 | `SERVICE_UNAVAILABLE` (retryable) |

### FR-5: `WalletRefunded` event

`shared/events/WalletRefunded.schema.json`, source `milkful.wallet`, with
`additionalProperties: false`.

- **Required:** `eventId`, `occurredAt`, `correlationId`, `userId`, `walletId`, `orderId`,
  `refundId`, `amountPaise` (>0), `balanceAfterPaise` (≥0), `ref`.
- Add it to `shared/events/README.md`'s producer/consumer table. There are no consumers today;
  MA-103 Notifications and MA-104 Reporting will be the future consumers.
- **Why a new event:** `WalletCredited` pins `type: RECHARGE` and requires `paymentId`.
  Loosening it would break its contract for existing consumers.

### FR-6: Order Service client

- Add `HttpWalletClient.refund(user_id, order_id, refund_id, amount_paise, correlation_id) ->
  Refunded` to `order/src/adapters/wallet_client_adapter.py`.
- It uses the same `call_with_retry` + `_RetryableWalletError` policy as `void_debit`. Retry on
  `503`, connection errors and timeouts; that's safe because the call is idempotent.
- `409` codes map to typed exceptions: `DebitNotFoundError`, `RefundExceedsDebitError` and
  `OrderUserMismatchError` (new in `order/src/domain/exceptions.py`; not retried).
- Exhausted retries → `WalletUnavailableError` (existing).

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Correctness | At most one credit per `refund:{orderId}:{refundId}`, under any retry or concurrency; the sum of refunds per order never exceeds its debit |
| Performance | p95 < 150 ms (one locked row and two inserts, the same as `debit`) |
| Reliability | Retry-safe by construction (idempotent); `503` only for database failures |
| Security | Internal only; never on the public gateway; no new PII |
| Observability | Structured log `refund` with `orderId`, `refundId`, outcome (`REFUNDED`/`REPLAYED`/error code) and `correlationId`, matching `_log_debit_call`; metric `wallet.refund.count{outcome}` |
| Auditability | Every refund is a ledger row (immutable), visible in `GET /wallet/me/transactions` as `REFUND` / "Refund for Order" (MA-149) |

## 7. Data Considerations

- **No migration.**
  - `ledger_entries` already allows `type = REFUND` (the `LedgerType` enum / column).
  - `ref` is already UNIQUE.
- Ref format: `refund:{orderId}:{refundId}`. This matches MA-149's parser, which takes
  `orderId` from the second segment, so the app links the refund row to the order.
- The cap query sums `amount_paise` for `type = 'REFUND'` and `wallet_id` = the locked wallet,
  where the ref **starts with the literal prefix** `refund:{orderId}:`.
  - Implement it as `left(ref, :n) = :prefix`, or with `LIKE` with `_`/`%` escaped (SQLAlchemy
    `startswith(..., autoescape=True)`).
  - Order IDs contain `_` (`ord_…`). An unescaped `LIKE` would treat it as a wildcard and
    could count another order's refunds.
- It runs inside the locked transaction. The volume per order is tiny (one row in MA-32).

## 8. Integration Considerations

| Dependency | Contract | Failure behaviour |
|------------|----------|-------------------|
| Order Service (caller) | FR-1 body; idempotent | It retries `503` or a timeout with the same `refundId`; a replay is safe |
| Outbox → EventBridge | `WalletRefunded` | The existing outbox publisher retries; at-least-once (consumers dedupe on `eventId`) |

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Same refund requested twice, or concurrently | Exactly one ledger row; both calls return it (the second with `replayed: true`) |
| Order was voided, never debited (MA-142) | `409 DEBIT_NOT_FOUND`; MA-154 treats it as "nothing to refund" |
| ₹0 order | Never called (MA-154 sets `refund_state = NOT_REQUIRED`); if it were, `amountPaise > 0` fails with `INVALID_AMOUNT` |
| Wallet `FAILED` / `CREATING` | Credited anyway (FR-2 step 5) |
| `userId` doesn't own the debit | `409 ORDER_USER_MISMATCH`; nothing written; logged at error level |
| Second refund for the same order with a different `refundId` | Allowed until the cap; MA-32 only ever uses `cancel` |
| Database down mid-transaction | Rolled back; `503`; the caller retries |

## 10. Testing Strategy

**Unit** (`wallet/tests/unit/domain/test_wallet_service.py`, using the in-memory/fake repo
pattern):
- A refund after a debit:
  - balance +amount;
  - a `REFUND` row with ref `refund:ord_1:cancel`;
  - a `WalletRefunded` outbox payload that validates against the schema.
- A replay returns the same entry, `replayed: true`, with no second row and no second outbox
  row.
- No debit → `DebitNotFoundError`. A voided order → `DebitNotFoundError`.
- Over-refund → `RefundExceedsDebitError`, with `details` set. Refunds totalling exactly the
  debit are allowed.
- The cap ignores another order's refunds whose id differs only where this id has `_` (e.g.
  `ord_1` vs `ordX1`). This guards the literal prefix match.
- `amountPaise` of 0 or negative → `InvalidAmountError`.
- A wallet in `FAILED` status is still credited.

**Integration / HTTP** (`wallet/tests/integration/test_wallet_http.py`, real Postgres):
- `POST /wallet/internal/refunds` after `POST /wallet/internal/debit` → `200`. Then `GET
  /wallet/me/transactions?types=REFUND` shows one entry with the right amount and ref.
- Two concurrent requests (threads) → one ledger row.
- Every FR-4 error code and status, with the envelope shape asserted.

**Order client** (`order/tests/unit/adapters/test_wallet_client_adapter.py`, mocked HTTP):
- `200` → `Refunded`.
- `503` then `200` → retried and succeeds.
- Each `409` code → its typed exception, and not retried.

## 11. Risks and Trade-offs

- **Crediting a non-ACTIVE wallet.** Chosen so refunds are never stranded; the alternative
  (failing) would leave money owed with no automatic path back. Reviewed with Finance.
- **A new event rather than reusing `WalletCredited`.** Costs one more schema; keeps
  `WalletCredited`'s contract intact for existing consumers.
- **The refund amount comes from the caller,** not derived from the debit. That keeps the API
  usable for future partial refunds. The cap (FR-2 step 4) is the safety net against a caller
  bug.

## 12. Open Questions

None blocking. A future cashback or partial-refund policy (out of scope) would reuse this route
with a new `refundId`.
