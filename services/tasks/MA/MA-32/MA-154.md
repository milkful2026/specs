## 2. Problem Statement

Customers can't cancel an order. Order Service has no customer write endpoint, and `CANCELLED`
is only ever set by the MA-143/144 sweep for orders that were never charged. MA-32 requires a
customer to cancel a paid order before the daily cut-off and get a full refund to their Wallet.

The cancel has to satisfy three things that pull against each other:
- a cancelled order must **never** be delivered;
- the refund must happen **exactly once**;
- a Wallet outage must not leave the customer in limbo.

**Expected outcome:** a JWT endpoint that atomically cancels the order, then refunds it, with
automatic recovery when the refund can't complete straight away.

## 3. Scope

### In scope

- `POST /orders/{orderId}/cancel` (Cognito JWT, the order owner only).
- The eligibility rules: status `CONFIRMED` and before the cut-off.
- An optional cancel reason.
- New columns on `orders`: `cancel_reason`, `cancelled_at`, `refund_state`. New failure reason
  `CUSTOMER_CANCELLED`.
- The refund via MA-153, and a new sweep pass that finishes refunds still `PENDING`.
- The `OrderCancelled` event (`shared/events/OrderCancelled.schema.json`).
- `cancellableUntil`, `cancelReason`, `cancelledAt` and `refundState` in the order DTO
  (`GET /orders/me`, `GET /orders/{id}`).

### Out of scope

- Cancelling a subscription delivery that isn't an order yet. That's the existing `POST
  /subscriptions/{id}/skip`, used by MA-155.
- Cancelling after the cut-off, or in any status other than `CONFIRMED`. Those go to support.
- Partial cancellation (dropping some lines) and cancellation fees.
- Restoring Inventory stock (orders don't reserve stock).
- Notifications. `OrderCancelled` is published; MA-103 will consume it later.

## 4. Functional Requirements

### FR-1: Endpoint

- `POST /orders/{orderId}/cancel`, with Cognito JWT (`current_user_id`).
- Optional body: `{"reason": "ORDERED_BY_MISTAKE" | "NOT_HOME" | "CHANGED_MIND" | "OTHER"}`. A
  missing or null reason is allowed. An unknown value → `400 VALIDATION_ERROR`.

### FR-2: Eligibility (checked in order)

| # | Rule | Failure |
|---|------|---------|
| 1 | The order exists and `order.user_id == caller` | `404 ORDER_NOT_FOUND` (never leaks existence, same as `get`) |
| 2 | Status is already `CANCELLED` with `failure_reason = CUSTOMER_CANCELLED` | **Not an error:** idempotent replay, return the current cancellation (FR-4) with `200`. If `refund_state` is still `PENDING`, run Step B first (idempotent via MA-153), so a customer retry can finish the refund sooner than the sweep |
| 3 | Status is `CONFIRMED` | `409 ORDER_NOT_CANCELLABLE` with `details: {status}` |
| 4 | `delivery_cutoff_passed(order.delivery_date, now, settings.checkout_cutoff_hour_ist)` is false | `409 CUTOFF_PASSED` with `details: {cancellableUntil}` |

- **Both sources qualify.** A `SUBSCRIPTION` order is only `CONFIRMED` before the cut-off in the
  same-day-create path; Subscription Service's Skip already rejects those dates as "already
  processed", so this endpoint is how such a delivery is cancelled.
- `now` is the server clock. The device clock is never trusted.

### FR-3: Cancel, then refund

**Step A: one database transaction** (`order_repository.cancel_by_customer`):
- Run a conditional `UPDATE orders SET status='CANCELLED', failure_reason='CUSTOMER_CANCELLED',
  cancel_reason=:reason, cancelled_at=:now, refund_state=:state WHERE id=:id AND
  status='CONFIRMED'`.
- `:state` is `PENDING` when `amount_paise > 0`, otherwise `NOT_REQUIRED`.
- **0 rows updated:** a concurrent cancel or a state change won the race. Re-read the order and
  apply FR-2 to the fresh row: a replay, or a `409`.
- **In the same transaction,** insert the `OrderCancelled` outbox row (FR-6).

**Step B: refund, only if `refund_state = PENDING`**, after the commit:
- Call `HttpWalletClient.refund(user_id, order_id, refund_id="cancel", amount_paise=
  order.amount_paise, correlation_id)` (MA-153).
- **`Refunded`** → set `refund_state='REFUNDED'` and `refunded_at=now`. This is a conditional
  update `WHERE refund_state='PENDING'`, so it's idempotent.
- **`DebitNotFoundError`** (never debited) → set `refund_state='NOT_REQUIRED'`, and log a
  warning. A `CONFIRMED` order should always have a debit, so this is investigated, not fatal.
- **`WalletUnavailableError`, a timeout, or any other error** → leave it `PENDING`. **The
  request still succeeds:** the order is cancelled, and the FR-5 sweep finishes the refund.
- **`RefundExceedsDebitError` / `OrderUserMismatchError`** → leave it `PENDING`, log at error
  level, and alarm (a data bug; support resolves it). The request still succeeds.

**Why this order:** cancelling first guarantees a cancelled order is never delivered, and the
refund is guaranteed by recovery. Refunding first could refund an order that then still ships,
if Step A failed.

### FR-4: Response

`200`, wrapped in `success_envelope`. The body is the full serialized order (same shape as `GET
/orders/{id}`, FR-7), so the client can redraw without another `GET`:

```json
{ "orderId": "ord_…", "status": "CANCELLED", "failureReason": "CUSTOMER_CANCELLED",
  "cancelReason": "NOT_HOME", "cancelledAt": "…", "refundState": "REFUNDED",
  "amountPaise": 15500, "cancellableUntil": null, … }
```

`refundState` is `PENDING` when Step B didn't complete. The app shows "Refund in progress"
(MA-155).

### FR-5: Sweep: finish pending refunds

- Add a fourth pass to `handlers/sweep.py::run_once`: `("refund",
  service.finish_pending_refunds)`. It runs after `settle`.
- `SweepService.finish_pending_refunds(correlation_id, now)`:
  - **Select:** orders with `refund_state='PENDING' AND cancelled_at < now - 60s`. The 60 s
    grace avoids racing the request's own Step B.
  - **Claim:** use the existing lease columns (`claimed_until` / `claim_owner`), so only one
    worker handles an order.
  - **Process:** run the same Step B logic for each order.
  - **Return:** a `Counter` of `{refunded, not_required, still_pending, error}`.
- **Alarm:** metric `order.refund.pending_age_seconds` (the max age of `PENDING`). Alarm if it's
  > 15 min. Also emit `order.refund.outcome{outcome}`.

### FR-6: `OrderCancelled` event

`shared/events/OrderCancelled.schema.json`, source `milkful.order`, with
`additionalProperties: false`.

- **Required:** `eventId`, `occurredAt`, `correlationId`, `orderId`, `userId`, `source`,
  `amountPaise`, `deliveryDate`, `cancelledBy` (const `CUSTOMER`), `refundState` (`PENDING` or
  `NOT_REQUIRED`, the value at cancel time).
- **Optional:** `cancelReason` (enum or null), `subscriptionId`, `checkoutId`, and `items`
  (same shape as `OrderConfirmed`).
- Published once, from Step A's outbox row. The later refund outcome is carried by MA-153's
  `WalletRefunded`, not by a second order event.
- Add it to `shared/events/README.md`. **Future consumers:** MA-103 (customer notification),
  MA-104 (cancel-reason reporting), MA-102 (drop the delivery stop).

### FR-7: DTO additions

`_serialize(order)` adds:

| Field | Value |
|-------|-------|
| `cancellableUntil` | ISO datetime of `checkout_cutoff_hour_ist`:00 IST on `delivery_date - 1`, **only when** status is `CONFIRMED` and that moment is in the future; otherwise `null` |
| `cancelReason` | Enum value or `null` |
| `cancelledAt` | ISO datetime or `null` |
| `refundState` | `PENDING` / `REFUNDED` / `NOT_REQUIRED` / `null` |

- These fields are additive; existing clients ignore unknown keys.
- The `cutoff.py` helper gains `delivery_cutoff_moment(delivery_date, cutoff_hour_ist) ->
  datetime`, shared by FR-2 and FR-7 so they can't drift apart.

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Correctness | A `CUSTOMER_CANCELLED` order is never delivered; refunded at most once (MA-153 idempotency); every `PENDING` refund reaches a terminal state or alarms |
| Performance | p95 < 400 ms including the Wallet call; the Wallet client's timeout (3 s × retries) bounds the worst case, and the request returns even when Wallet is down |
| Reliability | Step B failure never fails the request; the sweep resolves it; at-least-once events |
| Security | JWT owner check; 404 for a non-owner; reason is an enum (no free text, no PII) |
| Observability | `X-Correlation-Id` propagated app → Order → Wallet; structured logs `order.cancel` with `orderId`, outcome and `refundState`; metrics `order.cancel.count{outcome}`, `order.refund.outcome`, `order.refund.pending_age_seconds` |
| Compatibility | Additive migration and DTO fields; no change to existing statuses or transitions |

## 6. Technical Design

```
App ──POST /orders/{id}/cancel (JWT)──▶ order_handlers.cancel_order
                                          └─ OrderService.cancel(order_id, user_id, reason, now)
                                               ├─ FR-2 checks (repo.get, cutoff)
                                               ├─ repo.cancel_by_customer  [txn: UPDATE … WHERE CONFIRMED + outbox OrderCancelled]
                                               └─ _refund(order)  → HttpWalletClient.refund (MA-153)
                                                                     └─ repo.mark_refund_state
Sweep loop ── finish_pending_refunds ──▶ same _refund(order) for stale PENDING
```

## 7. Data Considerations

`order/migrations/0004_customer_cancel.sql` (additive; existing rows are unaffected):
- `cancel_reason TEXT NULL CHECK (cancel_reason IN ('ORDERED_BY_MISTAKE','NOT_HOME','CHANGED_MIND','OTHER'))`
- `cancelled_at TIMESTAMPTZ NULL`
- `refund_state TEXT NULL CHECK (refund_state IN ('PENDING','REFUNDED','NOT_REQUIRED'))`
- `refunded_at TIMESTAMPTZ NULL`
- a partial index `ON orders (cancelled_at) WHERE refund_state = 'PENDING'`, for the sweep.

`failure_reason` is free text today; `CUSTOMER_CANCELLED` is a new value. The existing
`CANCELLED` + `CUTOFF_PASSED` rows (MA-144) are untouched.

## 8. Integration Considerations

| Dependency | Contract | Failure behaviour |
|------------|----------|-------------------|
| Wallet `POST /wallet/internal/refunds` (MA-153) | Idempotent on `refund:{orderId}:cancel` | Retries in the client; then `PENDING` and the sweep (FR-5) |
| Outbox → EventBridge | `OrderCancelled` | The existing publisher; at-least-once |
| App (MA-155) | FR-1/FR-4/FR-7; error codes `CUTOFF_PASSED`, `ORDER_NOT_CANCELLABLE` | The app maps both to its blocked copy |

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Double tap / retry | The second call is a replay (FR-2 #2) → `200` with the current state; one refund (MA-153) |
| Two concurrent cancels | The conditional `UPDATE` lets one win; the loser re-reads and replays |
| Cancel at 19:59:59.9 vs 20:00 IST | The server decides; at or after 20:00:00 → `409 CUTOFF_PASSED` |
| Order is `CREATED` (checkout still charging) | `409 ORDER_NOT_CANCELLABLE`; MA-144 recovery owns it |
| Order is `CANCELLED` by the sweep (`CUTOFF_PASSED`) | `409 ORDER_NOT_CANCELLABLE` (it's not a customer cancel, so not a replay) |
| ₹0 order | Cancelled with `NOT_REQUIRED`; no Wallet call |
| Wallet down during Step B | `200` with `refundState: PENDING`; the sweep refunds within minutes; alarm after 15 min |
| Process crash between Step A and Step B | Order is `CANCELLED` + `PENDING`; the sweep finishes it |
| Debit missing for a `CONFIRMED` order | `NOT_REQUIRED` + warning log (should be impossible) |
| Non-owner or unknown id | `404 ORDER_NOT_FOUND` |

## 10. Testing Strategy

**Unit** (`order/tests/unit/domain/test_order_service.py`, using fake repo + fake Wallet
client):
- Happy path:
  - status `CANCELLED`, `CUSTOMER_CANCELLED`, the reason stored;
  - an outbox `OrderCancelled` row that validates against the schema;
  - the Wallet called once with `refund_id="cancel"` and the full amount;
  - `refundState REFUNDED`.
- No reason → stored as null. An unknown reason → `ValidationError`.
- At the cut-off moment exactly → `CutoffPassedError`. One second before → succeeds (fixed
  clocks).
- Non-owner → `OrderNotFoundError`. Status `CREATED`, `PAYMENT_FAILED`, or `CANCELLED` with
  `CUTOFF_PASSED` → `OrderNotCancellableError`.
- A replay after success returns the same state with no second Wallet call.
- A replay while `PENDING` runs Step B, and it becomes `REFUNDED`.
- Wallet unavailable → `200`-equivalent result with `PENDING`. `DebitNotFoundError` →
  `NOT_REQUIRED`.
- A ₹0 order → `NOT_REQUIRED`, no Wallet call.
- `cancellableUntil`: set for a `CONFIRMED` order before the cut-off; null after it, and null
  for other statuses.

**Sweep** (`order/tests/unit/domain/test_sweep_service.py`):
- A stale `PENDING` → refunded.
- A fresh `PENDING` (< 60 s) → skipped.
- A claimed order is skipped by a second worker.
- Wallet still down → stays `PENDING` and counted.

**Integration** (`order/tests/integration/test_order_http.py`, real Postgres, stub Wallet):
- `POST /orders/{id}/cancel` → `200`, then `GET /orders/{id}` shows the new fields.
- Two concurrent cancels → one `UPDATE`, one Wallet refund call.
- Every error code and status, with the envelope shape asserted.
- Migration `0004` applies on top of `0003`.

**Local-dev E2E (manual):**
1. Check out a cart, then `POST /orders/{id}/cancel`.
2. `GET /wallet/me/transactions?types=REFUND` shows "Refund for Order" for that order.
3. The balance is back to its value before checkout.

## 11. Risks and Trade-offs

- **Cancel-then-refund leaves a window where the customer sees "Refund in progress".**
  Accepted. It's visible, short, alarmed and self-healing. Refund-then-cancel risks delivering
  a refunded order, which is worse.
- **The request succeeds even if the refund failed.** The customer's intent (cancel) is
  honoured immediately; the money follows. The UI must not claim "Refunded" while it's
  `PENDING` (MA-155).
- **Same-day-create subscription orders are cancellable here,** but their dates can't be
  skipped. Consistent: "an order before the cut-off is cancellable", whatever its source.
- **Cut-off reuse:** the cancel deadline is the checkout cut-off (20:00 IST). If Product ever
  separates the two, `delivery_cutoff_moment` is the single place to change.
