## 2. Problem Statement

No pricing, tax, or offers logic exists anywhere in the platform today — Catalog Service exposes
only a flat `price_b2c`/`price_b2b` per product, with no tax/HSN modeling and no offer/coupon
concept at all. Cart Service (MA-96/MA-121, spec'd in parallel) and MA-23's mobile screen both
depend on a real, authoritative price/tax/delivery-fee quote and offer validation. Without this
service, every consumer would need to duplicate pricing/tax logic independently — exactly what
this service exists to prevent.

## 3. Scope

**In scope:**
- `POST /pricing/quote` — price/tax/delivery-fee computation for one or more line items.
- `GET /offers` — active, eligible offers for the caller.
- `POST /offers/validate` — real-time code validation and best-offer auto-apply.
- Offer data model: percentage / flat / BOGO / first-order / subscription-specific types, with a
  documented precedence rule for simultaneous eligibility.
- Aurora `offers` cluster schema; Redis caching layer.
- A new `CatalogUpdated` domain event, published by Catalog Service (MA-94, already shipped) and
  consumed here — see §7 for why this is a small, additive addition to an already-approved
  service, not a new dependency invented from nothing.

**Out of scope:**
- Offer/coupon authoring (create/edit/deactivate) — MA-45 (Admin / Promotions, `portal-ui`). This
  service serves and validates offers; it does not manage their lifecycle.
- GST invoice document generation (PDF, HSN-compliant) — MA-38 (Invoice Generation). This service
  supplies the tax figures Invoice consumes; it does not produce the invoice itself.
- Order-time price locking (does a quote stay valid for the duration of a checkout session?) —
  Order Service's concern (MA-97, unbuilt), not this service's.

## 4. Functional Requirements

### FR-1: `POST /pricing/quote`

- Request: a list of `{productId, quantity, frequency}` (accepts one or many — resolves Step 1
  open question #1 in favor of a single endpoint handling both MA-23's single-item need and Cart
  Service's full-cart need, rather than two separate endpoints with duplicated tax/offer logic)
  plus the caller's delivery-address state (required for the CGST/SGST vs. IGST determination,
  FR-2), plus an **optional cart-level `offerCode`** field. **Gap found and resolved:** FR-4's
  auto-apply behavior was previously defined only in terms of "called without an explicit offer
  code," but no request field existed anywhere in the platform to carry a code the caller
  deliberately chose via `POST /offers/validate` (FR-4) — `offerCode` is that field. When present
  and valid, it is applied instead of running auto-apply; when present but no longer valid at quote
  time (expired/usage-limit hit since validation), the quote falls back to auto-apply rather than
  failing the whole request, and the response's applied-offer field reflects what was actually used
  so the caller can detect the substitution. This field must be added to Cart Service's identical
  request shape (MA-96/MA-121 §6) in lockstep, per that spec's own "kept in sync" commitment.
- Response: per-line-item breakdown (base price, tax amount, tax rate applied) plus a
  cart-level delivery fee and net payable total, and — if any offer is auto-applied (FR-4) — the
  discount amount and which offer was applied.
- For subscription frequencies (`DAILY`/`ALTERNATE_DAYS`), the response additionally frames the
  net payable as a monthly estimate (matching MA-120's "/ month" display need) — computed as
  `net payable per delivery × billing occurrences per month` for the given frequency (Daily = ~30,
  Alternate Days = ~15 — exact day-count convention confirmed in Step 4/implementation, not
  re-litigated here), **not** unit price alone: "net payable per delivery" is this same FR's
  per-delivery total (base price × quantity, plus tax, plus any per-delivery share of the delivery
  fee, minus any auto-applied discount) — the same figure the response already returns for a
  one-time order, just projected across a month's occurrences. This matches MA-23/MA-120's own
  stated expectation ("base price × quantity, plus tax/delivery per MA-101") and must match
  whatever Cart Service (MA-96/MA-121) computes from the same response, since both read this same
  field rather than each deriving their own monthly figure.

### FR-2: GST/HSN tax computation

- Each product's tax rate is resolved by HSN code, sourced from `CatalogUpdated` (FR-6) — never
  hardcoded per-service, since HSN/GST-rate ownership belongs to Catalog Service's product data
  (NSMB spec row 23.0: Catalog/Admin owns "taxes/HSN" per product).
- CGST + SGST split applies when the delivery address's state matches the seller's registered
  state; IGST applies otherwise (standard GST interstate-supply rule) — resolves Step 2's data
  gap: the quote request must carry a delivery state (§3 FR-1), not just product/quantity.

### FR-3: `GET /offers`

- Returns currently-active offers eligible for the caller (first-order offers filtered by whether
  the caller has a prior order — via a lightweight flag on the request/JWT context, not a live
  Order Service call, to avoid a hard dependency on an unbuilt service; exact source of that flag
  confirmed at implementation time).
- Each offer's type, value, and eligibility conditions (min cart value, applicable products,
  subscription-only, etc.) are returned so the mobile client can display terms, not just a code.

### FR-4: `POST /offers/validate` and best-offer auto-apply

- Manual code entry: validates a caller-supplied code against active offers, current eligibility,
  and any per-offer usage limits; returns valid/invalid + the resulting discount if valid. A code
  validated here is passed to `POST /pricing/quote` as `offerCode` (FR-1) to actually apply it.
- Auto-apply (no `offerCode` in the request, FR-1): when `POST /pricing/quote` is called without an
  explicit offer code, this service automatically evaluates all currently-eligible offers and
  applies the best one per the precedence rule below — resolves Step 1 open question #3, which was
  left undecided:

  **Precedence rule:** when more than one offer is simultaneously eligible, the offer yielding the
  **largest absolute discount amount** for the given cart is applied (not offer-type priority,
  not most-recently-created) — a simple, explainable, customer-favorable rule that avoids needing
  a hand-maintained priority table per offer type. BOGO offers are compared by their equivalent
  discount value — the **sum of the prices of all M free/discounted units** in a buy-N-get-M offer
  (not just one unit; FR-5's BOGO type is general buy-N-get-M, and a single-unit value would
  undervalue any M>1 offer in this comparison) — for this comparison. Ties broken by offer ID
  (deterministic, arbitrary) — not expected to matter in practice given the continuous nature of
  discount amounts.

### FR-5: Offer types supported

- **Percentage** — `X%` off eligible items/cart.
- **Flat** — fixed ₹ amount off.
- **BOGO** — buy-N-get-M-free/discounted on eligible products.
- **First-order** — eligibility gated on no prior completed order (FR-3's flag).
- **Subscription-specific** — eligibility gated on `frequency != ONE_TIME` in the request.

### FR-6: `CatalogUpdated` consumption

- Catalog Service (MA-94, already shipped) gains a new outbox-published event,
  `CatalogUpdated`, mirroring the exact envelope/publishing pattern `user`'s service already
  established (`outbox_event_publisher.py`) — resolves Step 2's highest-priority risk (the
  payload was previously unconfirmed) by defining it now:
  ```json
  {
    "eventId": "uuid",
    "productId": "uuid",
    "name": "string",
    "priceB2C": 0.0,
    "priceB2B": 0.0,
    "hsnCode": "string",
    "gstRatePercent": 0.0,
    "categoryId": "uuid",
    "subscriptionEligible": true,
    "active": true,
    "occurredAt": "2026-08-20T10:00:00Z"
  }
  ```
  Published whenever a product's price, HSN code, GST rate, subscription eligibility, **or active
  status** changes (creation, update, and deactivation/delisting all) — mirrors `StockChanged`'s
  existing "one focused event per changed aspect" convention rather than a generic catch-all
  "product changed" event. **Gap found and resolved:** the original draft of this event had no
  signal for a product being discontinued/delisted, so this service's local read model would have
  had no way to learn that and would keep quoting a delisted product indefinitely; `active` closes
  that gap (defaults `true` — this is additive for any consumer that predates the field, matching
  §7's own precedent for other backward-compatible additions). If Catalog Service's current
  product model has no active/deleted concept yet, this is a small, additive prerequisite on that
  side, same category as the `hsnCode`/`gstRatePercent` addition already flagged in §7/§11.
- This service consumes it via an SQS-per-consumer worker (same background-thread-in-Fargate
  pattern already used by `inventory`'s and `catalog`'s own consumers,
  `stock_changed_consumer.py`), maintaining a local, denormalized price/tax read model — this is
  the correct database-per-service pattern (§6 Technical Design), not a violation of it, since the
  alternative (calling Catalog Service synchronously on every quote) would be both slower and a
  tighter coupling than an eventually-consistent local copy. `product_tax`'s local row is updated
  (never deleted) on an `active: false` event, so a quote request for that product can distinguish
  "never seen" (`PRODUCT_PRICING_UNKNOWN`, §9) from "was priced, now delisted"
  (`PRODUCT_DISCONTINUED`, §9) — the row's price/tax data is retained for that error path and for
  any already-in-flight order that still needs to reference it.

## 5. Non-Functional Requirements

- **Performance:** `POST /pricing/quote` is a hot path (called on every MA-23 screen open and
  every `GET /cart`) — target p99 under 300ms, backed by Redis caching of offer lookups and the
  local `CatalogUpdated`-sourced price/tax read model (no synchronous Catalog call on the request
  path at all, per FR-6).
- **Reliability:** `CatalogUpdated` consumer lag must not silently serve stale prices indefinitely
  — a consumer-lag alarm (CloudWatch) is required, not just best-effort processing.
- **Consistency:** offer validation (FR-4) must reflect the current state at request time (no
  stale-cache tolerance for whether a code is still valid/within its usage limit) — Redis caching
  applies to offer *lookup*, not the final valid/invalid decision, which always checks Aurora.
- **Observability:** correlation ID propagation; CloudWatch + X-Ray per `services/README.md`.

## 6. Technical Design

- **Compute:** Fargate + FastAPI/uvicorn, following `inventory`/`catalog`'s established structure
  (`src/main.py` entrypoint running both the FastAPI app and a background consumer thread, exactly
  matching `inventory/src/main.py`'s existing docstring'd pattern).
- **`POST /pricing/quote` contract:** shared verbatim with MA-96/MA-121 §6 — both specs were
  drafted in the same pass specifically to keep this in sync; any future change to one must be
  checked against the other.
- **`CatalogUpdated` producer (Catalog Service side):** a small, additive change to the
  already-shipped Catalog Service — a new `adapters/catalog_updated_publisher.py` (or an addition
  to an existing outbox mechanism if Catalog Service already has one; none was found during Step 2
  — confirmed by inspecting `services/catalog/src` directly, only a consumer
  (`stock_changed_consumer.py`) exists today, no publisher) — invoked from the same code path that
  handles product create/update (Catalog Service's own admin-facing write path, MA-42/23.0 in the
  NSMB spec — out of this spec's direct control, but the hook point is Catalog Service's, not
  this service's).
- **Aurora `offers` schema (outline):**
  ```
  offers (table)
    id (uuid, PK), type (percentage|flat|bogo|first_order|subscription), value (numeric),
    conditions (jsonb — min cart value, applicable product/category IDs, usage limit),
    valid_from (timestamptz), valid_to (timestamptz), active (bool)
  offer_redemptions (table)
    id (uuid, PK), offer_id (fk), user_id (uuid), redeemed_at (timestamptz)
  product_tax (table)                 -- local read model, populated from CatalogUpdated
    product_id (uuid, PK), hsn_code (text), gst_rate_percent (numeric),
    price_b2c (numeric), price_b2b (numeric), subscription_eligible (bool),
    active (bool, default true),        -- false on a CatalogUpdated deactivation event (FR-6)
    updated_at (timestamptz)
  ```
- **Redis:** cache key per `(productId, quantity, frequency, deliveryState)` tuple for computed
  tax. **Invalidation (clarified — the two mechanisms below are not redundant, both required):**
  primary invalidation is event-driven — a `CatalogUpdated` for a product deletes every cached key
  for that `productId` immediately, so a price/tax change is never served stale past the next
  quote after the event is consumed. A **long backstop TTL** (e.g. 24h, well beyond the
  Reliability NFR's consumer-lag alarm threshold) additionally bounds worst-case staleness if the
  event-driven invalidation itself is ever missed (a bug, a lost message despite at-least-once
  delivery) — it is not a substitute for the event-driven path and must not be implemented as the
  sole invalidation mechanism, since a short time-only TTL alone would let the Reliability NFR's
  "no silently-unbounded stale price" guarantee depend entirely on cache-expiry timing rather than
  the `CatalogUpdated` signal. Offer list cached with a short TTL for `GET /offers`'s read-heavy
  pattern (time-only expiry is acceptable there — offers change far less urgently than a live
  price). Confirms this service's Redis role is comparable to Cart Service's (a performance cache
  in front of otherwise-expensive lookups), not a second source of truth.

## 7. Data Considerations

**Gap found and resolved — `CatalogUpdated` didn't exist:** confirmed during Step 2 by searching
`services/catalog/src` directly — no outbox publisher exists there today, only the `StockChanged`
*consumer*. This spec resolves that by defining the event (FR-6) rather than leaving "how does
Pricing get tax data" unanswered. This is a new capability for an already-shipped service
(MA-94), analogous to MA-120/MA-23's own Catalog Service contract addition (`availableQuantity`)
— both are small, additive changes surfaced by this SDD pass, not scope creep invented here.

**HSN/GST data doesn't exist on Catalog's product model either** — `services/catalog/src/domain/
models.py`'s `Product` dataclass has no HSN/tax fields today. Catalog Service's own product
create/update path (admin-facing, MA-42/23.0) needs `hsn_code`/`gst_rate_percent` fields added
before `CatalogUpdated` can carry real values — flagged explicitly as a prerequisite for MA-42,
not assumed to already exist.

## 8. Integration Considerations

- **Catalog Service (MA-94):** event producer (FR-6) — new capability, see §6/§7.
- **Cart Service (MA-96/MA-121):** synchronous caller of `POST /pricing/quote` — contract kept in
  sync across both specs in this drafting pass.
- **Order Service (MA-97, unbuilt):** not integrated in this pass — FR-3's first-order flag avoids
  a hard dependency; a future revision may replace that flag with a real Order Service query once
  it exists.

## 9. Edge Cases and Failure Modes

- `CatalogUpdated` consumer lag means a quote briefly reflects a stale price/HSN rate after an
  admin price change — accepted as standard eventual consistency, bounded by the reliability NFR's
  consumer-lag alarm (not silently unbounded).
- A quote request for a `productId` this service has never received a `CatalogUpdated` for (e.g.
  a very newly created product, event not yet consumed) — returns a distinct error
  (`PRODUCT_PRICING_UNKNOWN`) rather than a zero/garbage price; Cart Service (MA-96 §9) surfaces
  this as its own `5xx` rather than silently proceeding.
- A quote request for a `productId` that was priced before but has since been deactivated/delisted
  (`product_tax.active = false`, FR-6) — returns a distinct error (`PRODUCT_DISCONTINUED`),
  never a stale valid-looking price for a product that should no longer be purchasable; Cart
  Service surfaces this the same way it surfaces `PRODUCT_PRICING_UNKNOWN`.
- Two simultaneously-eligible offers with an exactly-equal discount amount — resolved by the FR-4
  tie-break (offer ID), not left non-deterministic.
- A caller-supplied offer code that exists but has hit its usage limit — `POST /offers/validate`
  returns invalid with a specific reason code (`USAGE_LIMIT_REACHED`), not a generic "invalid
  code," so the mobile client can show an accurate message.

## 10. Testing Strategy

**Unit (domain):** tax computation (CGST/SGST vs. IGST by state match); offer-precedence
comparison (FR-4) across mixed offer types including BOGO's M>1 equivalent-discount conversion
(sum of all free/discounted units, not one); subscription monthly-estimate math (FR-1) for both
Daily and Alternate Days, asserting the tax/delivery/discount-inclusive formula against the
one-time net-payable figure for the same line item; `offerCode` request handling (valid code
applied, expired/limit-hit code falls back to auto-apply); `active: false` handling
(`PRODUCT_DISCONTINUED` returned, prior price/tax row retained not deleted).

**Integration:** `CatalogUpdated` → local `product_tax` read model round-trip against a local
EventBridge/SQS emulation (moto), matching `inventory`/`catalog`'s own consumer test pattern;
`POST /pricing/quote` against a seeded Aurora + read-model fixture.

**Contract:** the same fixture-based `POST /pricing/quote` shape test shared with MA-96/MA-121
(§6 there) — run in both services' suites so a drift between them fails CI on either side.

**Acceptance check:** `pytest services/pricing-offer/tests/` — all pass, including the
tie-break and stale-consumer-lag negative-path tests.

## 11. Risks and Trade-offs

- **Risk:** this spec requires Catalog Service (MA-94, already approved and shipped) to gain a new
  publisher and three new product fields (`hsnCode`, `gstRatePercent`, and now `active`/deactivation
  support, FR-6) — a real, if small, reopening of an already-delivered story. Flagged explicitly
  (§7) rather than assumed away; Catalog Service owner must confirm feasibility before
  implementation planning proceeds.
- **Risk:** `offerCode` (FR-1) is a new field on the shared `POST /pricing/quote` contract, added
  after MA-96/MA-121 was drafted against the prior shape — that spec's request definition must be
  updated in lockstep before implementation, or the two services' contracts diverge exactly where
  both claim to be kept in sync (§6).
- **Risk:** FR-3's first-order flag (avoiding an Order Service dependency) is a deliberate
  simplification that will need revisiting once Order Service (MA-97) exists — documented as
  interim, not permanent.
- **Trade-off:** local denormalized read model (FR-6) over synchronous Catalog calls — chosen for
  latency (NFR) and database-per-service correctness, at the cost of eventual-consistency lag
  (Edge Cases).
