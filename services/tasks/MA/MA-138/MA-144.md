## 2. Problem Statement

`POST /orders/checkout` (MA-136) runs `STARTED → PAID → SUBSCRIPTIONS_DONE → COMPLETED`.
When Wallet, Subscription or Cart fails partway, the checkout stays `IN_PROGRESS` and
the customer gets `503 CHECKOUT_INCOMPLETE`. Only a later Confirm from the customer
finishes it. If they never come back:

- they may have **paid** for one-time items while their **subscriptions never started**
  and the paid items are **still in their cart**;
- an unpaid checkout sits open indefinitely, and a much later Confirm would charge it
  (or, for a ₹0 order, confirm it) for a delivery date that has already passed its cut-off.

As built, the customer is not locked out: any Confirm takes over a checkout untouched
for 2 minutes (`_settle_live_checkout`, `_ABANDONED_AFTER`). That takeover has no claim,
so two workers can run the same checkout at once.

Expected outcome: every abandoned checkout reaches a terminal state without the
customer, with exactly one debit and one subscription per line, following Product
decisions PD-1 and PD-2 (MA-138, 2026-09-28).

## 3. Scope

### In scope

- The checkout pass of the MA-143 sweep.
- **PD-1**: cancel, without charging, a checkout whose charge never happened and whose
  delivery date can no longer be met — including ₹0 orders. Applied by the sweep **and**
  by the customer path. Uncharged is proven by the Wallet void (MA-142), never assumed.
- **PD-2**: complete a paid checkout whose subscriptions still fail at the budget; the
  unstarted lines stay in the cart, and their subscription keys are carried to the next
  checkout of the same cart line so a create that did land is never duplicated.
- Terminal checkout statuses `CANCELLED` and `NEEDS_ATTENTION`; terminal order status
  `CANCELLED` (MA-143 adds order `NEEDS_ATTENTION`).
- The lease on the customer path (new checkout, same-key resume, different-key takeover).
- Replay responses for the new terminal statuses.
- Correcting MA-136's description of FR-2a/FR-5 to the behaviour as built.

### Out of scope

- Refunds (a paid checkout is never reversed here).
- App changes: the new error codes fall into the app's existing "unknown error" path,
  which clears the pending key and shows the server message (MA-137). An app mapping for
  a nicer message is an optional follow-up.
- Operator tooling for `NEEDS_ATTENTION` (Admin stories MA-43/MA-46).

## 4. Functional Requirements

### FR-1: Selection

Each sweep run (MA-143 FR-1), oldest first, at most `ORDER_SWEEP_BATCH_SIZE`:

```sql
SELECT id FROM checkouts
 WHERE status = 'IN_PROGRESS'
   AND updated_at < now() - :checkout_stale_seconds
   AND (claimed_until IS NULL OR claimed_until < now())
 ORDER BY updated_at
 LIMIT :batch
```

For each: claim (MA-143 FR-2, owner `sweep:{host}:{pid}`, predicate
`status = 'IN_PROGRESS'`); skip if the claim is lost; re-read; skip (and release) if no
longer `IN_PROGRESS`.

### FR-2: "Charge not yet taken" and the cut-off (PD-1)

A checkout is **PD-1 eligible** when all hold:

- `step = STARTED`, it has an `order_id`, and that order is `CREATED` (any
  `amount_paise`, including `0`). A ₹0 order is inserted `CREATED` at step `STARTED`
  like any other and is only confirmed later, inside `_charge` (MA-136); until then it
  can be cancelled like any other unpaid order;
- the delivery can no longer be met: `now_IST ≥ (delivery_date − 1 day) at
  ORDER_CHECKOUT_CUTOFF_HOUR_IST:00` (the rule `_delivery_date` already uses to choose
  the date, so a checkout always starts before its own cut-off).

For an eligible checkout:

- **`amount_paise = 0`:** no Wallet call (`_charge` never debits a ₹0 order, so there is
  nothing to fence). Cancel as in the `Voided` row below.
- **`amount_paise > 0`:** close without charge through the Wallet void (MA-143 FR-4a,
  `HttpWalletClient.void_debit(user_id, order_id)`, MA-142):

| Void result | Action |
|-------------|--------|
| `Voided` (never debited, and now never can be) | **Cancel** in one transaction: order → `CANCELLED`, `failure_reason = 'CUTOFF_PASSED'`, `charge_state = 'NOT_CHARGED'`; checkout → `status = CANCELLED`, `result = {error: {errorCode: "CHECKOUT_CANCELLED", httpStatus: 409, message, details: {checkoutId}}}`; lease released. **No debit, no outbox event, cart untouched.** Metric `cancelled` |
| `DebitLookup` (`ALREADY_DEBITED`: a lost-response debit did land) | The customer **was** charged. Do not cancel; resume normally (FR-3). Wallet replays `DEBITED`, the order is `CONFIRMED`, the checkout completes. Metric `charged_after_cutoff` (ops review the delivery date) |
| `WalletUnavailableError` | Attempt failed (MA-143 FR-3). Never cancel on an unknown answer |

`message` for `CHECKOUT_CANCELLED`: *"This order was cancelled because it couldn't be
completed in time. You weren't charged. Review your cart and confirm again."*

The void is what makes cancelling safe while an earlier request's debit may still be
running inside Wallet (its client timed out, or its request released the lease on
`CHECKOUT_INCOMPLETE`, FR-6): the void and that debit serialize on the wallet row lock,
so either the void returns `ALREADY_DEBITED` (and we resume) or the late debit is refused
with `DEBIT_VOIDED` (FR-3). No timing assumption about the Order client's timeout is made.

### FR-3: Resume

A claimed checkout that is not cancelled by FR-2 is resumed with the existing
`CheckoutService._run(checkout, correlation_id, known_balance_paise=None)`. Every step
keeps its current idempotency: debit on `order:{orderId}`, subscriptions on the line's
key (FR-4a: the carried key if one exists, otherwise `checkout:{id}:{lineId}`), cart
clear with `ifVersion` and the one-retry rule.

| `_run` outcome | Result | Metric |
|----------------|--------|--------|
| Returns | `COMPLETED`, result stored (existing) | `completed` |
| `InsufficientBalanceError` / `WalletNotActiveError` | `PAYMENT_FAILED` (existing `_fail_checkout`) | `payment_failed` |
| `CheckoutIncompleteError` | Attempt failed → FR-4 | `failed_attempt` |
| `DebitVoidedError` (from `_charge`) | Another worker voided this order and is cancelling it (or crashed before it could). Re-read the order: `CANCELLED` → store/return the FR-2 cancelled result; still `CREATED` → apply FR-2 again (the cut-off has passed for good, so the repeated void returns `Voided`) | `cancelled` |

The same `DebitVoidedError` handling applies on the customer path: a request whose debit
is refused because the sweep or a takeover voided its order returns
`409 CHECKOUT_CANCELLED`.

The lease is renewed (MA-143 FR-2) before the debit, before each subscription create
and before the cart clear, so a checkout with many subscription lines never outlives its
lease. A failed renewal stops the run at once (another worker owns it now). The lease is
released with every terminal transition (the checkout `update_checkout` that sets a
terminal status also clears `claimed_until`/`claim_owner`).

### FR-4: Budget exhausted

When a failed attempt brings `sweep_attempts` to `ORDER_SWEEP_MAX_ATTEMPTS`, the outcome
depends on how far the checkout got:

| Stored `step` at exhaustion | Outcome |
|-----------------------------|---------|
| `STARTED` (charge outcome unknown: Wallet unreachable) | Checkout → `NEEDS_ATTENTION`, `last_sweep_error` kept; its order (still `CREATED`) → `NEEDS_ATTENTION`, `failure_reason = 'SWEEP_EXHAUSTED'`, `charge_state = 'UNKNOWN'`. The MA-143 settle pass (FR-4b) later voids it or alarms if it was charged. Metric `escalated{reason=CHARGE_UNKNOWN}` |
| `PAID` (paid; subscriptions failing) | **PD-2**: every subscription line without a recorded result is recorded `{lineId, status: FAILED, reason: "SUBSCRIPTION_UNAVAILABLE"}`, and its key is **carried** (FR-4a); step → `SUBSCRIPTIONS_DONE`; then the cart clear runs once in this same attempt (it removes only the paid one-time lines and the `CREATED` subscription lines, so the failed lines stay in the cart). Clear succeeds → `COMPLETED` with the normal result. Metric `completed_partial` + `escalated{reason=SUBSCRIPTIONS_ABANDONED}` (alarm; the customer lost nothing, but ops should know). Clear fails → as the next row |
| `SUBSCRIPTIONS_DONE` (cart clear failing) | Checkout → `NEEDS_ATTENTION`, `last_sweep_error = CART_CLEAR_FAILED`. The order stays `CONFIRMED`; created subscriptions stand. Metric `escalated{reason=CART_CLEAR_FAILED}` |

Leaving `IN_PROGRESS` releases `checkouts_one_live_per_user` (the index is partial on
`status = 'IN_PROGRESS'`), so the customer can check out again.

### FR-4a: Carried subscription keys (PD-2)

A PD-2 line failed on timeouts or 5xx, so its subscription **may already exist** (the
create landed and only the response was lost). Subscription Service stores every
`(userId, idempotencyKey)` for good and replays the existing subscription on a repeat
(MA-131), so the fix is to repeat the same key, not to guess.

- **Carry:** in the PD-2 transaction, for each line recorded `SUBSCRIPTION_UNAVAILABLE`,
  `INSERT INTO carried_subscription_keys (user_id, cart_line_id, idempotency_key,
  checkout_id) … ON CONFLICT (user_id, cart_line_id) DO NOTHING` with the key that line
  used (MA-143 §7 table). `cart_line_id` is the checkout line's `lineId`, which is the
  cart item's own `id`, so it is the same while the line stays in the cart.
- **Reuse:** when any later checkout (a new one, a resume, or a sweep run) creates the
  subscription for a line, it uses the carried key for `(userId, lineId)` if one exists,
  instead of `checkout:{id}:{lineId}`. If the earlier create landed, Subscription replays
  it and the line is `CREATED` with that subscription; if not, it is created now, once.
- **Forget:** the carried row is deleted in the same update that records a definitive
  result for that line (`CREATED`, or `FAILED` from a `SubscriptionRejectedError`). A
  line that fails transiently again keeps its row (the `DO NOTHING` keeps the original key).
- The carried key is internal: it is never returned in the API result.
- **Changed line:** if the customer edits the line (quantity, slot, start date) before
  checking out again, the replayed subscription has the old details. The line result is
  still `CREATED` with the existing `subscriptionId`, the line is removed from the cart as
  usual, and the checkout logs `checkout.subscription_replayed_with_changes`. The
  customer changes the existing subscription from the subscriptions screen. This is
  preferred over creating a second subscription.

### FR-5: Replay of the new terminal statuses

`POST /orders/checkout` with the key of a checkout in:

| Status | Response |
|--------|----------|
| `CANCELLED` | The stored `409 CHECKOUT_CANCELLED` (FR-2). No side effects |
| `NEEDS_ATTENTION` | `409 CHECKOUT_NEEDS_ATTENTION`, `details: {checkoutId}`, message *"We couldn't finish this order automatically. Our team has been alerted, and you won't be charged twice."* No side effects |
| `COMPLETED` via PD-2 | The stored `200` result (existing), with the failed lines listed under `subscriptions` |

Both new codes clear the app's pending key (they are not `CHECKOUT_IN_PROGRESS` or
`CHECKOUT_INCOMPLETE`), so the next Confirm starts a fresh checkout.

### FR-6: Customer path honours the lease and PD-1

`CheckoutService.checkout()` changes:

1. **New checkout:** `start_checkout` inserts the row with `claim_owner = request:{uuid}`,
   `claimed_until = now() + lease`. The lease is released when the request ends:
   terminal status, or on `CHECKOUT_INCOMPLETE` (so the sweep can take it after the
   stale threshold). Releasing it while this request's debit may still be running inside
   Wallet is safe: whoever takes the checkout next only cancels through the void (FR-2).
2. **Same key, `IN_PROGRESS`:** claim first. Lost (the sweep or another request holds it)
   → `409 CHECKOUT_IN_PROGRESS`, `details: {checkoutId, retryAfterSeconds}` where
   `retryAfterSeconds = ceil(claimed_until − now)`, minimum 1. Won → if PD-1 eligible,
   apply FR-2 (the customer gets `409 CHECKOUT_CANCELLED` and re-confirms at a valid
   date); otherwise resume as today.
3. **Different key, live checkout** (`_settle_live_checkout`): keep the existing 2-minute
   "busy" rule, and additionally require the claim. Claim lost → `409
   CHECKOUT_IN_PROGRESS` (as above). Won → if PD-1 eligible, cancel it per FR-2 and
   continue with this request as a new checkout; otherwise resume it as today. This
   closes the "two workers on one checkout" gap.
4. Customer requests never change `sweep_attempts`.

`retryAfterSeconds` is additive in `details`; the app already retries
`CHECKOUT_IN_PROGRESS` with the same key (MA-137).

### FR-7: Read APIs and events

- `GET /orders/me` / `GET /orders/{id}` show `CANCELLED` and `NEEDS_ATTENTION` like any
  status.
- No new event types. A `CANCELLED` order never emitted `OrderConfirmed` and was voided
  in Wallet, so there is nothing for consumers to undo. `OrderCancelled` (MA-97) remains
  reserved for customer cancellation (MA-32). A `NEEDS_ATTENTION` order with an unknown
  charge is settled and, if charged, alarmed by MA-143 FR-4b.

## 6. Technical Design

**Changes**

| Component | Change |
|-----------|--------|
| `domain/sweep_service.py` (MA-143) | `sweep_checkouts()`: FR-1 → FR-2 → FR-3 → FR-4 |
| `domain/checkout_service.py` | `_cancel_if_cutoff_passed(checkout)` (FR-2, shared by the sweep and FR-6; ₹0 branch skips Wallet); `_charge` maps `DebitVoidedError` (FR-3); `_start_subscriptions` picks the carried key (FR-4a); lease on insert/resume/takeover; `finish_partial(checkout)` for PD-2; replay branches for FR-5 |
| `domain/checkout_models.py` | `CheckoutStatus.CANCELLED`, `CheckoutStatus.NEEDS_ATTENTION`; `OrderStatus.CANCELLED` |
| `domain/exceptions.py` | `CheckoutCancelledError` (409 `CHECKOUT_CANCELLED`), `CheckoutNeedsAttentionError` (409 `CHECKOUT_NEEDS_ATTENTION`); `CheckoutInProgressError` gains `retryAfterSeconds` |
| `adapters/order_repository.py` | `list_stale_checkouts`, `claim_checkout`, `release_checkout`, `record_checkout_sweep_failure`, `cancel_checkout_and_order` (one transaction); `get_carried_keys(user_id)`, carry/forget inside the existing `update_checkout` transactions |
| `adapters/wallet_client_adapter.py` | `void_debit`, `DebitVoidedError` (MA-142 FR-6) |

**Decision flow (sweep, one checkout)**

```
claim ─▶ lost: skip
      └▶ won ─▶ PD-1 eligible? ─ yes ─▶ amount 0? ─ yes ─▶ CANCELLED (order + checkout), release
                     │                           └ no ──▶ Wallet POST /debits/{orderId}/void
                     │                                     ├ VOIDED          ─▶ CANCELLED (order + checkout), release
                     │                                     ├ ALREADY_DEBITED ─▶ _run (debit replays) ─▶ COMPLETED [charged_after_cutoff]
                     │                                     └ down            ─▶ attempt+1 (→ FR-4 at max), release
                     └ no ──▶ _run
                              ├ ok           ─▶ COMPLETED
                              ├ 402/403      ─▶ PAYMENT_FAILED
                              ├ DEBIT_VOIDED ─▶ re-read; CANCELLED result (FR-3)
                              └ INCOMPLETE   ─▶ attempt+1; at max: STARTED→NEEDS_ATTENTION (charge UNKNOWN),
                                                PAID→PD-2 (complete, lines FAILED, keys carried),
                                                SUBSCRIPTIONS_DONE→NEEDS_ATTENTION
```

## 7. Data Considerations

- Uses the `checkouts` lease/attempt columns, `orders.charge_state`, the
  `carried_subscription_keys` table and the `checkouts_sweep_in_progress` index added by
  MA-143's `0003_sweep.sql`. No further migration.
- `checkouts.status` gains `CANCELLED`, `NEEDS_ATTENTION` (`VARCHAR(16)`, no CHECK
  constraint). `orders.status` gains `CANCELLED`. `orders.failure_reason` gains
  `CUTOFF_PASSED`, `SWEEP_EXHAUSTED`.
- `subscription_results` entries may carry `reason: "SUBSCRIPTION_UNAVAILABLE"` (PD-2).
- A carried key row lives until its line gets a definitive result. A line the customer
  deletes from the cart leaves a harmless orphan row (keyed by a cart line id that no
  longer exists); no clean-up job is needed at this volume.
- The `orders_source_shape` constraint is unaffected.

| Counterparty | Contract | Failure behaviour |
|--------------|----------|-------------------|

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Abandoned after `PAID`, Subscription back up | Sweep resumes: subscriptions created with their keys, cart cleared, `COMPLETED`, one debit |
| Abandoned at `STARTED` (Wallet was down), date still valid, Wallet back | Sweep resumes: charged exactly once, completes |
| Abandoned at `STARTED`, cut-off passed, never debited | Void → `CANCELLED`, no charge, cart untouched |
| Abandoned at `STARTED`, cut-off passed, lost-response debit landed | Void → `ALREADY_DEBITED`; not cancelled; completes; `charged_after_cutoff` metric for ops |
| Same-key retry after the first request returned `CHECKOUT_INCOMPLETE` while its debit is still running inside Wallet | Retry claims, is PD-1 eligible, voids: either the void sees the debit (resume, one charge) or the late debit is refused `DEBIT_VOIDED` (order cancelled, no charge). Never charged-and-cancelled |
| Customer retries (same key) while the sweep holds the lease | `409 CHECKOUT_IN_PROGRESS` + `retryAfterSeconds`; app retries; then sees the terminal result |
| Customer confirms with a new key while the sweep holds the old checkout | `409 CHECKOUT_IN_PROGRESS` until the lease is released, then a normal new checkout |
| Customer's own retry reaches a `STARTED` checkout after the cut-off | `409 CHECKOUT_CANCELLED` (PD-1 on the customer path); the next Confirm re-validates at a valid date |
| Sweep dies mid-run | Lease expires; next run resumes; idempotency keeps one debit / one subscription per line |
| Sweep dies after the void, before cancelling | Next run: still eligible, void again → `Voided` → cancelled |
| Run outlives its lease (many subscription lines, slow dependency) | Renewal before each call keeps it; if a renewal fails, the run stops and the new owner continues |
| Subscription down for the whole budget after payment | PD-2: `COMPLETED`, failed lines stay in the cart with their keys carried, alarm |
| PD-2 line whose create actually landed, then the customer checks out again | The new checkout reuses the carried key → Subscription replays the existing subscription → line `CREATED`, removed from the cart; no second subscription |
| Cart down for the whole budget after payment | `NEEDS_ATTENTION(CART_CLEAR_FAILED)`, alarm; the lock is released. Risk: the paid lines are still in the cart (§11) |
| Wallet down for the whole budget at `STARTED` | Checkout and order `NEEDS_ATTENTION`, `charge_state = UNKNOWN`; MA-143 FR-4b settles it later |
| ₹0 one-time order (inserted `CREATED` at step `STARTED`; confirmed in `_charge` without Wallet) | Before the cut-off: resumes, `_charge` confirms it, completes. After the cut-off: PD-1 eligible; cancelled with no Wallet call, so it is never confirmed for a date that can't be met |
| ₹0 order confirmed by `_charge`, crash before the step moved to `PAID` | Order is `CONFIRMED`, so not PD-1 eligible; resumes (`_charge` sees `CONFIRMED` and skips) |
| Subscription-only checkout (no order) | Not PD-1 eligible; resumes at subscriptions |

## 10. Testing Strategy

- **Unit (`SweepService.sweep_checkouts`, fakes for every port):**
  - each FR-3 outcome from each step (`STARTED`, `PAID`, `SUBSCRIPTIONS_DONE`);
  - PD-1: eligible + void `Voided` → both records `CANCELLED`, **zero** debit calls, no
    outbox row, no cart call; eligible + void `ALREADY_DEBITED` → resumed, one debit call
    (replay), `COMPLETED`; eligible + void unavailable → attempt+1, nothing cancelled;
  - ₹0: before the cut-off → `CONFIRMED` + `COMPLETED`, no Wallet call; after the
    cut-off → `CANCELLED`, **no** Wallet call, **no** `OrderConfirmed` outbox row (the
    regression test for the PR #25 finding);
  - `DEBIT_VOIDED` from `_charge` → cancelled result, one outbox row fewer than a success;
  - cut-off boundary: 19:59:59 IST the day before delivery → not eligible (charged);
    20:00:00 → eligible;
  - FR-4 per step: `STARTED` → `NEEDS_ATTENTION` (checkout + order, `charge_state =
    UNKNOWN`); `PAID` → PD-2 `COMPLETED` with `SUBSCRIPTION_UNAVAILABLE` lines left in the
    cart and one carried key per failed line; `SUBSCRIPTIONS_DONE` →
    `NEEDS_ATTENTION(CART_CLEAR_FAILED)`;
  - claim lost → skipped with no dependency calls.
- **Unit (`CheckoutService`, customer path):** same-key resume blocked by a lease → 409
  with `retryAfterSeconds`; takeover blocked by a lease → 409; takeover of a PD-1
  eligible checkout → it is voided and cancelled and the new request proceeds; replay of
  `CANCELLED` / `NEEDS_ATTENTION` → the FR-5 errors with no side effects; a fresh
  checkout's lease is released on `CHECKOUT_INCOMPLETE`.
- **Carried keys (FR-4a):** PD-2 carries `checkout:{A}:{line}`; the next checkout B of the
  same cart line calls Subscription with `checkout:{A}:{line}`, not `checkout:{B}:{line}`;
  the stub replays → one subscription in total, line cleared, carried row deleted; a
  rejected create deletes the row; a transient failure in B keeps A's key; an edited line
  → replayed subscription kept, `subscription_replayed_with_changes` logged.
- **Race (money path):** first request's debit blocked inside the Wallet stub, first
  request returns `CHECKOUT_INCOMPLETE` and releases the lease, cut-off passes, same-key
  retry voids → with the stub honouring MA-142's lock semantics, exactly one of
  {completed with one charge, cancelled with the debit refused}. Run both orderings.
- **Repository:** `cancel_checkout_and_order` is atomic (fault injected between the two
  updates → neither applied); leaving `IN_PROGRESS` frees the partial unique index (a
  second checkout for the user inserts); carry is idempotent on `(user_id, cart_line_id)`.
- **Integration (TestClient + stubbed Wallet/Subscription/Cart):**
  - Ticket AC 1: abandon after `PAID` → `run_once()` → `COMPLETED`, subscriptions
    created, cart cleared, one debit;
  - Ticket AC 2: abandon at `STARTED` with Wallet down → Wallet restored → `run_once()` →
    exactly one debit;
  - Ticket AC 3: after completion/cancellation/escalation, a new checkout for the same
    user succeeds;
  - Ticket AC 6: a customer same-key retry racing the sweep (threads, blocking stubs) →
    one debit, one subscription per line;
  - Ticket AC 7: failing dependency for `max_attempts` runs → escalated + metric.
- **Contract:** `CHECKOUT_CANCELLED` / `CHECKOUT_NEEDS_ATTENTION` bodies use the standard
  error envelope; `CHECKOUT_IN_PROGRESS.details.retryAfterSeconds` is an integer ≥ 1;
  carried keys never appear in a response.
- **App regression (MA-137):** a widget/bloc test that an unknown 409 code clears the
  pending key and shows the message (confirms no app change is needed).

## 11. Risks and Trade-offs

- **`NEEDS_ATTENTION(CART_CLEAR_FAILED)` leaves paid lines in the cart.** The customer
  could buy them again once Cart recovers. It needs Cart down for the whole budget
  (≈ 30 min), and Cart being down also blocks new checkouts during that window. Ops are
  alarmed and can clear the cart. Accepted over retrying for ever.
- **`charged_after_cutoff`:** a lost-response debit discovered after the cut-off means a
  paid order whose delivery date may not be met. It is completed (never silently
  refunded, since refunds don't exist) and surfaced to ops through its alarm.
- **Carried keys keep the old details on an edited line.** Replaying the existing
  subscription is preferred over a duplicate; the customer edits it afterwards. Keying
  the subscription on cart line content instead was rejected: Subscription replays by key
  regardless of payload, so a content-derived key would create a duplicate on any edit.
- **PD-1 on the customer path** changes the as-built takeover: a late takeover of an
  uncharged checkout now cancels it instead of charging it. This is deliberate: the
  customer re-confirms against the current cart and a valid date.
- **Lease on every request** adds one conditional `UPDATE` per checkout request.
  Negligible next to the HTTP calls.
- **Holding the lease until Wallet's worst-case transaction time instead of voiding** was
  considered for the same-key race and rejected: it is a timing assumption about another
  service, and it would block the customer's retry for that long.
- **Alternative considered:** discard uncharged `STARTED` checkouts immediately (MA-136
  as specified). Rejected: without the Wallet void that isn't provably safe, and
  Product chose to keep valid-date checkouts (they are charged when resumed).
