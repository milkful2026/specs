## 2. Problem Statement

`OrderService.materialize` (MA-132) inserts a subscription order as `CREATED` and then
debits the wallet outside any transaction. If the process crashes, or Wallet stays down
until `order-events-q` moves the `SubscriptionOrderDue` message to its DLQ (5 receives,
about 2–3 minutes), the order stays `CREATED` for ever: the delivery is never paid for or
confirmed, and nobody is told. MA-132 §11 deferred the fix.

MA-138 also needs a checkout sweep (MA-144). Both need the same machinery: a scheduled
loop, a way to claim a record so two workers never run it at once, an attempt budget, a
terminal "operator must look" state, a way to prove an order was never charged before
closing it, and metrics.

Expected outcome: a background sweep in Order Service that (a) provides that shared
machinery and (b) finishes or safely closes every stuck subscription order, with exactly
one debit and exactly one outbox event, and never leaves a charged order unreported.

## 3. Scope

### In scope

- The sweep loop: an in-process daemon thread in Order Service (decision D-1, MA-138).
- Migration `0003_sweep.sql`: lease, attempt, error and charge-state columns on `orders`
  and `checkouts`; the carried-over subscription keys table used by MA-144; sweep indexes.
- Lease helper (claim / release) used by the sweep **and** by the SQS resume path.
- Attempt budget and escalation to a new terminal order status `NEEDS_ATTENTION`.
- **Close without charge** (FR-4a): every move of an unpaid order to a closed status goes
  through the Wallet void (MA-142); used here and by MA-144.
- **Charge settle pass** (FR-4b): escalated orders whose charge is unknown are resolved
  against Wallet later and a charged one is alarmed.
- Recovery of `SUBSCRIPTION` orders stuck `CREATED`.
- Metrics, structured logs, alarm definition, health reporting.
- local-dev wiring (short thresholds in `docker-compose.yml`).

### Out of scope

- Checkout recovery, the `CANCELLED` statuses, and the customer checkout path's use of
  the lease — all MA-144 (it reuses this spec's loop, lease, budget, FR-4a and FR-4b).
- The Wallet void and lookup endpoints themselves — MA-142.
- An operator UI or API for `NEEDS_ATTENTION` records (Admin stories MA-43/MA-46).
- Refunds, and customer notifications (no Notification Service yet).
- Re-driving messages out of the DLQ (the sweep makes that unnecessary for this flow).

## 4. Functional Requirements

### FR-1: Sweep loop

- `main.py` starts a daemon thread `order-sweep` next to the existing consumer thread.
- Each **run**: generate one `correlationId`, run the subscription-order pass (FR-4),
  the checkout pass (MA-144; a no-op until MA-144 lands), then the charge settle pass
  (FR-4b), then sleep `ORDER_SWEEP_INTERVAL_SECONDS`.
- An exception inside one record never stops the run (it is logged and counted; the
  record's attempt is recorded per FR-3). An exception escaping a whole run is logged
  and the loop continues after the interval.
- If the thread dies anyway, it sets `sweep_health.alive = False` (same `ConsumerHealth`
  pattern as the consumer), which fails `/healthz`, and logs at `CRITICAL`.
- `ORDER_SWEEP_ENABLED=false` skips starting the thread (tests, and an operational
  kill switch).

### FR-2: Lease (claim / release)

A record is worked on only by the holder of its lease.

- **Claim** is one conditional update, true only if exactly one row changed:
  ```sql
  UPDATE <table>
     SET claimed_until = now() + :lease_seconds, claim_owner = :owner
   WHERE id = :id
     AND <expected status predicate>
     AND (claimed_until IS NULL OR claimed_until < now())
  ```
- **Owner** strings: `sweep:{hostname}:{pid}` for the sweep, `sqs:{messageId}` for the
  consumer (and `request:{uuid}` for the checkout API in MA-144).
- **Release**: `SET claimed_until = NULL, claim_owner = NULL WHERE id = :id AND
  claim_owner = :owner`, in the same transaction as the terminal status change when
  there is one, otherwise on its own.
- **Renew**: before every dependency call in a long record run, the holder extends its
  own lease: `SET claimed_until = now() + :lease_seconds WHERE id = :id AND claim_owner
  = :owner`. If 0 rows change, the lease was lost (it expired and someone else claimed
  it): the holder stops immediately without writing anything further.
- A lease that is never released (holder crashed) simply expires after
  `ORDER_SWEEP_LEASE_SECONDS`; the next claimant takes it over.
- No DB transaction is held open across an HTTP call. The lease is what spans the call.
- The lease keeps Order Service workers apart. It does **not** bound a debit that an
  earlier holder started and whose response was lost: that debit may still commit inside
  Wallet after the holder gave up. Only the void (FR-4a) rules that out.

### FR-3: Attempt budget and escalation

- A sweep attempt on a record **fails** when it ends without reaching a terminal status
  (e.g. Wallet unreachable after the client's retries). On failure, in one update:
  `sweep_attempts = sweep_attempts + 1`, `last_sweep_error = <error code / class>`,
  lease released.
- When a failure brings `sweep_attempts` to `ORDER_SWEEP_MAX_ATTEMPTS`, the record is
  **escalated** in the same update: `status = NEEDS_ATTENTION`, `failure_reason =
  'SWEEP_EXHAUSTED'`, and the `escalated` metric is emitted. An order escalated this way
  **without** a successful void gets `charge_state = 'UNKNOWN'` and is picked up by FR-4b.
- Only sweep attempts count. Customer retries and SQS redeliveries do not change
  `sweep_attempts`.

### FR-4: Stuck subscription orders

**Selection** (each run, oldest first, at most `ORDER_SWEEP_BATCH_SIZE`):

```sql
SELECT id FROM orders
 WHERE source = 'SUBSCRIPTION' AND status = 'CREATED'
   AND created_at < now() - :subscription_order_stale_seconds
   AND (claimed_until IS NULL OR claimed_until < now())
 ORDER BY created_at
 LIMIT :batch
```

For each selected order: claim it (FR-2; skip silently if the claim is lost), re-read
it, and continue only if it is still `CREATED`.

1. **Charge deadline (D-5, amended 2026-09-29 — see §12):** a subscription order is
   created by the Daily Run (MA-131) at `SUBSCRIPTION_CUTOFF_HOUR_IST` (20:00) on the day
   before delivery, so the checkout cut-off (the same 20:00) has already passed for every
   subscription order and cannot be its deadline. A subscription order can still be
   charged while
   `now_IST < (delivery_date − 1 day) at ORDER_SUBSCRIPTION_CHARGE_DEADLINE_HOUR_IST:00`
   (default 23:00, the latest time a charged order still makes the next morning's
   dispatch list). Startup rejects a deadline hour ≤ `SUBSCRIPTION_CUTOFF_HOUR_IST`.
2. **Before the deadline:** resume at the debit with the existing
   `OrderService._debit_and_finalize(order, correlation_id)`:
   - `DEBITED` → `CONFIRMED` + `OrderConfirmed` outbox row (existing `mark_confirmed`).
     If Wallet reports a replay, the order was already charged by the crashed attempt;
     the outcome and the event are the same, so there is still exactly one debit and one event.
   - `INSUFFICIENT_BALANCE` / `WALLET_NOT_ACTIVE` → `PAYMENT_FAILED` +
     `OrderPaymentFailed` outbox row (existing `_fail_payment`).
   - `WalletUnavailableError` → attempt failed (FR-3).
   - `DebitVoidedError` → another worker already closed this order (FR-4a); re-read,
     release, skip.
3. **At or after the deadline:** close without charge (FR-4a) with
   `failure_reason = 'CUTOFF_PASSED'`.
4. Every terminal transition releases the lease in the same transaction (the existing
   `mark_confirmed` / `mark_payment_failed` repository methods gain the lease-release
   columns in their `UPDATE`).

### FR-4a: Close without charge (shared with MA-144)

An unpaid order is moved to a closed status (`NEEDS_ATTENTION` here, `CANCELLED` in
MA-144) only after Wallet has confirmed it can never be charged:

| `HttpWalletClient.void_debit(user_id, order_id)` (MA-142) | Action |
|------------------------------------------------------------|--------|
| `Voided` | Apply the closed status with `charge_state = 'NOT_CHARGED'`, release the lease, emit `escalated{reason}`. No debit can ever land for this order. No outbox event |
| `DebitLookup` (`ALREADY_DEBITED`: a crashed or lost-response debit did land) | The customer **was** charged. Do not close: resume via `_debit_and_finalize` (the debit replays) → `CONFIRMED` + `OrderConfirmed`. Emit `charged_after_cutoff` (ops review whether the delivery can still be met) |
| `WalletUnavailableError` | Attempt failed (FR-3). Never close on an unknown answer. If this attempt exhausts the budget, the order is escalated with `charge_state = 'UNKNOWN'` (FR-4b) |

If the holder crashes after the void but before the status update, the order is still
`CREATED`; the deadline has passed for good, so the next run takes step 3 again and the
repeated void returns `Voided`.

### FR-4b: Charge settle pass

Each run, after the other passes, at most `ORDER_SWEEP_BATCH_SIZE`:

```sql
SELECT id FROM orders
 WHERE status = 'NEEDS_ATTENTION' AND charge_state = 'UNKNOWN'
   AND (claimed_until IS NULL OR claimed_until < now())
 ORDER BY created_at
 LIMIT :batch
```

For each: claim, then `void_debit`:

- `Voided` → `charge_state = 'NOT_CHARGED'`, metric `settled_not_charged`.
- `DebitLookup` → `charge_state = 'CHARGED'`, metric `escalated_charged` (**alarm**: the
  customer paid for an order that is not confirmed; ops must deliver or refund by hand).
  The log line carries `orderId`, `userId`, `amountPaise`, `debitedAt`.
- `WalletUnavailableError` → release and try again next run. No budget: the order is
  already escalated and alarmed, and this is one idempotent Wallet call per run.

`status` never changes in this pass. It exists so that no charged order ever sits in
`NEEDS_ATTENTION` without anyone being told.

### FR-5: SQS resume path honours the lease

In `materialize`, where it finds an existing `CREATED` order and resumes at the debit:

- Claim the lease with owner `sqs:{messageId}` first.
- Claim lost (the sweep holds it) → raise `OrderBusyError` (an `OrderError`, not
  terminal). The consumer already leaves `OrderError` messages unacked, so SQS redelivers
  later; by then the sweep has finished and the redelivery sees a terminal order and
  no-ops.
- Claim won → resume as today, releasing the lease with the terminal transition. On a
  `WalletUnavailableError`, release the lease (no `sweep_attempts` change) and let the
  error propagate as today.
- `DebitVoidedError` (on this path or on the first-time insert path below) → the sweep
  has closed, or is closing, this order past its deadline. Release the lease, log
  `order.debit_refused_voided`, ack the message. The sweep finishes the close.
- The first-time insert path (no existing row) is unchanged: a brand-new `CREATED` row
  is not visible to the sweep until it is `SUBSCRIPTION_ORDER_STALE_SECONDS` old.
- The existing no-op for terminal orders now also covers `NEEDS_ATTENTION`: a late
  redelivery for an escalated order is acked and logged, never charged.

### FR-6: Read APIs

`GET /orders/me` and `GET /orders/{id}` return `NEEDS_ATTENTION` like any other status
(the API enum widens; no new fields; `charge_state` is internal). The customer sees the
order as not confirmed.

### FR-7: Configuration

| Env var | Default (prod) | local-dev compose |
|---------|----------------|-------------------|
| `ORDER_SWEEP_ENABLED` | `true` | `true` |
| `ORDER_SWEEP_INTERVAL_SECONDS` | `300` | `15` |
| `ORDER_SUBSCRIPTION_ORDER_STALE_SECONDS` | `900` | `60` |
| `ORDER_SUBSCRIPTION_CHARGE_DEADLINE_HOUR_IST` | `23` | `23` |
| `ORDER_CHECKOUT_STALE_SECONDS` (used by MA-144) | `600` | `60` |
| `ORDER_SWEEP_MAX_ATTEMPTS` | `6` | `3` |
| `ORDER_SWEEP_LEASE_SECONDS` | `120` | `60` |
| `ORDER_SWEEP_BATCH_SIZE` | `50` | `50` |

`ORDER_SWEEP_LEASE_SECONDS` must exceed the longest single **dependency call** (a debit
or one subscription create with retries is about 12 s), because the holder renews the
lease before each call (FR-2). At startup, a value below 60 is rejected.

With the defaults, a subscription order created at 20:00 has 3 hours to be recovered;
stale (15 min) + `max_attempts` × interval (30 min) fits well inside that.

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Correctness | Exactly one debit and at most one outbox event per order, under any interleaving of sweep, SQS redelivery, late in-flight debits and multiple tasks; no order is closed as uncharged unless Wallet voided it |
| Latency of recovery | A stuck subscription order is resolved within `stale + interval` (≈ 20 min prod) once Wallet is reachable |
| Load | ≤ `batch` Wallet calls per run per pass; sweep queries hit partial indexes only |
| Reliability | The thread survives per-record and per-run exceptions; death is visible through `/healthz` |
| Observability | Metrics and alarm per FR in §6 |
| Security | No new endpoints; uses the existing SigV4 Wallet client |

## 6. Technical Design

**Components**

| Component | Responsibility |
|-----------|----------------|
| `handlers/sweep.py` | `run_forever()` / `run_once()`; builds services; per-run correlation id; metrics |
| `domain/sweep_service.py` | `SweepService.sweep_subscription_orders()`, `settle_unknown_charges()`; deadline rule; budget/escalation; `close_without_charge()` (FR-4a, also used by MA-144) |
| `adapters/order_repository.py` | `list_stale_subscription_orders`, `list_unknown_charge_orders`, `claim_order`, `release_order`, `record_order_sweep_failure`, `close_order`, `set_charge_state`; lease columns added to `mark_confirmed` / `mark_payment_failed` |
| `adapters/wallet_client_adapter.py` | `void_debit`, `DebitVoidedError` (MA-142 FR-6) |
| `domain/order_service.py` | `materialize` claims before resuming and handles `DebitVoidedError` (FR-5); `_debit_and_finalize` unchanged otherwise |
| `main.py` | starts the `order-sweep` thread; `sweep_health`; deadline-hour startup check |

**Flow (one stuck order)**

```
sweep ─ list_stale ─▶ ord_1 (CREATED, 16 min old)
      ─ claim(ord_1, sweep:host:42) ─▶ won
      ─ before deadline? ─ yes ─▶ Wallet POST /debit (order:ord_1)
      │                           ├ DEBITED ─▶ CONFIRMED + OrderConfirmed, release
      │                           ├ INSUFFICIENT/NOT_ACTIVE ─▶ PAYMENT_FAILED + OrderPaymentFailed, release
      │                           ├ DEBIT_VOIDED ─▶ already closed; release, skip
      │                           └ unreachable ─▶ attempts+1 (→ NEEDS_ATTENTION, charge UNKNOWN at max), release
      └ no ─▶ Wallet POST /debits/ord_1/void
                 ├ VOIDED ─▶ NEEDS_ATTENTION(CUTOFF_PASSED), NOT_CHARGED, release
                 ├ ALREADY_DEBITED ─▶ debit replays ─▶ CONFIRMED + OrderConfirmed  [charged_after_cutoff]
                 └ unreachable ─▶ attempts+1 (→ NEEDS_ATTENTION, charge UNKNOWN at max), release
settle ─ NEEDS_ATTENTION ∧ UNKNOWN ─▶ void ─▶ NOT_CHARGED | CHARGED [alarm] | retry next run
```

**Metrics** (structured-log metrics, as `order.confirmed` etc. today):

- `sweep.subscription_order.found`, `.resumed`, `.confirmed`, `.payment_failed`,
  `.charged_after_cutoff`, `.escalated` (dimension `reason`: `CUTOFF_PASSED` |
  `SWEEP_EXHAUSTED`), `.failed_attempt`
- `sweep.settle.settled_not_charged`, `sweep.settle.escalated_charged`
- `sweep.run_duration_ms`, `sweep.run_failed`
- Alarms (CDK, with the service's infra stack): `sweep.*.escalated` sum > 0 over 5 min →
  ops notification; `sweep.*.charged_after_cutoff` or `sweep.settle.escalated_charged`
  > 0 → ops notification (money taken, delivery at risk); `sweep.run_failed` ≥ 3 in 15 min.

**Logs:** every record decision logs `orderId`, `attempt`, `outcome`, `correlationId`,
`claimOwner`, and `chargeState` when set.

## 7. Data Considerations

Migration `0003_sweep.sql` (applies on top of `0002_checkout.sql`):

```sql
ALTER TABLE orders    ADD COLUMN sweep_attempts   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE orders    ADD COLUMN claimed_until    TIMESTAMPTZ;
ALTER TABLE orders    ADD COLUMN claim_owner      VARCHAR(64);
ALTER TABLE orders    ADD COLUMN last_sweep_error TEXT;
ALTER TABLE orders    ADD COLUMN charge_state     VARCHAR(16);  -- NULL | NOT_CHARGED | CHARGED | UNKNOWN

ALTER TABLE checkouts ADD COLUMN sweep_attempts   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE checkouts ADD COLUMN claimed_until    TIMESTAMPTZ;
ALTER TABLE checkouts ADD COLUMN claim_owner      VARCHAR(64);
ALTER TABLE checkouts ADD COLUMN last_sweep_error TEXT;

-- MA-144 FR-4 (PD-2): subscription creates whose outcome is unknown, keyed by cart line.
CREATE TABLE carried_subscription_keys (
    user_id         VARCHAR(64)  NOT NULL,
    cart_line_id    VARCHAR(64)  NOT NULL,
    idempotency_key VARCHAR(128) NOT NULL,
    checkout_id     VARCHAR(64)  NOT NULL,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, cart_line_id)
);

CREATE INDEX orders_sweep_subscription
    ON orders (created_at) WHERE status = 'CREATED' AND source = 'SUBSCRIPTION';
CREATE INDEX orders_sweep_charge_unknown
    ON orders (created_at) WHERE status = 'NEEDS_ATTENTION' AND charge_state = 'UNKNOWN';
CREATE INDEX checkouts_sweep_in_progress
    ON checkouts (updated_at) WHERE status = 'IN_PROGRESS';
```

- Status columns are `VARCHAR(16)` with no CHECK constraint; `NEEDS_ATTENTION` (15 chars)
  fits. `OrderStatus` gains `NEEDS_ATTENTION`. `failure_reason` gains
  `CUTOFF_PASSED` and `SWEEP_EXHAUSTED`.
- `charge_state` is set only when an order is closed by the sweep (FR-4a / FR-3); every
  other order keeps `NULL`.
- The checkout columns and `carried_subscription_keys` are added here (one migration) but
  used only by MA-144.
- Existing rows default to `sweep_attempts = 0`, no lease, `charge_state = NULL`; no backfill.
- The SQLAlchemy Core tables in `order_repository.py` must stay column-for-column
  compatible, as the `0001` header requires.

## 8. Integration Considerations

| Counterparty | Contract | Failure behaviour |
|--------------|----------|-------------------|
| Wallet (MA-130, MA-142) | existing `POST /wallet/internal/debit` (now may return `409 DEBIT_VOIDED`); new `POST /wallet/internal/debits/{orderId}/void` | Retries in the client, then an attempt failure (FR-3); unknown void outcome → never close as uncharged |
| EventBridge | existing `OrderConfirmed` / `OrderPaymentFailed` via the outbox | Unchanged; the sweep writes the same outbox rows as `materialize` |
| SQS `order-events-q` | FR-5 lease check | Claim lost → message left unacked → later redelivery no-ops |

No new event types. A `NEEDS_ATTENTION` subscription order was never confirmed, so no
consumer ever saw it as paid. Whether it was **charged** is not assumed: it is
`NOT_CHARGED` only after a Wallet void, and an order whose charge could not be settled is
resolved by FR-4b, which alarms ops if money was taken. Ops, not an event consumer, act
on that alarm (refunds don't exist yet).

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Crash after the debit, before `mark_confirmed`, before the deadline | Sweep's debit replays → `DEBITED` → `CONFIRMED` + one event; still one debit |
| Crash after the debit, before `mark_confirmed`, found after the deadline | Void → `ALREADY_DEBITED` → debit replays → `CONFIRMED` + one event, `charged_after_cutoff` alarm |
| Lost-response debit still running inside Wallet when the sweep closes the order | Void and debit serialize on the wallet row lock (MA-142): either the void sees the debit (→ confirmed as above) or the debit is refused `DEBIT_VOIDED`. Never charged-and-closed |
| SQS redelivery and sweep reach the same order | One wins the claim; the other skips (sweep) or leaves the message unacked (SQS). One debit |
| Two Order tasks sweep at once | Claim is conditional; only one works each order |
| Sweep holder dies mid-debit | Lease expires; next run claims it; debit replays or charges once (before deadline) or void decides (after) |
| Sweep holder dies after the void, before the status update | Next run: past deadline → void again → `Voided` → closed |
| Wallet down for `max_attempts` runs | `NEEDS_ATTENTION(SWEEP_EXHAUSTED)`, `charge_state = UNKNOWN`, alarm; FR-4b settles it once Wallet is back and alarms again if it was charged |
| Order reaches the deadline while Wallet is down | Void can't run → attempt failed; at exhaustion as the row above |
| Late SQS redelivery for a `NEEDS_ATTENTION` order | Acked as a no-op; not charged (a debit attempt would be refused anyway if voided) |
| Order already terminal when re-read after the claim | Release and skip |
| Clock skew between tasks | The lease uses the DB's `now()` only, never the app clock. The deadline uses the app clock in IST; a skew of seconds only moves which branch runs, and both branches are safe |
| DB unavailable | The run fails, is logged, and the loop retries after the interval |

## 10. Testing Strategy

- **Unit (`SweepService`, fakes for the repository and Wallet):** before deadline +
  `DEBITED` → confirmed and one outbox row; `INSUFFICIENT_BALANCE` → payment failed;
  `DEBIT_VOIDED` → skipped, nothing written; Wallet unavailable → attempts+1 and lease
  released; the attempt that hits the limit → `NEEDS_ATTENTION(SWEEP_EXHAUSTED)` with
  `charge_state = UNKNOWN`; after deadline + void `Voided` →
  `NEEDS_ATTENTION(CUTOFF_PASSED)`, `NOT_CHARGED`, **no** debit call; after deadline +
  void `ALREADY_DEBITED` → one debit (replay) call, `CONFIRMED`, `charged_after_cutoff`;
  after deadline + void unavailable → attempt failed, order still `CREATED`; claim lost →
  skipped, no Wallet call; re-read terminal → skipped.
- **Settle pass:** `UNKNOWN` + `Voided` → `NOT_CHARGED`; `UNKNOWN` + `ALREADY_DEBITED` →
  `CHARGED` + `escalated_charged`; unavailable → unchanged, no attempt counted; status
  never changes.
- **Deadline boundary (IST):** an order created by the Daily Run at 20:00:00 is charged
  (not closed) — the regression test for the PR #25 finding; 22:59:59 the day before →
  charged; 23:00:00 → void path. Startup rejects deadline hour 20 with cut-off hour 20.
- **Repository (SQLite + Postgres 16 scratch DB, as MA-136):** migration applies on
  `0002`; claim succeeds once and fails for a second owner until expiry; expired lease can
  be re-claimed; release and renew by a non-owner change nothing; stale selection ignores fresh,
  terminal, `CHECKOUT` and leased rows; settle selection only returns `UNKNOWN` rows.
- **Integration (TestClient + stubbed Wallet):** insert a `CREATED` subscription order
  aged past the threshold → `run_once()` → `CONFIRMED`, exactly one debit call, exactly
  one `OrderConfirmed` outbox row.
- **Race tests:** consumer resume and sweep interleaved on the same order (threads with a
  Wallet stub that blocks) → one debit call, one event; the loser leaves the message
  unacked. A debit blocked inside the Wallet stub while the sweep voids the order past
  its deadline → exactly one of {confirmed, closed-and-debit-refused}.
- **Loop robustness:** a record that raises an unexpected exception doesn't stop the
  others; `run_forever` survives a failing run; a dead thread flips `/healthz`.
- **local-dev acceptance** (run before 23:00 IST, when the Daily Run's orders are still
  before their deadline): stop Wallet, trigger the Daily Run, wait for the DLQ, start
  Wallet → within about one local interval the order is `CONFIRMED` and the wallet is
  charged once.

## 11. Risks and Trade-offs

- **In-process thread vs EventBridge Scheduler (D-1):** chosen for no new route, IAM or
  scheduler resource, and precedent (Payment's reconcile). Cost: every task sweeps. The
  lease makes that safe and the batch size bounds it.
- **Lease column vs `SELECT … FOR UPDATE SKIP LOCKED`:** row locks would have to be held
  across the Wallet HTTP call, which the codebase forbids. The lease spans the call
  without a transaction.
- **Void before every uncharged close:** one extra Wallet write per closed order, in
  exchange for never having to guess whether a lost debit will still land.
- **Charge deadline at 23:00 IST (default):** gives the sweep 3 hours after the Daily Run.
  A later deadline recovers more orders but risks confirming orders after the dispatch
  list is built; the hour is configuration so Ops can move it.
- **Past deadline → `NEEDS_ATTENTION`, not `PAYMENT_FAILED`:** keeps "the customer lacked
  money" distinct from "we failed to process in time", so ops can see the latter.
- **Escalated orders are not retried for a charge:** an operator must act (manual confirm
  or leave). Accepted per the ticket ("never retried forever"). FR-4b only settles what
  happened; it never charges.
