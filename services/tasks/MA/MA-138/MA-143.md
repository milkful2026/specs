## 2. Problem Statement

`OrderService.materialize` (MA-132) inserts a subscription order as `CREATED` and then
debits the wallet outside any transaction. If the process crashes, or Wallet stays down
until `order-events-q` moves the `SubscriptionOrderDue` message to its DLQ (5 receives,
about 2–3 minutes), the order stays `CREATED` for ever: the delivery is never paid for or
confirmed, and nobody is told. MA-132 §11 deferred the fix.

MA-138 also needs a checkout sweep (MA-144). Both need the same machinery: a scheduled
loop, a way to claim a record so two workers never run it at once, an attempt budget, a
terminal "operator must look" state, and metrics.

Expected outcome: a background sweep in Order Service that (a) provides that shared
machinery and (b) finishes or safely closes every stuck subscription order, with exactly
one debit and exactly one outbox event.

## 3. Scope

### In scope

- The sweep loop: an in-process daemon thread in Order Service (decision D-1, MA-138).
- Migration `0003_sweep.sql`: lease, attempt and error columns on `orders` and
  `checkouts`; sweep indexes.
- Lease helper (claim / release) used by the sweep **and** by the SQS resume path.
- Attempt budget and escalation to a new terminal order status `NEEDS_ATTENTION`.
- Recovery of `SUBSCRIPTION` orders stuck `CREATED`.
- New terminal order status `NEEDS_ATTENTION` (subscription orders; also used by MA-144).
- Metrics, structured logs, alarm definition, health reporting.
- local-dev wiring (short thresholds in `docker-compose.yml`).

### Out of scope

- Checkout recovery, the `CANCELLED` statuses, and the customer checkout path's use of
  the lease — all MA-144 (it reuses this spec's loop, lease and budget).
- Wallet debit lookup — MA-142 (not needed for subscription orders; see FR-4).
- An operator UI or API for `NEEDS_ATTENTION` records (Admin stories MA-43/MA-46).
- Customer notifications (no Notification Service yet).
- Re-driving messages out of the DLQ (the sweep makes that unnecessary for this flow).

## 4. Functional Requirements

### FR-1: Sweep loop

- `main.py` starts a daemon thread `order-sweep` next to the existing consumer thread.
- Each **run**: generate one `correlationId`, run the subscription-order pass (FR-4),
  then the checkout pass (MA-144; a no-op until MA-144 lands), then sleep
  `ORDER_SWEEP_INTERVAL_SECONDS`.
- An exception inside one record never stops the run (it is logged and counted; the
  record's attempt is recorded per FR-3). An exception escaping a whole run is logged
  and the loop continues after the interval.
- If the thread dies anyway, it sets `sweep_health.alive = False` (same `ConsumerHealth`
  pattern as the consumer), which fails `/healthz`, and logs at `CRITICAL`.
- `ORDER_SWEEP_ENABLED=false` skips starting the thread (tests, and an operational
  kill switch).

### FR-2: Lease (claim / release)

A record is worked on only by the holder of its lease.

- **Claim** is one conditional update, true only if exactly one row changed:
  ```sql
  UPDATE <table>
     SET claimed_until = now() + :lease_seconds, claim_owner = :owner
   WHERE id = :id
     AND <expected status predicate>
     AND (claimed_until IS NULL OR claimed_until < now())
  ```
- **Owner** strings: `sweep:{hostname}:{pid}` for the sweep, `sqs:{messageId}` for the
  consumer (and `request:{uuid}` for the checkout API in MA-144).
- **Release**: `SET claimed_until = NULL, claim_owner = NULL WHERE id = :id AND
  claim_owner = :owner`, in the same transaction as the terminal status change when
  there is one, otherwise on its own.
- A lease that is never released (holder crashed) simply expires after
  `ORDER_SWEEP_LEASE_SECONDS`; the next claimant takes it over.
- No DB transaction is held open across an HTTP call. The lease is what spans the call.

### FR-3: Attempt budget and escalation

- A sweep attempt on a record **fails** when it ends without reaching a terminal status
  (e.g. Wallet unreachable after the client's retries). On failure, in one update:
  `sweep_attempts = sweep_attempts + 1`, `last_sweep_error = <error code / class>`,
  lease released.
- When a failure brings `sweep_attempts` to `ORDER_SWEEP_MAX_ATTEMPTS`, the record is
  **escalated** in the same update: `status = NEEDS_ATTENTION`, `failure_reason =
  'SWEEP_EXHAUSTED'`, and the `escalated` metric is emitted.
- Only sweep attempts count. Customer retries and SQS redeliveries do not change
  `sweep_attempts`.

### FR-4: Stuck subscription orders

**Selection** (each run, oldest first, at most `ORDER_SWEEP_BATCH_SIZE`):

```sql
SELECT id FROM orders
 WHERE source = 'SUBSCRIPTION' AND status = 'CREATED'
   AND created_at < now() - :subscription_order_stale_seconds
   AND (claimed_until IS NULL OR claimed_until < now())
 ORDER BY created_at
 LIMIT :batch
```

For each selected order: claim it (FR-2; skip silently if the claim is lost), re-read
it, and continue only if it is still `CREATED`.

1. **Cut-off check (D-5, approved 2026-09-28):** the delivery can no longer be scheduled
   when `now_IST ≥ (delivery_date − 1 day) at ORDER_CHECKOUT_CUTOFF_HOUR_IST:00`
   (20:00). Such an order is **not charged**: set `status = NEEDS_ATTENTION`,
   `failure_reason = 'CUTOFF_PASSED'`, release the lease, emit `escalated`. No Wallet
   call, no outbox event.
2. Otherwise resume at the debit with the existing
   `OrderService._debit_and_finalize(order, correlation_id)`, unchanged:
   - `DEBITED` → `CONFIRMED` + `OrderConfirmed` outbox row (existing `mark_confirmed`).
     If Wallet reports a replay, the order was already charged by the crashed attempt;
     the outcome and the event are the same, so there is still exactly one debit and one event.
   - `INSUFFICIENT_BALANCE` / `WALLET_NOT_ACTIVE` → `PAYMENT_FAILED` +
     `OrderPaymentFailed` outbox row (existing `_fail_payment`).
   - `WalletUnavailableError` → attempt failed (FR-3).
3. Every terminal transition releases the lease in the same transaction (the existing
   `mark_confirmed` / `mark_payment_failed` repository methods gain the lease-release
   columns in their `UPDATE`).

Why no Wallet lookup (MA-142) here: calling `debit` is always correct for a subscription
order that is still before its cut-off. Either it charges now, or it replays the earlier
charge. Nothing here needs "not charged" proven.

### FR-5: SQS resume path honours the lease

In `materialize`, where it finds an existing `CREATED` order and resumes at the debit:

- Claim the lease with owner `sqs:{messageId}` first.
- Claim lost (the sweep holds it) → raise `OrderBusyError` (an `OrderError`, not
  terminal). The consumer already leaves `OrderError` messages unacked, so SQS redelivers
  later; by then the sweep has finished and the redelivery sees a terminal order and
  no-ops.
- Claim won → resume as today, releasing the lease with the terminal transition. On a
  `WalletUnavailableError`, release the lease (no `sweep_attempts` change) and let the
  error propagate as today.
- The first-time insert path (no existing row) is unchanged: a brand-new `CREATED` row
  is not visible to the sweep until it is `SUBSCRIPTION_ORDER_STALE_SECONDS` old.
- The existing no-op for terminal orders now also covers `NEEDS_ATTENTION`: a late
  redelivery for an escalated order is acked and logged, never charged.

### FR-6: Read APIs

`GET /orders/me` and `GET /orders/{id}` return `NEEDS_ATTENTION` like any other status
(the API enum widens; no new fields). The customer sees the order as not confirmed.

### FR-7: Configuration

| Env var | Default (prod) | local-dev compose |
|---------|----------------|-------------------|
| `ORDER_SWEEP_ENABLED` | `true` | `true` |
| `ORDER_SWEEP_INTERVAL_SECONDS` | `300` | `15` |
| `ORDER_SUBSCRIPTION_ORDER_STALE_SECONDS` | `900` | `60` |
| `ORDER_CHECKOUT_STALE_SECONDS` (used by MA-144) | `600` | `60` |
| `ORDER_SWEEP_MAX_ATTEMPTS` | `6` | `3` |
| `ORDER_SWEEP_LEASE_SECONDS` | `120` | `60` |
| `ORDER_SWEEP_BATCH_SIZE` | `50` | `50` |

`ORDER_SWEEP_LEASE_SECONDS` must exceed the longest single record run (a debit with
retries is about 12 s; a checkout's subscription step is up to N × 12 s). At startup, a
value below 60 is rejected.

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Correctness | Exactly one debit and at most one outbox event per order, under any interleaving of sweep, SQS redelivery and multiple tasks |
| Latency of recovery | A stuck subscription order is resolved within `stale + interval` (≈ 20 min prod) once Wallet is reachable |
| Load | ≤ `batch` Wallet calls per run per flow; sweep queries hit partial indexes only |
| Reliability | The thread survives per-record and per-run exceptions; death is visible through `/healthz` |
| Observability | Metrics and alarm per FR in §6 |
| Security | No new endpoints; uses the existing SigV4 Wallet client |

## 6. Technical Design

**Components**

| Component | Responsibility |
|-----------|----------------|
| `handlers/sweep.py` | `run_forever()` / `run_once()`; builds services; per-run correlation id; metrics |
| `domain/sweep_service.py` | `SweepService.sweep_subscription_orders()`; cut-off rule; budget/escalation |
| `adapters/order_repository.py` | `list_stale_subscription_orders`, `claim_order`, `release_order`, `record_order_sweep_failure`; lease columns added to `mark_confirmed` / `mark_payment_failed` |
| `domain/order_service.py` | `materialize` claims before resuming (FR-5); `_debit_and_finalize` unchanged |
| `main.py` | starts the `order-sweep` thread; `sweep_health` |

**Flow (one stuck order)**

```
sweep ─ list_stale ─▶ ord_1 (CREATED, 16 min old)
      ─ claim(ord_1, sweep:host:42) ─▶ won
      ─ cut-off passed? ── yes ─▶ NEEDS_ATTENTION(CUTOFF_PASSED), release    [no Wallet call]
                        └─ no ──▶ Wallet POST /debit (order:ord_1)
                                   ├ DEBITED ─▶ CONFIRMED + OrderConfirmed, release
                                   ├ INSUFFICIENT/NOT_ACTIVE ─▶ PAYMENT_FAILED + OrderPaymentFailed, release
                                   └ unreachable ─▶ attempts+1 (→ NEEDS_ATTENTION at max), release
```

**Metrics** (structured-log metrics, as `order.confirmed` etc. today):

- `sweep.subscription_order.found`, `.resumed`, `.confirmed`, `.payment_failed`,
  `.escalated` (dimension `reason`: `CUTOFF_PASSED` | `SWEEP_EXHAUSTED`), `.failed_attempt`
- `sweep.run_duration_ms`, `sweep.run_failed`
- Alarm (CDK, with the service's infra stack): `sweep.*.escalated` sum > 0 over 5 min →
  ops notification. Alarm on `sweep.run_failed` ≥ 3 in 15 min.

**Logs:** every record decision logs `orderId`, `attempt`, `outcome`, `correlationId`,
`claimOwner`.

## 7. Data Considerations

Migration `0003_sweep.sql` (applies on top of `0002_checkout.sql`):

```sql
ALTER TABLE orders    ADD COLUMN sweep_attempts   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE orders    ADD COLUMN claimed_until    TIMESTAMPTZ;
ALTER TABLE orders    ADD COLUMN claim_owner      VARCHAR(64);
ALTER TABLE orders    ADD COLUMN last_sweep_error TEXT;

ALTER TABLE checkouts ADD COLUMN sweep_attempts   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE checkouts ADD COLUMN claimed_until    TIMESTAMPTZ;
ALTER TABLE checkouts ADD COLUMN claim_owner      VARCHAR(64);
ALTER TABLE checkouts ADD COLUMN last_sweep_error TEXT;

CREATE INDEX orders_sweep_subscription
    ON orders (created_at) WHERE status = 'CREATED' AND source = 'SUBSCRIPTION';
CREATE INDEX checkouts_sweep_in_progress
    ON checkouts (updated_at) WHERE status = 'IN_PROGRESS';
```

- Status columns are `VARCHAR(16)` with no CHECK constraint; `NEEDS_ATTENTION` (15 chars)
  fits. `OrderStatus` gains `NEEDS_ATTENTION`. `failure_reason` gains
  `CUTOFF_PASSED` and `SWEEP_EXHAUSTED`.
- The checkout columns are added here (one migration) but used only by MA-144.
- Existing rows default to `sweep_attempts = 0` and no lease; no backfill.
- The SQLAlchemy Core tables in `order_repository.py` must stay column-for-column
  compatible, as the `0001` header requires.

## 8. Integration Considerations

| Counterparty | Contract | Failure behaviour |
|--------------|----------|-------------------|
| Wallet (MA-130) | existing `POST /wallet/internal/debit` | Retries in the client, then an attempt failure (FR-3) |
| EventBridge | existing `OrderConfirmed` / `OrderPaymentFailed` via the outbox | Unchanged; the sweep writes the same outbox rows as `materialize` |
| SQS `order-events-q` | FR-5 lease check | Claim lost → message left unacked → later redelivery no-ops |

No new event types. A `NEEDS_ATTENTION` subscription order was never confirmed, so no
consumer ever saw it as paid; nothing downstream needs to be told.

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Crash after the debit, before `mark_confirmed` | Sweep's debit replays → `DEBITED` → `CONFIRMED` + one event; still one debit |
| SQS redelivery and sweep reach the same order | One wins the claim; the other skips (sweep) or leaves the message unacked (SQS). One debit |
| Two Order tasks sweep at once | Claim is conditional; only one works each order |
| Sweep holder dies mid-debit | Lease expires; next run claims it; debit replays or charges once |
| Wallet down for `max_attempts` runs | `NEEDS_ATTENTION(SWEEP_EXHAUSTED)`, alarm; never charged later by the sweep |
| Order reaches the cut-off while Wallet is down | Next run takes the cut-off branch first → `NEEDS_ATTENTION(CUTOFF_PASSED)`, not charged |
| Late SQS redelivery for a `NEEDS_ATTENTION` order | Acked as a no-op; not charged |
| Order already terminal when re-read after the claim | Release and skip |
| Clock skew between tasks | The lease uses the DB's `now()` only, never the app clock |
| DB unavailable | The run fails, is logged, and the loop retries after the interval |

## 10. Testing Strategy

- **Unit (`SweepService`, fakes for the repository and Wallet):** before cut-off + `DEBITED`
  → confirmed and one outbox row; `INSUFFICIENT_BALANCE` → payment failed; Wallet
  unavailable → attempts+1 and lease released; the attempt that hits the limit →
  `NEEDS_ATTENTION(SWEEP_EXHAUSTED)`; at/after cut-off → `NEEDS_ATTENTION(CUTOFF_PASSED)`
  with **no** Wallet call; claim lost → skipped, no Wallet call; re-read terminal → skipped.
- **Cut-off boundary (IST):** 19:59:59 the day before → charged; 20:00:00 → not charged.
- **Repository (SQLite + Postgres 16 scratch DB, as MA-136):** migration applies on
  `0002`; claim succeeds once and fails for a second owner until expiry; expired lease can
  be re-claimed; release by a non-owner does nothing; stale selection ignores fresh,
  terminal, `CHECKOUT` and leased rows.
- **Integration (TestClient + stubbed Wallet):** insert a `CREATED` subscription order
  aged past the threshold → `run_once()` → `CONFIRMED`, exactly one debit call, exactly
  one `OrderConfirmed` outbox row.
- **Race tests:** consumer resume and sweep interleaved on the same order (threads with a
  Wallet stub that blocks) → one debit call, one event; the loser leaves the message
  unacked.
- **Loop robustness:** a record that raises an unexpected exception doesn't stop the
  others; `run_forever` survives a failing run; a dead thread flips `/healthz`.
- **local-dev acceptance:** stop Wallet, trigger the Daily Run, wait for the DLQ, start
  Wallet → within about one local interval the order is `CONFIRMED` and the wallet is
  charged once.

## 11. Risks and Trade-offs

- **In-process thread vs EventBridge Scheduler (D-1):** chosen for no new route, IAM or
  scheduler resource, and precedent (Payment's reconcile). Cost: every task sweeps. The
  lease makes that safe and the batch size bounds it.
- **Lease column vs `SELECT … FOR UPDATE SKIP LOCKED`:** row locks would have to be held
  across the Wallet HTTP call, which the codebase forbids. The lease spans the call
  without a transaction.
- **Past cut-off → `NEEDS_ATTENTION`, not `PAYMENT_FAILED`:** keeps "the customer lacked
  money" distinct from "we failed to process in time", so ops can see the latter.
- **Escalated orders are not retried:** an operator must act (manual confirm or leave).
  Accepted per the ticket ("never retried forever").
