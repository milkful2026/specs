## 2. Problem Statement

Order Service debits a wallet with `POST /wallet/internal/debit`, which is idempotent on
the ledger reference `order:{orderId}`. If that call times out, Order Service cannot tell
whether the debit happened. Today the only way to find out is to call `debit` again,
which **charges the customer** if the first call never landed.

MA-144 must cancel an abandoned, uncharged checkout without taking money (Product
decision PD-1, MA-138). It can only do that safely if it can ask Wallet "was order X
debited?" without side effects.

Expected outcome: a read-only internal endpoint that answers that question from the
ledger.

## 3. Scope

### In scope

- `GET /wallet/internal/debits/{orderId}` — read-only lookup of the `ORDER_DEBIT` ledger
  entry for `ref = order:{orderId}`.
- Repository read method and service method.
- Order Service's `HttpWalletClient` gains `get_debit(order_id)` (typed client only;
  its callers are specified in MA-144).

### Out of scope

- Any write, reversal, refund or void of a debit.
- Listing a user's debits (the passbook is `GET /wallet/me/transactions`, unchanged).
- Public (JWT) exposure — this route is internal only.

## 4. Functional Requirements

### FR-1: Request

`GET /wallet/internal/debits/{orderId}`

- Internal only, under the same `/wallet/internal/*` prefix and the same service-to-service
  auth as `POST /wallet/internal/debit` (SigV4 / VPC-only in prod; not routed through the
  public API Gateway).
- `orderId`: path parameter, 1–64 characters, `[A-Za-z0-9_-]`. Anything else →
  `400 VALIDATION_ERROR`.

### FR-2: Found → `200`

Looks up the ledger entry with `ref = "order:{orderId}"`. If it exists:

```json
{
  "success": true,
  "data": {
    "orderId": "ord_…",
    "status": "DEBITED",
    "amountPaise": 10820,
    "balanceAfterPaise": 34180,
    "debitedAt": "2026-09-28T14:03:11.412Z",
    "walletId": "wal_…"
  }
}
```

- `amountPaise` is the **positive** amount debited (the ledger stores debits as negative
  `amount_paise`; the response returns its absolute value).
- `balanceAfterPaise` is the ledger entry's `balance_after_paise`.
- The same body shape is returned on every call for the same `orderId` (ledger rows are
  immutable).

### FR-3: Not found → `404`

No ledger entry for that `ref` → `404` with `errorCode: "DEBIT_NOT_FOUND"` and the
standard error envelope. This is a normal, expected answer (the order was never
charged), not an alarm condition.

### FR-4: No side effects

The endpoint never locks the wallet row, never writes, and never emits an event. It does
not check wallet status (a wallet that is no longer `ACTIVE` still reports its past debits).

### FR-5: Order Service client

`HttpWalletClient.get_debit(order_id) -> DebitLookup | None`:

- `200` → `DebitLookup(amount_paise, balance_after_paise, debited_at)`.
- `404 DEBIT_NOT_FOUND` → `None`.
- 5xx / timeout / connection error → retried with the client's existing retry policy
  (same as `debit`), then raises `WalletUnavailableError`. A caller must never treat
  "couldn't ask" as "not debited".
- Any other 4xx → raises `WalletUnavailableError` and logs at `ERROR` (a contract bug,
  never interpreted as "not debited").

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Performance | p99 < 50 ms at the service (single indexed lookup on the existing `UNIQUE(ref)` index) |
| Reliability | Read-only; safe to retry any number of times |
| Security | Internal route only; not reachable through the public API Gateway; no PII in the response beyond ids and amounts |
| Observability | Structured log per call: `orderId`, `found` (bool), `correlationId` (from `X-Correlation-Id` if sent) |
| Maintainability | Reuses the existing `ledger_entries` table and error envelope; no migration |

## 6. Technical Design

- **Handler:** `wallet/src/handlers/internal_handlers.py` — new `@router.get("/wallet/internal/debits/{orderId}")`.
- **Service:** `WalletService.get_debit_for_order(order_id) -> dict | None`.
- **Repository:** `get_ledger_entry_by_ref(ref) -> LedgerEntry | None`, a plain
  `SELECT … WHERE ref = :ref` with no `FOR UPDATE`.
- The ledger `type` must be `ORDER_DEBIT`. If a row exists for the ref with another type
  (should be impossible — refs are namespaced), return `404` and log at `ERROR`.

```
Order sweep ──GET /wallet/internal/debits/ord_123──▶ Wallet
                                                    └─ SELECT ledger_entries WHERE ref='order:ord_123'
                     ◀── 200 {DEBITED, amount, balanceAfter} | 404 DEBIT_NOT_FOUND
```

## 7. Data Considerations

- No schema change. `ledger_entries.ref` is already `UNIQUE` (so indexed).
- Read path only; no migration, no backfill.

## 8. Integration Considerations

| Counterparty | Contract | Failure behaviour |
|--------------|----------|-------------------|
| Order Service (MA-144) | This endpoint via `HttpWalletClient.get_debit` | Transport failure → `WalletUnavailableError`; the caller treats the outcome as unknown |

Contract test: the Order client's parsing is tested against the exact FR-2/FR-3 bodies.

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Order never debited | `404 DEBIT_NOT_FOUND` |
| Order debited, wallet no longer `ACTIVE` | `200` (history is still true) |
| Debit in flight in another transaction | `404` until that transaction commits. MA-144 only calls this while holding the checkout's lease, after any earlier request for it has ended (Order's client timeout is ≈ 12 s), so no debit for that order is in flight |
| Malformed `orderId` | `400 VALIDATION_ERROR` |
| DB unavailable | `503` via the existing error handler; the Order client retries and then raises `WalletUnavailableError` |
| Same call repeated | Identical response |

## 10. Testing Strategy

- **Unit (service):** found → dict with a positive amount; not found → `None`; wrong
  ledger type → `None` + error log.
- **Repository (SQLite in-memory):** returns the entry for an existing ref; `None` for an
  unknown ref; no lock taken.
- **Integration (FastAPI TestClient):** debit an order through `POST /wallet/internal/debit`,
  then `GET …/debits/{orderId}` → `200` with the matching amount and balance; unknown id →
  `404 DEBIT_NOT_FOUND`; invalid id → `400`.
- **Order client (unit, stubbed HTTP):** `200` → `DebitLookup`; `404` → `None`; `503`
  twice then `200` → `DebitLookup` (retries); `503` on every attempt →
  `WalletUnavailableError`; `400` → `WalletUnavailableError`.
- **Negative:** the endpoint is not mounted on any public/JWT router (route-table test).

## 11. Risks and Trade-offs

- **Reading "not found" as "never will be":** a `404` only means "not debited as of
  now". MA-144 makes this safe by calling it only under a lease on a checkout nobody else
  is driving, and by moving the order to `CANCELLED` in the same step, so no later debit
  can be attempted for it.
- **Alternative considered:** a "void" call that atomically blocks any future debit for
  an order id. It would be stronger, but needs a new ledger state and write path; not
  justified while the lease already rules out a concurrent debit.
