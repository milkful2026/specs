## 2. Problem Statement

Order Service debits a wallet with `POST /wallet/internal/debit`, which is idempotent on
the ledger reference `order:{orderId}`. If that call times out, Order Service cannot tell
whether the debit happened. Today the only way to find out is to call `debit` again,
which **charges the customer** if the first call never landed.

MA-143 and MA-144 must close an order without taking money (Product decision PD-1,
MA-138, and the subscription-order deadline). A read-only lookup is not enough for that:
a `404` only means "not debited **yet**". A debit whose client already timed out can
still be running inside Wallet (the Order client's ~12 s timeout does not stop Wallet's
own transaction) and commit after the lookup, charging an order that Order Service has
just cancelled.

Expected outcome: an internal **void** that atomically decides, once and for ever,
whether an order's debit exists; plus a read-only lookup for diagnostics.

## 3. Scope

### In scope

- `POST /wallet/internal/debits/{orderId}/void` — fence: after it succeeds, no debit for
  `order:{orderId}` can ever commit. If the debit already exists, it is returned instead.
- `POST /wallet/internal/debit` refuses an order that has been voided (`409 DEBIT_VOIDED`).
- `GET /wallet/internal/debits/{orderId}` — read-only lookup (ops diagnostics, tests).
- Migration: `debit_voids` table.
- Order Service's `HttpWalletClient` gains `void_debit(order_id)` and `get_debit(order_id)`,
  and `debit` raises `DebitVoidedError` on `409 DEBIT_VOIDED` (typed client only; its
  callers are specified in MA-143 and MA-144).

### Out of scope

- Reversal or refund of a debit that did happen (a void never touches money).
- Listing a user's debits (the passbook is `GET /wallet/me/transactions`, unchanged; voids
  are not ledger entries and never appear in it).
- Public (JWT) exposure — these routes are internal only.

## 4. Functional Requirements

### FR-1: Common request rules

- Internal only, under the same `/wallet/internal/*` prefix and the same service-to-service
  auth as `POST /wallet/internal/debit` (SigV4 / VPC-only in prod; not routed through the
  public API Gateway).
- `orderId`: path parameter, 1–64 characters, `[A-Za-z0-9_-]`. Anything else →
  `400 VALIDATION_ERROR`.

### FR-2: Void — `POST /wallet/internal/debits/{orderId}/void`

Body: `{"userId": "usr_…"}` (the order's owner; Wallet locks that user's wallet row).

In **one transaction**:

1. Lock the user's wallet row `FOR UPDATE` — the same lock the debit takes (FR-4), so a
   void and a debit for the same user are serialized. If the user has no wallet row, skip
   the lock (no debit can commit without one: the debit locks the row first).
2. If a ledger entry with `ref = order:{orderId}` exists → return `409 ALREADY_DEBITED`
   with the FR-5 debit body under `details`. Nothing is written.
3. Otherwise `INSERT INTO debit_voids (ref, user_id, voided_at) … ON CONFLICT (ref) DO
   NOTHING` → `200`:

```json
{ "success": true, "data": { "orderId": "ord_…", "status": "VOIDED", "voidedAt": "2026-09-28T14:03:11.412Z" } }
```

Repeating the void returns the same `200` (the stored `voidedAt`). A void never locks,
writes or changes the balance.

### FR-3: Debit refuses a voided order

`POST /wallet/internal/debit` (MA-130), after it locks the wallet row and before it
inserts the ledger entry, checks `debit_voids` for `order:{orderId}`. If present →
`409 DEBIT_VOIDED`, `details: {orderId, voidedAt}`; nothing is written. The existing replay
check (ledger entry already present → replay) runs first, so a debit that committed before
the void still replays.

Because both paths hold the same row lock, exactly one of these is true for every order,
for ever: a ledger debit exists, or a void exists. Never both.

### FR-4: Debit lock order (existing, made explicit)

The debit already locks the wallet row `FOR UPDATE` before checking the balance. FR-2 and
FR-3 rely on that; the lock must be taken before both the replay check and the void check.

### FR-5: Lookup — `GET /wallet/internal/debits/{orderId}`

Found → `200`:

```json
{
  "success": true,
  "data": {
    "orderId": "ord_…",
    "status": "DEBITED",
    "amountPaise": 10820,
    "balanceAfterPaise": 34180,
    "debitedAt": "2026-09-28T14:03:11.412Z",
    "walletId": "wal_…"
  }
}
```

- `amountPaise` is the **positive** amount debited (the ledger stores debits as negative
  `amount_paise`; the response returns its absolute value).
- A voided order returns `200` with `{"orderId", "status": "VOIDED", "voidedAt"}`.
- Neither → `404 DEBIT_NOT_FOUND`.
- Read-only: no lock, no write, no event, no wallet status check. **Callers must not use a
  `404` to decide that an order is uncharged; only the void (FR-2) decides that.**

### FR-6: Order Service client

- `void_debit(user_id, order_id) -> Voided | DebitLookup`: `200` → `Voided(voided_at)`;
  `409 ALREADY_DEBITED` → `DebitLookup(amount_paise, balance_after_paise, debited_at)`.
- `get_debit(order_id) -> DebitLookup | Voided | None` (`404` → `None`).
- `debit(...)`: new `409 DEBIT_VOIDED` → raises `DebitVoidedError` (an `OrderError`,
  never retried).
- 5xx / timeout / connection error → retried with the client's existing retry policy
  (same as `debit`), then raises `WalletUnavailableError`. A caller must never treat
  "couldn't ask" as "not debited".
- Any other 4xx → raises `WalletUnavailableError` and logs at `ERROR` (a contract bug).

## 5. Non-Functional Requirements

| Area | Target |
|------|--------|
| Performance | p99 < 50 ms for both routes (one row lock + one indexed lookup for the void) |
| Correctness | For every order id, at most one of {ledger debit, void} ever exists |
| Reliability | Void and lookup are idempotent; safe to retry any number of times |
| Security | Internal routes only; not reachable through the public API Gateway; no PII beyond ids and amounts |
| Observability | Structured log per call: `orderId`, `outcome` (`VOIDED` / `ALREADY_DEBITED` / `DEBIT_VOIDED` / `found`), `correlationId`; metric `wallet.debit_refused_voided` (should be rare; alarm if > 0 over 1 h, it means a debit raced a close) |

## 6. Technical Design

- **Handlers:** `wallet/src/handlers/internal_handlers.py` — `POST …/debits/{orderId}/void`,
  `GET …/debits/{orderId}`.
- **Service:** `WalletService.void_debit_for_order(user_id, order_id)`,
  `WalletService.get_debit_for_order(order_id)`; `debit_for_order` gains the FR-3 check.
- **Repository:** `get_ledger_entry_by_ref(ref)`, `get_void(ref)`, `void_debit_for_order(user_id, ref)`, one transaction with the same
  `SELECT wallets … WHERE user_id = … FOR UPDATE` that `debit_for_order` takes first.
- The ledger `type` must be `ORDER_DEBIT`. A row for the ref with another type (should be
  impossible, refs are namespaced) → treated as not found and logged at `ERROR`.

```
Order ──POST /debits/ord_1/void {userId}──▶ Wallet  BEGIN
                                             ├ SELECT wallets … FOR UPDATE      (same lock as debit)
                                             ├ ledger ref order:ord_1? ─ yes ─▶ 409 ALREADY_DEBITED {debit}
                                             └ no ─▶ INSERT debit_voids ─▶ COMMIT ─▶ 200 VOIDED
late debit ──POST /debit ord_1──▶ Wallet  lock ─▶ no ledger ref ─▶ void found ─▶ 409 DEBIT_VOIDED
```

## 7. Data Considerations

Migration `0002_debit_voids.sql` (applies on top of `0001_wallets_ledger.sql`):

```sql
CREATE TABLE debit_voids (
    ref        VARCHAR(80) PRIMARY KEY,   -- 'order:{orderId}', same namespace as ledger_entries.ref
    user_id    VARCHAR(64) NOT NULL,
    voided_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- `ledger_entries` is unchanged; voids are not money movements and stay out of the ledger
  and the passbook.
- No backfill.

## 8. Integration Considerations

| Counterparty | Contract | Failure behaviour |
|--------------|----------|-------------------|
| Order Service (MA-143, MA-144) | void, lookup, and `DEBIT_VOIDED` on debit via `HttpWalletClient` | Transport failure → `WalletUnavailableError`; the caller treats the outcome as unknown and never closes the order |
| Order Service debit callers (MA-130/MA-136 paths) | new `409 DEBIT_VOIDED` | Handled per MA-143 FR-5 and MA-144 FR-3 (the order was closed by another worker) |

Contract test: the Order client's parsing is tested against the exact FR-2/FR-3/FR-5 bodies.

## 9. Edge Cases and Failure Modes

| Case | Behaviour |
|------|-----------|
| Order never debited | Void → `200 VOIDED`; any later debit → `409 DEBIT_VOIDED` |
| Debit committed before the void | Void → `409 ALREADY_DEBITED` with the debit; the caller resumes instead of closing |
| Debit in flight when the void arrives (its client already timed out) | The two serialize on the wallet row lock: whichever commits first wins; the other sees it. No charge on a closed order |
| Void repeated | Same `200 VOIDED` |
| Debit repeated after it committed, then a void | Void → `ALREADY_DEBITED`; debit replay unchanged |
| User has no wallet | Void → `200 VOIDED` (nothing can be debited without the wallet row) |
| Wallet no longer `ACTIVE` | Void and lookup work as usual (no status check) |
| Malformed `orderId` | `400 VALIDATION_ERROR` |
| DB unavailable | `503`; the Order client retries and then raises `WalletUnavailableError` |

## 10. Testing Strategy

- **Unit (service):** void with no debit → `VOIDED` and a `debit_voids` row; void after a
  debit → `ALREADY_DEBITED` with the positive amount, nothing written; void twice → same
  `voidedAt`; debit after a void → `DEBIT_VOIDED`, balance unchanged; debit replay after
  commit still replays; lookup found / voided / not found.
- **Concurrency (Postgres 16 scratch DB):** a debit transaction paused after taking the
  lock while a void is issued → the void waits, then returns `ALREADY_DEBITED`; the
  reverse order → the debit returns `DEBIT_VOIDED`. Repeat 100× with random interleaving:
  never both a ledger entry and a void for one ref.
- **Integration (FastAPI TestClient):** debit an order, then void → `409 ALREADY_DEBITED`;
  void an unknown order, then debit it → `409 DEBIT_VOIDED`; invalid id → `400`.
- **Order client (unit, stubbed HTTP):** each status code → the FR-6 result; `503` twice
  then `200` → result (retries); `503` on every attempt → `WalletUnavailableError`.
- **Negative:** the routes are not mounted on any public/JWT router (route-table test).

## 11. Risks and Trade-offs

- **A write path on the money service.** Chosen over a read-only lookup because a lookup
  cannot rule out a debit still running inside Wallet, and any timing bound (client
  timeout, lease length) depends on Wallet's own transaction time, which Order cannot
  control. The void is a few lines on top of the lock the debit already takes.
- **Wallet row lock contention:** a void holds the user's row lock for one indexed lookup
  and one insert. Negligible next to the debit itself.
- **Alternative considered:** trust the lookup only after a "settle" delay since the last
  debit attempt. Rejected: still a timing assumption, and it needs a per-order
  last-attempt timestamp on every path.
