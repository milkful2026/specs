## 2. Problem Statement

Physical stock drifts from system-recorded stock — spoilage, damage, miscounts, manual corrections
after a supplier delivery. Ops staff need a way to adjust recorded quantities directly, and every
such adjustment must be traceable (who changed what, from what value, to what value, when) — both
for accountability and to distinguish "the system is wrong" from "a customer's reservation logic
has a bug" when investigating a discrepancy. Split from MA-118 (reserve/commit/release) because
this is a distinct access pattern — admin-triggered, not order/system-triggered — with its own
authz and audit requirements.

## 3. Scope

**In scope:**
- `PATCH /inventory` — admin manual stock adjustment.
- Audit log: every adjustment recorded immutably (who, what, before/after, when, optional reason).

**Out of scope:**
- The admin *UI* itself (portal-ui, MA-42's territory) — this spec is the backend API and audit
  storage only.
- Reservation/commit/release lifecycle — MA-118's concern; this spec's adjustments act directly on
  `on_hand`, not on the reservation state machine.
- Reorder/procurement workflow — item 29.0 in the NSMB spec, a separate future admin story;
  `LowStock` (published by MA-118) is this feature's only current hook into that concern.

## 4. Functional Requirements

### FR-1: `PATCH /inventory`

- Body: `productId`, `adjustment` (signed integer — positive for stock-in/correction-up, negative
  for spoilage/correction-down), `reason` (free text, optional but recommended), and the
  authenticated admin's identity (from the JWT — not a client-supplied field, to prevent
  spoofing).
- Applies directly to `on_hand` (per MA-118's schema) — does not touch `reserved`/the reservation
  state machine.
- Rejects an adjustment that would drive `on_hand` negative (a floor at zero — "correcting" stock
  below what's physically possible is a data-entry error, not a valid state).
- Publishes `StockChanged` (same event MA-118 publishes on reserve/commit/release — this is just
  another producer of it, sharing the payload contract MA-118/MA-94 agree on).

### FR-2: Audit trail

- Every successful `PATCH /inventory` call writes an immutable audit row:
  adminId, productId, previousQuantity, newQuantity, adjustment, reason, timestamp.
- No update/delete API for audit rows in this spec — immutability is enforced by simply not
  exposing a mutation path, not by a database-level trigger (simpler, sufficient given this is an
  internal-only table with no direct admin write access to the database).
- No read API for the audit log in this spec either — that's the admin console's (MA-42)
  responsibility to build a view over; this spec's job is only to *record* reliably.

### FR-3: Authorization

- `PATCH /inventory` requires an admin-scoped JWT claim (mirrors the platform's RBAC intent
  described in the NSMB spec's admin section — exact claim/role name is Step 4 implementation
  detail, not this spec's concern beyond requiring *some* admin-distinguishing check beyond plain
  "authenticated").

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| Auditability | 100% of successful adjustments produce exactly one audit row — no adjustment without a trail, ever |
| Security | Admin-only; a non-admin authenticated request is rejected (403), not silently ignored |
| Reliability | Audit-row write and the `on_hand` update happen in the same Aurora transaction — an adjustment is never applied without its audit record, or vice versa |
| Performance | Not a hot path (low-frequency, ops-driven) — no specific latency target beyond "not noticeably slow for a human operator" |

## 6. Technical Design

### Architecture

- Extends MA-118's `stock` domain model with an `adjust()` operation; a new `handlers/` route
  (`PATCH /inventory`); a new `inventory_audit_log` adapter/table, all within the same
  `services/inventory` service (per the Step 1 decision that this is additive scope, not a new
  service).
- The transactional guarantee in NFR (audit + adjustment atomic) is a single Aurora transaction
  wrapping both writes — no distributed-transaction complexity needed since both live in the same
  database.

## 7. Data Considerations

```sql
-- inventory_audit_log (Aurora, new — additive to the services/inventory database)
id                uuid primary key
product_id        uuid not null
admin_id          text not null        -- from JWT, not client-supplied
previous_quantity integer not null
new_quantity      integer not null
adjustment        integer not null     -- new_quantity - previous_quantity, stored redundantly for query convenience
reason            text
created_at        timestamptz not null default now()
```

Additive migration on the same `milkful_inventory` local Postgres database MA-118 already extends.

## 8. Integration Considerations

| Integration | Direction | Contract owner |
|-------------|-----------|-----------------|
| `StockChanged` event | Outbound (publish) | Shares MA-118's contract — same event, another producer |
| Admin console (MA-42) | Future caller of `PATCH /inventory` and future reader of the audit log | Not yet built; this spec's API is forward-looking, same situation as MA-118's Cart/Order dependency |

## 9. Edge Cases and Failure Modes

| Case | Behavior |
|------|----------|
| Adjustment would drive `on_hand` negative | Rejected with a specific validation error, `on_hand` unchanged, no audit row written (nothing happened) |
| Non-admin calls `PATCH /inventory` | 403, no audit row (the request never reached the point of making a change) |
| Aurora write fails mid-transaction | Whole transaction rolls back — never a partial state (adjustment applied without audit, or vice versa) |
| Adjustment for an unknown `productId` | 404 — cannot adjust stock for a product Inventory has no record of |
| Concurrent admin adjustment + a `reserve`/`commit` in flight (MA-118) | Same row-level locking mechanism MA-118 uses on the `stock` row serializes these — no special-casing needed beyond reusing that lock |

## 10. Testing Strategy

### Unit tests

- Floor-at-zero rejection logic.
- Audit-row field mapping from a given adjustment request.

### Integration tests (local-dev)

- A successful adjustment updates `on_hand` and produces exactly one matching audit row, in the
  same transaction (verify both together, not just each independently).
- A rejected (negative-driving) adjustment leaves both `on_hand` and the audit log untouched.
- A non-admin JWT is rejected before any state change.

### Negative scenarios

- Adjustment for a nonexistent product → 404, no audit row.
- Malformed request body → 400, no audit row.

## 11. Risks and Trade-offs

1. **No admin UI or admin-role infrastructure exists yet** — this spec defines the API contract
   admin tooling will eventually call, but can only be verified via direct API calls until MA-42
   exists.
2. **Merge-vs-split call**: this was flagged at decomposition time as possibly foldable into
   MA-118. Kept separate on the basis that admin-triggered adjustment is a distinct access pattern
   (different authz, different audit requirement) from the order-driven reserve/commit/release
   lifecycle — reviewable independently at Step 5 if this judgment should be revisited.
