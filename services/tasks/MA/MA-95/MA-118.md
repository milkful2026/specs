## 2. Problem Statement

Milk, curd, and paneer are perishable and finite per delivery cycle. Without real, concurrency-safe
stock tracking, the platform can oversell — promising a customer a product that isn't actually
available, a direct trust/operational failure for a daily-delivery dairy business. This spec gives
the platform its stock system-of-record: reserve stock during checkout, commit on order
confirmation, release on cancellation/timeout, with batch/expiry awareness for perishables and a
read API Catalog (MA-94) and, eventually, Cart/Order consume.

**Decision carried from Step 1:** this is additive scope on the existing `services/inventory`
FastAPI service (today: serviceability-zone checks only) — not a new or separate service.

## 3. Scope

**In scope:**
- New Aurora tables: stock, stock batches (expiry-aware), reservations.
- `POST /inventory/reserve`, `POST /inventory/commit`, `POST /inventory/release`,
  `GET /inventory/{productId}`.
- Overselling-prevention concurrency mechanism.
- `StockChanged`/`LowStock` publication; `OrderCancelled` consumption.
- Reservation timeout/auto-release (resolves Step 1's Q1 — see FR-2).

**Out of scope:**
- `PATCH /inventory` (admin manual adjustment) and its audit trail — separate spec, MA-119.
- Product/category identity (name, price, description) — Catalog's (MA-94) responsibility; this
  service only ever refers to a `productId` it doesn't otherwise interpret.
- The Cart/Order caller logic that decides *when* to reserve/commit/release — MA-96/MA-97's
  concern; this spec only defines Inventory's side of that contract.
- Existing serviceability-zone check functionality — unchanged, untouched by this spec.

## 4. Functional Requirements

### FR-1: `GET /inventory/{productId}`

- Returns: `productId`, `onHand` (total physical quantity across all batches), `reserved`
  (currently held by unexpired, uncommitted reservations), `available` (`onHand − reserved`),
  and a derived `stockState` (`IN_STOCK` when `available > 0`, `OUT_OF_STOCK` when `available == 0`
  and no future batch is scheduled, `AVAILABLE_FROM` with the earliest future batch's
  `availableFrom` date when `available == 0` but a scheduled batch exists).
- 404 if the productId is entirely unknown to Inventory (distinct from "known but zero stock").

### FR-2: `POST /inventory/reserve`

- Body: `productId`, `quantity`, `orderId` (or a cart/session reference — exact caller-side key is
  MA-96/MA-97's concern; this spec just needs *some* idempotency/correlation key), optional
  `ttlSeconds`.
- Decrements `available` (increments `reserved`) for the requested quantity, drawn from the
  oldest-expiry batch first (FIFO by expiry — the natural policy for perishables).
- **Resolves Step 1 Q1:** a reservation has a default TTL (configurable, default 15 minutes,
  matching a plausible checkout-session window) after which it auto-releases if not committed —
  prevents an abandoned cart from permanently locking stock. Implemented as a scheduled sweep
  (a periodic job checking for expired, uncommitted reservations) rather than a per-reservation
  timer, matching this platform's existing preference for simple polling over per-item scheduled
  infrastructure (mirrors `services/user`'s outbox-publisher polling pattern already in this
  repo).
- Fails with a specific error code (not a generic 500) if `quantity` exceeds `available` —
  overselling prevention's primary enforcement point.
- Concurrency: **row-level locking** (`SELECT ... FOR UPDATE` on the relevant stock row within a
  single Postgres transaction) — resolves Step 1's Q5. Chosen over optimistic concurrency because
  reserve/commit/release is a low-latency, high-contention-tolerant path (brief lock hold, not a
  long-running transaction), and pessimistic locking gives a simpler, more directly verifiable
  overselling-prevention guarantee than retry-on-conflict optimistic locking would.

### FR-3: `POST /inventory/commit`

- Body: `orderId` (or whatever correlation key FR-2's reservation was created with).
- Finalizes the reservation: decrements `onHand` by the reserved quantity (physically consumed),
  clears the `reserved` hold. Idempotent — committing an already-committed reservation is a no-op,
  not an error, so a retried caller can't double-decrement `onHand`.
- Publishes `StockChanged`.

### FR-4: `POST /inventory/release`

- Body: same correlation key as FR-2/FR-3.
- Returns the reserved quantity back to `available` without touching `onHand`. Idempotent (same
  reasoning as FR-3).
- Publishes `StockChanged`.
- Triggered either explicitly (this endpoint) or automatically (FR-2's TTL sweep, or FR-5's
  `OrderCancelled` consumption).

### FR-5: `OrderCancelled` consumption

- Consuming this event triggers the same effect as an explicit `POST /inventory/release` for that
  order's reservation. Idempotent against redelivery (a reservation already released is a no-op).

### FR-6: `StockChanged`/`LowStock` publication

- `StockChanged` fires on any event that changes `available` or `onHand` (reserve, commit,
  release, and — from MA-119's spec — admin adjustment).
- **Agreed payload contract** (joint with MA-94/MA-116, which consumes this):
  ```json
  {
    "eventId": "uuid",
    "productId": "uuid",
    "availableQuantity": 0,
    "stockState": "IN_STOCK | OUT_OF_STOCK | AVAILABLE_FROM",
    "availableFrom": "2026-09-01 | null",
    "occurredAt": "2026-08-16T10:00:00Z"
  }
  ```
  `eventId` is a fresh UUID per publish (not the reservation/adjustment id) — it's what lets
  MA-116's consumer detect and ignore a redelivered duplicate. `availableQuantity` is this
  service's own `available` field (§7); `stockState`/`availableFrom` are derived exactly as in
  FR-1, so Catalog never has to re-derive them.
- `LowStock` fires when `available` crosses below a configured threshold (per-product, resolving
  Step 1's Q2 in favor of per-product configurability over a single global default, since a
  "low stock" line for a fast-moving 1L milk pouch and a slow-moving specialty item are not
  comparable in absolute units).

### FR-7: Batch & expiry

- `GET /inventory/{productId}` does **not** expose batch-level detail by default (resolves Step 1's
  Q4 in favor of the simpler aggregate-quantity contract) — batch/expiry is handled internally for
  FIFO consumption (FR-2) and `AVAILABLE_FROM` derivation (FR-1), not surfaced as a public API
  concern. A future batch-detail endpoint can be added without breaking this one if a caller
  eventually needs it (e.g. an admin dashboard).

## 5. Non-Functional Requirements

| Category | Target |
|----------|--------|
| Correctness | Zero overselling under concurrent `reserve` calls against the same product — the single highest-priority NFR in this spec, verified via a concurrency/load test (Testing Strategy) |
| Performance | `reserve`/`commit`/`release` p95 < 200ms (checkout-path latency matters; row-level lock hold time must stay short) |
| Reliability | `OrderCancelled` consumption idempotent; a poison message routes to DLQ; the TTL sweep job is safe to run concurrently with itself (e.g. via a `SELECT ... FOR UPDATE SKIP LOCKED`-style pattern) without double-releasing |
| Security | Cognito JWT at API Gateway; `reserve`/`commit`/`release` are service-to-service calls (from Cart/Order once built) rather than directly customer-facing, so SigV4/mTLS applies per the platform's service-to-service auth model |
| Observability | CloudWatch alarm on TTL-sweep backlog (stuck reservations) and on elevated `reserve`-rejection rate (a proxy for demand exceeding supply, an operational signal worth watching) |

## 6. Technical Design

### Architecture

- Extends the existing `services/inventory` hexagonal structure: new domain models
  (`Stock`, `StockBatch`, `Reservation`) and a new `InventoryStockService` alongside the existing
  `serviceability_service.py`; new Postgres adapters alongside `zone_repository.py`; new FastAPI
  routes/DTOs alongside the existing `serviceability_check_handler.py`; a new
  `inventory-events-q` SQS consumer adapter (mirrors `zone_update_consumer.py`) for
  `OrderCancelled`.
- Compute: unchanged — already Fargate, already "a real FastAPI app" per this service's own
  local-dev README.

### Reservation state machine

```
                reserve()
   (none) ─────────────────► RESERVED ──── commit() ────► COMMITTED (terminal)
                                 │
                                 ├──── release() ────► RELEASED (terminal)
                                 │
                                 └──── TTL sweep ────► RELEASED (terminal)
```

## 7. Data Considerations

```sql
-- stock (Aurora, new — additive to existing services/inventory database)
product_id      uuid primary key
on_hand         integer not null default 0
reserved        integer not null default 0  -- derived/cached; source of truth is the reservations table's active rows, kept in sync transactionally
low_stock_threshold integer not null default 10

-- stock_batches
id              uuid primary key
product_id      uuid references stock(product_id)
quantity        integer not null
expiry_date     date
received_at     timestamptz not null default now()

-- reservations
id              uuid primary key
product_id      uuid references stock(product_id)
order_ref       text not null           -- caller-supplied correlation key (FR-2)
quantity        integer not null
status          text not null           -- RESERVED | COMMITTED | RELEASED
created_at      timestamptz not null default now()
expires_at      timestamptz not null    -- FR-2's TTL
```

Additive migration on the existing `services/inventory` local Postgres database (`milkful_inventory`,
already provisioned via this repo's `local-dev/docker-compose.yml`), alongside the existing
`0001_serviceability_zones.sql`.

## 9. Edge Cases and Failure Modes

| Case | Behavior |
|------|----------|
| Concurrent `reserve` calls exceeding available stock | Row-level lock serializes them; the call(s) that would exceed `available` fail with a specific "insufficient stock" error, not an oversold state |
| `commit`/`release` called on an already-committed/released reservation | No-op (idempotent), not an error |
| `commit`/`release` called on a nonexistent `order_ref` | 404-equivalent error — distinct from the idempotent-no-op case above |
| Reservation TTL expires mid-checkout (customer slow) | Auto-released; a subsequent `commit` attempt fails with a "reservation not found/expired" error — surfaces to Cart/Order to prompt the customer to retry |
| `OrderCancelled` for an already-released reservation | No-op (idempotent) |
| Batch fully consumed (FIFO) before its expiry | Simply excluded from future FIFO draws — not an error condition |

## 10. Testing Strategy

### Unit tests

- FIFO batch-consumption logic for a `reserve` spanning multiple batches.
- TTL-expiry derivation and the sweep job's release logic.
- Idempotency of `commit`/`release` against an already-terminal reservation.
- `LowStock` threshold-crossing logic.

### Concurrency/load test (the highest-priority test in this spec)

- N concurrent `reserve` requests against a product with stock for exactly N-1 — assert exactly
  N-1 succeed and exactly 1 fails with the insufficient-stock error; assert `available` never goes
  negative at any point during the test.

### Integration tests (local-dev)

- Full reserve → commit lifecycle against local Postgres, asserting `on_hand`/`reserved`/
  `available` transition correctly at each step.
- Full reserve → TTL-expire → sweep → release lifecycle (using a short TTL in test config).
- `OrderCancelled` consumption releasing an active reservation.

### Negative scenarios

- `reserve` for an unknown `productId` → 404, not a 500.
- `reserve` for `quantity` exceeding `available` → the specific insufficient-stock error, not a
  generic failure.

## 11. Risks and Trade-offs

1. **No real caller exists yet** (Cart/Order, MA-96/MA-97) — this spec's contract is validated by
   direct API/integration tests, not a true end-to-end checkout flow, until those services exist.
2. **Row-level locking under high contention** could become a throughput bottleneck for a
   fast-moving, single-popular-product scenario (e.g. a flash sale) — acceptable for this
   platform's actual load profile (daily dairy delivery, not flash-sale retail) but worth stating
   explicitly as a trade-off, not an oversight.
3. **TTL default (15 min) is a guess**, not a sourced business requirement — flagged as an open
   question for product sign-off.
