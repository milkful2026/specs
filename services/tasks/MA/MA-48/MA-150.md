## 2. Problem Statement

MA-118 gives the platform a stock system-of-record; MA-119 gives admins a way to correct it. Neither gives an admin a way to see stock at a glance across products (for reorder decisions), see batch/expiry detail for a single product (MA-118 deliberately excludes this from its aggregate read API), or record new stock arriving from the parent plant as a distinct, auditable event with its own batch identity (as opposed to an undifferentiated `on_hand` correction). This spec closes those gaps.

**Expected outcome:** An admin (Ops role) can see which products need reordering, inspect a product's batch/expiry detail, and record a goods receipt that creates a real batch — all reusing MA-118/MA-119's existing schema, concurrency controls, and audit guarantees, adding zero new tables.

## 3. Scope

### In Scope

- `POST /inventory/receive` — goods receipt: new `stock_batches` row with a real `expiry_date`, increments `on_hand`, writes an `inventory_audit_log` row, publishes `StockChanged`.
- `GET /inventory/{productId}/batches` — batch-level read, additive to MA-118's aggregate-only `GET /inventory/{productId}`.
- `GET /inventory` — paginated list/summary across all products (`onHand`/`reserved`/`available`/`stockState`/`lowStockThreshold`), the backend for the admin "reorder alerts" list view.
- `GET /inventory/{productId}/audit-log` — reads `inventory_audit_log`, the read API MA-119 explicitly states it does not build ("that's the admin console's responsibility to build a view over") — this spec is that responsibility's backend half.
- The admin-authorizer wiring (cross-stack Lambda REQUEST authorizer, same pattern as MA-139) for all four endpoints, gated to the Ops role.

### Out of Scope

- MA-118's reserve/commit/release/TTL-sweep/`StockChanged`-producer and MA-119's `PATCH /inventory` *write* path and the `inventory_audit_log` table itself — those specs' own scope, assumed implemented here, not redefined. (This spec adds the audit log's missing *read* path, FR-4 — MA-119 explicitly left that to the admin console.)
- Any change to Catalog's product identity, pricing, or its existing `StockChanged` consumer — unaffected by this spec; its only change is receiving real events once MA-118 ships.
- A `LowStock` consumer/notification pipeline — explicitly deferred (MA-118 §12 Q2, carried forward by MA-48's own Step 1 D3: list view is sufficient for v1).
- Accounting integration — named in MA-48's Jira "Key Dependencies" but nothing in the codebase or in MA-118/MA-119 defines an accounting system to integrate with; not built here.
- Reservation/commit/release's own concurrency or lifecycle — untouched, reused exactly as MA-118 built it.

## 4. Functional Requirements

### FR-1: `POST /inventory/receive`

- Body: `{ productId, quantity, expiryDate, reason? }`. `quantity` must be a positive integer; `expiryDate` required (a receipt with no expiry isn't valid for a perishables platform — distinguishes this from MA-119's adjustment, which has no batch concept at all).
- Row-level lock on the `stock` row for `productId` (same lock MA-118/MA-119 already take) within one Aurora transaction:
  1. `INSERT stock_batches (product_id, quantity, expiry_date, available_from=NULL, received_at=now())` — `available_from=NULL` means "available immediately," matching MA-118's own FR-1 semantics for a batch with no future-scheduling.
  2. `UPDATE stock SET on_hand = on_hand + quantity WHERE product_id = :productId`.
  3. `INSERT inventory_audit_log (admin_id, product_id, previous_quantity, new_quantity, adjustment=+quantity, reason)` — reuses MA-119's existing audit-write helper verbatim (not a re-implementation — see §6), with `reason` prefixed `"goods_receipt: "` if the caller supplied one, else `"goods_receipt"` alone, so audit rows are distinguishable from a MA-119 `PATCH /inventory` correction at a glance.
- Publishes `StockChanged` (MA-118's existing contract, FR-6) — this endpoint is a third producer alongside reserve/commit/release and MA-119's adjustment, not a new contract.
- `404 PRODUCT_NOT_FOUND` if `productId` has no `stock` row (same "Catalog hasn't told Inventory this product exists yet" semantics as MA-118 FR-1/FR-8).
- `400 VALIDATION_ERROR` for non-positive `quantity` or a past `expiryDate`.
- Idempotency: **not required** — unlike MA-118's reserve (idempotent on a client-supplied correlation key) or MA-119's adjustment (idempotent on repeat-same-status), a goods receipt has no natural correlation key and each call is intentionally a distinct, additive event (two receipts of the same quantity on the same day are two real deliveries, not a retry) — this is a deliberate design choice, not an oversight, flagged explicitly in §11.

### FR-2: `GET /inventory/{productId}/batches`

- Returns every `stock_batches` row for `productId`: `batchId`, `quantity` (remaining, not original — MA-118's FIFO consumption decrements this as reservations commit against it, though this spec does not change how that decrement happens), `expiryDate`, `availableFrom`, `receivedAt`, ordered oldest-expiry-first (matching MA-118's own FIFO consumption order, so what an admin sees matches what will actually be drawn down next).
- `404 PRODUCT_NOT_FOUND` if `productId` is unknown to Inventory (same semantics as MA-118 FR-1).
- Read-only; does not change `GET /inventory/{productId}`'s existing response shape at all (purely additive).

### FR-3: `GET /inventory`

- Paginated list: `productId`, `onHand`, `reserved`, `available`, `stockState`, `lowStockThreshold` — `stockState` derived exactly as MA-118 FR-1 already derives it per-product, just surfaced across every product in one call instead of one at a time.
- Optional `stockState` filter (`IN_STOCK`/`OUT_OF_STOCK`/`AVAILABLE_FROM`) so an admin can jump straight to "what's out of stock right now" — the concrete backend for the "reorder alerts" list view (D3).
- No `productId` search by name — Inventory doesn't own product names (Catalog does); the admin UI is expected to cross-reference against Catalog's own product list client-side or via a future join, out of scope here (flagged in §12, not solved).

### FR-4: `GET /inventory/{productId}/audit-log`

- Returns `inventory_audit_log` rows for `productId`, newest-first: `adminId`, `previousQuantity`, `newQuantity`, `adjustment`, `reason`, `createdAt`. Covers rows written by MA-119's `PATCH /inventory` **and** this spec's own `POST /inventory/receive` (§4 FR-1) — both write to the same table via the same helper, so this single read endpoint surfaces both action types without needing to distinguish them structurally (a `receive`-originated row is identifiable by its `reason` prefix, §4 FR-1, not a separate column — no schema change needed).
- Paginated (same shape as FR-3's list); `404 PRODUCT_NOT_FOUND` if `productId` is unknown to Inventory.
- Read-only; does not write anything, does not change MA-119's existing write-side contract at all.

## 5. Non-Functional Requirements

- **Performance:** `GET /inventory` p95 < 500ms for up to 10,000 products (indexed on `product_id`, same table MA-118 already indexes for its own reads); `POST /inventory/receive` p95 < 300ms including the lock hold (not a hot/checkout path, same latency class as MA-119's adjustment).
- **Security:** All four endpoints require a valid admin JWT (via the cross-stack authorizer, §6) with the Ops role claim (D4), checked server-side — never trust a client-supplied role. `adminId` for the audit row comes from the JWT, never the request body (same anti-spoofing rule as MA-119 FR-1).
- **Reliability:** `POST /inventory/receive`'s batch insert, `on_hand` update, and audit insert are one Aurora transaction — a receipt is never applied without its audit record, or vice versa (same guarantee as MA-119's NFR).
- **Auditability:** 100% of successful receipts produce exactly one audit row — same bar MA-119 already holds itself to for adjustments.
- **Observability:** CloudWatch metric `inventory.receive.count`, tagged by `productId`; reuses MA-118's existing TTL-sweep and reserve-rejection alarms (unaffected by this spec).

## 6. Technical Design

### Architecture Approach

Extends `services/inventory`'s existing hexagonal structure (FastAPI/Fargate, per MA-118 §6's own architecture section):
1. New domain method `InventoryStockService.receive(product_id, quantity, expiry_date, admin_id, reason)` alongside MA-118's `reserve`/`commit`/`release` and MA-119's `adjust`.
2. New read methods `get_batches(product_id)` and `list_stock(status_filter, page, page_size)` on the same service.
3. New FastAPI routes (`APIRouter(prefix="/v1", tags=["inventory-admin"])`, mirroring `serviceability_check_handler.py`'s existing router style) — `POST /inventory/receive`, `GET /inventory/{productId}/batches`, `GET /inventory`.
4. New `admin_context.py`-equivalent module (`Depends(get_caller_admin)`), reading `{adminId, email, role}` from the API Gateway authorizer context — mirrors `user/src/handlers/admin_context.py` byte-for-byte in contract, not imported cross-service (per the platform's established "never import another service's `src/`" rule — same note MA-139's own `admin_context.py` carries).
5. CDK: new API Gateway route integrations referencing Identity & Auth's existing admin authorizer Lambda by ARN — same `admin_authorizer_fn_arn` cross-stack parameter pattern `user_stack.py` already established for MA-139, including that implementation's own disclosed placeholder-ARN gap (not newly introduced here, inherited).

### Component Responsibilities

- **Admin inventory handlers** (`src/handlers/admin_inventory_handler.py`) — thin FastAPI routes, map HTTP ↔ domain, mirror the existing `serviceability_check_handler.py`'s shape.
- **`InventoryStockService`** (extends MA-118/MA-119's existing domain service, not a new class) — `receive()`, `get_batches()`, `list_stock()`, `get_audit_log()`.
- **Adapters** — extends MA-118/MA-119's existing stock/batch/audit repository methods with `insert_batch_and_increment_on_hand()` (one transaction, mirrors MA-119's existing adjustment-plus-audit transaction shape), `list_batches_by_product()`, `list_stock_paginated()`, `list_audit_log_by_product()` (a plain paginated `SELECT` against MA-119's existing `inventory_audit_log` table — no new table, no new write path).

### Workflow (`POST /inventory/receive`)

```
POST /inventory/receive {productId, quantity, expiryDate, reason?}
  → get_caller_admin(request) → 401 if missing/malformed
  → role != Ops → 403
  → load stock row for productId → 404 if missing
  → quantity <= 0 or expiryDate in the past → 400
  → row-level lock (SELECT ... FOR UPDATE on stock, same lock MA-118/MA-119 use)
      DB transaction:
        INSERT stock_batches (product_id, quantity, expiry_date, available_from=NULL, received_at=now())
        UPDATE stock SET on_hand = on_hand + quantity
        INSERT inventory_audit_log (admin_id, product_id, previous_quantity, new_quantity,
                                     adjustment=+quantity, reason="goods_receipt" [+ ": " + reason])
      commit
  → publish StockChanged (MA-118 FR-6 contract: productId, availableQuantity, stockState, availableFrom, occurredAt)
  → return 201 with the new batch + updated stock summary
```

### API/Interface Definitions

| Method | Path | Purpose |
|--------|------|---------|
| POST | `/v1/inventory/receive` | Goods receipt (FR-1) |
| GET | `/v1/inventory/{productId}/batches` | Batch detail (FR-2) |
| GET | `/v1/inventory` | Stock list/summary (FR-3) |
| GET | `/v1/inventory/{productId}/audit-log` | Audit-log read (FR-4) |

All responses use the standard envelope (`services/README.md` §5), consistent with MA-118/MA-119's own endpoints once implemented.

### Data Flow

`portal-ui` (MA-151) → API Gateway (admin JWT authorizer, cross-stack ref to Identity & Auth) → Inventory Service (Fargate, FastAPI) → Aurora `milkful_inventory` (`stock`/`stock_batches`/`inventory_audit_log`, all MA-118/MA-119's existing tables) → EventBridge → Catalog's existing `stock-changed` consumer.

## 7. Data Considerations

**Zero new tables.** Every read/write in this spec is a new shape over MA-118/MA-119's existing additive migrations:

```sql
-- stock, stock_batches, reservations: defined by MA-118 §7, unchanged here.
-- inventory_audit_log: defined by MA-119 §7, unchanged here — receive() writes
-- to it via the same helper/shape MA-119's PATCH /inventory already uses.
```

No migration file is added by this spec. If MA-118/MA-119's own migrations haven't landed yet when this spec's implementation starts, that's this spec's hard prerequisite (§1), not a schema gap of its own.

## 8. Integration Considerations

- **Upstream:** `portal-ui` (MA-151) is the only caller.
- **Downstream:** EventBridge → Catalog's existing `StockChanged` consumer (no change needed there — this spec is simply its third real producer, alongside MA-118/MA-119's own).
- **Contract ownership:** MA-118 owns the `StockChanged` payload contract (FR-6); this spec's `receive()` reuses it verbatim, does not redefine it.
- **Identity & Auth:** reuses the existing admin authorizer Lambda, same cross-stack ARN pattern as MA-139 — no change to Identity & Auth itself.
- **No cross-service DB reads** — this spec never queries Catalog's or any other service's database; product identity (name, price) stays entirely Catalog's concern, referenced here only by `productId`.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| `POST /inventory/receive` for an unknown `productId` | `404 PRODUCT_NOT_FOUND` — same as MA-118/MA-119's existing unknown-product semantics |
| `POST /inventory/receive` with a non-positive `quantity` | `400 VALIDATION_ERROR`, no batch/audit row written |
| `POST /inventory/receive` with a past `expiryDate` | `400 VALIDATION_ERROR` — receiving already-expired stock is a data-entry error, not a valid state, same floor-check philosophy as MA-119's negative-`on_hand` rejection |
| A receipt races a concurrent `reserve`/`commit`/adjustment on the same product | Serialized by the same row-level lock MA-118/MA-119 already use on the `stock` row — no special-casing needed |
| Aurora write fails mid-transaction | Whole transaction rolls back — never a partial state (batch inserted without audit, or vice versa), same guarantee as MA-119 |
| `GET /inventory/{productId}/batches` for a product with zero batches (freshly provisioned, never received) | `200` with an empty array — not a 404, since the product itself is known (distinct from the product-unknown 404 case) |
| Two receipts for the same product on the same day | Both succeed, both create distinct batch rows — not idempotent by design (§4 FR-1), since each is a genuinely separate delivery |
| Non-Ops authenticated admin calls any of the four endpoints | `403`, no state change — same posture as MA-119 FR-3 |

## 10. Testing Strategy

- **Unit:** `receive()`'s validation (positive quantity, future expiry), the audit-row reason-string construction (`"goods_receipt"` vs `"goods_receipt: {reason}"`), `list_stock()`'s `stockState` filter, `get_batches()`'s oldest-expiry-first ordering, `get_audit_log()`'s newest-first ordering and that it surfaces both `receive()`-originated and MA-119 `PATCH /inventory`-originated rows correctly.
- **Integration (local-dev):** full `receive()` call against local Postgres asserting `stock_batches` insert + `on_hand` increment + `inventory_audit_log` row all land in one transaction; `GET /inventory/{productId}/batches` after a receipt shows the new batch; `GET /inventory` reflects an updated `stockState` after a receipt moves a product from `OUT_OF_STOCK` to `IN_STOCK`.
- **Contract:** `StockChanged` payload from `receive()` validated against MA-118's existing schema fixture (shared, not re-derived) — and, since this is the first time this project gets to verify `StockChanged` against a *real* producer end-to-end, **this spec's test plan must include live-verifying Catalog's existing consumer actually updates `products.stock_state`** (R2 in MA-48's Step 2 context) — not just a schema-shape check.
- **Negative scenarios required:** unknown product, non-positive quantity, past expiry date, non-Ops caller, concurrent receive + reserve race.

## 11. Risks and Trade-offs

1. **`receive()` is deliberately non-idempotent** (§4 FR-1) — unlike every other write endpoint MA-118/MA-119 define. Accepted because a goods receipt has no natural retry-correlation key and genuinely-repeated identical calls represent genuinely-repeated real-world deliveries, not client retries; a network-level retry (e.g. a timed-out request that actually succeeded) double-counting a receipt is a real but low-likelihood risk, flagged rather than solved (a future `Idempotency-Key` header is a non-breaking addition if this becomes a real operational problem).
2. **No product-name search on `GET /inventory`** (§4 FR-3) — Inventory doesn't own product identity; cross-referencing against Catalog's product list is left to the admin UI (MA-151) or a future join, not solved here, to respect the database-per-service boundary rather than reach into Catalog's data.
3. **Inherits MA-139's placeholder-authorizer-ARN gap** (§6) — not a new risk this spec introduces, but worth naming so a future fix addresses both services' stacks together rather than being rediscovered twice.

## 12. Open Questions

1. Should `GET /inventory` support product-name search, requiring either a Catalog API call or a denormalized name cache in Inventory? Deferred — flagged in §11 as a real gap, not silently assumed away.
2. Should `receive()` eventually get an idempotency key (§11 Risk 1)? Not required for v1, flagged for a future iteration if retries prove to be a real operational issue.
