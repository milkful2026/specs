## 2. Problem Statement

The admin console has no inventory visibility at all today. Ops staff need to see which products are low/out of stock, correct quantities when they drift from reality, see batch/expiry detail for perishables, and record goods received from the parent plant — all with the same console, RBAC, and interaction patterns already established for Admin Users (MA-128) and Customer Accounts (MA-141).

**Expected outcome:** An Ops admin can open an Inventory screen, immediately see which products need attention, drill into any product's batch/expiry detail and audit history, correct a quantity with a reason, and record a goods receipt — each action reflected live and durably audited.

## 3. Scope

### In Scope

- **Inventory** list screen: all products with on-hand/reserved/available/stock-state, filterable by stock state (the "reorder alerts" view, D3), under RBAC (Ops, D4).
- Per-product detail: aggregate numbers + a batch/expiry table (consumes MA-150's new `/batches` endpoint).
- Adjustment dialog: reason required, consumes MA-119's `PATCH /inventory` (once implemented).
- Goods-receipt dialog: quantity + expiry date, consumes MA-150's new `POST /inventory/receive`.
- Audit-trail view per product, reading MA-119's audit log via MA-150's new `GET /inventory/{productId}/audit-log` (FR-4).
- All UI states (loading, empty, error, success, validation) matching the established patterns in `CustomerAccountsPage.tsx`/`AdminUsersPage.tsx`.

### Out of Scope

- The backend itself — owned by [MA-150](https://milkfuldairyindia.atlassian.net/browse/MA-150) (this story's new endpoints) and [MA-118](https://milkfuldairyindia.atlassian.net/browse/MA-118)/[MA-119](https://milkfuldairyindia.atlassian.net/browse/MA-119) (the prerequisite schema/endpoints this spec's screens ultimately depend on).
- Reservation/commit/release UI — that's an order-time system concern (Cart/Order, not built), never admin-facing.
- Any Catalog (product identity/pricing) admin screens — MA-42's territory, not this spec's.
- A `LowStock` notification/alert mechanism beyond the list view itself — explicitly deferred (D3).
- Accounting/reconciliation workflows beyond what a plain adjustment+reason already captures.

## 4. Functional Requirements

### FR-1: Navigation and Access

- A new **Inventory** item appears in the main navigation, visible only to Ops (and SuperAdmin, same question MA-141 §12 Q1 left open for its own role split — recorded consistently here, not re-litigated).
- `RequireRole roles={['Ops', 'SuperAdmin']}` at the route level, mirroring `CustomerAccountsPage`'s exact existing gate. Other roles see no nav entry and are redirected to `/403` on direct URL access.

### FR-2: Inventory List

- Table columns: Product ID (until Catalog cross-referencing exists per MA-150 §11 Risk 2 — flagged, not solved here either; show the raw `productId` for v1), On Hand, Reserved, Available, Stock State, actions.
- Stock-state filter dropdown: All / In Stock / Out of Stock / Available From — this **is** the reorder-alerts view (D3): an Ops admin filters to "Out of Stock" to see exactly what needs attention, no separate alert mechanism needed.
- Stock-state badge pairs color with a text label (never color-only), same accessibility pattern as `CustomerStatusBadge`.

### FR-3: Product Detail

- Clicking a row (or a "View" action) opens a detail view: aggregate on-hand/reserved/available/stock-state + a batch table (quantity remaining, expiry date, received date, available-from), oldest-expiry-first — matches MA-150 FR-2's own ordering, so what the admin sees matches real FIFO draw order.
- An audit-trail table below the batch table: who changed what, from what value, to what, when, why — reusing the exact table shape `CustomerDetailPage`'s status-history table already established.

### FR-4: Adjust Stock

- A product-detail action opens an **Adjust** dialog: signed quantity field (clearly labeled "positive to add, negative to remove/report spoilage" so the sign convention from MA-119 FR-1 is legible to a human, not just an API detail) + required **Reason** field.
- On confirm: `PATCH /inventory` (MA-119). Success → toast "Stock adjusted for {productId}."; the detail view's aggregate numbers and audit table update.
- Server-side floor-at-zero rejections (MA-119 FR-1 — both the `on_hand` and the `available` checks) surface as a clear inline error, not a generic failure — e.g. "This would leave negative available stock (reserved orders exist)." for the `available`-specific case, distinct wording from the plain `on_hand` case, since they're different failure reasons an Ops admin needs to understand differently.

### FR-5: Record Goods Receipt

- A product-detail action opens a **Receive Stock** dialog: quantity (positive integer) + expiry date (required, must be a future date, inline-validated before submit — same pattern as MA-141's Suspend dialog's future-date validation) + optional reason/note.
- On confirm: `POST /inventory/receive` (MA-150). Success → toast "{quantity} units received for {productId}, expiring {date}."; the new batch appears immediately in the batch table, aggregate numbers update.
- Distinct dialog from Adjust (FR-4) — reinforces MA-150's own design decision that a receipt is not just a correction, it establishes a real batch.

## 5. Non-Functional Requirements

- **Performance:** Inventory list loads in < 1.5s p95, same target class as MA-128/MA-141's lists, server-side filtered (MA-150's `GET /inventory` already supports a `stockState` filter server-side — no client-side-first precedent needed here, unlike MA-128's original client-side choice).
- **Security:** No inventory data logged client-side beyond what's already visible on screen; all calls require a valid admin JWT with the Ops role, enforced server-side — identical posture to MA-128/MA-141.
- **Accessibility:** WCAG AA, inheriting MA-128/MA-141's established requirements (keyboard nav, ARIA labels, focus management, non-color-only status indication).
- **Observability:** Every adjust/receive action logs a structured client-side analytics event via the existing `logAdminAnalyticsEvent` utility, extending its action-type union with `inventory.*` events — same extension pattern MA-141 already used for `customer_account.*`.

## 6. Technical Design

### Architecture Approach

Standard `portal-ui` React SPA screens under the existing admin shell, calling MA-150's REST endpoints through API Gateway with the existing admin JWT authorizer — same BFF pattern as every other admin screen.

### Component Responsibilities

- **`InventoryListPage`** — mirrors `CustomerAccountsPage`'s structure (filter state, table, row actions).
- **`useInventoryListQuery` / `useProductBatchesQuery` / `useAdjustStockMutation` / `useReceiveStockMutation`** — React Query hooks, same file-organization convention as `pages/customer-accounts/hooks.ts`.
- **`AdjustStockDialog`** / **`ReceiveStockDialog`** — structurally mirror `CustomerStatusDialog`'s shape (form + validation + confirm).
- **`InventoryDetailPage`** — a dedicated route `/inventory/{productId}`, following `CustomerDetailPage`'s established precedent (full route, not a drawer, for navigation-model consistency) rather than re-opening that layout question.

### Workflow (Receive Stock)

```
Admin on product detail → "Receive Stock" → dialog: quantity, expiry date (required, future), reason (optional)
  → Confirm → POST /v1/inventory/receive
      → 201: new batch appears in batch table, aggregate numbers update, toast shown
      → 404 (PRODUCT_NOT_FOUND — shouldn't reach here from an existing detail page, handled
         defensively): toast "Something changed — refresh and try again.", detail refetched
      → 400 (VALIDATION_ERROR — e.g. past expiry slipped past client validation): inline
         dialog error, dialog stays open with entered values retained
      → 5xx: toast "Something went wrong. Try again.", dialog stays open
```

### API/Interface Definitions

Defined authoritatively in MA-150 (new) and MA-119 (adjustment, once implemented); `portal-ui` consumes:

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/v1/inventory` | List/filter (FR-2) |
| GET | `/v1/inventory/{productId}` | Aggregate detail (MA-118) |
| GET | `/v1/inventory/{productId}/batches` | Batch detail (FR-3, MA-150) |
| GET | `/v1/inventory/{productId}/audit-log` | Audit trail (FR-3, MA-150) |
| PATCH | `/v1/inventory` | Adjust (FR-4, MA-119) |
| POST | `/v1/inventory/receive` | Goods receipt (FR-5, MA-150) |

### Data Flow

Browser → API Gateway (Cognito admin JWT authorizer) → Inventory Service (MA-118/MA-119/MA-150) → Aurora `milkful_inventory`. No direct call from `portal-ui` to Catalog or any other service.

No new datastore owned by `portal-ui` (stateless SPA, same as every prior admin spec). DTOs this UI depends on:

## 8. Integration Considerations

- **Upstream:** none — entry point, same as every prior admin spec.
- **Downstream:** Inventory Service (MA-118/MA-119/MA-150) exclusively. No direct calls to Catalog, Order, or any other service.
- **Contract ownership:** MA-150 (new endpoints) and MA-119 (adjustment) are the sources of truth; this spec's DTOs must be kept in sync with them during implementation.
- **Error handling:** standard envelope (`services/README.md` §5c) — 401 → redirect to login, 403 → "Permission denied" toast, 5xx → generic retry toast, identical to every prior admin spec.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| Admin navigates directly to an Inventory URL without the Ops role | Redirected to `/403`, same as every other role-gated admin screen |
| Two admins adjust the same product concurrently | Last write wins at the API layer (serialized by Inventory's own row-level lock); UI shows the server's returned state after the action, not a locally-optimistic one — same non-optimistic-on-conflict principle as every prior admin spec |
| Receive-stock dialog submitted with a past expiry date | Inline validation error before submit; no request sent (mirrors MA-141's Suspend-dialog pattern) |
| Adjustment rejected because it would drive `available` negative (reserved orders exist) | Distinct, specific inline error text from the plain `on_hand`-negative case (FR-4) — an Ops admin needs to know *why* differently |
| Product detail opened for a product with zero batches (freshly provisioned) | Batch table shows an empty state ("No batches recorded yet."), not an error |
| Network failure mid-action | Same generic retry toast pattern as every prior admin spec; no partial-success ambiguity since both Adjust and Receive are single atomic server-side actions |

## 10. Testing Strategy

Unit tests for form validation (future-date expiry, positive-quantity, required reason) and the two distinct floor-check error messages (FR-4). Integration tests mock MA-150/MA-119's API per the DTOs in §7. E2E via Playwright per the scenarios below, same tooling/convention as every prior admin spec.

```
Scenario: Ops admin records a goods receipt
Given: An Ops admin is logged in and viewing a product's detail page
Steps:
  1. Click "Receive Stock" (getByRole('button', { name: 'Receive Stock' }))
  2. Enter quantity and a future expiry date (getByLabel('Quantity'), getByLabel('Expiry Date'))
  3. Confirm (getByRole('button', { name: 'Receive' }))
Outcome: A toast confirms the receipt; the new batch row appears in the batch table with the entered quantity and expiry date; the aggregate "On Hand" number increases by that quantity.
Selectors: getByRole for buttons, getByLabel for form fields, getByText for the toast and the new batch row.
```

```
Scenario: Non-Ops admin cannot see Inventory
Given: An admin logged in with the "Finance" role
Steps:
  1. Inspect the main navigation
Outcome: No "Inventory" navigation item is present. Direct navigation to the Inventory URL redirects to /403.
Selectors: getByRole('link', { name: 'Inventory' })
```

```
Scenario: Adjustment that would drive available stock negative is rejected with a clear reason
Given: A product with on_hand=100, reserved=90 (available=10), an Ops admin viewing its detail page
Steps:
  1. Click "Adjust" and enter -20 with a reason
  2. Confirm
Outcome: An inline error distinguishes this from a plain negative-on_hand rejection (e.g. references reserved/outstanding orders); on_hand and the audit table remain unchanged.
Selectors: getByRole('button', { name: 'Adjust' }), getByLabel for the quantity field, getByText for the inline error.
```

## 11. Risks and Trade-offs

- **No product-name display** (inherits MA-150 §11 Risk 2) — the list/detail screens show raw `productId` until a Catalog cross-reference exists; a real usability gap for v1, flagged rather than silently worked around with a client-side guess.
- **Server-side filtering from day one** (§5) — unlike MA-128's original client-side-first choice, this spec defaults to server-side given MA-150's `GET /inventory` already supports it and inventory lists are expected to scale with the full product catalog, not a small admin-staff list.
- **Two separate dialogs (Adjust vs Receive) rather than one "stock update" dialog** — a deliberate UX choice mirroring MA-150's own backend design decision (D2) that a receipt is categorically different from a correction; the alternative (one dialog with a toggle) was considered and rejected as more confusing, not less, for an Ops admin distinguishing "a delivery arrived" from "I'm correcting a miscount."
