## 2. Problem Statement

Milkful's admin console (`portal-ui`) has no way today to create additional admin/staff accounts or control what each one can see and do — there is exactly one implicit "admin" identity model, undocumented and unscoped. As operations, finance, support, and marketing staff are onboarded, the business needs a way to grant each person only the access their job requires (least privilege), see who did what (accountability), and revoke access immediately when someone leaves or is compromised. Without this, every staff member would need full access to every admin capability, which is an unacceptable security and compliance posture for a system handling payments, wallets, and customer PII.

**Expected outcome:** A Super-Admin can create a staff account, assign it exactly one of five fixed roles, and that person can then log in (with 2FA) and use only the screens/actions their role permits — with every privileged action attributable and auditable.

## 3. Scope

### In Scope

- Admin login screen and 2FA challenge UI (email/password + TOTP)
- Admin user list, create, edit, and deactivate/reactivate screens
- Fixed 5-role assignment during account creation/edit (Ops, Finance, Support, Marketing, Super-Admin)
- Per-admin session/IP restriction configuration screen
- Client-side enforcement of role-based UI visibility (hide/disable actions the current admin's role does not permit), driven by role claims from the JWT — **not** a substitute for server-side authorization
- All UI states (loading, empty, error, success, validation) for the above screens

### Out of Scope

- The audit log **viewer** — owned by MA-50 (System Configuration & Audit Log); this spec only ensures the actions above are attributable, not that they are displayed anywhere in `portal-ui`
- A custom/configurable role-permission editor — the 5 roles and their permission sets are fixed, not admin-definable
- Any non-admin (consumer-facing) screens
- The backend implementation of authentication, roles, session/IP enforcement, and audit event emission — covered by the paired spec [MA-129](https://milkfuldairyindia.atlassian.net/browse/MA-129) (`services`, extends Identity & Auth)

## 4. Functional Requirements

### FR-1: Admin Login

- Given an admin navigates to the admin console login page, they see fields for **Email** and **Password**, and a **Log In** button.
- On submitting valid credentials, the system prompts for a 2FA code (6-digit TOTP) on a second screen with a **Verify** button and a **Back** link.
- On a correct 2FA code, the admin is redirected to the console's default landing page for their role.
- On an incorrect password or 2FA code, an inline error appears below the relevant field ("Incorrect email or password." / "Incorrect code. Try again.") without revealing which field was wrong for password failures (prevents user enumeration).
- After 5 consecutive failed 2FA attempts within 15 minutes, the account is temporarily locked and the UI shows "Too many attempts. Try again in 15 minutes." (server-enforced; see MA-129).

### FR-2: Admin User List

- The **Admin Users** page shows a table with columns: Name, Email, Role, Status (Active/Deactivated), Last Login, and an actions menu.
- Supports search by name/email and filter by Role and Status.
- Only a Super-Admin sees this page and its actions; other roles do not see **Admin Users** in the navigation at all.

### FR-3: Create Admin Account

- Clicking **Add Admin** opens a form: Name, Email, Role (single-select: Ops / Finance / Support / Marketing / Super-Admin).
- On **Create**, if the email is not already registered, the new admin is created in a **Pending** state and an invitation email is sent (invitation delivery itself is a backend concern per MA-129) to set their password and enroll 2FA.
- If the email is already registered, an inline error appears: "An admin with this email already exists."
- On success, a toast reads "Admin account created. An invitation has been sent to {email}." and the new row appears in the list.

### FR-4: Edit / Deactivate / Reactivate Admin Account

- Clicking a row's actions menu offers **Edit Role**, **Deactivate** (or **Reactivate** if already deactivated).
- **Edit Role** opens the same form pre-filled; changing the role and saving shows a confirmation dialog ("Change {name}'s role from {old} to {new}?") before committing, since this immediately changes their access.
- **Deactivate** opens a confirmation dialog ("Deactivate {name}? They will be logged out and unable to log in until reactivated.") with **Cancel** / **Deactivate** buttons. On confirm, the row's Status updates to "Deactivated" and a toast confirms the action.
- A Super-Admin cannot deactivate their own account (the action is disabled with a tooltip: "You cannot deactivate your own account.").

### FR-5: Session / IP Restriction Configuration

- Each admin's edit form includes an optional **IP Allowlist** field (comma-separated CIDR ranges) and a **Max Concurrent Sessions** field (default: unlimited).
- Leaving IP Allowlist empty means no IP restriction is applied.
- Validation rejects malformed CIDR entries inline before submission.

## 5. Non-Functional Requirements

- **Performance:** Admin Users list loads in < 1.5s p95 for up to 500 admin accounts (no pagination needed at that scale; add server-side pagination only if the list is expected to exceed this — flagged as an open question, see §12).
- **Security:** No admin PII (email, IP ranges) is logged client-side; all admin-management API calls require a valid Cognito JWT with the `SuperAdmin` role claim, enforced server-side (client-side hiding is UX only, never the authorization boundary).
- **Reliability:** Role/permission changes take effect within one JWT refresh cycle (existing token is not silently revoked mid-session; see MA-129 for exact timing).
- **Accessibility:** WCAG AA — see §10c.
- **Observability:** Every create/edit/deactivate action logs a structured client-side analytics event (action name, target admin id, timestamp) in addition to the server-side audit event from MA-129.

## 6. Technical Design

### Architecture Approach

Standard `portal-ui` React SPA screens, calling REST endpoints exposed by the extended Identity & Auth service (MA-129) through API Gateway with a Cognito JWT authorizer — the same BFF pattern used by every other Milkful client.

### Component Responsibilities

- **Login screens** — unauthenticated route, calls `/v1/admin/auth/*` endpoints (MA-129)
- **Admin Users screens** — authenticated, Super-Admin-only route; calls `/v1/admin/users*` endpoints (MA-129)
- Role claim read from the decoded JWT (`cognito:groups`) drives navigation visibility and route guards

### Workflow (Create Admin)

```
Super-Admin fills form → Create → POST /v1/admin/users
  → 201: row added optimistically, toast shown, invite-sent state
  → 409 (duplicate email): inline field error, no row added
  → 5xx: toast "Something went wrong. Try again.", form stays populated
```

### API/Interface Definitions

Defined authoritatively in MA-129; `portal-ui` consumes:

| Method | Path | Purpose |
|--------|------|---------|
| POST | `/v1/admin/auth/login` | Step 1: email+password |
| POST | `/v1/admin/auth/2fa/verify` | Step 2: TOTP code |
| GET | `/v1/admin/users` | List admins |
| POST | `/v1/admin/users` | Create admin |
| PATCH | `/v1/admin/users/{id}` | Edit role / session-IP config |
| POST | `/v1/admin/users/{id}/deactivate` | Deactivate |
| POST | `/v1/admin/users/{id}/reactivate` | Reactivate |

### Data Flow

Browser → API Gateway (Cognito JWT authorizer) → Identity & Auth service → Admin Cognito User Pool + `admin_user` table (Aurora, owned by Identity & Auth per MA-129) → `admin.*` domain events → EventBridge (consumed later by MA-50's audit pipeline).

## 7. Data Considerations

No new datastore is owned by `portal-ui` (stateless SPA). All admin-user data (schema, migrations) is owned and versioned by MA-129. This spec only defines the request/response DTOs the UI depends on:

```json
// GET /v1/admin/users → 200
{
  "requestId": "uuid",
  "status": "success",
  "data": {
    "items": [
      { "id": "uuid", "name": "string", "email": "string", "role": "Ops|Finance|Support|Marketing|SuperAdmin",
        "status": "Active|Pending|Deactivated", "lastLoginAt": "ISO-8601|null" }
    ]
  }
}
```

## 8. Integration Considerations

- **Upstream:** none — this is the entry point.
- **Downstream:** Identity & Auth service (MA-129) exclusively. No direct calls to User, Wallet, or any other service from these screens.
- **Contract ownership:** MA-129 is the source of truth for the API contract; this spec's request/response shapes must be kept in sync with it during implementation (flag drift as tech debt, not silently reconciled).
- **Error handling:** All API errors follow the standard envelope (`services/README.md` §5c) — 401 → redirect to login, 403 → "Permission denied" toast, 5xx → generic retry toast.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| Network failure during login | Inline error: "Couldn't reach the server. Check your connection and try again." Form retains entered email. |
| JWT expires mid-session | Silent refresh attempt; on refresh failure, redirect to login with a toast: "Your session expired. Please log in again." |
| Two admins edit the same account concurrently | Last write wins at the API layer (per MA-129); UI shows the server's returned state after save, not the locally-optimistic one, to avoid silently masking a conflicting concurrent edit |
| Admin deactivates their own session's role (e.g., another Super-Admin demotes them) mid-session | Next API call returns 403; UI redirects to login with "Your access has changed. Please log in again." |
| Duplicate email on create | Inline 409 error, no partial account created (see FR-3) |
| Malformed IP CIDR entry | Inline validation error before submit; no request sent |

## 10. Testing Strategy

Unit tests for form validation logic (CIDR parsing, duplicate-role-change confirmation gating) and role-based navigation visibility. Integration tests mock the MA-129 API per the DTOs in §7. E2E via Playwright per the scenarios below.

```
Scenario: Super-Admin creates a new admin account
Given: Super-Admin is logged in and on the Admin Users page
Steps:
  1. Click the "Add Admin" button (getByRole('button', { name: 'Add Admin' }))
  2. Fill Name, Email fields (getByLabel('Name'), getByLabel('Email'))
  3. Select "Finance" from the Role dropdown (getByLabel('Role'))
  4. Click "Create" (getByRole('button', { name: 'Create' }))
Outcome: A toast reading "Admin account created. An invitation has been sent to {email}." appears; the new row is visible in the table with Role "Finance" and Status "Pending".
Selectors: getByRole for buttons/dropdown, getByLabel for form fields, getByText for the toast and table cell values.
```

```
Scenario: Non-Super-Admin cannot see Admin Users
Given: An admin logged in with the "Ops" role
Steps:
  1. Inspect the main navigation
Outcome: No "Admin Users" navigation item is present (getByRole('link', { name: 'Admin Users' })).queryable === null. Direct navigation to the Admin Users URL redirects to a 403 page.
Selectors: getByRole('link', { name: 'Admin Users' })
```

```
Scenario: Admin login fails 2FA five times and is locked out
Given: A valid admin account exists
Steps:
  1. Log in with correct email/password (getByLabel('Email'), getByLabel('Password'), getByRole('button', { name: 'Log In' }))
  2. Submit an incorrect 2FA code 5 times (getByLabel('Verification code'), getByRole('button', { name: 'Verify' }))
Outcome: After the 5th attempt, an inline message reads "Too many attempts. Try again in 15 minutes." and the Verify button is disabled.
Selectors: getByLabel for the code field, getByText for the lockout message.
```

## 10b. Responsive Behavior

| Breakpoint | Layout | Changes from Desktop |
|------------|--------|------------------------|
| Desktop (≥1024px) | Table with all columns visible, filters inline in a toolbar | baseline |
| Tablet (600–1023px) | Table scrolls horizontally within its own container (page itself does not scroll horizontally); filters collapse into a "Filters" button that opens a drawer | Last Login column hidden by default (visible via row expand) |
| Mobile (<600px) | List view (cards) replaces the table — one card per admin with Name, Role, Status, and an actions menu | Search and filters collapse into a single icon-triggered drawer |

## 10c. Accessibility Requirements

- **Keyboard navigation:** Full tab order through login form → 2FA form; Admin Users table rows and their action menus are reachable and operable via keyboard; modals (Add/Edit, Deactivate confirmation) trap focus and return focus to the triggering element on close.
- **ARIA labels:** Icon-only action buttons (row actions menu) have `aria-label` (e.g. "Actions for {admin name}"); the Admin Users table has `role="table"` with proper header associations; loading states use `aria-busy="true"` and `role="status"` for the loading spinner.
- **Focus management:** Opening a dialog moves focus to its first focusable element (typically the first field or the dialog title); closing returns focus to the button that opened it.
- **Color contrast:** All text and interactive elements meet WCAG AA (4.5:1 body text, 3:1 large text/UI components), including the Status badges (Active/Pending/Deactivated) which must not rely on color alone — pair with a text label or icon.

## 11. Risks and Trade-offs

- **Component library not yet ratified.** This spec assumes MUI; if the architect chooses differently, the Component Map (§10a) needs revision but the functional/interaction requirements (§4) do not change.
- **List performance at scale is untested** — see NFR in §5 and open question in §12 about pagination threshold.
- **Optimistic UI vs. server-confirmed state** (§9, concurrent edit case) trades a slightly less snappy UX for correctness; alternative (fully optimistic, reconcile silently) was rejected because silently overwriting a concurrent admin's change is a security-relevant correctness bug, not just a UX nit.

## 12. Open Questions

1. Is MUI the confirmed component library for `portal-ui`, or is this still an open architecture decision? (This spec assumes MUI as a baseline per §10a.)
2. At what admin-account-count should the Admin Users list move from client-side to server-side pagination?
3. What is the exact JWT refresh/expiry window, so the "session expired" UX (§9) can be tuned? (Owned by MA-129.)
4. Should deactivating an admin who is mid-session force an immediate logout (server-side session kill) or wait for their next API call to 403? (Owned by MA-129; affects the UX described in §9.)
