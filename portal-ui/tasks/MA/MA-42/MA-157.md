## 2. Problem Statement

The admin console has no product/catalog management at all today — the only way to add a product or change a price is a developer editing seed data or running raw SQL. Ops staff need to create and maintain the product catalog itself (identity, pricing, eligibility, categories) with the same console, RBAC, and interaction patterns already established for Admin Users (MA-128), Customer Accounts (MA-141), and Inventory (MA-151).

**Expected outcome:** An Ops/SuperAdmin admin can open a Catalog screen, see every product (including inactive ones), create a new product with full detail, edit or deactivate an existing one, manage categories, and see an audit trail of who changed what — each action reflected live and durably audited.

## 3. Scope

### In Scope

- **Catalog** product list screen: all products (including inactive, distinct from the consumer-facing filtered view), filterable by category and active status, under RBAC (Ops + SuperAdmin, same set as Inventory).
- Create-product form: name, category, unit, description, price B2C/B2B, HSN code, tax rate, veg/organic, subscription-eligible, image URL (plain text field).
- Per-product detail/edit view: same fields as create, plus the active/inactive toggle and an audit-trail table.
- Category list screen + create/edit dialog.
- All UI states (loading, empty, error, success, validation) matching the established patterns in `InventoryListPage.tsx`/`InventoryDetailPage.tsx`.

### Out of Scope

- The backend itself — owned by [MA-156](https://milkfuldairyindia.atlassian.net/browse/MA-156).
- Image upload UI — `imageUrl` is a plain text field (an admin pastes an already-hosted URL); no file picker, no CDN integration (MA-42 Step 1's deferred scope).
- Scheduled/future-effective price changes — no UI for this; deferred (MA-42 Step 1).
- CSV bulk import/export — no UI for this; deferred (MA-42 Step 1).
- Any Inventory (stock/batch/adjustment) admin screens — MA-48's territory, already shipped, not this spec's.
- B2B-pricing-aware UI beyond a plain editable field — no caller signals B2B intent yet (unchanged open question).

## 4. Functional Requirements

### FR-1: Navigation and Access

- A new **Catalog** item appears in the main navigation, visible only to Ops and SuperAdmin.
- `RequireRole roles={['Ops', 'SuperAdmin']}` at the route level, identical gate to `/inventory`. Other roles see no nav entry and are redirected to `/403` on direct URL access.

### FR-2: Product List

- Table columns: Name, Category, Price (B2C), Active status, actions. Includes inactive products (distinct from the consumer app, which never sees them) — an inactive row is visually de-emphasized (e.g. a muted/greyed row or a clear "Inactive" badge), never hidden from the admin's own list.
- Filters: category dropdown, active-status dropdown (All / Active / Inactive).
- A **"New Product"** action opens the create-product form (FR-3).

### FR-3: Create Product

- A dialog or dedicated form (implementer's choice, consistent with whichever existing pattern — `AdminFormDialog.tsx` vs. a full-page form — reads more naturally for this many fields; recommend a dedicated page given the field count, closer to `InventoryDetailPage`'s full-route precedent than a dialog) capturing: name, category (dropdown, from `GET /categories`), unit, description, price B2C, price B2B (optional), HSN code (optional), tax rate (optional), veg/organic (checkboxes), subscription-eligible (checkbox), image URL (optional text field).
- Client-side validation before submit: name/unit required, price B2C > 0 — mirrors `InventoryValidation`-style patterns already established (`src/utils/inventoryValidation.ts`).
- On confirm: `POST /products` (MA-156). Success → toast "Product {name} created."; navigates to the new product's detail view.

### FR-4: Product Detail / Edit

- Clicking a row opens `/catalog/{productId}`: every field from FR-3, editable, plus an **Active** toggle switch and an audit-trail table below (who changed what, from what value, to what, when — reusing the exact table shape `InventoryDetailPage`'s own audit-trail table already established, including its "Showing the most recent N of {total} entries" truncation notice for a long history).
- On save: `PATCH /products/{id}` (MA-156), sending only changed fields. Success → toast "Product {name} updated."; the audit table updates.
- Toggling **Active** off: a confirm step ("Deactivate {name}? It will no longer appear to customers.") before submitting — deactivation is a real, customer-visible action, not a casual toggle; mirrors the confirm-before-destructive-action pattern `DeactivateDialog.tsx` already established for admin users.

### FR-5: Category Management

- A **Categories** tab or sub-screen: list of categories (name, icon, sort order), a **"New Category"** action and a per-row edit action, each opening a small form (name, icon name, sort order).
- On confirm: `POST /categories` / `PATCH /categories/{id}` (MA-156). Success → toast; list refreshes.
- No audit-trail view for categories (MA-156 FR-3's own scope line — categories aren't audited on the backend, so there's nothing for this screen to display).

## 5. Non-Functional Requirements

- **Performance:** Catalog list loads in < 1.5s p95, server-side filtered (MA-156's `GET /admin/products` supports `categoryId`/`isActive` filters server-side from day one — same precedent as Inventory's own list, not MA-128's original client-side-first choice).
- **Security:** all calls require a valid admin JWT with Ops or SuperAdmin role, enforced server-side — identical posture to every prior admin spec.
- **Accessibility:** WCAG AA, inheriting MA-128/MA-141/MA-151's established requirements (keyboard nav, ARIA labels, focus management, non-color-only active/inactive indication).
- **Observability:** every create/edit/deactivate action logs a structured client-side analytics event via `logAdminAnalyticsEvent`, extending `AdminAnalyticsAction` (`src/utils/analytics.ts`) with `catalog.product_created` / `catalog.product_updated` / `catalog.product_deactivated` / `catalog.category_created` / `catalog.category_updated` — same extension pattern MA-151 already used for `inventory.*`.

## 6. Technical Design

### Architecture Approach

Standard `portal-ui` React SPA screens under the existing admin shell, calling MA-156's REST endpoints through API Gateway with the existing admin JWT authorizer — same BFF pattern as every other admin screen.

### Component Responsibilities

- **`CatalogListPage`** — mirrors `InventoryListPage`'s structure (filter state, table, row actions, "New Product" action).
- **`useCatalogListQuery` / `useCategoriesQuery` / `useCreateProductMutation` / `useUpdateProductMutation` / `useCreateCategoryMutation` / `useUpdateCategoryMutation`** — React Query hooks, same file-organization convention as `pages/inventory/hooks.ts`.
- **`CatalogDetailPage`** — dedicated route `/catalog/{productId}`, following `InventoryDetailPage`'s established full-route precedent (not a drawer or dialog, for navigation-model consistency).
- **`CategoryFormDialog`** — structurally mirrors `AdminFormDialog.tsx`'s shape (form + validation + confirm), reused for both create and edit.
- **`DeactivateProductDialog`** — structurally mirrors `DeactivateDialog.tsx`'s confirm-before-destructive-action shape.

### Workflow (Create Product)

```
Admin on Catalog list → "New Product" → form: name, category, unit, description,
  priceB2c, priceB2b?, hsnCode?, taxRate?, isVeg, isOrganic, subscriptionEligible, imageUrl?
  → Confirm → POST /v1/products
      → 201: toast "Product {name} created.", navigate to /catalog/{id}
      → 404 (CATEGORY_NOT_FOUND — shouldn't reach here from a populated category
         dropdown, handled defensively): inline form error, form stays populated
      → 400 (VALIDATION_ERROR): inline form error, form stays populated
      → 5xx: toast "Something went wrong. Try again.", form stays populated
```

### API/Interface Definitions

Defined authoritatively in MA-156; `portal-ui` consumes:

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/v1/admin/products` | Product list, incl. inactive (FR-2) |
| GET | `/v1/categories` | Category dropdown source (FR-3), existing endpoint |
| POST | `/v1/products` | Create (FR-3) |
| PATCH | `/v1/products/{id}` | Edit / activate-deactivate (FR-4) |
| POST | `/v1/categories` | Create category (FR-5) |
| PATCH | `/v1/categories/{id}` | Edit category (FR-5) |

### Data Flow

Browser → API Gateway (Cognito admin JWT authorizer) → Catalog Service (MA-94/MA-156) → Aurora `milkful_catalog`. No direct call from `portal-ui` to Inventory or any other service.

## 8. Integration Considerations

- **Upstream:** none — entry point, same as every prior admin spec.
- **Downstream:** Catalog Service (MA-156) exclusively. No direct calls to Inventory or any other service.
- **Contract ownership:** MA-156 is the source of truth; this spec's DTOs must be kept in sync with it during implementation.
- **Error handling:** standard envelope (`services/README.md` §5c) — 401 → redirect to login, 403 → "Permission denied" toast, 5xx → generic retry toast, identical to every prior admin spec.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| Admin navigates directly to a Catalog URL without Ops/SuperAdmin role | Redirected to `/403`, same as every other role-gated admin screen |
| Deactivating a product | Confirm step required (FR-4); on success, the product remains visible in the admin list (marked Inactive) but disappears from the consumer app |
| Two admins edit the same product concurrently | Last write wins at the API layer; UI shows the server's returned state after the action, not a locally-optimistic one — same non-optimistic-on-conflict principle as every prior admin spec |
| Create-product form submitted with an unknown/stale category (e.g. deleted between page load and submit — no delete endpoint exists, so only a theoretical race) | `404` handled defensively per the workflow (§6); not expected in practice since categories are never deleted by this spec |
| Network failure mid-action | Same generic retry toast pattern as every prior admin spec |
| A product's audit history exceeds what a single page shows | Same truncation notice pattern `InventoryDetailPage` already established ("Showing the most recent N of {total} entries") |

## 10. Testing Strategy

Unit tests for create-product form validation (required fields, positive price) mirroring `inventoryValidation.test.ts`'s existing pattern. Integration tests mock MA-156's API per the DTOs in §7. E2E via Playwright per the scenarios below, same tooling/convention as every prior admin spec.

```
Scenario: Ops admin creates a new product
Given: An Ops admin is logged in and viewing the Catalog list
Steps:
  1. Click "New Product" (getByRole('button', { name: 'New Product' }))
  2. Fill name, select a category, enter unit and price B2C
  3. Confirm (getByRole('button', { name: 'Create' }))
Outcome: A toast confirms creation; the admin is navigated to the new product's detail page showing the entered values.
Selectors: getByRole for buttons, getByLabel for form fields, getByText for the toast.
```

```
Scenario: Deactivating a product requires confirmation and hides it from the public catalog
Given: An Ops admin viewing an active product's detail page
Steps:
  1. Toggle "Active" off
  2. Confirm in the dialog that appears
Outcome: Toast confirms deactivation; the product's Active badge now reads "Inactive"; the product still resolves at its own URL (not 404) but no longer appears in the Catalog list's default (Active) filter.
Selectors: getByRole('switch', { name: 'Active' }), getByRole('button', { name: 'Deactivate' }) in the confirm dialog.
```

```
Scenario: Non-Ops/SuperAdmin admin cannot see Catalog
Given: An admin logged in with the "Finance" role
Steps:
  1. Inspect the main navigation
Outcome: No "Catalog" navigation item is present. Direct navigation to the Catalog URL redirects to /403.
Selectors: getByRole('link', { name: 'Catalog' })
```

## 11. Risks and Trade-offs

- **Dedicated-page vs. dialog for create-product** (§4 FR-3) — a deliberate recommendation (full page, not a dialog) given the field count (11 fields across pricing/tax/eligibility), departing from `AdminFormDialog.tsx`'s smaller-form precedent; the implementer may choose a dialog instead if it proves workable, but a long scrolling dialog is the worse of the two UX options for this many fields.
- **No product-name uniqueness check client-side** — mirrors MA-156 §12 Q1's own deferred backend decision; two products can share a name today, by design, not an oversight.
