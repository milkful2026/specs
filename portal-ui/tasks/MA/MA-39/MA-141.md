> **Process note:** Same as MA-128 — Task left at its default status.
>
> Unlike MA-128 (drafted before `portal-ui` had any code), this spec is grounded directly in the shipped MA-47/MA-128 implementation: MUI is confirmed (not assumed), React Query hooks + `notistack` snackbars + MUI `Table`/`Dialog` are the established pattern (`src/pages/admin-users/AdminUsersPage.tsx`), and role-gating is `RequireRole`/`RequireAuth` (`src/routes/guards.tsx`) checking `user.role` from the decoded JWT — not a permission-string system. This spec follows those real patterns exactly rather than re-deriving new ones.

## 2. Problem Statement

The admin console has a Customer Accounts... nothing, today. Ops/Support staff have no way to find a customer account, see its status, or act on it — every "disable this customer" request currently requires a direct database edit by an engineer. This is slow, unaudited, and error-prone at any real operational scale.

**Expected outcome:** An authorized admin can find a customer by name/phone/email, see their account status and history, and suspend/deactivate/reactivate them (individually or in bulk) with a required reason — all through the existing admin console, with the same look, RBAC model, and interaction patterns as the Admin Users screens shipped in MA-47/MA-128.

## 3. Scope

### In Scope

- **Customer Accounts** list screen: search (name/phone/email) + status filter, under existing RBAC (see §4 FR-1 for the exact role gate)
- Customer detail view: current status + full status-change history
- Suspend (reason + end date) / Deactivate (reason) / Reactivate (optional reason) actions, each with a confirmation dialog
- Bulk selection + bulk suspend/deactivate/reactivate with a per-row result summary
- All UI states (loading, empty, error, success, validation) for the above, matching the established patterns in `AdminUsersPage.tsx`

### Out of Scope

- The backend status model, admin APIs, and Cognito login-block — owned by the paired spec [MA-139](https://milkfuldairyindia.atlassian.net/browse/MA-139) (`services`, extends User Service)
- Any Subscription-pausing behavior — owned by [MA-140](https://milkfuldairyindia.atlassian.net/browse/MA-140); this UI never calls Subscription Service directly
- KYC/risk-flag filtering or B2B-specific UI — no such data exists yet (per MA-39 Step 1's resolved scope)
- The Admin Users (staff account) screens — already shipped (MA-47/MA-128); this is a **separate** section for **customer** accounts, and must not be visually or navigationally conflated with it (see §9 for the naming-collision risk this spec explicitly guards against)
- The audit log **viewer** — owned by MA-50; this spec only ensures actions are attributable via MA-139's history API, not that they're displayed anywhere beyond this screen's own detail view

## 4. Functional Requirements

### FR-1: Navigation and Access

- A new **Customer Accounts** item appears in the main navigation, alongside the existing **Admin Users** item, visible only to roles permitted to manage customer accounts.
- **Role gate:** per MA-139 §12 Q3 (flagged there as needing a decision), this spec proposes **Ops and SuperAdmin** — `RequireRole roles={['Ops', 'SuperAdmin']}` (mirrors `RequireSuperAdmin`'s existing pattern in `guards.tsx`, as a new `RequireCustomerAccountManagers` or an inline `RequireRole` call at the route level). Other roles (Finance, Support, Marketing) see no nav entry and are redirected to `/403` on direct URL access — exact parity with how `Admin Users` already behaves for non-SuperAdmin roles today (`AppLayout.tsx`'s conditional nav item, `App.tsx`'s `RequireSuperAdmin` route wrapper).

### FR-2: Customer Accounts List

- Table columns: Name, Mobile, Email, Account Type (B2C/B2B), Status (Active/Suspended/Deactivated), Last Status Change, actions menu — same column/menu shape as `AdminUsersPage`'s table.
- Search box filters by name/mobile/email (client-side substring match on the loaded page, same pattern as `AdminUsersPage`'s `filtered` `useMemo`, unless the account volume requires server-side search — flagged in §12, same open question class as MA-128's own §12 Q2).
- Status filter dropdown: All / Active / Suspended / Deactivated.
- Status badge is not color-only (reuses `StatusBadge`'s existing pattern of pairing color with a text label, per MA-128 §10c's accessibility requirement, which this spec inherits rather than restates).

### FR-3: Customer Detail

- Clicking a row (or a "View" action) opens a detail view: profile summary (name, mobile, email, account type) + current status + a reverse-chronological history table (previous status → new status, reason, effective date, actor, timestamp) — sourced from MA-139 FR-2's `GET /v1/admin/customers/{id}`.

### FR-4: Suspend / Deactivate / Reactivate (Single)

- Row actions menu: **Suspend**, **Deactivate** (mutually exclusive with each other based on current status — an already-`Suspended` account offers **Deactivate** and **Reactivate**, not **Suspend** again; an already-`Deactivated` account offers only **Reactivate**; an `Active` account offers **Suspend** and **Deactivate**) — mirrors `AdminUsersPage`'s existing pattern of showing Deactivate **or** Reactivate based on current status, extended to a three-state machine.
- **Suspend** opens a dialog: required **Reason** field (multiline text), required **Until** date field (must be a future date, inline validation before submit). On confirm: `POST /v1/admin/customers/{id}/suspend`. Success → toast "{name} suspended until {date}."; the row's Status updates.
- **Deactivate** opens a dialog: required **Reason** field, a warning ("This account will be logged out and unable to log in until reactivated.") — mirrors MA-128's own deactivate-confirmation copy pattern. On confirm: `POST /v1/admin/customers/{id}/deactivate`. Success → toast "{name} deactivated."
- **Reactivate** opens a lighter confirmation ("Reactivate {name}? They will be able to log in again. Any subscriptions paused by the earlier deactivation will stay paused until resumed separately.") — the second sentence is a deliberate, explicit UX choice so an admin is never surprised by D2's "no auto-resume" behavior. On confirm: `POST /v1/admin/customers/{id}/reactivate`. Success → toast "{name} reactivated."

### FR-5: Bulk Actions

- Checkboxes per row + a "select all on this page" header checkbox, consistent with standard MUI `Table` multi-select patterns (new to this screen — `AdminUsersPage` has no bulk action today, so this is new UI, not a reused component).
- A bulk action bar appears when ≥1 row is selected, offering Suspend / Deactivate / Reactivate applied to the whole selection (same dialogs as FR-4, applied via `POST /v1/admin/customers/bulk-status`, MA-139 FR-6).
- On completion, a summary dialog/toast reports per-row outcome: "{N} succeeded, {M} failed" with the failed rows and their reasons listed (never a bare "some failed" with no detail) — this is the UI's obligation to surface MA-139 FR-6's per-row result array, not silently collapse it.

## 5. Non-Functional Requirements

- **Performance:** Customer Accounts list loads in < 1.5s p95, same target class as MA-128's Admin Users list, at a scale flagged as an open question (§12) since the customer base is much larger than the admin-staff base MA-128 was sized for.
- **Security:** No customer PII (mobile, email, status-change reasons) is logged client-side; all customer-management API calls require a valid admin JWT with the role from FR-1, enforced server-side (client-side hiding is UX only, never the authorization boundary) — identical posture to MA-128 §5.
- **Reliability:** Bulk actions have no partial-UI-state ambiguity — the summary in FR-5 always reflects the server's actual per-row result, never an optimistic assumption.
- **Accessibility:** WCAG AA, inheriting MA-128 §10c's established requirements (keyboard nav, ARIA labels on icon-only actions, focus management on dialogs, non-color-only status indication) — this spec does not re-derive them, it applies them.
- **Observability:** Every suspend/deactivate/reactivate/bulk action logs a structured client-side analytics event via the existing `logAdminAnalyticsEvent` utility (`AdminUsersPage.tsx`'s own precedent), in addition to the server-side `user_status_history` row (MA-139 §7) and `user.status.changed` event.

## 6. Technical Design

### Architecture Approach

Standard `portal-ui` React SPA screens under the existing admin shell, calling REST endpoints exposed by User Service (MA-139) through API Gateway with the existing admin JWT authorizer — same BFF pattern as every other admin screen, no new infrastructure.

### Component Responsibilities

- **`CustomerAccountsPage`** — authenticated, role-gated (FR-1) route; mirrors `AdminUsersPage`'s structure (search/filter state, `useMemo` filtering, table, row actions menu, dialogs)
- **`useCustomerAccountsQuery`** / **`useSuspendCustomerMutation`** / **`useDeactivateCustomerMutation`** / **`useReactivateCustomerMutation`** / **`useBulkCustomerStatusMutation`** — React Query hooks, same file-organization convention as `pages/admin-users/hooks.ts`
- **`CustomerStatusDialog`** (suspend/deactivate/reactivate, parameterized by action) — new, but structurally mirrors `DeactivateDialog`'s existing shape
- **`CustomerDetailDrawer`** or route (`/customer-accounts/{id}`) — new, no direct MA-128 precedent to mirror, but follows the same MUI `Dialog`/route-param pattern used elsewhere in the app

### Workflow (Deactivate, single)

```
Admin clicks row actions → Deactivate → dialog: Reason (required)
  → Confirm → POST /v1/admin/customers/{id}/deactivate
      → 200: row's Status updates to "Deactivated", toast shown — including
         when the account was already Deactivated (MA-139 FR-4 is always
         idempotent/200 here; this endpoint never returns 409)
      → 5xx: toast "Something went wrong. Try again.", dialog stays open with
         the entered reason retained
```

**Suspend differs from Deactivate here**: `POST /v1/admin/customers/{id}/suspend` *can* return `409 INVALID_STATUS_TRANSITION` (MA-139 FR-3, when the account is already `Deactivated`) — shouldn't reach here given FR-4's state-aware menu, but handled defensively the same way: toast "Something changed — refresh and try again.", list refetched. Reactivate has no 409 case either (MA-139 FR-5 defines no status-transition restriction on it).

### API/Interface Definitions

Defined authoritatively in MA-139; `portal-ui` consumes:

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/v1/admin/customers` | List/search/filter |
| GET | `/v1/admin/customers/{id}` | Detail + history |
| POST | `/v1/admin/customers/{id}/suspend` | Suspend |
| POST | `/v1/admin/customers/{id}/deactivate` | Deactivate |
| POST | `/v1/admin/customers/{id}/reactivate` | Reactivate |
| POST | `/v1/admin/customers/bulk-status` | Bulk action |

### Data Flow

Browser → API Gateway (Cognito admin JWT authorizer) → User Service (MA-139) → Aurora `users`/`user_status_history` + consumer Cognito Pool. No direct call from `portal-ui` to Subscription Service — MA-140's consumer reacts to the event MA-139 publishes, invisibly to this UI.

## 7. Data Considerations

No new datastore owned by `portal-ui` (stateless SPA, same as MA-128 §7). DTOs this UI depends on:

## 8. Integration Considerations

- **Upstream:** none — entry point, same as MA-128.
- **Downstream:** User Service (MA-139) exclusively. No direct calls to Subscription, Wallet, or Identity & Auth from these screens.
- **Contract ownership:** MA-139 is the source of truth; this spec's DTOs must be kept in sync with it during implementation.
- **Error handling:** standard envelope (`services/README.md` §5c) — 401 → redirect to login, 403 → "Permission denied" toast, 5xx → generic retry toast, identical to MA-128 §8.

## 9. Edge Cases and Failure Modes

| Scenario | Behavior |
|----------|----------|
| Admin navigates directly to a Customer Accounts URL without the required role | Redirected to `/403`, same as non-SuperAdmin on Admin Users today |
| Two admins act on the same customer concurrently | Last write wins at the API layer; UI shows the server's returned state after the action, not a locally-optimistic one (same non-optimistic-on-conflict principle as MA-128 §9) |
| Network failure mid-bulk-action | Whatever the server actually completed is reflected in the per-row summary (FR-5) — the UI never claims success for a row it didn't get a confirmed result for |
| **Naming/navigational collision with "Admin Users"** | Explicitly guarded against: distinct nav label ("Customer Accounts" vs "Admin Users"), distinct route prefix (`/customer-accounts` vs `/admin-users`), distinct icon. This is called out because MA-39's own Step 1 analysis found the two concepts (admin-account management, done in MA-47, vs. customer-account management, this spec) are easy to conflate and must not be merged into one screen or menu item. |
| Suspend dialog submitted with a past-dated "Until" | Inline validation error before submit; no request sent (same pattern as MA-128's CIDR validation) |
| Reactivating an account with paused subscriptions | Confirmation copy explicitly states they stay paused (FR-4) — no silent surprise |

## 10. Testing Strategy

Unit tests for form validation (future-date "Until", required reason) and state-aware action-menu logic (FR-4's three-state machine). Integration tests mock the MA-139 API per the DTOs in §7. E2E via Playwright per the scenarios below — same tooling/convention as MA-128 §10 and the shipped `admin-users-refresh.spec.ts`/`dashboard-welcome.spec.ts` tests.

```
Scenario: Ops admin deactivates a customer account
Given: An Ops admin is logged in and on the Customer Accounts page
Steps:
  1. Search for a customer by name (getByLabel('Search'))
  2. Open the row's actions menu and click "Deactivate" (getByRole('menuitem', { name: 'Deactivate' }))
  3. Enter a reason (getByLabel('Reason')) and confirm (getByRole('button', { name: 'Deactivate' }))
Outcome: A toast reading "{name} deactivated." appears; the row's Status badge reads "Deactivated".
Selectors: getByRole for menu/buttons, getByLabel for form fields, getByText for the toast and status badge.
```

```
Scenario: Non-Ops, non-SuperAdmin cannot see Customer Accounts
Given: An admin logged in with the "Support" role
Steps:
  1. Inspect the main navigation
Outcome: No "Customer Accounts" navigation item is present. Direct navigation to the URL redirects to /403.
Selectors: getByRole('link', { name: 'Customer Accounts' })
```

```
Scenario: Bulk deactivate reports partial failure clearly
Given: An Ops admin has selected 3 customers, one of which the server will reject
Steps:
  1. Click "Deactivate selected" (getByRole('button', { name: 'Deactivate selected' }))
  2. Enter a reason and confirm
Outcome: A summary shows "2 succeeded, 1 failed" with the failed customer's name and error reason visible, not just a bare failure count.
Selectors: getByText for the summary counts and the failed-row detail.
```

## 11. Risks and Trade-offs

- **Role gate (FR-1) is a proposal, not yet confirmed** — see §12 Q1; if the answer differs (e.g. SuperAdmin-only for Deactivate specifically), FR-1/FR-4's menu logic needs revision but the rest of this spec is unaffected.
- **Client-side search/filter** (FR-2) assumes the customer list is small enough to load client-side, same trade-off MA-128 made for admin accounts — but the customer base is likely much larger than the admin-staff base, making this a real risk MA-128 didn't face at its scale. Flagged, not resolved, in §12.
- **New bulk-selection UI has no MA-128 precedent to mirror** — built fresh per FR-5's own description rather than copied from an existing pattern; slightly higher implementation risk than the rest of this spec, which mostly reuses shipped components.

## 12. Open Questions

1. **Exact role gate** (FR-1) — this spec proposes Ops + SuperAdmin for all actions uniformly; should Deactivate (the more consequential, indefinite action) require SuperAdmin specifically while Suspend/Reactivate stay Ops-accessible? Mirrors the same question raised in MA-139 §12 Q3 — must be answered consistently across both specs before implementation.
2. **List scale and pagination threshold** (§5, §11) — at what customer-account count does client-side filtering (FR-2) need to become server-side search/pagination? MA-139's `GET /v1/admin/customers` already supports server-side filtering per its own spec (MA-139 §4 FR-1) — this UI could adopt server-side search from day one rather than repeating MA-128's client-side-first choice; recommend defaulting to server-side given the larger expected scale, flagged for architect confirmation rather than assumed.
